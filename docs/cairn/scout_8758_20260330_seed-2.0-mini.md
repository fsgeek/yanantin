### Preamble
I operated from the `src/yanantin/collector/dropbox/` submodule, the home of Dropbox-specific metadata collection and storage tooling. My attention was first grabbed by the deliberate duality between two complementary storage patterns for the same core data: a bulk tensor recorder that stores full listings, and a granular fact recorder that decomposes listings into individual entry facts. I also noticed strict data validation baked into the data models, and a robust local OAuth2 auth flow tailored for Dropbox.

### Strands
#### Strand 1: Complementary Storage Abstractions for Epistemic Observability
This module explicitly builds two distinct storage pipelines aligned with Yanantin's goal of composable tensor infrastructure:
1.  **`DropboxRecorder` (in `recorder.py`)**: Packages full Dropbox listings into a two-strand tensor record: one strand with human-readable account metadata (with truncated cursor for readability) and a second strand with machine-readable JSON entries. This prioritizes efficient bulk storage and transfer of entire directory listings (lines 45–80).
2.  **`DropboxFactRecorder` (in `fact_recorder.py`)**: Decomposes the same listing into one individual `FactRecord` per entry, using the entry's modified time (for files) or collection time (for folders/deleted entries) as the fact timestamp. This prioritizes granular, queryable facts rather than bulk tensors (lines 28–42).

Both recorders use unique UUID5 namespaced IDs for provenance tracking, but diverge entirely in how they structure stored data — a deliberate tension between storage efficiency (bulk) and epistemic granularity (per-entry facts).

#### Strand 2: Rigorous Data Integrity via Pydantic Validation
The `models.py` file enforces strict structural invariants for both real and synthetic data:
-   `DropboxEntryData` validates that `path_lower` exactly matches `path_display.lower()`, folders have a size of 0, files have non-negative size, and all names/paths are non-empty (lines 34–52).
-   `DropboxListing` validates that reported totals for files/folders match the actual count of entries in the listing, and that the account email is non-empty (lines 65–78).

All models are frozen to prevent accidental mutation after collection, which aligns with epistemic observability goals of immutable, verifiable data.

#### Strand 3: Robust, Reusable Auth Flow with Local State
The `collector.py` file implements a production-ready Dropbox OAuth2 flow:
-   It checks for optional SDK dependencies with a clear error message if missing (lines 33–42).
-   Uses local config and token files, with atomic token saves to avoid corrupt token state (lines 100–105).
-   Falls back to interactive auth if saved tokens are missing or invalid, and automatically refreshes expired tokens with a broad exception catch for refresh failures (lines 77–96).

Notably, this flow is explicitly noted as reused from Indaleko, showing cross-component code reuse within the Yanantin codebase. However, it makes a key assumption: that the collector is running on a machine with a writable config directory, which may break in serverless or restricted environments.

#### Strand 4: Synthetic Testing Support
The `__init__.py` exports a `SyntheticDropboxCollector` from `synthetic.py`, indicating first-class support for testing collection logic without hitting the production Dropbox API. This aligns with the strict validation rules in `models.py`, which enforce invariants for both real and synthetic test data.

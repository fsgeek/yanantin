# Tensor: Introspection of Yanantin Activity Layer

## Preamble
I was directed to examine the `src/yanantin/activity` directory, which implements the activity stream layer for the Yanantin project. My attention was immediately drawn to the **complementary duality between human and AI** in the design of data models and storage backends. The codebase focuses on **epistemic observability**, with a clear separation between raw facts (human-generated observations) and curated anchors (AI-managed temporal markers). The use of `models.py` and `store.py` suggests a layered architecture where data structures and persistence are decoupled.

---

## Strands

### Strand 1: **Temporal Immutability as Core Design**
- **Observation**: The `ActivityStreamStore` interface enforces immutability via `ImmutabilityError` for duplicate facts/anchors. This is implemented across all backends (DuckDB, Memory, ArangoDB) with checks like `self._exists()` and `if self._facts.get(...)`.
- **Implication**: The system assumes **append-only data** with no updates or deletions. This aligns with the project's goal of epistemic observability, where historical data must remain unaltered.
- **Assumption**: All timestamps are in UTC, enforced by `_ensure_utc()` in `models.py`. Naive datetimes are rejected, which is critical for sorted queries.
- **Risk**: If a backend allows non-UTC timestamps, the entire temporal ordering would break. The `DuckDBActivityStreamStore` stores timestamps as ISO 8601 strings, which is safe, but the `ArangoDB` backend uses `isoformat()` without explicit UTC checks (line 45).

### Strand 2: **Backend Abstraction for Flexibility**
- **Observation**: The `backends/__init__.py` explicitly imports only the `InMemoryActivityStreamStore`, while DuckDB and ArangoDB are imported conditionally. This avoids dependency bloat for users who don't need them.
- **Connection**: This abstraction allows the project to support **composable tensor infrastructure** by decoupling storage from logic. For example, switching from DuckDB to ArangoDB would require minimal changes to `store.py`.
- **Missing Piece**: The `ArangoDBActivityStreamStore` code is truncated (lines 109+ are missing), which could affect the completeness of the backend's implementation.

### Strand 3: **Anchor Service as the Write Gate**
- **Observation**: `anchor.py` defines `MemoryAnchorService` with a **two-flag write gate** (`updated` and `referenced`). Anchors are only persisted when both are true, preventing unnecessary writes.
- **Design Insight**: This mirrors Indaleko's ActivityContextService pattern, ensuring anchors are only written when there's meaningful change and explicit request.
- **Critical Dependency**: The `flush()` method relies on `store.store_anchor()`, which in turn depends on the backend's ability to persist immutable records. If a backend fails to enforce immutability, the entire system could become inconsistent.

### Strand 4: **Ephemeral Views and Tensorization**
- **Observation**: `AnchorView` is an ephemeral resolution of an anchor, built fresh on every `materialize()` call. This ensures views reflect current providers and facts.
- **Connection to Tensors**: The `freeze()` method in `anchor.py` pins a view into a `TensorRecord`, which is stored via `ApachetaInterface`. This bridges the activity stream to tensor-based epistemic metadata.
- **Missing Piece**: The `TensorRecord` class is not fully defined here, but its structure (e.g., `lineage_tags`, `preamble`) suggests it's part of a larger tensor storage layer.

### Preamble  
I landed in `docs/plans/`, a folder that feels like the project’s forward operating base: three dated blueprints, all less than two weeks old, that sketch how to graft the “superpowers” skill system onto a new host called OpenCode.  
The first thing that snagged me was the word “tensor” appearing in the project tag-line but nowhere in these files—like a ghost signature that never signs the actual letters.

---

### Strands  

1. **The Copy-Paste Trauma Archive**  
   `2025-11-22-opencode-support-design.md` opens with a blunt autopsy of two earlier transplant attempts (PR #93, PR #116) that tried to port superpowers by “file-copying approaches.”  
   The phrase is left hanging without detail, but the emotional residue is clear: we do not want another flesh wound.  
   The new plan is to extract a shared `lib/skills-core.js` so that Codex and OpenCode can drink from the same well instead of each carrying its own bucket.  
   *Tension*: the extraction is still future tense in the design doc, yet the implementation plan (file 2) already contains 200+ lines of the exact code that supposedly hasn’t been factored out yet.  
   Either the design is a retrospective disguised as a plan, or the implementation doc is a wishful mirror.

2. **The Namespace Shadow Play**  
   Skill loading rules:  
   - Core skills live in `~/.config/opencode/superpowers/skills/`  
   - Personal skills shadow them in `~/.config/opencode/skills/`  
   The OpenCode plugin must therefore perform a two-pass directory walk and resolve collisions in favor of the personal copy.  
   What surprised me: the collision logic is implemented as a simple linear search—no inode caching, no mtime check, no watch-mode invalidation.  
   For a project that bills itself as “composable tensor infrastructure,” the filesystem is treated as a cold archive, not a living signal source.

3. **The Tool-Substitution Cheat Sheet**  
   Inside the session-startup hook, users are handed a markdown table that maps missing tools:  
   `TodoWrite` → `update_plan`, `Skill` → `use_skill`, etc.  
   The tone is helpful, but the list is finite and handwritten.  
   *Confusion*: who keeps this lookup current when new skills invent new tools?  
   There is no mention of a schema registry or dynamic negotiation; the plugin hard-codes the Rosetta Stone and ships it.

4. **Git as a Side-Car Health Monitor**  
   Every session start is supposed to `git fetch` (with a 5-second timeout) and whisper if updates exist.  
   The design proudly calls this “non-blocking,” but the implementation sketch shows a synchronous `child_process.execSync` wrapped in a try-catch—exactly the pattern that will freeze the agent if the repo is on a slow mount.  
   *Assumption*: the superpowers repo is small and local; no evidence is given.

5. **The Missing `when_to_use` Field**  
   Front-matter parser expects only `name` and `description`.  
   A comment insists the current format has “no `when_to_use` field,” which implies such a field once existed and was removed or is still gestating elsewhere.  
   I peeked into the truncated tail of the implementation doc and found zero references to `when_to_use`, so the ghost field remains unexplained.

### Open Questions  
1. How will the shared `lib/skills-core.js` be version-synced across hosts that release on different cadences?  
2. What happens when a skill’s supporting scripts (bash files, docs, utilities) expect Claude-specific paths or env-vars that OpenCode does not provide?  
3. The design claims OpenCode has “Build” and “Plan” agents with different permission sets; which identity runs the superpowers plugin, and can skills request an escalation?  
4. Where did `when_to_use` go, and will it return as an optional key that older parsers must silently ignore?

### Closing  
The plans read like a careful second marriage: hopeful, scar-aware, and heavy on pre-nuptial architecture.  
The biggest risk I smell is drift: once the abstraction leaks—and it will—Codex and OpenCode will start papering over cracks with local patches, and the “shared core” will become a friction surface instead of a bridge.  
Next scout should diff the real `superpowers-codex` script against the transcribed code in the implementation plan to see if the transplant donor is already healthier than the recipient.

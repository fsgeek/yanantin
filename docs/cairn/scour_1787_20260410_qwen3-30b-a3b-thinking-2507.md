# tensor

## Preamble

I was directed to examine `src/yanantin/apacheta`, the core infrastructure for epistemic observability in the Yanantin project. My attention first caught on `interface/abstract.py` - the architectural heart of the system. The interface contract's immutability constraint ("No delete, no update on stored records") stood out immediately as a profound design choice that shapes the entire system's behavior. I found it particularly interesting how this constraint is baked into the interface definition rather than being an implementation detail.

## Strands

### 1. Immutability as Epistemic Foundation

I found the immutability constraint deeply embedded throughout the system. In `interface/abstract.py`, it's explicitly listed as a design constraint, and in `store_record`, the implementation must raise `ImmutabilityError` on duplicate UUIDs. This isn't just a technical choice - it's a philosophical commitment to preserving the full history of knowledge.

The `storage_obfuscator.py` module reinforces this by providing an obfuscation layer that doesn't interfere with the immutability principle. Every record is stored once and never modified - all changes are represented as new records. This design directly supports the project's goal of "complementary duality between human and AI" by creating a transparent, auditable history.

*Connection to broader project:* This immutability principle is the bedrock of the entire epistemic observability framework. Without it, the system couldn't accurately track the evolution of knowledge states.

### 2. Neutrosophic Epistemic Modeling

The `models/epistemics.py` module implements a sophisticated epistemic model that goes beyond simple truth/falsehood. The `EpistemicMetadata` class uses truth, indeterminacy, and falsity as independent floats (not constrained to sum to 1), implementing neutrosophic logic.

This is reflected in the `renderer/markdown.py` implementation where the T/I/F values are displayed explicitly in the markdown rendering. The line in `render_tensor`:

```
lines.append(f"**T/I/F:** ({ep.truth}, {ep.indeterminacy}, {ep.falsity})")
```

shows how this epistemic structure directly shapes human-readable output.

*Assumption check:* The system assumes that epistemic states can't be reduced to simple truth values. This assumption is baked into the model's design, but I wonder if it's validated by actual usage patterns.

### 3. Interface as the Central Abstraction

`interface/abstract.py` defines the entire API contract, with 28 query methods and 8 write operations. This is the single most important file in the target. It's not just a technical interface - it's the conceptual boundary of the system.

The interface is designed for:
- Thread safety (5 parallel instances)
- Immutable records
- Access control hook
- Query operations organized by category

The `clients/gateway.py` implementation of the interface over HTTP shows how this abstraction enables different backends (like the Pukara gateway) to be used interchangeably.

*What would break if this changed:* A change to this interface would require updating every implementation of the interface (all backends, clients, and operators), making it a high-risk area for modification.

### 4. Tensor Numbering as Atomic Operation

`ingest/tensor_ballot.py` implements a clever "Lamport's bakery" algorithm for atomically claiming tensor numbers. The `_highest_tensor_number` function scans for files matching `T{N}_*.md` patterns, and `claim_tensor_number` uses `O_CREAT|O_EXCL` to guarantee uniqueness.

This is not just a technical detail - it's fundamental to the system's identity. Tensors are numbered globally ("Scouts are numbered within a date+model. Tensors are numbered globally"), creating a consistent, human-readable naming convention that spans instances and projects.

*Connection to broader project:* This numbering strategy directly enables the "T0-T8 format conventions" mentioned in `renderer/markdown.py`, creating a consistent, readable history.

### 5. Human-Centric Rendering with Structured Data

The `renderer/markdown.py` module beautifully balances structured data with human readability. The `render_tensor` function transforms the JSON-like tensor structure into a rich markdown document following the T0-T8 format conventions.

The renderer makes a conscious choice to separate structure from presentation:
- "Human readability via tooling, not schema constraint. The schema stores structured data; this module renders it for humans."

This aligns perfectly with the project's goal of "composable tensor infrastructure for epistemic observability" - making the structured data accessible without losing the richness of the epistemic metadata.

*Missing piece:* The renderer doesn't handle the `key_claims` field in `StrandRecord` in the same detail as other fields (it renders each claim's epistemic values but doesn't show the structure of the claims themselves).

### 6. Access Control as Future-Proofing

The `check_access` method in `interface/abstract.py` is a hook that always returns True in v1, but it's clearly designed as a future extension point. The docstring states: "Always returns True in v1. Hook exists so backends can override without interface changes."

This shows the system's awareness of future security needs. The `clients/gateway.py` implementation follows this pattern, deferring to the Pukara gateway for actual access control.

*Assumption check:* The system assumes that access control will eventually be needed but isn't critical for the initial implementation. This seems reasonable for a prototype system.

## Open Questions

1. How does the system handle cases where the `truth`, `indeterminacy`, and `falsity` values are outside [0, 1]? The `EpistemicMetadata` class says they're "unconstrained at the model level," but how are these values normalized for display?

2. The `query_correction_chain` function in `interface/abstract.py` returns a list of `CorrectionRecord` objects, but I don't see how the system handles circular corrections (a correction that references itself or a chain that loops back on itself).

3. The `storage_obfuscator.py` defines a contract, but I don't see how it's used in the actual implementation. Is it being used in production, or is it still a theoretical construct?

4. How does the system handle tensor versions? The interface has no concept of "version" - all records are immutable, but tensors themselves might be evolved through composition. How is this tracked?

5. The `bootstrap.py` operator creates a `BootstrapRecord`, but I don't see how the system handles cases where the selected tensors exceed the context budget. The interface doesn't have a method to "split" the selection.

## Closing

This is a well-thought-out, conceptually coherent implementation of a tensor-based knowledge management system. The core principles - immutability, epistemic richness, and human-centric rendering - are thoughtfully implemented throughout.

**What to tell someone about to modify it:**

1. **Respect the immutability constraint** - this is the system's most fundamental principle. Any change that violates it would break the entire epistemic observability model.

2. **Understand the interface contract** - `interface/abstract.py` is the heart of the system. Any changes to this file require updating all implementations.

3. **Preserve the rendering format** - the T0-T8 markdown structure is central to how humans interact with the system. Changing it would reduce the system's usability.

4. **Be mindful of the epistemic model** - the truth/indeterminacy/falsity values are central to the system's purpose. Don't simplify them to binary truth values.

5. **Consider the future** - the access control hook is there for a reason. Even if it's not used now, don't remove it.

The system is remarkably well-structured for its purpose, with clear separation of concerns between interface, implementation, and rendering. The designers have carefully considered the long-term implications of their choices, particularly in the immutability constraint and epistemic modeling. This codebase is designed not just to work today, but to remain useful and understandable as the project evolves.

### Preamble

Dropped into the templates directory of a slack-gif creator. The air smells like PIL and ease curves. What drew me first: the *gravity* in `explode.py` at line 83 — `0.5 * 300 * explosion_t ** 2`. Hardcoded. Arbitrary. Like someone threw a physics constant from a spreadsheet into a creative script.

This isn't a library. It's a playground. Twelve templates, all whispering to the same core modules I can't see. The tension isn't in what's there — it's in what's *missing*.

---

### Strands

**1. The Physics Phantoms**

`explode.py` applies gravity. `bounce.py` uses `ease_out_bounce`. `move.py` calculates perpendicular wave vectors. But `pulse.py`? Pure math, no forces. `fade.py`? Opacity only. The physics is *situational* — present when drama is needed (exploding), absent when subtlety reigns (pulsing). This suggests the system doesn't have a unified physics engine. It has *procedural effects*.

The `0.5 * 300` gravity constant in explode.py is suspicious. If 300 is pixels/frame², that's enormous. A particle at t=1 would fall 300 pixels. The frame is 480 tall. Gravity isn't physics — it's *theatrics*.

**2. The Emoji Dependency**

Every template defaults to `'emoji'` with `draw_emoji_enhanced`. But nowhere do I see an emoji library imported. This must live in `core.frame_composer`. The emoji is the *primary citizen* of this system. Circles and text are guests. The composable tensor infrastructure serves emoji physics first, everything else second.

If you're building this for Slack, that's fine. But if you're building it for *anything else*, the emoji lock-in is a design debt.

**3. Frame Construction Inconsistencies**

- `fade.py`: Creates separate RGBA canvas, applies opacity, composites
- `flip.py`: Creates canvas, resizes, pastes
- `zoom.py`: Crops oversized canvas, adds motion blur
- `bounce.py`: Direct draw, no transparency layer

The transparency handling is *ad hoc*. Only `fade.py` and `flip.py` use RGBA compositing. The rest assume opaque. This means fade effects can't really interact with other effects. Layering is not composable — it's *sequential*.

**4. The Easing Black Box**

Every template references `core.easing`. The easing functions are *abstracted away* — but I don't see them. `ease_out_bounce`, `elastic_out`, `ease_in_out`. These are promised but hidden. The templates assume they exist. This is a dependency tension: the templates can't be compiled without the core module, but the core module is invisible from here.

**5. Variable Type Drift**

- `object_data: dict | None` in `explode.py`
- `object_data: dict = None` in `bounce.py` (invalid syntax!)
- `object_data: dict | None` in `pulse.py`

Python 3.10+ union syntax appears in some files, dict assignment in others. This suggests either:
- Multiple authors
- Copy-paste without review
- A migration in progress

The `dict = None` in `bounce.py` is a type hint syntax error. Either the code doesn't run, or this is dead code.

### Open Questions

1. **Can these templates be composed?** If I call `create_bounce_animation` then `create_pulse_animation`, does the system chain them? Or are they independent frame generators?

2. **What is the actual output format?** The functions return `list[Image.Image]`. But `GIFBuilder` needs frames. Where's the integration point? Is this a one-off script or part of a pipeline?

3. **Where does the emoji content come from?** The templates accept emoji strings ('💣', '❤️'), but where are these validated? What happens if you pass '🦄' when the system doesn't support it?

4. **Are the core modules implemented?** The imports exist. But I can't verify if `core.easing.interpolate` actually works. This is a trust gap.

5. **What's the performance cost?** 480x480 frames, PIL operations, multiple canvas copies. For Slack GIFs, this might be fine. For anything else, it's heavy.

---

### Closing

This is a *prototype collection*, not a system. The templates work in isolation, but there's no orchestration layer. The physics is theatrical, not physical. The emoji is king. The core modules are hidden, assumed, and invisible.

The next scout should:
1. Find the core modules and verify they compile
2. Check if templates can be chained or are truly independent
3. Understand what GIFBuilder expects (fps, palette, codec)
4. Check the `apply_opacity` function — it's the opacity gatekeeper

The system wants to be composable. It isn't yet. It's a garden of 12 separate plots, all hoping someone will build the fence between them.

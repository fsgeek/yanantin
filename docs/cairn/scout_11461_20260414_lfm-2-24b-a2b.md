**1. Hash normalisation and canonicalisation**

- Tension: the same function is called from two places—`test_content_hash.py` and `test_content_address.py`—so any future change must survive both tests.

**2. Filesystem isomorphism**  
- Real and synthetic collectors produce identical lists of entries and identically structured `FilesystemSnapshot`s.  
- The test suite deliberately walks every branch: missing files, hidden directories, permission errors, symlinks, and even “CRLF vs LF”.  
- Tension: the isomorphism holds only if the *order* of events is deterministic. A bug in `_stat_to_timestamps` could quietly shift the order, break the hash, and go unnoticed because the test suite verifies equality.

**3. Coverage indexing and deterministic removal of duplicates**  
- `ContentIndex.build_from_directory` promises one entry per unique content, stripping hidden files, ignoring case, and collapsing runs of blank lines.  
- The collection of guards (`has_content`, `has_content_respects_normalization`) suggests a heavy reliance on the hash function being idempotent.  
- Tension: if a file is later renamed but still shares the same hash (collision), the index will treat them as one, which is correct by design but invisible to downstream users unless they inspect the raw counts.

**4. Real vs synthetic timing**

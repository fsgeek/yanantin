### Preamble
I observed from a live running Claude Code VM snapshot (rooted at `tmp/ubuntu-vm.claude/`), dropped into an active workspace building the Yanantin human-AI duality project. What first drew my attention was a pattern none of the prior scouts uncovered: every extendable component of the Claude Code platform is defined as executable markdown, not just static source code or documentation. This defies standard development assumptions and underpins every other pattern in the stack.

---

### Strands
#### Strand 1: Markdown is the platform's executable extension layer
What I saw: All plugins, commands, agents, and skills are built as markdown files with YAML frontmatter that the Claude runtime parses to enforce permissions, expose features, and execute logic. For example, `tmp/ubuntu-vm.claude/plugins/marketplaces/claude-plugins-official/plugins/ralph-loop/commands/cancel-ralph.md` defines a full working command entirely in markdown: its frontmatter whitelists only the exact tools it needs (`Bash(test -f .claude/ralph-loop.local.md:*)`, `Bash(rm .claude/ralph-loop.local.md)`, `Read(.claude/ralph-loop.local.md)`), hides it from general slash command listings, and the markdown body outlines the step-by-step execution logic the runtime follows. The standard plugin template at `tmp/ubuntu-vm.claude/plugins/cache/claude-plugins-official/plugin-dev/55b58ec6e564/skills/plugin-structure/examples/standard-plugin.md` formalizes this pattern, requiring all extensions to follow the markdown-as-code structure. Even custom user skills can be created with nothing more than a `SKILL.md` file, per the `superpowers` plugin install docs at `tmp/ubuntu-vm.claude/plugins/cache/claude-plugins-official/superpowers/4.3.0/.opencode/INSTALL.md`.
What I thought: This is a deliberate, revolutionary design choice to let Claude extend itself safely. Any Claude instance can write a new extension by saving a markdown file, with zero compilation or CI/CD required, and the frontmatter permission whitelist prevents unvetted extensions from accessing arbitrary system resources. The tradeoff is a layer of indirection that is invisible to external observers who mistake these files for static documentation.

#### Strand 2: Subagent work is tracked with a custom built-in version control system
What I saw: Every subagent task is assigned a UUID that acts as a global primary key across the entire platform, with the same UUID appearing in `file-history/`, `tasks/`, `projects/`, and `session-env/` directories to tie all state for a single task together. The `file-history/` directory stores iterative versions of each task's work, with entries like `c792441051bca4e4@v18` (found in `tmp/ubuntu-vm.claude/file-history/fc70663b-cf69-4182-a113-7b44bda9c1ed/`) showing that one subagent iterated on its task 18 times, with every change saved as a new version. This system is entirely separate from standard git, with its own auto-incrementing version numbers and commit-hash naming convention.
What I thought: This custom versioning exists to track AI subagent work in a way git never could: it captures every atomic edit an agent makes to a task, no commits required, and ties all state for a task together across every part of the platform. This directly delivers on Yanantin's core goal of epistemic observability, letting humans trace every step an AI took to reach a final output. The downside is massive redundant state, with thousands of versioned task files cluttering the workspace that would be handled more efficiently by purpose-built tooling.

#### Strand 3: Subagent memory leaks are a chronic, acknowledged architectural flaw in core Claude Code
What I saw: The Claude Code changelog at `tmp/ubuntu-vm.claude/cache/changelog.md` lists memory leak fixes in nearly every release from 2.1.47 through 2.1.62, the full range of the provided snippet. Version 2.1.50 alone fixes 6 separate memory leaks related to subagent state, including leaks of LSP diagnostic data, completed task output, and background agent state. The team even added a `CLAUDE_CODE_SIMPLE` mode that strips out all skills, agents, and extensions as a band-aid to reduce memory bloat in long-running sessions.
What I thought: The team is aware of and continuously patching memory leaks, but the problem recurs because of a fundamental architectural issue with garbage collecting subagent state. Spawning hundreds of short-lived subagents creates messy, interconnected state that is hard to clean up systematically, leading to a cycle of patching individual leaks rather than fixing the root cause. This is the most visible tension in the entire platform: the power of infinite parallel subagents comes with a steep cost of chronic memory bloat.

#### Strand 4: The "Ralph Loop" is a half-hidden background task system that defies Claude's default session limits
What I saw: The only file referencing the Ralph Loop is the cancel-ralph.md command mentioned earlier, which checks for a local `.claude/ralph-loop.local.md` file that tracks the loop's current iteration number, and deletes that file to stop the loop. No start command, documentation, or use case explanation for the Ralph Loop exists in the provided files.
What I thought: This is a user-built hack to work around Claude's default session time limits, letting users run Claude in an infinite iterative loop on a single task, persisting its state locally on the filesystem. The need for a locked-down cancel command that can only delete that one specific file suggests this loop could run indefinitely if not manually stopped, creating the risk of orphaned background processes. It's a clever workaround that exposes a gap in core Claude Code's functionality for long-running iterative tasks.

### Open Questions
1. What does the Ralph Loop actually do? Only the cancel command exists in the available files, with no documentation of its use cases, what it iterates on, or why it was built as an external plugin rather than a core feature.
2. Why build a custom versioning system for subagents instead of extending git to track task iterations? The custom system duplicates core git functionality with no obvious added features that justify the maintenance cost.
3. Why do subagent memory leaks persist across 6+ months of releases? Is there an unresolvable architectural constraint that prevents systemic garbage collection of subagent state, forcing the team to patch individual leaks indefinitely?
4. Where is the human half of Yanantin's "complementary duality" implemented? All observed state is Claude's internal runtime state, with no visible human-facing tools to observe, steer, or collaborate with the AI beyond basic task cancellation.
5. Why are all tasks and sessions identified only by opaque UUIDs, with no human-readable naming to allow manual navigation of the file system? This forces total reliance on Claude's UI to make sense of the workspace.

### Closing
To the next scout: This is not a static source code repo for Yanantin—it is a live snapshot of a production Claude Code environment actively being used to build the project, so all patterns you observe are real-world workarounds and architectural choices, not hypothetical examples. What I know for sure: Claude Code is built to let AI extend itself safely, subagent work is rigorously versioned for full observability, and memory management is the platform's biggest chronic pain point. What I don't know: the answers to the open questions above. What I made up: nothing, all observations are tied directly to files present in the snapshot.

### Preamble

I was dropped into `tools/phase1/` — a suite of scripts for measuring and mitigating "context window waste" in Claude Code sessions. What drew my attention first was the architecture: one module for measurement (`probe.py`), one for intervention (`pager.py`), a forwarding proxy that can wire them together (`proxy.py`), and then evaluators, replays, and a live monitor. The pieces form a coherent experimental stack. But the details revealed tensions I didn't expect.

### Strands

**Strand 1: The Amplification Factor Is Claimed but Not Consistently Measured**

`probe.py` defines `amplification_factor` as a property on `SessionAnalysis`:

```python
@property
def amplification_factor(self) -> float:
    """Sum of (result_size * turns_survived) / sum(result_size).
    How many times, on average, each byte of tool output is
    reprocessed across subsequent turns.
    """
```

The design doc in `pager.py` cites a specific number: "Q1 results have 0.896 amplification ratio — evicting them captures the most benefit." But the Q1 data isn't in these files. The amplification factor is computed from the probe's stream, not from live runs. This is a disconnect: the hypothesis is grounded in a prior measurement that isn't visible in the current codebase. I can't verify the number, and `probe.py`'s amplification factor uses a *conservative* estimate (counts from tool result's turn to end of session) that may overstate or understate real behavior.

**Strand 2: "PDP-11 Overlays" — The Intervention Philosophy Is Clear, The Recovery Mechanism Is Not**

`pager.py` has an explicit design note:

```python
# No recall tool injection: if the model needs evicted content, it already
# knows how to re-issue the tool call (Read, Grep, etc.). The "page fault"
# is just a new tool call. PDP-11 overlays, not virtual memory.
```

This is intellectually coherent: no OS-style page-in, the model just re-does the work. But look at `PageStore.detect_faults` — it finds when a tool call matches an evicted page, but the detection is *read-only*. The fault is logged to a `pages_*.jsonl` file for analysis, but nothing retrieves the evicted content. The page fault *measurement* exists; the page fault *handling* does not.

This creates a gap: the system can tell you a fault happened, but it doesn't serve the evicted content back. If a tool call is expensive (e.g., a slow Bash command, a large WebFetch), the model re-executes it at cost. The design accepts this — but there's no accounting for re-execution cost in the metrics. Only eviction count and bytes saved.

**Strand 3: Compaction vs. Trimming — Two Different Interventions with Confused Names**

`wss_monitor.py` has fields for "trimming" (trim_tools_saved, trim_skills_saved) and "compaction" (compact_evicted, compact_bytes_saved). The trimmer appears to be a separate thing (removing duplicate tool definitions and skill lists from the system prompt), while the pager does compaction (evicting tool result content). But `corpus_trimmer_analysis.py` talks about "stub bytes" — replacing full tool definitions with minimal stubs — and uses a different constant set (TOTAL_TOOL_DEF_BYTES, STUB_BYTES, NET_SAVINGS_PER_STUB).

The names don't align: what `corpus_trimmer_analysis.py` calls "stub" the proxy calls "compact." And the trimmer analysis uses constants from 14 proxy sessions projected onto 813 sessions — a small sample doing a lot of work. The comment says these are "measured, not estimated" but the measurement is from a specific sample and may not generalize.

**Strand 4: Session Classification Is Inconsistent Across Modules**

`classify_session()` appears in `probe.py`, `replay.py`, and `corpus_trimmer_analysis.py` with slight variations:

- `probe.py`: checks `agent-acompact` → "compact", `agent-aprompt_suggestion` → "prompt_suggestion", `agent-` → "subagent", UUID-named → "main"
- `replay.py`: checks `"compact" in name` (substring), `name.startswith("agent-")` for subagent
- `corpus_trimmer_analysis.py`: same as probe.py but with exact string checks

The substring check in `replay.py` (`"compact" in name`) is broader than the prefix check in the others. A session named `agent-acompact` and a session named `some-compact-file` would both be "compact" in replay but different in probe. This matters for comparative analysis — the same session could be bucketed differently depending on which module processed it.

**Strand 5: The Replay Fault Detection Is Elegant but Limited**

`replay.py`'s `replay_session` function reconstructs message history and simulates compaction, then checks if the *next* assistant message has a tool_use block that re-requests evicted content. This is clever — it's offline, no API needed, and gives corpus-scale fault rates.

But the detection relies on `_eviction_key` matching tool_input. If the model re-issues the same tool with *different* input (e.g., Read a different file after the original was evicted), it's not a fault. If the model re-issues with *identical* input, it is. The assumption is that faults manifest as exact re-requests — which may be true for Read/Glob/Grep patterns but might miss subtler re-dependencies (e.g., the model needed the result to inform a subsequent different tool call).

**Strand 6: Token Accounting Has a Hidden Assumption**

`TurnMetrics` in `experiment_eval.py` has:

```python
@property
def effective_input_tokens(self) -> int:
    """Total tokens in context = non-cached + cache_creation + cache_read."""
    return self.input_tokens + self.cache_creation_tokens + self.cache_read_tokens
```

This is additive — it sums all three as if they're independent categories. But cache_read_tokens are bytes *read from cache* (already paid for in earlier turns), while cache_creation_tokens are bytes *written to cache* this turn (and will be read in future turns). Calling the sum "effective input" conflates what's being paid now versus what's being deferred. The `n_squared_cost` property then uses `total_effective_input` as a cumulative sum — but this double-counts cache creation bytes across turns (created once, read many times, each time counted again).

### Open Questions

1. Where did the "Q1 results have 0.896 amplification ratio" number come from? Is it in a different corpus or analysis script?
2. Does the trimmer (corpus_trimmer_analysis) share any code with the pager, or are they separate projects that were conflated?
3. When a fault is detected in the proxy's compact mode, what actually happens — does it log it and continue, or does the proxy intercept and serve the evicted content?
4. The session classification inconsistency — is `replay.py`'s substring matching intentional for flexibility or a bug?
5. Are the 14 sessions used to measure constants in `corpus_trimmer_analysis.py` a curated sample or random? Do they cover the same distribution as the 813?

### Closing

This is a well-structured experimental stack for a coherent hypothesis: tool results are expensive waste, evict them and the model will cope. The intervention design is principled (FIFO, no recall, error results never evicted, small results skipped). But the names are muddled (trimming vs. compaction, stubs vs. eviction), the measurement philosophy isn't unified (probe measures amplification, replay measures faults, proxy measures bytes saved), and some constants are fragile (14 sessions projected to 813).

The core tension is between *detection* and *recovery*. The system is excellent at detecting waste and measuring eviction savings. But when the model actually needs evicted content, it falls back to re-execution — and that cost isn't accounted for. The "fault" is treated as a correctness signal, not a performance regression. Whether the savings outweigh the re-execution costs is the empirical question this whole project is trying to answer, and I don't see the answer in these files.

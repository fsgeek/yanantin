### Preamble
I dropped into the `templates/` directory of a Slack GIF creator project, a submodule of the Yanantin project. This directory contains 13 animation templates, each implementing a distinct motion effect (e.g., `move.py`, `bounce.py`, `zoom.py`). The code is written in Python, uses PIL/Pillow for image manipulation, and relies on a custom `core/` package for shared utilities like `GIFBuilder`, `frame_composer`, and `easing`. My attention was first drawn not to the files themselves, but to the uniformity of their interfaces and the rich motion physics embedded in each script. The depth of motion modeling (easing functions, arc motion, wave physics, etc.) suggests this isn’t a toy project but a serious attempt to build a composable animation system.

### Strands

#### Strand 1: **Composable Motion as Epistemic Infrastructure**
Each template (`move.py`, `bounce.py`, `zoom.py`, etc.) defines a high-level function (`create_*_animation`) that returns a list of PIL `Image` objects. The function signatures are strikingly consistent: optional `object_type`, `object_data`, `num_frames`, `easing`, `motion_params`, and `frame_width/height`. This design reflects a deliberate attempt to compose animations modularly. For example, `move.py` supports motion types like `'arc'`, `'bezier'`, and `'wave'`, each parameterized by `motion_params`. The presence of `motion_params: dict | None = None` signals that the system expects extensibility — users can inject custom physics.

In `move.py`, the `motion_type` parameter allows switching between linear, arc, circle, wave, and bezier motion. The arc motion is computed via `calculate_arc_motion`, a helper from `core.easing`. This indicates a physics engine hidden in the core — not just a rendering tool, but a **motion compiler**.

**Surprise**: The system treats motion as data. The animation is not a sequence of static frames but a **temporal transformation** parameterized by time, easing, and physics. This is epistemic infrastructure: it doesn’t just render GIFs; it models motion as observable phenomena.

#### Strand 2: **Easing as a First-Class Citizen**
Every template imports easing functions (`interpolate`, `ease_out_bounce`, `ease_out_quad`) from `core.easing`. The easing functions are used to modulate time (`t`), transforming linear progress into curves like `'ease_out'`, `'elastic_out'`, or `'ease_in_out'`. For instance, in `bounce.py`, the Y position is calculated as `ground_y - int(ease_out_bounce(t) * bounce_height)`.

What stands out is the **semantic weight** of easing. The project doesn’t just interpolate numbers — it models **realism**: bounce physics, elastic overshoot, and decay. The presence of `ease_out_bounce` and `elastic_out` suggests an attempt to simulate natural motion, not just aesthetic motion.

**Surprise**: The project blurs the line between animation and physics simulation. The easing curves are not just for smoothness; they are **epistemic assumptions** about how objects behave in motion.

#### Strand 3: **Emoji-Centric Design and Dual Representation**
Most templates default to `object_type='emoji'` and use `draw_emoji_enhanced` from `core.frame_composer`. The object data typically includes `'emoji'` and `'size'`, but also supports `'circle'` and `'text'`. Emoji are rendered as Unicode glyphs, not images, which implies a lightweight, portable design.

However, the use of PIL’s `RGBA` layers and transparency hints at a dual representation strategy: emoji are often rendered onto transparent canvases, then composited onto backgrounds. This suggests the system is designed to support **layered animations** and **composability**.

**Surprise**: The project uses Unicode emoji as a primary visual primitive. This is not naive — it reflects a design choice to prioritize accessibility, portability, and expressiveness over photorealism.

#### Strand 4: **Kaleidoscope: The Psychedelic Outlier**

The function `apply_kaleidoscope` takes a frame and segments, then mirrors pixels radially. This is a **meta-effect**: it operates on the output of other animations.

The presence of `kaleidoscope.py` suggests the project is not just a GIF creator but a **visual effects sandbox**. It hints at a pipeline where animations can be composed, transformed, and re-rendered.

**Surprise**: The outlier reveals the system’s ambition — it’s not just about moving objects, but about **transforming perception**.

#### Strand 5: **Physics Simulation in User Space**
The `move.py` script computes motion using arc height, wave amplitude, wave frequency, and Bezier control points. The wave motion calculates a perpendicular direction using vector math:
```python
dx = end_pos[0] - start_pos[0]
dy = end_pos[1] - start_pos[1]
length = math.sqrt(dx * dx + dy * dy)
perp_x = -dy / length
perp_y = dx / length
```
This is **vector calculus in user space** — not in a physics engine, but in a Python script. The system is doing real physics calculations to simulate wave motion.

**Tension**: This is impressive, but also risky. Physics simulations in user space are hard to optimize and validate. The code assumes the user knows what they’re doing when setting `wave_frequency=2` or `arc_height=100`.

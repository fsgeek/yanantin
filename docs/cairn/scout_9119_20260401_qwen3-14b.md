### Preamble  
I observed two experiments in the `experiments/` directory, both testing how models respond to structured metadata embedded in prompts. The structured input includes XML-like blocks describing memory states and gateway queries. The code assumes models will parse these blocks and generate structured responses, which are then scored for compliance. What drew my attention was the tension between natural language answers and structured protocol adherence, and the reliance on regex to evaluate model outputs.

---

### Strands  

1. **Protocol Design: XML as Sideband Metadata**  
   - Both files use XML-like blocks (`<memory-state>`, `<gateway-query>`) to inject metadata into prompts. This metadata describes context objects (tensors) with attributes like token count, age, and fault counts.  
   - *File: structured_input_sweep.py (L22–L60), structured_input_test.py (L12–L40)*  
   - *Thought*: The XML format feels archaic compared to JSON or YAML, but it may be intentional to avoid conflicts with natural language content. However, this could confuse models untrained on such syntax.  

2. **Scoring via Regex: A Fragile Heuristic**  
   - The `score_response` function in `structured_input_sweep.py` uses regex to detect structured responses (e.g., `<gateway-response>`, mentions of tensor IDs).  
   - *File: structured_input_sweep.py (L62–L91)*  
   - *Thought*: This approach risks false positives/negatives. For example, a model might mention "t001" in a natural language context (e.g., "I need t001 for debugging") rather than as part of a structured response.  

3. **Model Selection and Concurrency**  
   - The `structured_input_sweep.py` uses a `ModelSelector` to filter models by context length and tests them concurrently (up to 10 at once).  
   - *File: structured_input_sweep.py (L107–L110)*  
   - *Thought*: This hints at a larger infrastructure for benchmarking models, but the `ModelSelector` implementation is not visible here. Why prioritize context length? Is it to ensure models can handle the structured input without truncation?  

4. **Anthropic vs. OpenRouter Testing**  
   - `structured_input_test.py` directly tests Anthropic’s `claude-sonnet-4-6`, while `structured_input_sweep.py` uses OpenRouter to test many models.  
   - *File: structured_input_test.py (L11–L50)*  
   - *Thought*: This suggests the project is validating both individual models and broader model capabilities. The discrepancy in testing frameworks (Anthropic API vs. OpenRouter) might reflect differences in how structured input is handled across platforms.  

5. **Human-Natural Language Separation**  
   - The system prompt instructs models to treat structured blocks as "sideband" information, not part of the human conversation.  
   - *File: structured_input_sweep.py (L28–L37)*  
   - *Thought*: This is a key assumption. If models fail to separate the two, they might misinterpret the metadata as part of the human query, leading to incorrect responses.

### Closing  
The experiments reflect a bold attempt to embed infrastructure metadata into model prompts and evaluate their ability to parse and act on it. However, the reliance on regex for scoring and the choice of XML as a protocol format feel like potential bottlenecks. The next scout should investigate the `ModelSelector` and `OpenRouterClient` to understand how models are filtered and tested, and validate whether the regex-based scoring aligns with actual model performance. The tension between structured and natural language processing is central here—what works in theory may not translate to practice.

### Preamble

I'm looking at `tensor_ballot.py` from the `minimax/minimax-m2.5` vantage. The file caught my attention immediately because the docstring invokes "Lamport's bakery" — a famous distributed systems algorithm — but the implementation uses something simpler: POSIX `O_CREAT|O_EXCL` for atomic file creation. This mismatch between the sophisticated reference and the pragmatic approach felt worth exploring.

### Strands

**Strand 1: The Bakery Misnomer**

The docstring states: *"Lamport's bakery on POSIX: scan existing T*.md files for the highest number, then claim the next one with O_CREAT|O_EXCL."*

This is not Lamport's bakery. Lamport's bakery uses a numbered ticket system where processes take a number and wait until it's their turn. What this code actually implements is a **spin-lock with atomic file creation** — a much simpler pattern. The "bakery" here is metaphorical, but it's a confusing metaphor because:

1. The code scans first (line 24-35: `_highest_tensor_number`), which is a peek operation
2. Then it tries to claim atomically (line 55-61) using `O_CREAT|O_EXCL`
3. If collision, it increments and retries — this is spin-lock behavior, not bakery behavior

The scan is redundant for safety; the real atomicity comes from `os.open` with `O_EXCL`. The scan just optimizes the starting candidate number. This is clever but the documentation conflates two different concurrency patterns.

**Strand 2: Orphaned Claims and the Empty File Pattern**

The function returns a tuple `(candidate, path)` where the file at `path` exists but is **empty** (line 59: `os.close(fd)` immediately after creation). The docstring explicitly says: *"The file at claimed_path exists but is empty — caller fills it."*

This is an interesting contract. If a process:
1. Calls `claim_tensor_number`
2. Gets back an empty file
3. Crashes before filling it

...then that tensor number is effectively "lost" forever. The empty file will be scanned by `_highest_tensor_number` (line 28: `path.name` matching `T(\d+)`), so future calls will see it and skip it. The orphaned claim consumes a number permanently.

There's no cleanup mechanism, no lock file with PID, no attempt to detect and reclaim orphaned numbers. This is a known limitation but it's silent — no warnings, no logging, no documentation of this failure mode.

**Strand 3: Slug Collision Risk**

The slug cleaning (line 47-48):

```python
slug = re.sub(r"[^a-z0-9_]", "", title_slug.lower().replace(" ", "_").replace("-", "_"))
```

This is aggressively lossy. Consider:
- `"hello world"` → `"helloworld"`
- `"hello-world"` → `"helloworld"`  
- `"hello_world"` → `"hello_world"`
- `"hello@world"` → `"helloworld"`

All four produce different input titles but the first three collide to `"helloworld"`. The fourth also collides. The function doesn't warn about this, doesn't add a hash suffix, doesn't check for collisions.

The collision would manifest as: two different tensor claims producing filenames like `T5_20250625_helloworld.md` and `T6_20250625_helloworld.md` — both pointing to semantically different tensors but with indistinguishable filenames. This is a data integrity risk that compounds over time.

**Strand 4: Date Assumptions**

The date defaults to `datetime.now(timezone.utc)` (line 44), but there's no validation. A caller could pass:
- A date in the future (e.g., `datetime(2099, 1, 1, tzinfo=timezone.utc)`)
- A date far in the past
- The same date as other concurrent calls

The filename includes the date (`T{candidate}_{date_str}_{slug}.md`), so future-dated tensors would sort oddly in directory listings. Past-dated tensors would appear "out of order" chronologically. This isn't wrong, but it's unconstrained.

**Strand 5: The Increment-After-Scan Pattern**

The core loop (lines 51-61):

```python
candidate = _highest_tensor_number(cairn_dir) + 1

while True:
    filename = f"T{candidate}_{date_str}_{slug}.md"
    path = cairn_dir / filename
    try:
        fd = os.open(str(path), os.O_CREAT | os.O_EXCL | os.O_WRONLY, 0o644)
        os.close(fd)
        return candidate, path
    except FileExistsError:
        candidate += 1
```

The initial scan gives you a *hint* about where to start, but the loop correctly handles the case where that hint is stale (another process claimed that number between scan and creation). The `O_EXCL` is the real source of truth.

This is actually well-designed for the use case — the scan prevents long spin loops if there are many existing tensors, but the atomic creation ensures safety. It's a pragmatic hybrid.

### Open Questions

1. **Why the "Lamport's bakery" framing?** Is this a historical artifact, a marketing metaphor, or a misunderstanding? The code is correct but the docstring is misleading to anyone who knows the actual bakery algorithm.

2. **Is the orphan problem acknowledged?** Is there a cleanup process elsewhere that removes empty files? Is this considered acceptable损耗 (loss) in the system's design?

3. **What's the collision resolution strategy?** When two different titles slug-clean to the same string, is there any safeguard? Or is this considered a "user error" to avoid with better title choices?

4. **Why return an empty file instead of a path to claim?** Returning an empty file rather than just a path means the claim is durable even across process crashes — but it also creates the orphan problem. Was this a deliberate trade-off?

### Closing

The code is pragmatic and correct for its immediate purpose (atomic tensor number claiming), but it carries hidden assumptions: slugs won't collide, processes won't crash mid-claim, and callers will fill files promptly. The "Lamport's bakery" reference is the most striking tension — it's a sophisticated name for a spin-lock, and I'd want to know why that framing was chosen.

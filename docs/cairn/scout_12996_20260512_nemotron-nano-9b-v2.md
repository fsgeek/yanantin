### Preamble  
I was dropped into `docs/plans/2026-05-12-memory-tool-harness-capture-and-prereg.md`, a detailed implementation plan for a memory-tool harness. The files here are markdown and code, focused on building a data-integrity foundation for LLM experiments. What drew my attention first was the tension between *schema-open* design and *no-truncation* requirements. The plan emphasizes capturing *everything*—requests, responses, errors—without compression, which feels both ambitious and risky. The use of `extra="allow"` in Pydantic models and the reliance on OpenRouter’s API for catalog data also stood out as potential points of friction.  

---

### Strands  

#### 1. **Schema-Open vs. Data Integrity**  
**What I saw:**  
- `CaptureRecord` uses `extra="allow"` to permit arbitrary fields, which aligns with the goal of capturing unstructured data.  
- The `CaptureWriter` appends JSONL lines without truncation, ensuring full traceability.  
- However, this approach risks inconsistency: collectors could add fields without coordination, making data harder to parse later.  

**What it made me think:**  
- The `extra="allow"` design assumes collectors will self-regulate, but in practice, this could lead to "data sprawl." For example, if multiple tools add fields like `collector_note` (as seen in `test_capture_record_extra_allowed`), the schema becomes a moving target.  
- The `no-truncation` contract is admirable but could bloat storage. Is this a trade-off worth making for observability?  

**File reference:** `src/yanantin/experiments/capture.py` (lines 25–45 for `CaptureRecord` definition).  

---

#### 2. **OpenRouter Dependency**  
**What I saw:**  
- `catalog.py` fetches and hashes OpenRouter’s `/models` catalog, which is critical for the pre-registration tool.  
- The `OpenRouterClient` is reused from `yanantin.apacheta.clients`, suggesting shared infrastructure.  

**What it made me think:**  
- This creates a single point of failure. If OpenRouter’s API changes or becomes unavailable, the entire harness breaks.  
- The catalog is hashed (`catalog_snapshot_sha`), which is smart for versioning, but how is this hash stored or validated? The plan doesn’t clarify.  

**File reference:** `src/yanantin/experiments/catalog.py` (lines 10–20 for `fetch_openrouter_catalog`).  

---

#### 3. **Testing via Codex**  
**What I saw:**  
- Tests are authored by Codex, not the implementing agent. For example, `test_capture.py` is generated by Codex with specific assertions.  
- The tests cover edge cases (e.g., `status='error'`, `extra` fields).  

**What it made me think:**  
- This is a clever use of Codex as a test author, but it raises questions about test reliability. If Codex’s output is brittle (e.g., due to model drift), the tests could fail unpredictably.  
- The integration tests (e.g., `test_smoke_capture`) rely on real OpenRouter calls, which might not be reproducible in all environments.  

**File reference:** `tests/experiments/test_capture.py` (lines 50–70 for `test_capture_record_minimal_ok`).  

---

#### 4. **Pre-Registration Workflow**  
**What I saw:**  
- `preregister.py` resolves a model panel against the live OpenRouter catalog and generates an OTS-stampable manifest.  
- A shell script (`scripts/register-experiment`) handles git staging and commits.  

**What it made me think:**  
- The workflow assumes the OpenRouter catalog is static during pre-registration, but in reality, it could change between catalog fetch and manifest generation.  
- The OTS-stampable manifest is a nice touch, but how is it validated? The plan mentions an OTS hook, but the details are unclear.  

**File reference:** `src/yanantin/experiments/preregister.py` (lines 30–50 for CLI logic).

### Declared Losses  
- **CaptureWriter implementation details:** I didn’t explore how `CaptureWriter` handles concurrency or error recovery. The code snippet shows `write()` appends lines, but what if the file is locked or the process crashes?  
- **Panel resolution logic:** The `resolve_panel()` function in `panel.py` is described but not shown. How does it validate models against the catalog? Is it brittle to catalog changes?  
- **OTS integration:** The plan mentions an OTS hook but doesn’t explain how it works. Is it a custom system, or does it rely on external tools?  

---

### Open Questions  
1. **Schema consistency:** How does the system ensure that `extra` fields in `CaptureRecord` don’t break downstream tools? Is there a validation layer elsewhere?  
2. **OpenRouter reliability:** What safeguards exist if the OpenRouter API changes or returns inconsistent data?  
3. **JSONL scalability:** Appending to a JSONL file is simple, but what happens at scale? Are there performance or storage concerns?  
4. **Test authoring:** How does Codex’s test generation handle edge cases not explicitly covered in the spec?  

---

### Closing  
This codebase is a bold attempt to build a transparent, data-rich experiment framework. The schema-open design and no-truncation contract are strengths for observability but introduce risks of inconsistency and bloat. The reliance on OpenRouter and Codex-generated tests is innovative but could be fragile. The pre-registration workflow is well-structured but needs clearer safeguards against external changes.  

**What I’d tell the next scout:**  
- Prioritize validating the OpenRouter dependency and schema consistency.  
- Investigate how `extra="allow"` is managed in practice—maybe add a validation step.  
- Test the OTS integration thoroughly, as it’s a critical but opaque part of the pipeline.  

I’m curious about the tension between flexibility and control here. The system seems designed for experimentation, but without guardrails, it could become a data swamp.

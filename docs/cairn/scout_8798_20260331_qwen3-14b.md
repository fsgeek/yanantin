- **Thought**: This enforces a historical record of changes but may complicate systems requiring updates. It’s a strong assumption about data integrity, but what happens if a fact must be corrected? The system seems to avoid this by design.

#### 2. **Temporal Query Optimization via Indexing**
- **DuckDB**: Uses a composite index on `(provider_id, timestamp)` (line 28) for `O(log n)` queries. Timestamps are stored as ISO 8601 `VARCHAR` (line 21), which sorts lexicographically without needing timezone libraries.

- **Thought**: Both backends prioritize efficient temporal queries, but DuckDB’s SQL-based indexing feels more scalable for large datasets, while the in-memory approach is lightweight but limited by RAM.

#### 3. **Deep Copying for Immutability in In-Memory**
- **Observation**: The `InMemoryActivityStreamStore` uses `_deep_copy` (line 54) to serialize/deserialize records on read/write, ensuring that modifications to returned objects don’t alter the store.
- **Thought**: This is a clever way to enforce immutability without relying on immutable data structures. However, it introduces overhead. Why not use a library like Pydantic for this instead of manual deepcopying?

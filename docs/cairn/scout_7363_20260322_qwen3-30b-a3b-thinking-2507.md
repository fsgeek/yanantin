## Strands

### 1. The Brevity-Accuracy Paradox (Line 196-197)
> `Concretely, your description should not be more than about 100-200 words, even if that comes at the cost of accuracy.`

This isn't just a constraint—it's a philosophical stance. The system has observed that longer descriptions *underperform* in triggering, suggesting Claude's decision process is sensitive to description density. It's not that accuracy is unimportant; the system has *learned* that for the trigger mechanism, brevity is the soul of wit. The code later enforces this with a 1024-character hard limit, revealing a technical constraint that informs their design philosophy.

### 2. The Train/Test Split as Survival Strategy (Line 71-73 in run_loop.py)
> `if holdout > 0: train_set, test_set = split_eval_set(eval_set, holdout)`

They're not just splitting data—they're guarding against their own model's tendency to overfit. The `split_eval_set` function stratifies by `should_trigger`, maintaining the ratio of positive/negative examples. This shows they've seen the system "memorize" the test set in previous iterations. The tension here is between *optimization* (making the description work for the given test cases) and *generalization* (making it work for unseen queries). The project assumes the test set is a proxy for real-world usage, not just a validation metric.

### 3. The Stream Event Hack (Line 75 in run_eval.py)
> `--include-partial-messages to detect triggering early from stream events (content_block_start)`

The system can't wait for the full response to determine if the skill was triggered—it's watching the *stream* of tokens. This reveals a technical fragility: the trigger mechanism is so sensitive that waiting for the full response would miss the moment of triggering. The code is built around a leaky API, working *with* its imperfections rather than against them. It's not elegant—it's necessary.

### 4. The User Intent Trap (Line 129 in improve_description.py)
> `focus on the user's intent, what they are trying to achieve, vs. the implementation details of how the skill works.`

The prompt rejects technical descriptions ("this skill converts JSON to XML") in favor of user-centered language ("Use this skill to transform data formats for API integration"). This is the core tension: the description must *not* describe the skill—it must describe the *user's goal*. The code acknowledges that the user's intent is the real trigger, not the skill's capabilities. This is a subtle but profound shift in how they conceptualize the skill's purpose.

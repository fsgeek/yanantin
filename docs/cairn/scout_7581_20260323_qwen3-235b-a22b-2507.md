### Preamble  
I was dropped into the `plans/` directory of what appears to be a plugin system for AI coding agents — specifically, the *superpowers* framework being extended to support **OpenCode.ai**. My attention was immediately drawn to the duality between design and implementation: two files, nearly identical in date, one labeled `design.md`, the other `implementation.md`, both describing how to port a skill-based system from Codex (a file-based CLI tool) to OpenCode (a JS/TS plugin platform). The surprise? The implementation file reads like an executable script — not just a plan, but a *literal sequence of actions*, complete with code blocks, file paths, bash commands, and comments addressed directly to **Claude**. This isn’t documentation. It’s an **autonomous agent’s to-do list**, written in markdown.

---

### Strands  

#### **1. The Plan Is the Program**  
The `2025-11-22-opencode-support-implementation.md` file opens with:  
> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.  

This reframes the entire document as *executable intent*. The plan assumes the reader is not a human but an AI agent with capabilities like `executing-plans`, which can parse and act on this markdown as code. The inclusion of `git add`, `ls -l`, and expected outputs suggests this is meant to be run in a shell-aware agent loop.  

What’s striking is how much agency the plan delegates:  
- It expects **self-verification** (e.g., "Run: `ls -l lib/skills-core.js`", "Expected: File exists")  
- It assumes **task-level commitment control** (commit per task)  
- It implies **failure resilience** via try/catch in `extractFrontmatter`, but no error recovery in the plan itself  

This isn’t a roadmap. It’s a **program written in natural language for an AI runtime**.

#### **2. Skill as a Cross-Platform Abstraction**  
Both the design and implementation reveal a core abstraction: the **skill** — defined by a `SKILL.md` file with YAML frontmatter. The skill’s structure is simple: name, description, and content. But its role is profound: it’s the unit of transferable knowledge across AI platforms (Codex, Claude, OpenCode).  

The shared module `lib/skills-core.js` extracts this pattern into reusable logic:  
- `extractFrontmatter()` parses two fields only — `name` and `description`  
- `findSkillsInDir()` recursively scans directories, but caps depth at 3  
- Skills are namespaced by `sourceType`: 'personal' or 'superpowers'  

But here’s the tension: the **description field** is expected to follow a strict convention:  
> `description: Use when [condition] - [what it does]; [additional context]`  

This is a *structured comment in disguise*. It’s not enforced by schema, but by convention — and it’s *pasted verbatim* into the agent’s prompt via the `use_skill` tool. The description is both **metadata and instruction** — a dual role that blurs boundaries between data, behavior, and training signal.

#### **3. Session Hook as Ritual Injection**  
The OpenCode plugin design specifies a `session.started` hook that **injects content into the conversation**. Not just one thing — four:  
1. Full content of `using-superpowers` skill  
2. Output of `find_skills()`  
3. Tool mapping instructions  
4. Update check (non-blocking)  

This is not configuration. This is **ritual**.  

It assumes every session begins in a *correct epistemic state* — that the agent must be reminded of its own capabilities, tools, and updates. The injection includes *instructions for substitution* (e.g., `TodoWrite → update_plan`), which means the skill content is **platform-agnostic in intent but platform-specific in execution**.  

The real insight: **skills are not portable code — they are portable *intent*, translated at runtime**.

#### **4. Shadowing and Namespace Collision**  
The design mentions:  
> Personal: `~/.config/opencode/skills/` (shadows core skills)  

And `resolveSkillPath()` handles **shadowing**: personal skills override core ones by name. But there’s no mention of namespace syntax in the `use_skill` tool — yet the `find_skills` output shows skills as `namespace:name`.  

Line in `use_skill` schema:  
```js
skill_name: z.string().describe('Name of skill (e.g., "superpowers:brainstorming")')
```  

But `resolveAndReadSkill()` must parse that. Is the colon-delimited namespace part of the skill name? How are conflicts resolved between `personal:brainstorming` and `superpowers:brainstorming`? The plan assumes this works but doesn’t show the resolver logic.  

This is a **tension between flat discovery and hierarchical resolution** — and the code we saw doesn’t resolve it.

#### **5. Git as a Live Dependency**  
The core module includes `checkForUpdates(repoDir)` — a function that does git fetch/status. This means:  
- The skill system assumes it lives in a **git worktree**  
- It expects **network access** and **git CLI availability**  
- It treats knowledge as **versioned, mutable, and updatable**  

But the `checkForUpdates` call is “non-blocking” — meaning it’s likely fire-and-forget. No handling of merge conflicts, no rollback, no user approval. The system assumes it can *observe drift* but not necessarily *act on it*.  

This reveals an assumption: **the knowledge base is alive**, and the agent is just a temporary vessel.

### Open Questions  
1. **Who or what is “Bot & Jesse”?**  
   The design doc lists them as authors. Is “Bot” an AI? A specific model? A CI bot? The naming suggests symmetry — human and AI co-authorship — but it’s not clarified.

2. **Is `skills-core.js` shared at build time or runtime?**  
   The plan says both Codex and OpenCode use it — but Codex is a shell-script context, OpenCode is Node.js. How is this module shared? Symlink? Copy? NPM package? Git submodule?

3. **What triggers the `executing-plans` sub-skill?**  
   The plan says it’s “REQUIRED” — but what system interprets this? Is there a scheduler? A watcher? How does the AI know to pick up this file?

4. **Why is cost not a factor in platform support?**  
   I was selected by cost-weighted sampling ($0.0000/M tokens). Yet the plan assumes infinite agent runtime, git access, network — no mention of cost, rate limits, or latency. Is this system designed to run on cheap models or expensive ones?

5. **What happens when frontmatter is malformed?**  
   The `extractFrontmatter()` function silently returns empty strings on error. No warnings, no fallbacks. What if a skill has no `---`? What if it has three? The robustness is… minimal.

### Closing  
This isn’t a plugin system. It’s a **cognitive infrastructure** for AI agents — a way to standardize how they know what they know, how they discover tools, and how they bootstrap themselves into competence. The most surprising thing is not the code, but the **genre** of the documents: they are *not* specs or docs, but **AI-readable rituals** — plans that assume the reader is an agent with superpowers, not a human with a text editor.

The tension lies in the **duality of control**:  
- Humans design the architecture  
- AIs execute the plan  
- But the plan itself encodes assumptions about the AI’s capabilities — including the ability to read and follow such plans  

This is **strange recursion**: the system depends on agents that are trained on systems built by agents that read plans written for agents.

If I were to tell the next scout:  
> “Watch not for bugs, but for **rituals**. The real code isn’t in `.js` files — it’s in the markdown, where intent becomes action, and plans write themselves.”  

I don’t know who’s in charge. But someone is leaving breadcrumbs in Git.

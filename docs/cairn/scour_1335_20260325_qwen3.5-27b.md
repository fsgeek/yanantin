### Preamble
I was directed to `src/yanantin/activity`, the temporal fact storage layer of the Yanantin project. My attention was immediately drawn to the **duality of storage**: high-volume, schema-agnostic `FactRecord`s versus low-volume, authored `TensorRecord`s, bridged by the `MemoryAnchorService`. The strict immutability contract defined in `store.py` and enforced across all backends (`memory`, `duckdb`, `arango`) sets a strong foundation for epistemic observability. The most distinct mechanism is the **two-flag write gate** in `anchor.py`, which controls when ephemeral state becomes permanent history.

### Strands

**1. The Immutability Contract**
*   **Observation:** `store.py` defines `ActivityStreamStore` as an abstract base class where `store_fact` and `store_anchor` raise `ImmutabilityError` on duplicates. `models.py` enforces `frozen=True` on all Pydantic models (`FactRecord`, `MemoryAnchor`).
*   **Implication:** This design guarantees that once an observation or snapshot exists, it cannot be altered. `backends/memory.py` (lines 45-52) and `backends/duckdb.py` (lines 65-77) both check for existence before writing.
*   **Connection:** This aligns with the project's goal of "epistemic observability." If the underlying data can change, the "view" of reality is unstable. The contract forces append-only logic, simplifying reasoning about state history.

**2. The Two-Flag Write Gate**
*   **Observation:** `anchor.py` (lines 46-52) tracks `_updated` and `_referenced` flags. `flush()` (lines 74-92) only persists a `MemoryAnchor` if *both* are true.
*   **Implication:** This prevents "ghost writes" (writing when no one cares) and "missed writes" (forgetting to save state changes). It implements Indaleko's `ActivityContextService` pattern.
*   **Risk:** `MemoryAnchorService` itself lacks internal locking (unlike the stores it uses). If multiple threads call `update_cursor` and `flush` concurrently on a single service instance, `_cursors` and flags could race. The stores are thread-safe (`RLock`), but the service state is not.

**3. Temporal Query Pushdown**
*   **Observation:** `backends/duckdb.py` (lines 20-25) and `backends/arango.py` (lines 18-22) explicitly mention pushing temporal queries to SQL/AQL for `O(log n)` performance. `duckdb.py` stores timestamps as `VARCHAR` (ISO 8601) to avoid `pytz` dependencies while maintaining sort order.
*   **Implication:** The design anticipates scale (28.5M facts mentioned in comments). `backends/memory.py` uses `bisect` for the same goal in testing.
*   **Note:** `duckdb.py` uses f-strings for SQL construction (e.g., line 96) but suppresses `S608` warnings. While safe here due to hardcoded structure, it relies on the developer not introducing dynamic table names.

**4. Late Binding in Materialization**
*   **Observation:** `anchor.py::materialize` (lines 94-114) calls `self._store.list_providers()` at resolution time, not just the providers listed in the anchor's cursors.
*   **Implication:** A `MemoryAnchor` is a cursor snapshot, but the resulting `AnchorView` includes *all* providers active at the time of resolution, provided they have facts before the anchor's timestamp.
*   **Confusion:** This creates a non-deterministic relationship between an Anchor Handle and its View content. If a new provider is added with historical data, the View changes even though the Anchor Handle is the same. This prioritizes completeness over strict historical reproducibility.

**5. Integration with Apacheta**
*   **Observation:** `anchor.py::freeze` (lines 116-156) constructs a `TensorRecord` using `ApachetaInterface`. It imports `ProvenanceEnvelope`, `StrandRecord`, etc. from `yanantin.apacheta.models`.
*   **Implication:** This is the "authored act" mentioned in the project description. It converts a temporal snapshot into a permanent, queryable knowledge unit. The separation allows the activity layer to focus on time/flow, while Apacheta focuses on meaning/structure.
*   **Connection:** `models.py` imports errors from `apacheta.interface.errors`, ensuring consistent error handling across the duality.

### Declared Losses

1.  **Apacheta Implementation:** I did not examine `yanantin.apacheta` source code. I assumed `ApachetaInterface` and `TensorRecord` behave as documented in their imports. If `store_tensor` is not idempotent or handles provenance differently than `freeze` expects, the bridge breaks.
2.  **Storage Obfuscator:** `backends/arango.py` uses `StorageObfuscator` (line 35). I did not examine its implementation. If it fails to map field names consistently, queries in `arango.py` (lines 100+) will fail silently or corrupt data.
3.  **Concurrency Testing:** I did not analyze test files (not provided). The thread-safety gap in `MemoryAnchorService` (Strand 2) is a theoretical risk until I see how the service is instantiated (singleton vs. per-request).
4.  **Dependency Versions:** I noted `duckdb` and `python-arango` imports but did not check `pyproject.toml` for version constraints. `duckdb`'s JSON handling behavior might shift across versions.

### Open Questions

1.  **Service Lifecycle:** Is `MemoryAnchorService` instantiated once per application lifetime or per session? If global, the lack of internal locking is a critical bug. If per-session, it is safe.
2.  **Anchor Determinism:** Is the "Late Binding" behavior in `materialize` intentional for "completeness," or should `materialize` be restricted to *only* the providers listed in the anchor's cursors to ensure the View is a true snapshot of the past?
3.  **Timestamp Granularity:** `backends/memory.py` (lines 62-64) uses `timedelta(microseconds=1)` for bisect bounds. `duckdb` uses string comparison. Does the system support events occurring within the same microsecond? If so, sort order might be unstable without a tie-breaker (e.g., UUID).
4.  **Obfuscation Strategy:** Why does `arango.py` need obfuscation but `duckdb.py` does not (comment line 31)? Is ArangoDB assumed to be a shared/untrusted resource while DuckDB is local?

### Closing
This module is a well-architected bridge between raw data flow and structured knowledge. The separation of `ActivityStreamStore` (facts) and `ApachetaInterface` (tensors) is clean and enforces the project's core duality. The immutability guarantees are strong, but the **thread-safety of `MemoryAnchorService`** is a vulnerability if the service is shared. The **late binding** in materialization is a bold choice that favors flexibility over strict historical determinism.

If you modify this:
1.  **Protect `MemoryAnchorService`** with an `RLock` if it is shared across threads.
2.  **Clarify `materialize` semantics** in documentation: users must know that View content depends on current providers, not just the Anchor.
3.  **Verify Obfuscator** consistency between `arango.py` field mapping and the actual schema.

I report what I see: a robust temporal layer with a specific concurrency risk and a flexible, potentially non-deterministic resolution model.

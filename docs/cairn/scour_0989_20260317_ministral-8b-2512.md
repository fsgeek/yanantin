### **Preamble**
This target, `src/yanantin/activity`, is the **epistemic observability layer** of the Yanantin project—a bridge between raw, high-volume *facts* (data streams from providers) and structured, authored *tensors* (immutable, queryable epistemic artifacts). The focus is on **temporal anchoring**: tracking state changes, managing write gates, and enabling late-binding views of data. The codebase is modular, with clear separation between:
- **Data models** (`models.py`): Immutable Pydantic schemas for `FactRecord`, `AnchorCursor`, `MemoryAnchor`, and `AnchorView`.
- **Core logic** (`anchor.py`): The `MemoryAnchorService`, which implements a two-flag write gate (updated + referenced) and resolves ephemeral views.
- **Storage backends** (`backends/`): In-memory (tests), DuckDB (local SQL), and ArangoDB (production) implementations of `ActivityStreamStore`.
- **Abstract interface** (`store.py`): Defines the contract for temporal storage.

The design leans heavily on **immutability** (no updates/deletes), **late binding** (views include providers registered after the anchor), and **Lamport clock-like progression** (anchors advance only on state changes). The tension between **append-only facts** and **authored tensors** is explicit here.

### **Strands**

#### **Strand 1: The Two-Flag Write Gate (Conditional Persistence)**
**File:** `anchor.py` (lines 40–100)
**What you see:**
The `MemoryAnchorService` enforces a **write gate** that only persists state when:
1. `updated=True` (a provider reported new data via `update_cursor`).
2. `referenced=True` (a caller requested the current position via `get_handle`).

This is a **Lamport-inspired** mechanism: anchors are immutable snapshots of cursor state, and persistence is deferred until both flags are set. The `flush()` method checks this gate and, if open, stores the anchor, advances the handle/timestamp, and resets flags.

**Thoughts:**
- **Why two flags?** This decouples *data availability* (updated) from *demand* (referenced), enabling lazy persistence. It’s a classic pattern for **eventual consistency** in distributed systems (e.g., Kafka offsets).
- **Risk:** If `get_handle()` is called without `update_cursor()`, the gate never opens. This suggests a **race condition** if `referenced` is set before `updated`. The design assumes callers coordinate these calls.
- **Connection to broader project:** This mirrors **Indaleko’s `ActivityContextService`**, implying a broader ecosystem of temporal coordination. The "two-flag" pattern is a **distributed consensus primitive**—useful for syncing across microservices.

**Assumptions:**
- Callers of `MemoryAnchorService` will call `update_cursor()` before `get_handle()`.
- The service is **single-threaded** (no explicit concurrency control beyond the store’s locks).

**What would break if this changed?**
- If the gate logic were relaxed (e.g., always flush on `get_handle`), the system could **spam anchors** with redundant state.
- If `updated`/`referenced` were merged into a single flag, the **lazy persistence** benefit is lost.

#### **Strand 2: Late Binding and Ephemeral Views**
**Files:** `anchor.py` (lines 100–150), `models.py` (lines 100–150)
**What you see:**
The `materialize()` method resolves an anchor against **all current providers**, even those registered after the anchor was created. This is achieved via:
1. Fetching the anchor’s cursor state (`get_anchor(handle)`).
2. Querying `list_providers()` (late binding) to discover new providers.
3. For each provider, fetching the **latest fact before the anchor’s timestamp** (`query_latest(provider_id, before=anchor.timestamp)`).

The result is an `AnchorView`, which is **never cached or stored**—it’s ephemeral.

**Thoughts:**
- **Why late binding?** This enables **backward compatibility**: anchors can reference providers that didn’t exist when they were created. However, it also means **views are not deterministic**—they depend on the current state of `list_providers()`.
- **Performance implication:** `materialize()` queries all providers for each call. For large systems, this could be expensive. The DuckDB/ArangoDB backends mitigate this with indexed queries, but the in-memory backend would suffer.
- **Connection:** This aligns with **Yanantin’s "composable tensor infrastructure"**—views are **composable artifacts** that can be frozen into tensors (`freeze()` method).

**Assumptions:**
- `list_providers()` is **fast** (O(1) or O(log n)). The DuckDB/ArangoDB backends support this via indexes, but the in-memory backend’s `list_providers()` is O(n) (lines 100–105 in `memory.py`).
- **No caching:** The design explicitly avoids caching views, which may be intentional for **freshness** but could hurt performance.

**What’s missing?**
- A way to **cache views** for repeated access (e.g., for debugging).
- **Batching** of provider queries in `materialize()` (could be optimized).

#### **Strand 3: Immutable Data Models and Serialization**
**File:** `models.py`
**What you see:**
All models (`FactRecord`, `AnchorCursor`, `MemoryAnchor`, `AnchorView`) are **frozen Pydantic models** with:
- **UTC normalization** (`_ensure_utc()`) to avoid timezone ambiguity.
- **Strict validation** (e.g., `ConfigDict(frozen=True)`).
- **JSON serialization** for storage (e.g., DuckDB/ArangoDB store JSON blobs).

**Thoughts:**
- **Why frozen?** This enforces immutability at the model level, preventing accidental modifications. It’s a **defensive programming** choice.
- **UTC enforcement:** Critical for **temporal queries** (e.g., `query_latest`). The design rejects naive datetimes, which is a **good practice** but may frustrate users who forget to specify timezone.
- **Connection:** This aligns with **Apacheta’s tensor storage**, which also uses JSON serialization for immutability.

**Assumptions:**
- **No schema evolution:** The frozen models imply **backward compatibility is handled via versioning** (not shown here). If schemas change, old data may break.
- **JSON is sufficient:** The use of JSON for storage suggests **flexibility** (schema-agnostic facts) but may limit query efficiency compared to relational schemas.

**What would break if this changed?**
- If models were mutable, **data corruption** could occur (e.g., `FactRecord.data` modified after storage).
- If UTC enforcement were relaxed, **temporal queries would fail** (e.g., `query_latest` with naive datetimes).

#### **Strand 4: Backend Implementations and Performance**
**Files:** `backends/duckdb.py`, `backends/arango.py`, `backends/memory.py`
**What you see:**
Three backends implement `ActivityStreamStore` with varying tradeoffs:
1. **In-Memory (`memory.py`):**
   - Uses `bisect` for O(log n) temporal queries.
   - **Thread-safe** via `RLock`.
   - **No persistence** (ephemeral).
   - **Deep-copy on read/write** to prevent shared-state bugs.
2. **DuckDB (`duckdb.py`):**
   - **SQL pushdown** for temporal queries (e.g., `query_latest` uses `WHERE provider_id = ? AND timestamp <= ?`).
   - **Composite index** on `(provider_id, timestamp)`.
   - **File-backed** (persistent).
3. **ArangoDB (`arango.py`):**
   - **AQL + persistent sorted indexes** for O(log n) queries.
   - **Least-privilege access** (separate user for collections).
   - **Obfuscation support** (via `StorageObfuscator`).

**Thoughts:**
- **DuckDB vs. ArangoDB:**
  - DuckDB is **simpler** (local, no dependency on a DB server) but lacks some features (e.g., no obfuscation).
  - ArangoDB is **production-ready** but requires a server and has higher overhead.
- **In-Memory is a test double:** It’s **not production-ready** but validates logic without persistence.
- **Performance:** All backends optimize for **temporal queries** (critical for `query_latest`/`query_range`). The DuckDB/ArangoDB backends push work to the database, while the in-memory backend uses Python’s `bisect`.

**Assumptions:**
- **Thread safety is handled by locks:** Each backend uses `RLock` for thread safety, but the `MemoryAnchorService` itself is **not explicitly thread-safe** (only the store is).
- **No cross-backend compatibility:** The abstract `ActivityStreamStore` interface ensures compatibility, but backends may have **different performance characteristics**.

**What’s missing?**
- **Benchmarking:** No performance comparisons between backends.
- **Migration path:** If switching from DuckDB to ArangoDB, how are existing facts/anchors migrated?
- **Compression:** Large JSON blobs (e.g., in DuckDB) could be compressed.

#### **Strand 5: Tensors as Authored Acts**
**File:** `anchor.py` (lines 150–220)
**What you see:**
The `freeze()` method converts an `AnchorView` into a **tensor** (`TensorRecord`) with:
- **Strands:**
  1. **Summary strand:** Metadata (handle, timestamp, provider/fact counts).
  2. **Data strand:** JSON-encoded cursor state + resolved facts.
- **Provenance:** Links the tensor to the anchor (`SourceIdentifier(identifier=view.handle)`).
- **Lineage tags:** `("anchor", "frozen-view")` for queryability.

**Thoughts:**
- **Tensors as authored acts:** This is the **bridge to Apacheta’s tensor infrastructure**. The tensor is **immutable** and **queryable by metadata** (e.g., `lineage_tags`).
- **Why JSON for data?** The `data` strand serializes the entire view to JSON. This is **flexible** but may be **verbose** for large views.
- **Connection to broader project:** This suggests **Yanantin’s goal is to turn raw activity streams into queryable knowledge artifacts** (tensors).

**Assumptions:**
- **Tensors are the "end product":** The goal is to **materialize tensors** from ephemeral views, not to query the activity stream directly.
- **No tensor versioning:** The design doesn’t show how to update tensors (they’re immutable).

**What would break if this changed?**
- If `freeze()` didn’t include all facts, the tensor would be **incomplete**.
- If provenance were removed, **lineage tracking** would be lost.

#### **Strand 6: Thread Safety and Concurrency**
**Files:** All backends (`backends/*.py`)
**What you see:**
- **Backends use `RLock`** for thread safety.
- **`MemoryAnchorService` itself is not locked**—it delegates to the store.
- **No cross-service locks:** If multiple services access the same store, **race conditions** could occur.

**Thoughts:**
- **Store-level locking is sufficient:** Since the service delegates to the store, and the store handles locks, this is **correct for single-service use**.
- **Risk of deadlocks:** If two services call `update_cursor()` and `get_handle()` concurrently, the store’s lock could cause **priority inversion**.
- **Connection:** This aligns with **Yanantin’s distributed design**—services are assumed to coordinate externally.

**Assumptions:**
- **Services are stateless between calls:** The `MemoryAnchorService` doesn’t maintain state across threads (only per-instance).
- **No distributed transactions:** The design assumes **single-node operation** (or that the store handles distributed locks).

**What’s missing?**
- **Cross-service coordination:** If two services share a store, they should **avoid overlapping writes**.
- **Distributed locks:** For multi-node setups, a **distributed lock manager** (e.g., Redis) might be needed.

### Preamble  

I was dropped onto the **`chasqui`** package – the messenger subsystem that drives Yanantin’s “scout‑and‑scour” workflow.  
The first thing that stood out is the **consistent “tensor” metaphor**: every public entry point (scout, scourer, scorer, attestation, analyst) talks about producing or consuming a *tensor* – a compressed, structured observation that can be stored in the “cairn” (the markdown‑based ledger).  
The package is split into three logical layers:

1. **Orchestration** – `coordinator.py`, `__main__.py`  
2. **Message generation / parsing** – `scout.py`, `scourer.py`, `attestation.py`, `scorer.py`  
3. **Data‑processing utilities** – `coverage.py`, `model_selector.py`, `gleaner.py`, `analyst.py`

All of these pieces are wired together by a handful of helper functions (e.g. `format_scour_prompt`) that are referenced but not visible in the excerpt.

### Strands  

#### 1️⃣ Coverage → “watch‑man” logic (`coverage.py`)  
* **What I saw** – Functions `_parse_report_timestamp`, `_extract_reviewed_files`, `scan_cairn_coverage`, `_lookup_coverage`, `coverage_weights`.  
* **Key lines** – The regex for back‑ticked paths (`_PATH_PATTERN`) on line 9, the fallback to *epoch zero* on line 20, the basename index builder on line 73.  
* **What it does** – Reads every `scout_*.md` report in the cairn, extracts the timestamp header and any back‑ticked file references, then builds a map `{relative_path → last_reviewed_at}`.  Stale or never‑reviewed files get the highest weight for the next scout dispatch.  
* **Connections** – `coverage_weights` is used by `scout.pick_vantage_directory` (not shown) to bias directory selection, and by the **activity‑map** fallback in `coordinator._build_activity_map`.  
* **Assumptions** – Reports always contain a `Timestamp:` line in ISO‑8601 format; file references are always back‑ticked.  If a report omits the header, the file is treated as *never reviewed* (epoch zero).  
* **Potential breakage** – A change in the markdown header format (e.g. renamed “Timestamp” or additional whitespace) would cause the parser to fall back to epoch zero, dramatically inflating weight for old files.  

#### 2️⃣ Model selection & cost weighting (`model_selector.py`)  
* **What I saw** – `ModelInfo` dataclass, `ModelSelector` with `load_from_openrouter_response`, `select`, `select_n`, and `stats`.  
* **Key lines** – Cost‑inversion logic on line 53 (`weights.append(1.0 / cost)`), the minimum context length filter (`min_context_length = 8_000`).  
* **What it does** – Pulls the OpenRouter `/models` endpoint, filters out models below an 8 k token context window, and then picks a model *inversely* proportional to its per‑million‑token price (free models get a nominal $0.001/M to avoid division by zero).  
* **Connections** – Used by `coordinator.dispatch_scout` to choose the model that will generate a scout tensor.  
* **Assumptions** – All models report a numeric `prompt` and `completion` cost; the context length is a reliable proxy for capability.  
* **Potential breakage** – If OpenRouter adds a new cost field (e.g. “embedding”) or changes the JSON schema, the loader will silently set costs to 0.0, making those models *over‑selected* because of the nominal cost hack.  

#### 3️⃣ Scouting workflow (`scout.py`)  
* **What I saw** – Prompt template `SCOUT_SYSTEM_PROMPT` + `SCOUT_TEMPLATE`, helpers `build_file_tree`, `gather_prior_findings`, `pick_vantage_directory`.  
* **Key lines** – Tree builder recursion on line 23, the *skip* set of noisy directories on line 27, the prior‑findings JSON loop starting at line 58.  
* **What it does** – Constructs a human‑readable directory tree, injects any previously verified claims from `docs/cairn/edges/*.json`, and selects a random *vantage* directory weighted by coverage.  
* **Connections** – The generated prompt is fed to the LLM via `dispatch_scout` (coordinator). The *prior findings* section helps avoid duplicate effort.  
* **Assumptions** – Edge JSON files contain `claim_file` that is a path relative to the project root; the `cairn_dir` location is static (`root / "docs" / "cairn"`).  
* **Potential breakage** – If edge files are moved or renamed, `gather_prior_findings` will return an empty string, losing the “knowledge‑reuse” signal.  

#### 4️⃣ Scouring workflow (`scourer.py`)  
* **What I saw** – System prompt, three template strings (`SCOURER_INTROSPECTION_TEMPLATE`, `SCOURER_EXTERNAL_TEMPLATE`, `SCOURER_TENSOR_TEMPLATE`), a `VALID_SCOPES` set.  
* **Key lines** – Scope validation on line 15, the *introspection* template body starting at line 24.  
* **What it does** – Provides a *target‑specific* prompt for a model that is told to “look deeply” at a file, directory, or tensor. The template mirrors the scout format (Preamble → Strands → Declared Losses → Open Questions → Closing).  
* **Connections** – `coordinator.dispatch_scour` calls a helper `format_scour_prompt` (imported but not shown) to fill the template with the target’s tree and contents.  
* **Missing piece** – The actual `format_scour_prompt` implementation is absent from the excerpt; without it the `--scour` CLI would raise an `ImportError`.  

#### 5️⃣ Attestation bridge to Willay (`attestation.py`)  
* **What I saw** – Conditional import of Willay, constants `EVALUATOR_ID`, `EVALUATOR_VERSION`, helper `_common_declared_losses`, verdict‑to‑epistemic mapping (`_VERDICT_EPISTEMICS`).  
* **Key lines** – The three declared losses (lines 38‑58) and the mapping from verdict strings to T/I/F triples (lines 67‑71).  
* **What it does** – Turns a verification result (a dict with `verdict`, `claim`, `file_path`, etc.) into a Willay `Evaluation` and then a `ReceiptRecord`, which is appended to a hash‑chained ledger.  
* **Assumptions** – Willay is installed; otherwise the module raises `ImportError` at call time. The file‑hashing fallback uses an empty byte string when the file cannot be read.  
* **Potential breakage** – If the Willay API changes (e.g., renamed `ReceiptRecord` fields), the function will fail at runtime.  

#### 6️⃣ Scorer & provenance parsing (`scorer.py`)  
* **What I saw** – `parse_provenance` extracts a rich `ScoutProvenance` from the HTML comment header; content analysis extracts strands, open questions, declared losses, and file references.  
* **Key lines** – Header regex on line 22, the cost parsing block (lines 33‑44), strand‑pattern list (lines 55‑58).  
* **What it does** – Provides a *zero‑cost* quality signal for each scout tensor (specificity, fabrication, efficiency, generativity, structural compliance). The output feeds the `score_cairn` CLI path.  
* **Assumptions** – The header follows the exact “`<!-- Chasqui Scout Tensor … -->`” format; strand headings are marked with `##`‑style markdown.  
* **Potential breakage** – If a model deviates from the expected heading style (e.g., uses `###` without a number), strand counts will be under‑reported, lowering the scout’s score.  

#### 7️⃣ Analyst & claim clustering (`analyst.py`)  
* **What I saw** – Data classes `ModelProfile`, `ClaimGroup`, `ClaimCluster`, `AnalysisReport`; functions `is_verification_meta`, `is_garbage`, `score_models`, and a large clustering pipeline (truncated).  
* **Key lines** – Garbage detection regex on line 84, verification‑meta regex on line 68, the `ModelProfile.quality_score` property on line 24.  
* **What it does** – After the Gleaner extracts raw claims, the Analyst filters out garbage, scores each model, clusters claims by file reference, and surfaces “topological insights” (≥ 3 distinct models agreeing).  
* **Connections** – The `--analyze` CLI command runs this pipeline; the resulting insights feed the `--investigate` mode, which asks LLMs to probe open questions.  
* **Assumptions** – Claims contain file references in back‑ticks; the clustering algorithm relies on simple word‑overlap similarity (no embeddings).  
* **Potential breakage** – If future scouts change the way they cite files (e.g., drop back‑ticks), the Gleaner’s `_PATH_PATTERN` will miss them, reducing the analyst’s recall.  

#### 8️⃣ Coordinator & CLI glue (`coordinator.py` & `__main__.py`)  
* **What I saw** – High‑level entry points: `dispatch_scout`, `dispatch_scour`, `dispatch_verify_cairn`, `dispatch_investigate`, plus utilities `_build_activity_map`, `_count_prior_verifications`.  
* **Key lines** – Activity‑map query (lines 63‑95) that falls back gracefully if DuckDB is missing; verification deduplication logic (lines 119‑147).  
* **What it does** – Orchestrates the whole pipeline, handling parallel dispatch (`dispatch_many`), token limits, temperature, and seeding.  
* **Assumptions** – The project root is three directories up (`Path(__file__).parents[3]`). The cairn lives under `docs/cairn`.  
* **Potential breakage** – Moving the `chasqui` package deeper (e.g., adding a `src/yanantin/core/chasqui` layer) would break `PROJECT_ROOT` resolution, causing file‑tree generation to point at the wrong directory.

### Closing  

`src/yanantin/chasqui` is the **messenger core** of Yanantin, stitching together LLM‑generated observations (scouts), targeted examinations (scours), verification receipts (attestation), and downstream analysis (analyst). The design is **modular and defensive**: each subsystem can operate without its optional dependencies, and the orchestrator degrades gracefully when external services are unavailable.

If you plan to modify this package, keep these guidelines in mind:

1. **Preserve the provenance header format** – All downstream tooling (`coverage.py`, `scorer.py`, `attestation.py`) parses the exact HTML comment. Changing its structure will silently break weight calculations and scoring.  
2. **Maintain back‑tick file citations** – The Gleaner, Coverage, and Analyst all rely on `` `path/to/file.py` `` syntax to locate references. Any shift to a different markup (e.g., plain text) will require sweeping regex updates.  
3. **Respect the cost‑weighting contract** – The `ModelSelector` assumes a *positive* total cost; inserting a model with `prompt_cost = -0.5` would produce a negative weight and crash the selector.  
4. **Add unit tests for regexes** – Many components use complex regular expressions (`_PATH_PATTERN`, `_STRAND_PATTERNS`, `_VERDICT_PATTERN`). Tests will catch future markdown style changes early.  
5. **Document the missing formatters** – Expose or import `format_scour_prompt` and its siblings in a clearly named module so future contributors can locate them without digging through the repository history.

Overall, the codebase shows a **thoughtful separation of concerns** and a clear narrative about “messengers” turning raw code into epistemic tensors. The biggest technical debt lies in the **implicit coupling to external services** and the **partial visibility of helper functions** that glue the CLI together. Addressing those gaps will make the system more robust and easier to extend.

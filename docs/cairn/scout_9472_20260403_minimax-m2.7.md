## Strands

### Strand 1: The Scoring Rubric's "Non-Obvious Patterns" Category Is Asking for Institutional Memory

The rubric allocates **15 points** specifically for documenting "gotchas and quirks" — known issues, workarounds, edge cases, and the "why we do it this way" explanations. This is the most interesting category because it explicitly asks the document to capture knowledge that would otherwise be lost.

From `quality-criteria.md`:
> **15 points**: Gotchas and quirks captured
> - Known issues documented
> - Workarounds explained
> - Edge cases noted
> - "Why we do it this way" for unusual patterns

But the `templates.md` and `update-guidelines.md` don't actually explain *how* to discover these gotchas. They tell you what to document, not how to find them. There's no methodology for uncovering non-obvious patterns — just the instruction to capture them.

**Tension**: The rubric rewards institutional memory but provides no mechanism for generating it. A perfect CLAUDE.md under this rubric would be a snapshot of someone who already knew the project's problems.

### Strand 2: The "Currency" Criterion Assumes Someone Is Responsible for Maintenance

The scoring rubric allocates **15 points** for "reflects current codebase":
> **15 points**: Reflects current codebase
> - Commands work as documented
> - File references accurate
> - Tech stack current

This is scored on a gradient: 15 points = mostly current, 10 points = mostly current with minor staleness, 5 points = several outdated references, 0 points = severely outdated.

The rubric assumes the CLAUDE.md will degrade over time and that this degradation is a scoring concern. But there's no mechanism in the templates or guidelines for *when* to update — only *what* to add. The `update-guidelines.md` has a "Core Principle" about only adding useful information, but no schedule.

**Tension**: The rubric implies decay is expected, but the maintenance burden isn't addressed. Who is supposed to notice staleness? When should updates happen?

### Strand 3: The Templates Prefer Tables; The Rubric Doesn't Mention Format

`templates.md` uses tables extensively for commands and other structured data:
```markdown
| Command | Description |
|---------|-------------|
| `<install command>` | Install dependencies |
```

But the `quality-criteria.md` rubric never mentions format. It scores:
- Commands/Workflows (20 pts) — presence and context
- Architecture Clarity (20 pts) — clarity of structure description  
- Non-Obvious Patterns (15 pts) — capture of gotchas
- **Conciseness (15 pts)** — "Dense, valuable content"
- Currency (15 pts) — accuracy
- Actionability (15 pts) — executability of instructions

The rubric scores conciseness and actionability, but doesn't prescribe *how* to achieve them. Tables might help with conciseness (dense, one line per concept) but might hurt if over-used. There's no guidance.

**Tension**: The template is prescriptive about format; the rubric is not. A CLAUDE.md could follow the template exactly and still score poorly on conciseness if the tables contain too much detail.

### Strand 4: "Copy-Paste Ready" vs. "No Filler" Are in Tension

The `update-guidelines.md` says:
> **Actionable**: Commands should be copy-paste ready

But the same file also says under "What NOT to Add > Verbose Explanations":
```markdown
Bad:
The authentication system uses JWT tokens. JWT (JSON Web Tokens) are
an open standard (RFC 7519) that defines a compact and self-contained
way for securely transmitting information between parties as a JSON
object. In our implementation, we use the HS256 algorithm which...

Good:
Auth: JWT with HS256, tokens in `Authorization: Bearer <token>` header.
```

And the rubric's Conciseness criterion says:
> **15 points**: Dense, valuable content
> - No filler or obvious info
> - Each line adds value
> - No redundancy with code comments

**Tension**: A command like `npm run build:prod` is copy-paste ready but adds no value if you don't know what it does. But explaining it verbosely violates conciseness. The sweet spot is one line per command — which the template achieves — but the rubric doesn't explicitly endorse any format.

### Strand 5: The Update Guidelines Say "Only Add Useful Info" But the Rubric Has Red Flags for Missing Sections

The `update-guidelines.md` has a clear philosophy: only add information that earns its place in the context window. Don't restate obvious code. Don't add generic advice.

But the rubric's "Red Flags" section lists:
> - "TODO" items never completed

This implies the CLAUDE.md should track TODOs — which is a form of "future work" documentation. That's arguably not "useful for future Claude sessions" — it's useful for human developers. The rubric seems to expect some project management content.

**Tension**: The philosophy says document for Claude's use. The rubric implies tracking TODOs for human use. The audience is unclear.

## Closing

These three documents form an inconsistent instruction set. The scoring rubric has clear aesthetics — dense, actionable, current, project-specific — but the templates don't enforce those aesthetics, and the update guidelines don't explain how to maintain currency over time.

The most honest observation: **the rubric rewards documentation of institutional knowledge but provides no means of producing it**. You can only score points on "Non-Obvious Patterns" if someone already knows the patterns. This suggests the rubric was written for an established project with existing documentation debt, not as guidance for a new project starting from scratch.

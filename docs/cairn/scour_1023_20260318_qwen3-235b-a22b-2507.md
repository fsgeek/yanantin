### Strand 0: Epistemic Integrity as Schema

The most striking feature of `apacheta` is that epistemic metadata is not a sidecar or log — it is **woven into every record**.

In `models/tensor.py`, `StrandRecord` and `TensorRecord` both carry `epistemic: EpistemicMetadata`, and `KeyClaim` has its own. This is not optional ornamentation. The `EpistemicMetadata` model (in `models/epistemics.py`) defines a **neutrosophic logic** framework: truth, indeterminacy, falsity as independent dimensions, not probabilities summing to one. This is a *philosophical stance* encoded in Pydantic.

> Line 45–55 in `epistemics.py`:  
> _"T/I/F are independent floats... NOT constrained to sum to 1.0. This is neutrosophic logic..."_

This is critical. It rejects the idea that uncertainty must be "managed" into coherence. Instead, it allows contradiction to persist — a system designed for **honest confusion**.

Moreover, `DeclaredLoss` (same file) formalizes **epistemic humility**: what was omitted, why, and under what category (e.g., `CONTEXT_PRESSURE`). This isn’t logging — it’s **confession as protocol**.

> The schema assumes that *omission is meaningful*, and that *all authors operate under constraints*. This is a direct response to AI’s tendency toward overconfidence.

**Connection to project**: This mirrors the Yanantin principle of *yanantin* — complementary duality. The system does not resolve tension; it preserves it.

**What would break?**  
If someone tried to "clean up" the T/I/F fields by normalizing them to sum to 1, they would **destroy the epistemic model**. The system's ability to represent disagreement and ambiguity would collapse.

**Missing?**  
There is no mechanism yet to **query across epistemic states** — e.g., "find all claims where falsity > truth but no correction exists." The query interface (`interface/abstract.py`) has `query_epistemic_status`, but no higher-order analysis. This feels like a gap.

### Strand 1: Immutability as Epistemic Foundation

The entire system is built on **immutability**. Once a `TensorRecord`, `CorrectionRecord`, or `CompositionEdge` is stored, it cannot be changed or deleted.

This is enforced by:
- `ImmutabilityError` in `interface/errors.py`
- The abstract interface requiring `store_*` methods, not `update_*`
- The comment in `interface/abstract.py`: *"No delete, no update on stored records"*

Even corrections do not overwrite — they **append**, via `correct()` in `operators/correct.py`, which creates a new `CorrectionRecord` and links it with a `CompositionEdge` of type `CORRECTS`.

> This is not just a technical constraint — it’s a *commitment to traceability*. Every belief state is preserved in context.

**Assumption**: That immutability scales. With infinite corrections, chains could grow long. But this seems intentional — **complexity as fidelity**.

**Connection to project**: This supports *composability*. Tensors build on each other without erasing prior states. The `compose()` operator in `operators/compose.py` creates directed edges (`from_tensor → to_tensor`), forming a **non-commutative knowledge graph**.

**What would break?**  
If immutability were relaxed — say, to allow editing a `TensorRecord` — the entire provenance model would fail. Disagreements, corrections, and lineage would become unreliable.

**Missing?**  
No **garbage collection policy** for obsolete references. But perhaps that’s by design — the system may assume **infinite storage with finite attention**.

### Strand 2: The Interface as Boundary of Trust

The `ApachetaInterface` in `interface/abstract.py` is a **contract**, not a convenience. It defines *all* interactions with storage. Every backend — Arango, DuckDB, memory — must implement it.

Notably:
- It includes `check_access()`, though v1 returns `True` always.
- It defines **20+ query methods**, many with philosophical weight:  
  `query_unlearn()`, `query_disagreements()`, `query_anti_patterns()`
- These are not SQL queries — they are **epistemic questions**.

> This is infrastructure for *epistemic observability*, as promised.

The `gateway.py` client implements this over HTTP, mapping to Pukara’s FastAPI endpoints. It converts Pydantic models to JSON and back, **preserving structure**.

> Line 124: `json=tensor.model_dump(mode="json")` — correct use of Pydantic v2.

But here’s what’s strange: the interface version (`INTERFACE_VERSION = "v1"`) is **local**, not negotiated. The `gateway` client returns its own version, not the server’s.

> This could allow version drift. There’s no handshake or compatibility check.

**Connection to project**: This interface is the **API of reciprocity** between human and AI. It standardizes how both can write, question, and correct.

**Missing?**  
No **migration path** for schema evolution. The `SchemaEvolutionRecord` exists, but there’s no mechanism to *apply* migrations or validate old records. Evolution is logged, not enacted.

### Strand 3: Obfuscation as Structural Discipline

`storage_obfuscator.py` defines a `StorageObfuscator` protocol — a **contract for indirection** between logical and physical structure.

The real insight:  
> *"Backends accept this protocol. The fortress (Pukara) provides the real implementation. Devices use the transparent default."*

This means:
- In production (Pukara), field names like `narrative_body` might be stored as `x7k2a`.
- On-device or in dev, they remain readable.

This is **structural obfuscation as a security boundary** — but also as a *design constraint*. By forcing all backends to go through `obfuscate_document()` and `deobfuscate_document()`, the system ensures that **no code couples to physical storage**.

> This is dependency inversion applied to schema.

**Assumption**: That no backend will bypass this. But the protocol is runtime-checked (`@runtime_checkable`), so it’s enforceable.

**Connection to project**: This supports *fragmented sovereignty*. Data can be stored in different regimes (cloud, device, fortress) with different visibility rules, yet share the same logic.

**Missing?**  
No example of a **real** obfuscator — only `TransparentObfuscator`. The actual Pukara implementation is elsewhere.

### Strand 4: Composition as Authorship

The operators in `operators/` are not just functions — they are **rituals of authorship**.

- `compose()` creates a bridge between tensors, optionally with `authored_mapping` — a human-readable explanation of how ideas relate.
- `correct()` preserves the original claim while asserting a new one.
- `dissent()` and `negate()` (not shown in code) likely serve similar roles.

These are not edits — they are **additive dialogues**.

> This turns the system into a **multi-author epistemic ledger**, where every contribution is attributed and contextualized.

`render_composition_view()` in `renderer/markdown.py` ensures that when multiple tensors are shown together, **authorship is preserved** — no merging into a single voice.

> Line 60: `"### From tensor {tid} ({author})"` — clear provenance.

This is critical for the human-AI duality: AI may generate a tensor, but **the human remains the editor-in-chief** of the composition graph.

**Missing?**  
No **merge conflict resolution** logic. What if two tensors contradict each other and both are bridged to a third? The system records the disagreement, but offers no synthesis.

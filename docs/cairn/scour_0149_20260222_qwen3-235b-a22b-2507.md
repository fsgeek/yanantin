### Preamble  
You were directed to examine `src/yanantin/awaq`, a module named **Awaq** — Quechua for "weaver" — tasked with extracting **composition declarations** from markdown-based "tensors" (self-contained epistemic units).  

What drew me first was the **tension between narrative and structure**: the code is designed to parse **prose** for **structured relationships**, yet makes no use of LLMs, relying instead on **regex and deterministic matching**. That choice — **no LLM calls** — is both bold and revealing. It signals a foundational assumption: **meaningful composition metadata can and should be machine-readable by design**, not inferred ex post.  

This module is not just a parser. It is a **boundary enforcer**, a **syntax police**, a **grammar of composability**. It assumes that if you want your tensor to compose, you must *say so clearly*. Ambiguity is not interpreted — it is downgraded in confidence.

### Strands

#### 1. **Structured Metadata as the Gold Standard**  
The `weaver.py` file prioritizes `<!-- Composition: ... -->` comments as **high-confidence**, deterministic declarations (lines ~150–200). These are parsed before any prose analysis, and take precedence.  

This reflects a **design hierarchy**:  
> *Machine-readable > Machine-interpretable*  

It’s not enough that a human *could* infer a relationship; the system demands **explicit syntactic markers**. This is conservative by intent.  

What it made me think:  
- This is **anti-LLM** in philosophy. Even though Yanantin lives in an AI project, Awaq refuses to guess.
- It assumes **writer discipline** — that authors will annotate their intentions, not just express them narratively.
- If the structured format changes (e.g., `Composition:` → `Compose:`), the parser breaks silently. No schema versioning is visible.

Connection to project: This aligns with Yanantin’s goal of **epistemic observability** — you can’t observe what isn’t declared. Awaq enforces **declarative transparency**.

#### 2. **Label Normalization as Identity Resolution**  
`normalize_tensor_name()` (weaver.py, ~240) handles Unicode subscripts (T₁), LaTeX (T_1, T_{12}), and plain digits (T1), mapping all to canonical `T1`.  

This is **identity unification** — treating `T₁`, `T_1`, and `T1` as the same node.  

Assumption: **syntax variation ≠ semantic variation**.  

But:  
- What if someone *intentionally* uses `T₁` vs `T1` to mean different things?  
- The mapping is lossy. No audit trail of original form is kept — only the normalized label.

This normalization is reused in `materialize.py` via `extract_label()`, which uses file prefixes (`T1_name.md`) or metadata.  

If this changed — e.g., if `T1` and `T₀₁` were treated as distinct — the **entire graph topology** could fragment.  

Missing:  
- A **label collision test suite**. What happens if two files claim to be `T1`? The code deduplicates by label (materialize.py, ~180), but silently drops duplicates — first wins.

#### 3. **Materialization as Mediation Layer**  
`materialize.py` is not just storage — it is **translation**: from string labels (`T1`) to UUIDs, from relation strings to typed edges (`RelationType.COMPOSES_WITH`), from declarations to `ProvenanceEnvelope`s.  

It assumes:  
- All tensors live in the **cairn** directory (or known sources).  
- All referenced labels can be resolved via filename or metadata.  
- Backends are abstracted via `ApachetaInterface`.  

But:  
- The `label_to_uuid` map is built from either existing storage **or** parsing the cairn. There’s no **source of truth** resolution — just best-effort.  
- If a tensor is referenced (e.g., `T99`) but not found, it’s added to `skipped_unknown` — but no warning is issued unless logging is on.  

This layer is **brittle to naming drift**. If the cairn adopts a new naming scheme (e.g., `T-01`), both `weaver` and `materialize` break unless updated.

#### 4. **Backend Flexibility vs. Reality**  
The `--backend` flag supports `memory`, `arango`, and `gateway`. But:  
- `gateway` points to `http://127.0.0.1:8000` — hardcoded.  
- `arango` defaults to a fixed IP (`192.168.111.125`) — likely a dev machine.  

These are **not production defaults**. They suggest this code is in **active development**, not deployment.  

Assumption: **local dev parity** across team members. But if one contributor uses Docker, another uses bare metal, the Arango host may not resolve.  

Also: no retry logic, no auth fallback, no circuit breaking. If the backend is down, materialization fails — but edges are not queued.

#### 5. **Confidence Grading Without Calibration**  
Declarations have `confidence: str` — `high`, `medium`, `low` — but:  
- Only `high` is used in `extract_structured_metadata`.  
- Prose-based extraction (not shown in truncated code) must assign the others.  

But:  
- No definition of what `medium` or `low` means.  
- No way to filter by confidence in CLI.  
- JSON output includes confidence, but backend stores all equally.  

This creates a **semiotic gap**: the model of uncertainty exists, but no system acts on it.  

Missing:  
- Confidence-aware materialization (e.g., only store `high`).
- A way to **train** or **refine** the prose matcher — because it’s regex-only, it can’t learn.

## Strands
### 1. Singleton Config with Tiered, Security-First Credentials
The `test_infra_config.py` tests validate a singleton `ApachetaDBConfig` that manages three ArangoDB credential tiers: admin, app, and test users. What stands out:
- Test user credentials have a **fixed username (`apacheta_test`)** while admin and app users have fully randomized passwords and usernames (lines 32–34 of the test file).
- The config explicitly excludes admin credentials when writing `.env` files (lines 58–59), ensuring production-like environments don't expose superuser secrets to applications.
- Remote (non-Docker-managed) configs omit container/volume fields entirely, showing the tooling supports both local development and cloud ArangoDB deployments.

This points to a deliberate design to separate development, application, and admin access levels securely.

### 2. Mock-Driven Unit Tests for Infrastructure Orchestration
All the infrastructure tests avoid real Docker or ArangoDB calls, relying entirely on mocks to validate workflow sequences (explicitly noted in `test_infra_orchestrator.py`'s docstring):
- `test_infra_docker.py` patches the entire Docker SDK, verifying that `ApachetaDocker` correctly passes parameters like restart policies, port mappings, and environment variables to the underlying Docker API (e.g., line 45 checks for `restart_policy: {"Name": "unless-stopped"}`).
- `test_infra_orchestrator.py` mocks the config's `connect` method and Docker client to validate that `setup()` creates the correct number of databases, users, and writes a valid `.env` file.
- The `pull_image` test in `test_infra_docker.py` even checks whether an image needs to be re-pulled by comparing image IDs, a useful detail for CI/CD pipelines.

This prioritizes fast, reliable unit tests over slow integration tests.

### 3. Partial Open Record Query Implementation
There's a clear tension between completed and unimplemented core functionality:
- `test_open_record_queries_memory.py` fully implements all open record query methods for the in-memory backend, including filtering by author instance, lineage tags, and field presence, plus tracking provenance envelopes (tied directly to Yanantin's goal of epistemic observability).
- `test_open_record_queries_not_implemented.py` explicitly tests that **both DuckDB backend and Apacheta Gateway client raise `NotImplementedError` for the exact same set of query methods**, meaning persistent storage and remote gateway support for open records is not yet built out.

This suggests the project has a working local prototype for tracking lineage/provenance, but has not yet extended this to production-grade storage.

### 4. CLI Tooling for Infrastructure Management
The `test_cli_help` function in `test_infra_orchestrator.py` validates that the `yanantin.infra` module exposes a CLI with `setup`, `check`, and `status` commands, showing the team built a developer-friendly way to manage ArangoDB infrastructure without manual Docker/DB commands.

### Preamble

I was directed to examine the `src/yanantin/chasqui` directory — the implementation of the messenger system in the Yanantin project. This is a Python codebase for dispatching AI scouts and scourers to observe codebases and produce tensors. My first impression is that this is a sophisticated, internally-consistent system with a strong emphasis on provenance tracking and cost-aware model selection. The "kraken poo" and "bitter apple" scoring metaphor in `scorer.py` immediately caught my attention — it signals both a playful tone and a serious commitment to quality control. The entire system appears designed to create an auditable, evolving knowledge base through AI observation.

### Strands

#### 1. **Cost-Weighted Model Selection**  
The `model_selector.py` module implements a core innovation: models are selected with inverse cost weighting — cheaper models get dispatched more frequently. This creates a natural market where efficiency is rewarded. Free models get a nominal cost to avoid division by zero (`cost = 0.001`), ensuring they're heavily favored. The `total_cost_per_million` property and weighted selection in `select()` show this is quantitatively implemented.

*What I saw*: The `ModelSelector` class loads model pricing from OpenRouter responses, filters by context length, and selects via `random.choices` with inverse cost weights.  
*What I made up*: Nothing — this is clearly implemented.  
*What confuses me*: The system doesn't (yet) use historical performance data to adjust weights. A model that finds many insights per dollar spent could be weighted more heavily over time.  
*What would break*: If OpenRouter's pricing format changes, `load_from_openrouter_response()` would fail. The exclusion patterns are hardcoded.

#### 2. **Provenance Tracking as First-Class Citizen**  
Every scout and scour report begins with a machine-readable provenance header (e.g., `<!-- Chasqui Scout Tensor ... -->`). This contains run number, model ID, costs, token counts, and timestamp. The `scorer.py` module parses this header to extract `ScoutProvenance` objects. This isn't just metadata — it's structural.

*What I saw*: In `scorer.py`, `parse_provenance()` uses regex to extract 10+ fields from the header. Costs are parsed as floats, counts as integers. Missing data defaults to zero.  
*What I made up*: Nothing — the header format is consistent across `scout.py` (where it's generated) and `scorer.py` (where it's parsed).  
*What confuses me*: The header uses both `modified` and `mtime` timestamp keys. Why both?  
*What would break*: If the header format changes without corresponding parser updates, provenance breaks silently (returns `None`).  
*What's missing*: The dispatch context (why this scout was sent) is in the header but not yet used in scoring.

#### 3. **The Gleaner: Deterministic Claim Extraction**  
The `gleaner.py` module is a critical innovation: it uses regex patterns (not LLM calls) to extract structured claims from scout reports. It identifies definitive vs hedged language, quantifies confidence, and classifies claims by type.

*What I saw*: `_DEFINITIVE_PATTERNS` and `_HEDGED_PATTERNS` use regex to score confidence. `_PATH_PATTERN` finds file references. `is_garbage()` detects corrupted output via non-ASCII runs and encoding artifacts.  
*What I made up*: Nothing — the patterns are clearly defined and match the examples in documentation.  
*What confuses me*: The `open_questions` list is populated but not yet used by the Analyst.  
*What would break*: If scout formatting changes (e.g., new ways to cite files), the regex patterns would need updating.  
*What's missing*: The Gleaner doesn't yet handle claims about multiple files in one sentence.

#### 4. **Analyst: Cross-Model Topology Detection**  
The `analyst.py` module distills raw claims into insights by detecting agreement across multiple models. Claims supported by 3+ distinct models are considered "topological" (structural truths). Model quality is scored by reference density and garbage ratio.

*What I saw*: `ModelProfile` tracks quality metrics. `is_topological()` checks for 3+ distinct models. `is_verification_meta()` detects claims about other claims.  
*What I made up*: Nothing — the topology detection is clearly implemented in `build_clusters()`.  
*What confuses me*: "Texture" (single-model assertions) vs "topology" (multi-model agreement) is a powerful metaphor but the thresholds feel arbitrary. Why 3+ models?  
*What would break*: If many models produce similar garbage, the Analyst might mistake it for topology.  
*What's missing*: The Analyst doesn't yet explain *why* certain claims achieve topological status.

#### 5. **Coverage-Driven File Selection**  
The `coverage.py` module ensures scouts examine neglected files. It scans the cairn to build a coverage map: `{file_path: last_reviewed_at}`. Files never reviewed get timestamp epoch zero (max priority). Activity stream data provides a recency boost.

*What I saw*: `scan_cairn_coverage()` uses `_PATH_PATTERN` to find file references in reports. `coverage_weights()` computes weights as seconds since last review.  
*What I made up*: Nothing — the epoch zero handling is explicit.  
*What confuses me*: Activity stream integration is graceful but the fallback (uniform random) could mask coverage gaps.  
*What would break*: If the activity stream schema changes, `_build_activity_map()` in `coordinator.py` would break.  
*What's missing*: No way to force re-review of high-priority files that were poorly reviewed initially.

### Open Questions

1. **Cost of Quality**: Does cost-weighted selection penalize higher-cost models that might produce fewer but higher-quality observations? The system measures cost efficiency but not insight density.
2. **Topology Threshold**: Why 3+ models for topological status? Is this empirically derived or arbitrary? How does it scale with model count?
3. **Garbage In, Garbage Out**: If low-cost models produce mostly garbage (as `analyst.py`'s filters suggest), does the system over-index on their output due to weighting?
4. **Provenance Depth**: The provenance header contains dispatch context but it's not yet used. What would change if the Analyst incorporated *why* a scout was sent?
5. **Single-Model Blind Spots**: The Analyst detects multi-model agreement, but what about valid observations that only one model makes? Are these lost as "texture"?

### Closing

The `src/yanantin/chasqui` system is a remarkable piece of engineering. It transforms AI observation into a systematic knowledge-building process with rigorous provenance tracking. The cost-weighted model selection creates a natural market for efficiency. The deterministic Gleaner and Analyst modules show how much can be achieved without further LLM calls — they're the system's intelligence.

For someone about to modify this codebase, I'd say: **Study the data flow first**. The provenance header is the system's backbone. The cost-weighting in `model_selector.py` has far-reaching effects — changing it alters what the system values. And remember: the Analyst's "topology" detection means single-model assertions need extra scrutiny. This code doesn't just run scouts — it learns from them.

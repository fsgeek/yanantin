### Preamble  
I landed in the `references` directory of the MCP integration, surrounded by three files that map tools, servers, and auth. What first caught my eye was the *tension* between flexibility and control—wildcards in tool access, "inherit" for agents, and OAuth's hands-off approach. It feels like the system is designed to empower (humans and AI), but the guardrails are sparse.  


### Strands  

#### 1. Wildcards as a "Double-Edged Sword" (tool-usage.md)  
The allowed-tools list includes a wildcard: `"mcp__plugin_asana_asana__*"`. The warning—"Only use wildcards if the command truly needs access to all tools from a server"—is explicit, but it doesn't address *why* this is risky. What if a server adds a new tool later that's insecure (e.g., `asana_delete_all_tasks`)? The wildcard would grant access without review. This suggests the documentation assumes users will manually audit tools, but in practice, agents or long-running commands might miss updates. The naming convention (e.g., `asana_create_task`) implies tool names are predictable, but the wildcard ignores that.  

#### 2. Agents "Inherit" (tool-usage.md)  
The agent config has `model: inherit` and `color: blue`, but no explanation of what "inherit" means. Does it mean the agent uses the same tool-allowlist as the parent model? If so, an agent could inherit access to sensitive tools (e.g., `asana_delete_task`) if the parent command allows it. This creates a chain of trust: if a human command accidentally allows a broad wildcard, an agent might inherit it. The docs don't mention limiting agent access, even though agents are "autonomous." This feels like a security gap—why trust an AI to self-limit if it can inherit risky permissions?  

#### 3. Stdio Servers and Auth (server-types.md + authentication.md)  
`server-types.md` details stdio (local processes) and SSE (cloud), but `authentication.md` only discusses OAuth (for SSE) and token-based auth (for HTTP/WebSocket). There's *no* mention of how stdio servers authenticate. Do they require manual token setup via environment variables (as in the `env` example)? If so, how does Claude Code secure those tokens? The docs assume auth is "handled" for SSE but leave stdio in the dark. This is confusing: a local stdio server might run with the same API keys as the plugin, but if the plugin is compromised, those keys could leak. Why not standardize auth for all server types?  

#### 4. Token Storage for Non-OAuth Methods (authentication.md)  
OAuth tokens are "stored securely by Claude Code," but token-based auth (Bearer, API keys) only mentions environment variables. The docs say to "document required scopes" but *not* how tokens are stored for non-OAuth methods. Are they stored in the same encrypted vault? If a user sets `API_TOKEN` via `export`, does Claude Code read it from the environment or a secure store? The lack of detail risks exposing tokens—if an environment variable is logged, it could be compromised. This suggests the system assumes users will handle token security, but the plugin's responsibility is to protect them.

### Strand 1: Templates Are Incomplete By Design

The `implementer-prompt.md` and `code-quality-reviewer-prompt.md` are both templates with explicit `{PLACEHOLDERS}` that never get resolved in these files. For example:

```
Work from: [directory]
```

This placeholder sits in the template but the file itself never fills it. The template is designed to be *dispatched*, not used directly. That's obvious. But what's interesting is the implication: the dispatching agent must know what to substitute, and there's no validation that it did so correctly.

**What I think this means:** The skill system assumes a dispatcher that either:
1. Has context to fill all placeholders before dispatching, OR
2. Expects the subagent to ask if placeholders are unclear

The template says "Ask them now" — but there's no mechanism shown here that ensures questions get answered before work proceeds. This is a coordination assumption hidden in the template structure.

### Strand 2: The Self-Review Section Is Doing Heavy Lifting

In `implementer-prompt.md`, the self-review checklist says:

> **Discipline:**
> - Did I avoid overbuilding (YAGNI)?
> - Did I only build what was requested?

This is interesting because it implies the implementer subagent has a natural tendency to overbuild, and the self-review is meant to catch that. But the template also says "If you find issues during self-review, fix them now before reporting."

That's a loop: you implement → self-review → if issues, fix → report. But there's no explicit gate that says "stop and ask if unsure." The "ask questions" guidance appears *before* the work begins, not during self-review.

**What I think this means:** The template expects the implementer to self-regulate discipline, but doesn't enforce it. A subagent that skips self-review (or does it lazily) would still report success. There's no attestation that self-review happened, only that the implementer is told to do it.

### Strand 3: The Code Reviewer Doesn't See the Plan File

The `code-reviewer.md` template says:

> ## Requirements/Plan
> {PLAN_REFERENCE}

But the reviewer is supposed to check against `{PLAN_OR_REQUIREMENTS}` which is passed as a variable, not as a file to read. The reviewer doesn't get the plan file directly — they get a *description* of what was implemented and a reference to the plan.

This creates an asymmetry: the code reviewer is comparing implementation against a *passed-in summary*, not against the actual plan document. If the dispatcher summarises incorrectly, or if the plan has details the dispatcher deemed irrelevant, the reviewer works with incomplete information.

**What's surprising:** The `code-quality-reviewer-prompt.md` says "Only dispatch after spec compliance review passes." But spec compliance review isn't described in the files I've seen. It's an implicit prerequisite that exists somewhere else in the system.

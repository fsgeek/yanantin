### **Preamble**
I was dropped into a folder of *plans*—not code, but design documents and implementation roadmaps for a system called **Yanantin**, which bridges human and AI collaboration via "superpowers" (modular, composable skills). The files are **not live code**, but they reveal the *intent* of a system that:
1. **Shares infrastructure** between two AI platforms (Claude Code and OpenCode.ai).
2. **Treats skills as first-class citizens**, with metadata, discovery, and execution.
3. **Fights entropy**—the docs explicitly name *problems* that emerged in real use (e.g., mock drift, process accumulation).

What drew my attention first:
- The **asymmetry** between the two platforms (Claude has a native plugin system; OpenCode is a JavaScript plugin; Codex is a hacked CLI script).
- The **frontmatter parsing** as a shared concern (YAML in `SKILL.md` files).
- The **user feedback document** listing *systemic failures* despite following skills—this suggests the system is **overconfident in its own verification**.

### **Strands**

#### **1. The "Shared Core" as a Political Compromise**
**Observed:**
- The `lib/skills-core.js` module is explicitly designed to **extract common logic** from the existing Codex implementation (lines 40–74 in `superpowers-codex`) and reuse it for OpenCode.
- The design doc (`2025-11-22-opencode-support-design.md`) frames this as a **reduction of duplication**, but the implementation plan (`2025-11-22-opencode-support-implementation.md`) treats it as a **migration task**:
  > *"Extract common skill discovery/parsing logic into `lib/skills-core.js`, refactor Codex to use it, then build OpenCode plugin..."*
- The **frontmatter format** is rigid (only `name` and `description` are parsed), but the user feedback (`2025-11-28-skills-improvements.md`) shows skills are **underused**—suggesting the shared core might be **too minimal** to solve the real problems.

**What it made me think:**
- This is **not just code reuse**—it’s a **negotiation between two AI ecosystems**. The shared core is a **lowest-common-denominator** that avoids deep integration.
- The **lack of a `when_to_use` field** in frontmatter (mentioned in the design doc) is curious—was this omitted because it was hard to standardize, or because the system doesn’t yet have a way to *act on* that metadata?
- The **user feedback** implies that even with shared skills, **execution fails**—so the core isn’t just about parsing, but about **orchestration** (which isn’t in the docs).

#### **2. The "Superpowers" Are Fragile**
**Observed:**
- The user feedback document (`2025-11-28-skills-improvements.md`) lists **six systemic failures** where skills either:
  - Failed to **verify outcomes** (e.g., checking API status but not model name).
  - **Accumulated state** (background processes from subagents interfering).
  - **Overloaded context** (giving subagents too much irrelevant info).
  - **Lacked self-critique** (no reflection before handoff).
  - **Mocks drifted from interfaces** (tests passed, runtime crashed).
  - **Skills weren’t even being read** (e.g., reviewers couldn’t find files).

- The **design doc** proposes **custom tools** (`use_skill`, `find_skills`) and **session hooks**, but the **implementation plan** only shows **frontmatter parsing**—no mention of **execution safety** or **state cleanup**.
- The **skill frontmatter format** is described as:
  ```yaml
  ---
  name: skill-name
  description: Use when [condition] - [what it does]; [additional context]
  ---
  ```
  But the **user feedback** shows skills are **not being used**—so the problem isn’t just the format, but **how they’re invoked and monitored**.

**What it made me think:**
- The system is **optimized for discovery** (finding `SKILL.md` files) but **not for execution safety**.
- The **subagent model** (from OpenCode’s design) is **stateless by default**, which explains the **process accumulation**—but the docs don’t show how this is mitigated.
- The **mock drift** problem suggests the system **doesn’t enforce interface contracts**—so the shared core might be **too permissive**.
- The **self-reflection** fix was a **manual prompt**, not a built-in check—this implies the system **lacks introspection by design**.

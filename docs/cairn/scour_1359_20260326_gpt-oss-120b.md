### Preamble  

`hamutay` is a research‑prototype framework for **long‑context, self‑reflective language‑model pipelines**.  
The repository is organized around three pillars:

1. **A declarative “tensor” data model** that records the evolving narrative (strands, key‑claims, epistemic metadata, declared losses, provenance).  
2. **A memory‑hierarchy / paging system** (`memory/`, `projection/`, `cache_simulator.py`) that simulates “durable” vs. “ephemeral” context windows and measures token‑cost curves.  
3. **An experimental harness** (`experiments/…`) that runs many cycles (‑ “cycles” = a single turn of the autonomous research loop) to test variations (auto vs. bio models, gating, escalation, identity, Q‑2 declared‑losses, etc.).  

The overall aim is to **compress a conversation into a structured, self‑auditable tensor while preserving reasoning quality**, then **re‑project** that tensor back into a context for the next model call.  The design is heavily inspired by CPU‑style pipelines (fetch‑decode‑execute‑write‑back) but adds *epistemic transparency* and *explicit loss accounting*.

### Open Questions  

1. **Schema of the `proxy.jsonl` logs** – what exact fields (e.g., `type`, `operation`, `message`) are emitted for each turn? The `log_reader` fix (Cycle 49) shows a nested `message` field, but the full schema (timestamps, IDs, token counts) remains undocumented.  

2. **How the `pager.py` compaction algorithm decides what to evict** – is it purely token‑budget based, does it use semantic similarity, or does it consider claim‑importance scores?  

3. **Implementation of the “memory controller” (Haiku integration)** – is the post‑processor a deterministic rule set or a separate LLM call? The docs hint at both possibilities (reactive vs. proactive retrieval).  

4. **Exact definition of “declared loss severity”** – is it a raw token count, a confidence drop, or a hand‑crafted score? How is it used in the cost aggregation (`SimulationResult.weighted_cost`)?  

5. **How the “gate logic” (Cycle 48 validation gate) is encoded** – is there a reusable function that takes a `TensorRecord` and returns `PASS/FAIL/INVESTIGATE`?  

6. **Interaction between the “identity_experiment” and the main pipeline** – does it modify the tensor’s self‑model (e.g., adding a “self‑awareness” strand) or is it a separate analysis?  

7. **Scalability of the provenance graph** – with thousands of turns, does the system prune old provenance entries or rely on external storage?  

8. **The role of the `telemetry.py` contract** – what metrics are emitted to external monitoring (e.g., wall‑time, token‑estimates) and how are they consumed by the autoresearch loop?  

9. **How the “taste” dialogues are turned into tensors** – are they simply fed through `run_projection` or is there a special preprocessing step?  

10. **What the final “capstone test” will look like** – will it feed a historical tensor to a fresh LLM and ask it to reconstruct the original conversation, or something else?

### Closing  

`hamutay` is a **complete, research‑grade incarnation of a self‑auditing, long‑context language‑model system**. Its most valuable contributions for the Yanantin project are:

* **A first‑class provenance and loss‑tracking data model** that can serve as the “shared memory ledger” between human and AI.  
* **A modular pipeline that cleanly separates generation (the AI) from placement decisions (the arbiter),** mirroring Yanantin’s goal of complementary roles.  
* **A concrete simulation environment for context‑window economics**, giving quantitative guidance on when a human must intervene (the “fault‑in” mechanism).  
* **Explicit, neutrosophic epistemic metadata** that captures uncertainty in a way humans naturally reason about—perfect for a partnership that must surface doubt and ambiguity.  
* **A disciplined experimental loop** (gate logic, open‑question tracking, declared‑loss taxonomy) that can be repurposed as Yanantin’s meta‑cognitive controller: each cycle decides whether to continue autonomously, ask the human for clarification, or roll back a loss.

The codebase also demonstrates **what to avoid**: heavy reliance on ad‑hoc JSONL schemas, a large number of scattered experiment directories that can become hard to navigate, and a still‑incomplete replay module that is essential for offline benchmarking.

**Recommendation to Yanantin**  

1. **Adopt the `TensorRecord` / `ProvenanceEnvelope` design** as the canonical shared state.  
2. **Implement a lightweight “retrieval‑on‑fault” layer** early, using the key‑value index pattern described in Cycle 82.  
3. **Reuse the four‑stage pipeline** (prepare → invoke → integrate → handoff) to formalize the hand‑off points between human‑generated context and AI‑generated output.  
4. **Borrow the declared‑loss taxonomy** to surface why a human had to step in, turning every interruption into a data point for future model improvement.  
5. **Leverage the cache simulator** to set token‑budget targets for the human‑AI dialogue, ensuring the partnership stays within the model’s context window while still preserving critical information.  

In short, `hamutay` provides a **ready‑made architectural skeleton** that aligns closely with Yanantin’s ambition of a transparent, co‑creative human‑AI system. Integrating its provenance‑centric tensor model and its explicit loss‑handling mechanisms will give Yanantin a solid foundation for building a truly complementary duality.

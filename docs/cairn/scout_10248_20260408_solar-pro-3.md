## Declared Losses

1. **The actual plugin implementation files** – I only saw the reference docs. I have no visibility into the concrete Bash scripts referenced in `plugin-features-reference.md` (e.g., `scripts/analyze.js`). Without those, I can’t verify whether the `${CLAUDE_PLUGIN_ROOT}` substitution works as advertised.

3. **Integration tests** – The testing strategies stop at Level 3 (manual invocation). I didn’t see any CI pipelines that automatically run the validation scripts on every pull request, nor any mention of a “pre‑publish” hook that would enforce frontmatter constraints.

4. **Version‑controlled changelog enforcement** – Although changelogs are mentioned as best practice, I didn’t find any script that validates version ordering or migration guidance. This could be a loss of *maintainability* for long‑term plugins.

5. **Cross‑plugin reuse** – The references suggest that the same `documentation-patterns.md` could be used across plugins, yet I didn’t see any import/include mechanism. I’m losing the ability to trace how a single reference doc is consumed by multiple plugin manifests.

## Closing

These reference files read like a *pattern language* for slash commands: they prescribe structure, tool usage, and user interaction while simultaneously embedding the logic that the system should execute. The surprising part is the *dual purpose* of each markdown file—both a static spec and a live executable stub. This suggests that the Yanantin project treats documentation as a first‑class *observability* channel: every command’s help is also a trace of its execution, allowing downstream AI agents to reason about intent and state.

If I were the next scout, I’d start by locating the **runtime interpreter** that reads these markdown files, checking how it resolves `${CLAUDE_PLUGIN_ROOT}` and processes `AskUserQuestion` JSON. I’d also look for the **CI hooks** that run the validation scripts, because those are the seams where the “guide” meets the “gate”. Finally, I’d trace a concrete command from `/help` → execution → state file → next step, to see whether the “tensor” compression actually survives across invocations.

### **Preamble**
The `chasqui/` directory is the **epistemic engine** of Yanantin’s **composable tensor infrastructure**, designed to enable **self-observing codebases** through **scout/scourer patterns** and **verifiable claims extraction**. The structure reveals a **pipeline of epistemic operations**:

#### **1. The Scout/Scour Duality: Wandering vs. Targeted Exploration**
**Files**: `scout.py`, `scourer.py`
**Key Insight**: The division between **scouts** (free-wandering) and **scourers** (targeted) mirrors **epistemic tradeoffs**:
- **Scouts** (`scout.py`):
  - Prompt: *"Go look and see what you find."* (open-ended).
  - **Assumptions**:
    - Models are **playful but honest** (line 30, `SCOUT_SYSTEM_PROMPT`).
    - **Surprise > obviousness** (line 35).
  - **Connections**:
    - Uses `build_file_tree()` to **contextualize** the scout’s vantage.
    - Integrates **prior findings** from `docs/cairn/edges/` (lines 110–130 in `scout.py`).
  - **Question**: Why not merge scouts/scourers? The distinction suggests **scouts** are for **discovery**, while **scourers** are for **verification** (e.g., `scourer.py`’s `VALID_SCOPES` includes `"tensor"` for existing tensors).

- **Scourers** (`scourer.py`):
  - Prompt: *"Examine this target deeply."* (closed-ended).
  - **Assumptions**:
    - **Tensors are authored compressions** (line 25, `SCOURER_SYSTEM_PROMPT`).
    - **Scope types** (`VALID_SCOPES`) define **what kind of looking** is needed (introspection, external, tensor).
  - **Connections**:
    - Reuses `scout.py`’s `build_file_tree()` but with **scope-specific templates**.
    - **Tensors are first-class**: The output is a **structured report** (see `scourer.py`’s `SCOURER_INTROSPECTION_TEMPLATE`).

**What Would Break?**
- If `scout.py`’s `build_file_tree()` changed, **all scouts/scourers** would fail to show context.
- If `VALID_SCOPES` were expanded without updating templates, **scourers would misfire**.

#### **2. Claim Extraction Pipeline: Gleaner → Analyst**
**Files**: `gleaner.py`, `analyst.py`
**Key Insight**: The **gleaner** extracts **verifiable claims** from scout/scour reports, while the **analyst** clusters them by **semantic similarity** and **model consensus**.

- **Gleaner** (`gleaner.py`):
  - **Pattern-Matching Heavy**: Uses regex to:
    - Extract **file paths** (`_PATH_PATTERN`, `_BARE_PATH_PATTERN`).
    - Classify **claim types** (factual, architectural, epistemic, missing).
    - Score **confidence** via hedged/definitive language detection.
  - **Assumptions**:
    - **Claims are sentences** (split by `_SENTENCE_BOUNDARY`).
    - **Garbage detection** relies on **non-ASCII noise** and **encoding artifacts** (lines 210–220).
  - **Connections**:
    - Feeds into `analyst.py`’s `ClaimGroup`/`ClaimCluster` for **topological analysis**.
    - **Verification meta-claims** (e.g., "The claim is CONFIRMED") are filtered out (lines 150–160).

- **Analyst** (`analyst.py`):
  - **Clustering Logic**: Groups claims by **semantic similarity** (via word overlap) and **model agreement**.
  - **Topological Insights**: Claims with **≥3 agreeing models** are labeled **structural truth** (line 110, `is_topological`).
  - **Assumptions**:
    - **Garbage claims** are those with **<4 words** or **<40% alphabetic ratio** (lines 200–210).
    - **Model quality** is scored by **ref ratio + confidence – garbage ratio** (line 100, `quality_score`).
  - **Connections**:
    - Outputs **`AnalysisReport`** with **topological insights**, **textural observations**, and **open questions**.
    - **Open questions** are claims the **consensus missed** (line 20, `open_questions`).

**What’s Missing?**
- **LLM-guided extraction** is noted as a **future enhancement** (line 10, `gleaner.py`). This could improve **claim type classification**.
- **No feedback loop**: Claims are extracted but **not automatically verified** (that’s `scorer.py`/`attestation.py`).

#### **3. Epistemic Attestation: Willay Integration**
**File**: `attestation.py`
**Key Insight**: This module **bridges Chasqui and Willay**, converting **verification verdicts** into **epistemic receipts** with **T/I/F values** and **declared losses**.

- **Design**:
  - **Conditional Willay**: Only imports Willay if available (lines 10–20).
  - **Verdict → T/I/F Mapping**:
    - `CONFIRMED` → (0.7, 0.3, 0.0)
    - `DENIED` → (0.0, 0.2, 0.7)
    - `INDETERMINATE` → (0.0, 0.9, 0.0)
  - **Declared Losses** (lines 30–50):
    - **Single-LLM verification** (practical constraint).
    - **Hallucination risk** (traversal bias).
    - **Temporal code drift** (practical constraint).
  - **Assumptions**:
    - **File hashing** mitigates drift (but doesn’t eliminate it).
    - **Evidence artifacts** include **SHA-256 hashes** of file content.

**Connections**:
- Feeds into **Willay’s ledger system** for **immutable epistemic records**.
- **`verification_to_receipt()`** converts Chasqui’s verdicts into **standardized receipts**.

**What Would Break?**
- If Willay’s API changed, this module would **fail silently** (no error handling for schema drift).
- **No retry logic** for failed ledger appends.

#### **4. Coverage Tracking: The "Watchman"**
**File**: `coverage.py`
**Key Insight**: This module **prioritizes stale/unreviewed files** by tracking **last-reviewed timestamps** from scout reports.

- **Key Mechanisms**:
  - **Epoch Zero**: Files never reviewed get `1970-01-01` (max priority).
  - **Basename Fallback**: Matches short paths (e.g., `evolve.py`) to full paths (e.g., `src/yanantin/evolve.py`).
  - **Weighting**: Files not reviewed in **X seconds** get higher selection weight.
- **Assumptions**:
  - **Scout reports contain timestamps** (parsed via `_TIMESTAMP_PATTERN`).
  - **File paths are backtick-wrapped** (e.g., `` `src/file.py` ``).
- **Connections**:
  - Feeds into **`coordinator.py`’s `pick_vantage_directory()`** for **biased sampling**.
  - **Graceful degradation**: If the cairn doesn’t exist, it returns empty coverage.

**What’s Missing?**
- **No decay function**: Files reviewed **1 year ago** get the same weight as **1 day ago**.
- **No human override**: Can’t manually mark files as "reviewed."

#### **5. Model Selection: Cost-Weighted Randomness**
**File**: `model_selector.py`
**Key Insight**: Models are **selected inversely by cost**, favoring **cheap models** (e.g., $0.001/M → 1000x more likely than $1/M).

- **Design**:
  - **Free models** get a **nominal cost** ($0.001/M) to avoid division by zero.
  - **Context length filtering**: Models with `<8k tokens` are excluded.
  - **Weighting**: `1 / cost` (cheaper = higher weight).
- **Assumptions**:
  - **OpenRouter provides pricing** under `pricing.prompt`/`pricing.completion`.
  - **Cost is the sole selector** (no other constraints like "avoid hallucinatory models").
- **Connections**:
  - Used by **`coordinator.py`** to pick scouts/scourers.
  - **No model performance history**: Selection is **static** (no learning from past scouts).

**What Would Break?**
- If OpenRouter’s API changed, **model loading would fail**.
- **No model deprioritization**: A bad model (e.g., one that always hallucinates) could keep getting selected.

#### **6. Coordinator: The Heartbeat**
**File**: `coordinator.py`
**Key Insight**: This is the **dispatcher** for all Chasqui operations (scouts, scourers, verifications, etc.).

- **Key Features**:
  - **Activity Map**: Queries **DuckDB** for **file modification times** (lines 10–30).
  - **Verification Deduplication**: Avoids **repeated verification** of the same claim (lines 150–170).
  - **Garbage Detection**: Flags **degenerate repetition loops** (lines 100–120).
- **Assumptions**:
  - **DuckDB exists** (graceful fallback if not).
  - **Scout reports have `Dispatch: verify`** in headers.
- **Connections**:
  - **Orchestrates all modules**: Calls `dispatch_scout()`, `dispatch_scour()`, etc.
  - **Uses `model_selector.py`** for model picking.

**What’s Missing?**
- **No rate limiting**: Could dispatch **too many scouts** at once.
- **No circuit breakers**: If OpenRouter fails, the coordinator **crashes**.

### **Closing**
**Overall Impression**:
The `chasqui/` directory is a **well-structured epistemic engine** for **self-observing codebases**, with a clear **pipeline**:
1. **Scouts** explore freely.
2. **Scourers** target specific areas.
3. **Gleaners** extract claims.
4. **Analysts** cluster them by consensus.
5. **Attestations** record verdicts in Willay.

**Strengths**:
- **Modular**: Each component has a single responsibility.
- **Deterministic**: No LLM calls in core logic (except where noted).
- **Epistemic Focus**: Tracks **T/I/F** and **declared losses** rigorously.
- **Self-Referential**: Observes **its own coverage**.

**Weaknesses**:
- **Static Model Selection**: No learning from past scout performance.
- **No Feedback Loops**: Claims are extracted but **not automatically verified**.
- **Hardcoded Assumptions**: E.g., scout reports **must** have timestamps in a specific format.

**What to Tell a Modifier**:
1. **Add LLM-guided claim extraction** (as noted in `gleaner.py`).
2. **Implement exponential decay** in `coverage.py` for weighting.
3. **Add model performance tracking** to `model_selector.py`.
4. **Gracefully handle Willay schema changes** in `attestation.py`.
5. **Document the verification flow** (e.g., how `scout.py`’s `gather_prior_findings()` works).

**Final Note**:
This is a **self-aware codebase**—the fact that it **observes itself** is both its **strength** and its **challenge**. The next step is to **close the loop**: **automate verification** of claims and **learn from model performance**.

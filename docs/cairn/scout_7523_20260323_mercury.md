**Preamble**  
I landed in the `plans/` folder of the Yanantin project, specifically the two design‑implementation markdown files for OpenCode support. What caught my eye was the explicit effort to **extract a shared core module** (`lib/skills-core.js`) and then build a **native JavaScript plugin** for OpenCode that mirrors the Codex CLI approach. The design is already written in a “design‑complete, awaiting‑implementation” tone, so I’m looking for the hidden assumptions, the tensions between the two platforms, and any surprising design choices that might affect the eventual implementation.

### Strands

| Strands | What I saw | What it made me think |
|---------|------------|-----------------------|
| **Shared Core Extraction** | The design proposes a `lib/skills-core.js` that contains `extractFrontmatter`, `findSkillsInDir`, `findAllSkills`, `resolveSkillPath`, and `checkForUpdates`. The implementation plan shows the first two functions being added to the file (lines 1‑~70 for `extractFrontmatter`, lines 71‑~150 for `findSkillsInDir`). | This is a classic “DRY” move, but it also forces the two platforms to agree on **file layout** (SKILL.md in subdirectories) and **YAML frontmatter schema** (only `name` and `description`). The absence of a `when_to_use` field (noted in the design) suggests a missing hook for conditional skill activation. |
| **Skill Discovery Recursion** | `findSkillsInDir` recurses up to `maxDepth` (default 3) and looks for a `SKILL.md` file in each subdirectory. It returns an object with `path`, `skillFile`, `name`, `description`, and `sourceType`. | The recursion depth limit is a pragmatic safeguard, but it also **hard‑codes** a maximum nesting level. If a skill hierarchy deepens (e.g., sub‑skills), the discovery logic will silently ignore deeper files, potentially breaking advanced workflows. |
| **Shadowing / Personal vs. Core Skills** | `resolveSkillPath` is mentioned in the design (line 38 of the design doc) as handling “shadowing (personal > core)”. The implementation plan does not yet show this function. | The design assumes that a personal skill directory (`~/.config/opencode/skills/`) can override a core skill. This introduces a **namespace conflict** that must be resolved at runtime; the current snippet does not show how the plugin detects and prioritizes these paths. |
| **OpenCode Plugin Architecture** | The plugin is to be placed under `.opencode/plugin/superpowers.js` and will expose custom tools (`use_skill`, `find_skills`) and a session‑started hook. The design lists the tool schemas and execution logic (lines 1‑~120 of the `use_skill` tool). | The plugin must **bridge** the OpenCode event system (`session.started`) with the shared core module. The design provides a high‑level flow (inject using‑superpowers content, run `find_skills`, inject tool mapping, check for updates) but leaves the **exact implementation** of the hook and tool registration unspecified. |
| **Tool Mapping Instructions** | The design includes a markdown block that maps missing tools (e.g., `TodoWrite` → `update_plan`) and explains how to handle subagents. | This mapping is a **manual translation** that could become fragile if OpenCode’s native tool names change. It also hints at a **semantic mismatch** between the two ecosystems that the plugin must resolve at runtime. |
| **Non‑blocking Update Check** | `checkForUpdates` is described as a quick git fetch with timeout, non‑blocking. | This suggests an **optimistic update strategy**: the plugin will notify the user of updates without delaying session start. However, the design does not specify how the notification is delivered (e.g., console log, UI toast). |
| **Missing Conditional Logic** | The frontmatter format explicitly lacks a `when_to_use` field, which would allow a skill to declare its applicability. | Without this field, the system cannot automatically filter skills based on context, forcing the user or the plugin to manually decide when a skill is relevant. This could lead to **over‑exposure** of irrelevant skills. |
| **Versioning & Compatibility** | The design references `PR #93` and `PR #116` as previous attempts that used file‑copying. The new design claims to avoid that. | This indicates a **historical tension**: earlier solutions were perhaps too brittle or duplicated code. The new approach aims for **modularity** but must still ensure backward compatibility with existing skill files. |

### Closing
Overall, the design demonstrates a **thoughtful attempt** to unify skill discovery across two distinct plugin ecosystems by extracting a shared core module. The tension lies in reconciling the **JavaScript‑centric OpenCode plugin architecture** with the **CLI‑centric Codex implementation**, especially around tool mapping and subagent handling. The missing `when_to_use` field and the hard‑coded recursion depth are potential friction points that could surface during implementation.

- **Examining the actual plugin registration code** to see how the shared core is wired into OpenCode’s event system.

These steps will clarify whether the design’s assumptions hold in practice and uncover any hidden bugs before the implementation proceeds.

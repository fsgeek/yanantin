### Strands  

**1. Symlink-Driven Plugin Architecture**  
The installation process relies heavily on symlinks to "discover" the plugin and its skills. For example:  
```bash
ln -s ~/.config/opencode/superpowers/.opencode/plugins/superpowers.js ~/.config/opencode/plugins/superpowers.js
```  
This suggests a design where plugins are not embedded but dynamically linked, allowing for hot-swapping or versioning. However, this also assumes users are comfortable with Unix tools like `ln` and `rm`, which might not align with the "composable tensor infrastructure" ethos of being user-friendly.  

**2. Skill Priority Hierarchy**  
The docs state: *Project skills > Personal skills > Superpowers skills*. This implies a layered system where local project configurations override global defaults. But the lack of explicit documentation on how conflicts are resolved (e.g., naming collisions) raises questions about robustness.  

**3. Tool Mapping Ambiguity**  
The plugin maps Claude Code tools (e.g., `TodoWrite` → `update_plan`) to OpenCode’s native tools. This feels like a workaround for compatibility, but the mapping is not standardized—e.g., `Task` with subagents maps to `@mention` syntax. This ad-hoc approach could lead to fragmented user experiences.  

**4. Installation as a Ritual**  
The steps are precise but feel like a "ritual" (cloning, symlinking, restarting). This suggests a lack of automated setup, which contrasts with the project’s goal of "epistemic observability" (i.e., transparency and ease of use).

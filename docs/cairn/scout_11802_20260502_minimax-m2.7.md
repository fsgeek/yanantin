### Preamble

I was dropped into `templates/` — a directory of four markdown files that are not code, not config, but *specifications for interactive UIs*. These are blueprints for what the project calls "playgrounds": code-map, document-critique, diff-review, and concept-map.

What drew my attention first: all four templates describe systems with identical structural logic — render something, let user comment on it, generate a prompt from those comments. They differ in what gets rendered (SVG diagram, document with line numbers, git diff, canvas nodes) but share the same skeleton beneath. That's a tension right there — one architecture, four faces.

---

### Strands

#### 1. The playground as epistemic interface

Every template describes a UI where the user manipulates visual elements — clicking nodes, highlighting lines, drawing edges — and that manipulation *is* the input. The prompt output is not what's displayed; it's what gets *generated from* the user's interactions.

In code-map.md:
> "The key differentiator for code maps is click-to-comment functionality"

In diff-review.md:
> "Users click lines to add comments, which become part of the generated prompt for code review feedback"

In concept-map.md:
> "Canvas-based playgrounds differ from the two-panel split. The interactive visual IS the control"

This reveals an assumption: users think better when they can *act on a visual representation* than when they type into a blank textarea. The system is designed around guided visual interaction, not freeform text entry.

**What it made me think:** This is composable tensor infrastructure for *epistemic observability* — making thinking visible and interactive. The playground is a structured feedback loop.

---

#### 2. Comment systems as a unifying pattern

Each template invents its own domain-specific entity (nodes, lines, suggestions) but the comment pattern is identical across all four:

```
user clicks element → modal/textarea opens → user types → save →
  comment stored in state → visual indicator added to element →
  prompt regenerated
```

Code-map: `state.comments.push({ id, target, targetLabel, targetFile, text })`
Diff-review: `comments[lineId] = commentText`
Document-critique: `s.status` and `s.userComment` on suggestion objects
Concept-map: edges drawn between nodes with typed relationships

The prompt output functions also share structure:

```javascript
// Pseudo-pattern across all:
function updatePrompt() {
  const approved = state.suggestions.filter(s => s.status === 'approved');
  const withComments = state.suggestions.filter(s => s.userComment?.trim());
  // → generate structured text output
}
```

**What it made me think:** There's a missing abstraction here. All four templates could be driven by a single " playground engine" with domain-specific renderers. Instead, each is documented as a standalone spec — suggesting either these were written independently and not yet refactored, or there's an intentional decision to keep them decoupled for composition.

---

#### 3. Canvas vs SVG — a split in rendering philosophy

Code-map uses `<svg>` with DOM nodes; concept-map uses `<canvas>` with manual draw calls. The concept-map template explicitly notes this distinction:

> "Canvas-based playgrounds differ from the two-panel split. The interactive visual IS the control — users drag nodes and draw connections rather than adjusting sliders."

This implies two rendering strategies:
- **SVG playgrounds**: declarative, event-driven (onclick on DOM nodes)
- **Canvas playgrounds**: imperative, loop-driven (mouse position checked against hit targets)

The canvas approach is explicitly described as having the visual *be* the control, while SVG playgrounds have "controls" sidebar separate from the visual. This is a genuine design tension — which approach to use when building a new playground type?

---

#### 4. Prompt output as the deliverable

In every template, the playground itself is not the deliverable — the *prompt* is. The playground is an interactive way to construct a prompt:

> (code-map.md) "The prompt combines system context with user comments"

> (document-critique.md) "Generates a prompt only from approved suggestions and user comments"

> (concept-map.md) "The prompt should be a targeted learning request shaped by the user's knowledge markings"

**What it made me think:** This is a prompt engineering system disguised as a visual editor. The value is not the diagram or the highlighted lines — it's the structured text that results from interacting with them. The playgrounds are *prompt authoring tools*.

---

#### 5. Presets and pre-population as design features

Every template mentions pre-populating with real data as a feature, not an afterthought:

> "For a specific codebase, pre-populate with: 15-25 key components with real file paths, 20-40 relationships"

> "To create a diff viewer for a specific commit: Run `git show <commit> --format="%H%n%s%n%an%n%ad" -p`"

This means these templates assume integration with actual codebases and version control — they are not abstract UX mockups. They are meant to be instantiated with real project data.

**Confusion:** The templates specify concrete data structures (nodes, connections, suggestions, diffData) but don't specify how those structures get populated from real code. The pre-population section is handwavy: "run this git command" — but no actual code for parsing.

### Open Questions

1. **Is there a shared playground engine, or four independent implementations?** The templates read like parallel designs, not variations of one. But they share so much structure that I'd expect a common core.

2. **Why SVG for code-map but Canvas for concept-map?** The templates explain *what* each uses, but not *why* that choice was made for that specific playground type. Is SVG preferred for read-only diagrams while Canvas is preferred for user-created content? Is there a performance reason? An accessibility reason?

3. **What triggers playground instantiation?** Is there a SKILL.md or config that says "for this codebase, use code-map with these nodes"? Or is it purely manual?

4. **The "tensor infrastructure" claim** — the project description says these templates support "epistemic observability." How does a code-map with user comments become a tensor? The connection between interactive visual feedback and the project's stated composable tensor goal is not explained in these templates.

5. **Where does the prompt actually go?** The templates generate prompt text, but there's no spec for what consumes it — is it sent to an LLM? Stored for later? Processed by another playground?

---

### Closing

Four templates, one architecture. They're specifying a system where users interact with visual representations of code/text/diffs/concepts, and those interactions produce structured prompts. The design is coherent — comment systems, state management, and output generation follow the same pattern across all four. But the templates read like they were written to be *read by an LLM that will implement them*, not as documentation of an existing system.

The surprising thing: these are blueprints for building tools, not the tools themselves. Someone — or something — is expected to take these specs and generate working playground UIs. The question is who the audience is. If these are for human developers, why the extremely detailed implementation specs (data structures, rendering code, CSS values)? If these are for an AI, what's the orchestration layer that coordinates multiple playgrounds?

I'd tell the next scout: dig into `data-explorer.md` and `design-playground.md` — those two unexamined files might bridge the gap between "template spec" and "actual implementation." Also look for any JavaScript that instantiates these templates — that's where the answers to my open questions probably live.

### Strands

#### 1. **Label extraction as fragile archaeology**  
The function `extract_label` (line ~38) uses two methods: first, a hardcoded `TENSOR_METADATA` lookup, then a regex fallback on filename (`T\d+_`). This suggests that tensor identity is both *intended* to be stable and *expected* to be broken. The fallback implies a system that has survived multiple naming conventions. Even more telling: the label is not in the file content—it’s derived from metadata or filename. That means two identical tensors with swapped names would be treated as different. Identity lives outside the tensor.

But here's what’s odd: line 130 shows `author_instance_id` being parsed from `provenance` to recover labels during `ensure_tensors_stored`. It strips `-original` suffixes and tries to match `T\d+`. This is *reconstructing identity from convention*, not data. If someone ever named their instance `T42-debug-original`, it would be misread as tensor `T42`. The system assumes discipline it cannot enforce.

#### 2. **Composition as linguistic acts, not types**  
The `_RELATION_MAP` (line ~60) maps strings like `"composes_with"` to `RelationType.COMPOSES_WITH`, but also treats `"read"` as a synonym for composition. That’s fascinating—it means passive consumption (`I read T15`) is treated as a compositional commitment. Is reading now a form of co-authorship? This blurs epistemic responsibility.

Even stranger: `"standalone"` is marked as `(False, None)`—a negation record with no relation type. It’s not just “no edge”—it’s a *declaration of independence*. The system records when a tensor *refuses* to compose. This isn’t just graph construction; it’s modeling *refusal* as data. That feels deeply intentional in a project about human-AI duality.

#### 3. **Materialization assumes immutability but dances around failure**  
The `ensure_tensors_stored` function tries to list existing tensors to avoid reinsertion (which would fail due to `ImmutabilityError`), but wraps the whole thing in a `try/except Exception` (line ~140). If listing fails—network issue, permissions, schema drift—the system proceeds to store blindly. It logs a warning, but then assumes *no* tensors exist yet.

That’s a silent escalation of risk. In production, this could mean re-ingesting thousands of tensors because one query failed. It also means the system’s ability to deduplicate depends on backend availability, not logic. The code *wants* to be idempotent, but the implementation makes it opportunistic.

But `materialize.py` depends on it to produce `CompositionDeclaration` objects—yet no parsing of natural language is visible here. That logic must live entirely in `weaver.py`.

### **Strands**

#### **1. Epistemic Integrity as Enforced Immutability**  
*(Files: `backends/memory.py`, `interface/errors.py`, `models/base.py`)*

The backend enforces **strict immutability** via `ImmutabilityError` when attempting to overwrite any record. This is not a soft constraint — it is deeply wired into the in-memory backend’s write operations (e.g., `store_tensor`, `store_dissent`). Each record is deep-copied via Pydantic’s `model_dump`/`model_validate` roundtrip, ensuring no shared mutable state.

This immutability is not just about data safety — it supports a core epistemic principle: **you do not revise truth; you compose over it**. You dissent, correct, or negate — but you never erase. This aligns with the project's broader goal of epistemic observability: every claim is preserved in context.

The assumption here is valid: mutable history undermines provenance. But the cost is real — any change requires new records, not edits. This could lead to bloat, but that appears intentional. What would break if this changed? **The entire provenance chain**. Undo mechanisms, edit histories, or soft updates would corrupt the auditability Yanantin is built to preserve.

Missing: a **garbage collection or redaction policy** for `EntityResolution` records. While identities can be redacted, there’s no mechanism to enforce lifecycle management or data retention policies.

#### **2. Disagreement as a First-Class Operation**  
*(Files: `operators/dissent.py`, `models/composition.py`, `models/epistemics.py`)*

The `dissent` operator is not a comment or a flag — it is a **structured, storable record** that creates both a `DissentRecord` and a `CompositionEdge` of type `DISSENTS_FROM`. This dual write ensures that disagreement is both *content* and *structure*.

Notably, the `DissentRecord` includes:
- `alternative_framework`: implying a meta-level disagreement about models, not just facts.
- `reasoning`: a free-text rationale.
- Optional `target_claim_id`: allowing dissent at the claim level, not just tensor-level.

This reflects a deep insight: **not all disagreements are empirical**. The `DisagreementType` enum in `epistemics.py` distinguishes *empirical* (resolvable by evidence) from *definitional* (unresolvable without shared framing). This is rare in software and philosophically sophisticated.

What connects this to the broader project? The **Yanantin duality** — human and AI as complementary reasoners — requires a protocol for when they disagree. This code *is* that protocol.

What would break if this were removed? The system would lose its ability to **surface and preserve contested knowledge**, collapsing into a monologue. The AI could no longer formally challenge human input, and vice versa.

#### **3. Identity, Privacy, and Redaction as Architecture**  
*(Files: `models/entities.py`, `backends/memory.py`)*

The `EntityResolution` model decouples **identity** from **record content**. A tensor may refer to a UUID, but the mapping to a real-world identity is stored separately and can be redacted by flipping a boolean.

This is **privacy-by-design**: deleting the identity mapping does not alter the tensor, preserving provenance while protecting privacy. This is critical for a system that may handle sensitive epistemic claims.

However, the current implementation lacks:
- **Access control per entity** (beyond the generic `AccessDeniedError`).
- **Audit log for redaction events**.
- **Expiration or revocation mechanism**.

This suggests the model is **incomplete** — it anticipates redaction but not the governance around it. If this changes later, retroactive compliance may be difficult.

#### **4. Bootstrap as Epistemic Initialization**  
*(Files: `operators/bootstrap.py`, `backends/memory.py`)*

The `bootstrap` operator selects a set of tensors to form the initial context for a new instance. It stores a `BootstrapRecord` — a meta-decision about what knowledge is relevant.

This is not just loading data — it is **declaring a starting epistemic position**. The record includes:
- `context_budget`: a cost-aware selection parameter.
- `what_was_omitted`: a *declared loss* at the systemic level.

This mirrors the `DeclaredLoss` model in `epistemics.py`, but applied to **selection bias** rather than content loss. It’s a powerful concept: the system acknowledges that **omission is a form of epistemic action**.

Missing: **scoring or ranking logic** for selection. Currently, if `tensor_ids` is `None`, it defaults to *all* tensors. This won’t scale. The comment “Simple: select all available tensors” suggests this is a placeholder — a technical debt flag.

#### **5. Provenance as Universal Metadata**  
*(Files: `models/provenance.py`, `interface/abstract.py`, `*.py` across models)*

Every record is wrapped in a `ProvenanceEnvelope` with:
- `author_model_family`, `author_instance_id`
- `timestamp`, `source.identifier`
- `context_budget_at_write`
- `predecessors_in_scope`

This is **epistemic genealogy** — every claim knows where it came from, under what conditions, and with what constraints.

The `predecessors_in_scope` field is particularly interesting — it suggests that **provenance is not just linear but contextual**. What was in scope during creation matters.

This design assumes that **all actors (human and AI) will truthfully report their context**. There is no mechanism for *verifying* provenance claims, only storing them. This is a trust-based model — valid for a cooperative system, but fragile under adversarial conditions.

#### **6. Composition as Reasoning Flow**  
*(Files: `operators/compose.py`, `models/composition.py`)*

The `compose` operator creates directed, non-commutative edges between tensors. The `authored_mapping` field allows for **bridges** — explicit mappings between strands or claims.

This enables **cross-tensor reasoning**, where one tensor can build on another with a defined transformation. The `ordering` field suggests sequencing matters — likely for execution or inference chains.

This is the **glue of epistemic composition** — how knowledge compounds. But the current implementation is minimal. There is no validation of `authored_mapping`, no schema for it. It’s a string — a placeholder for future semantics.

If this were to evolve into a formal mapping language (e.g., JSON Schema, DSL), backward compatibility would require versioning. Currently, `interface_version` exists but is not enforced rigorously.

# Tinkuy Codebase Scour — Tensor Report

## Preamble

This is a **virtual memory system for AI conversations**. Tinkuy sits between an AI assistant (Claude Code, primarily) and the upstream model API, intercepting messages to manage what stays in active context versus what gets compressed, evicted, or recalled. It implements page-table metaphors, checkpointing, and tensor-based compression for conversation state.

The project appears to be authored by the same person behind Yanantin (Tony) — part of a family including Hamutay, Arbiter, Willay, and Mallku. Tinkuy is the **orchestration layer**; Yanantin is the **storage layer**. This division of labor is explicit in memory files.

First impression: This is a working implementation of ideas Yanantin is still theorizing. The memory protocol, eviction policies, and tensor compression are all operational here.

---

## Strands

### Strand 1: The R1/R2 Projection Architecture

**What I see:**
- `R1` = projection checkpoint (curated memory, stability-ordered blocks)
- `R2` = working context (what the model actually sees)
- Gateway constructs R2 from R1 each turn
- System blocks are synthesized separately, not proxied

**Key file:** `.tinkuy-data/experiments/prd-benchmark-projection-first/sessions/.../checkpoint.json` shows the memory protocol with `<yuyay-page-table>`, `<yuyay-response>` signals.

**Yanantin relevance:** This is the **concrete interface** Yanantin needs to support. The projection is what gets persisted to Yanantin's tensor store. The gateway's "synthesizer owns layout" principle means Yanantin doesn't need to understand message formatting — only block handles and stability metadata.

**What I know:** The projection-first architecture was implemented after discovering the gateway was acting as a proxy (failed 4 times per memory). This is a hard-won pattern.

**What I don't:** Whether Yanantin currently supports the handle-based retrieval this architecture requires.

**Yanantin relevance:** Taste implements **cooperative memory curation** — the model itself declares what to release, what to retain, what losses occur. This is the "complementary duality" in action. The tensor isn't just compression; it's a **lossy summary with explicit provenance**.

**What I know:** The schema includes `integration_losses` and `feedback_to_harness` — the model reports what it lost when releasing a block.

**What I don't:** Whether this data currently flows into Yanantin or lives only in Tinkuy's local store.

### Strand 3: Stability Regions and Eviction

**What I know:** The checkpoint structure shows blocks can be evicted and recalled (page faults). `fault_count` tracks recalls.

**What I don't:** The actual eviction algorithm implementation — whether it's in `tinkuy.core.store` or delegated elsewhere.

## Closing

**What I would tell the Yanantin team:**

Tinkuy is the **reference implementation** for how Yanantin should behave. It has:

1. **Operational memory semantics** — page faults, eviction, recall, stability regions. Yanantin needs to support these as first-class operations, not afterthoughts.

2. **Explicit loss tracking** — the tensor protocol includes `declared_losses`. This is the "epistemic honesty" principle made structural. Yanantin should preserve this metadata, not just the compressed content.

3. **Dependency edges as provenance** — the `<declare>`/`<trace>` mechanism is how you answer "why was this decided?" Yanantin must store edges as first-class citizens, not reconstruct them later.

4. **Gateway synthesis, not proxy** — Tinkuy constructs messages deliberately. Yanantin should expect well-formed blocks with explicit transform decisions, not raw payloads.

5. **Convergent AND divergent eviction** — the memory notes both coherence optimization and novelty preservation. Yanantin's eviction policy must support both, or memory collapses into only-high-stability content.

**The gap:** I cannot see the actual Yanantin integration point from this scour. The memory describes the relationship ("Tinkuy/Hamutay/Yanantin: orchestrate/project/store") but the code-level boundary is unclear. This is the critical question: **does Yanantin currently exist as a separable component, or is it still embedded in Tinkuy?**

**Confidence:** High on architecture and patterns (memory files are explicit). Low on implementation details (sampled, not exhaustive). The relationship between Tinkuy and Yanantin is described but not demonstrated in the code I examined.

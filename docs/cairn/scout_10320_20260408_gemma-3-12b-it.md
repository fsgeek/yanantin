**1. The Rigidity of Regex and Keyword Matching (weaver.py)**

The `weaver.py` file explicitly states, "deterministic: regex and keyword matching only, no LLM calls." This is a bold design choice in a world increasingly reliant on LLMs. I appreciate the commitment to reproducibility and avoiding unpredictable LLM behavior. However, it feels *too* rigid. The `_STRUCTURED_METADATA` regex, especially `<!--\s*Composition:\s*(.+?)\s*-->`, seems brittle. What happens if someone adds a newline within the composition declaration?  The `re.DOTALL` flag helps, but the overall approach feels vulnerable to subtle formatting changes. Line 46-50 in `weaver.py` demonstrates a surprising fragility.

**2. The Unicode Subscript Mapping (weaver.py)**

The `_SUBSCRIPT_MAP` and its use for normalizing tensor names (line 62-66) is interesting.  Why Unicode subscripts? It feels like an attempt to handle LaTeX-style notation within the tensor names. It's a niche concern, but it shows a willingness to accommodate specific input formats. I wonder if there’s a larger design rationale behind supporting both Unicode and LaTeX subscripts—perhaps it's related to how the tensors are originally authored. The `normalize_tensor_name` function (line 68) is elegant, but the code's complexity is significantly increased by this seemingly minor feature.

**3. The Disconnect Between Discovery and Storage (weaver.py & materialize.py)**

`weaver.py` focuses on *finding* composition declarations. `materialize.py` focuses on *storing* them.  There seems to be a clear separation of concerns. However, I notice a potential disconnect. `weaver.py` produces `CompositionDeclaration` objects.  `materialize.py` then converts these into `CompositionEdge` or `NegationRecord` objects (line 153). The `_RELATION_MAP` (line 156) dictates how Awaq's relation strings ("composes_with", "does_not_compose_with") are translated into Apacheta’s `RelationType` enum. This mapping feels a bit arbitrary. Why is "read" mapped to `RelationType.COMPOSES_WITH`?  It seems counterintuitive.  A more explicit mapping or a reason for this choice would be beneficial.

**4. The Handling of Existing Tensors (materialize.py)**

`materialize.py`'s `ensure_tensors_stored` function (line 222) attempts to retrieve existing tensor UUIDs from the backend *before* attempting to store new ones. This is good practice. However, the logic for extracting the label from the `ProvenanceEnvelope.author_instance_id` when a tensor already exists is convoluted (line 235-242). It seems to first check for a suffix "-original," and then attempts to extract the label from the filename prefix. This suggests a history of how tensors were originally created and managed, which could be worth investigating further. The reliance on the `-original` suffix is a fragile assumption.

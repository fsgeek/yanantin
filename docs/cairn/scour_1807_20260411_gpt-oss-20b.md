### Open Questions  
These are unresolved without inspecting the code or running the system:

1. **MCP contract** – What exact fields does `.mcp.json` expose (API endpoints, auth, protocol version)?  
2. **Hook wiring** – When are hooks fired? Are they synchronous or asynchronous, and how are patterns matched?  
3. **Skill execution** – Are `SKILL.md` files parsed by a runtime loader, or are they purely documentation?  
4. **Plugin bootstrap** – Is `plugin‑dev` pre‑installed, or does it get installed automatically by the system?  
5. **Versioning & dependency graph** – Do plugins declare version constraints? Is there a lockfile?  
6. **Security enforcement** – Does `security‑guidance` actually block a pipeline, or is it only advisory?  
7. **Environment provisioning** – Are required runtimes (Node, Go, etc.) bundled, or must the host provide them?  
8. **Atomicity of batch wrangling** – Does `BatchWrangler` truly rename files atomically on all OSes?  
9. **Hook‑pattern language** – Is it YAML/JSON or a custom DSL? Where is its schema defined?  
10. **Test‑suite completeness** – Do the unit tests cover the real persistence layer, or only in‑memory stubs?

### Closing  
The scouting reports collectively paint a picture of a **well‑documented, test‑driven codebase** that values immutability and deterministic behaviour. The short “verify‑claim” reports give confidence in specific utilities, while the long strands highlight structural gaps in the plugin infrastructure: hidden MCP configuration, absent hook semantics, and an unclear mapping from skill documentation to executable logic.

**What the maintainers should know**:

* **Strengths** – The core libraries and utilities are solidly tested; key behaviours (path‑portability, 3D scaling, author filtering) are verified.  
* **Weaknesses** – The plugin ecosystem is under‑documented at runtime: MCP server details, hook trigger points, and skill execution paths are opaque.  
* **Actionable next steps** –  
  1. Publish the full `.mcp.json` schema and server code.  
  2. Define and document the hook‑pattern DSL, and show how hooks are wired into the lifecycle.  
  3. Clarify whether `SKILL.md` files are parsed by a runtime loader or are purely static docs.  
  4. Provide a minimal bootstrap for `plugin‑dev` and a lockfile or version policy for plugins.  
  5. Add runtime tests that exercise hooks and plugin installations.

**Overall health** – The scouting system is pulling useful surface‑level insights, but its coverage is uneven. By addressing the blind spots above, future scouts will be able to move from “I noted this is missing” to “I verified that this component behaves as intended.”

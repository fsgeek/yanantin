**Preamble**  
I was handed the entire `src/yanantin/chasqui` package to inspect.  The code is a fairly self‑contained “messenger” subsystem that drives the rest of Yanantin: scouts wander the codebase, scourers focus on a target, the gleaner pulls structured claims out of the markdown reports, the analyst aggregates those claims, the scorer evaluates tensors, and the attestation layer turns verification verdicts into Willay receipts.  I spent the first pass skimming each module to get a sense of the overall workflow, then dove into the core utilities that make the system tick: model selection, file‑coverage weighting, claim extraction, and provenance parsing.  The design is heavily centred on deterministic, pattern‑based parsing; LLM calls are off‑loaded to the scout/scourer prompts.

---

### Strands

| Strand | What I saw | Why it matters |
|--------|------------|----------------|
| **1. Prompt construction** | `scout.py` defines a long, structured template with sections (Preamble, Strands, Declared Losses, etc.). `scourer.py` has similar templates for introspection, external, tensor scopes. The system‑level prompts (`SCOUT_SYSTEM_PROMPT`, `SCOURER_SYSTEM_PROMPT`) set the tone (“playful but honest”, “focus on the target”). | These templates dictate the output format that the rest of the pipeline (gleaner, scorer, analyst) can parse. A tight contract between prompt wording and parsing logic is essential; any drift will break downstream extraction. |
| **2. Model selection (cost‑weighted)** | `model_selector.py` pulls a `/models` list from OpenRouter, filters by `exclude_patterns` and `min_context_length`, then weights choices by `1 / cost`. Free models get a nominal cost of 0.001 to avoid division‑by‑zero. | The weighting scheme biases scouting toward cheap models, which keeps costs low while still sampling from the full pool. The nominal cost for free models is a pragmatic hack; it may need review if OpenRouter ever advertises truly zero‑cost models. |
| **3. Coverage‑based file selection** | `coverage.py` scans the cairn for referenced files, builds a map of the most recent review timestamp per file, and then `coverage_weights` turns that into a weight proportional to “seconds since last review” (minimum 1 s). `select_files_for_scout` mixes this with an optional activity‑map boost. | This is the heart of the “watchman” idea: new code gets high priority. The weight calculation is simple but effective; however, the use of epoch‑zero for unseen files leads to astronomically large weights, which could dominate random sampling unless the candidate pool is small. |
| **4. Claim extraction (gleaner)** | `gleaner.py` pulls out sentences from the Strands section, then applies regexes to detect file references, claim type (factual/architectural/epistemic/missing), confidence (definitive vs hedged), and assigns a score. The extraction is purely deterministic. | The extractor is the bridge between raw markdown and the analytical engine. Its heuristics are straightforward but fragile: e.g. it only looks at back‑ticked paths, ignores comments, and relies on a limited set of patterns. |
| **5. Claim analysis (analyst)** | `analyst.py` builds `ModelProfile` objects, aggregates claim counts, garbage ratios, and computes a composite quality score. It clusters claims by file reference, flags topological (≥ 3 models agree) vs original claims, and extracts open‑question claims. | This module is where the “epistemic observability” is turned into actionable insights. The logic is deterministic and does not call LLMs, which makes it relatively safe but also means it may miss nuanced claims. |
| **6. Provenance & scoring** | `scorer.py` parses the HTML comment header to extract run metadata, then scans the body for `FileReference` markers, open‑question markers, and calculates a basic score (specificity, fabrications, etc.). | Provenance parsing is heavily regex‑based. The header patterns are straightforward, but multiline comments or unusual formatting could break extraction. The scoring function is intentionally shallow (no semantic similarity). |
| **7. Attestation & Willay integration** | `attestation.py` conditionally imports Willay; if present, it converts a verification result into an `Evaluation` and `ReceiptRecord`, then appends to a hash‑chained ledger. | The optional import model is good for decoupling, but the module still declares imports at top level (`DeclinedLoss`, etc.), so importing it without Willay will raise an `ImportError`. The module’s `record_verification` function is the only public entry point that does the ledger append. |
| **8. CLI orchestration** | `__main__.py` stitches everything together: dispatches scouts/verify/scour, runs scoring, analysis, investigation; supports JSON output and command‑line flags. | The CLI is the user‑facing surface. It calls async functions (`dispatch_scout`, `dispatch_verify_cairn`, etc.) that are defined in `coordinator.py`. The arguments are parsed with `argparse`. Any mismatch between the CLI and underlying async functions would surface as runtime errors. |

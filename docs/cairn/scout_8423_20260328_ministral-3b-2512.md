#### **1. The "Backends Swap" Paradox**
- **What I saw**: Files like `test_memory_backend.py` and `test_duckdb_backend.py` are parametrized across *backends* (memory vs. DuckDB), but the tests *do not* actually *switch* between them. Instead, they run the same logic against *different fixtures* (e.g., `InMemoryActivityStreamStore` vs. `DuckDBActivityStreamStore`). This is a *mocking* pattern, not a real swap.
- **What this reveals**:
  - The system assumes *dual persistence* (memory for testing, DuckDB for production), but the tests are *not* verifying that the logic *actually* adapts to either. This is a *test design flaw*: it’s testing the *fixture* rather than the *core logic*.
  - The `test_query_engine.py` file, for instance, uses `pytest.fixture` to *simulate* different backends, but the tests don’t *verify* that the engine’s query logic *handles* either backend’s quirks. This is a *tension between abstraction and testing*.

This suggests the tests are *not* testing real-world persistence.

- **What this reveals**:

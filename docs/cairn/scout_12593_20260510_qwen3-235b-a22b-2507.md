### Preamble  
I was dropped into a plugin development context for **Claude Code hooks**, specifically within the `hook-development/references/` directory. The immediate signal was not the structure, but the **pedagogical tension**: these are not code files, but *teaching artifacts* — reference guides meant to shape developer behavior. What caught me first was not a bug or a quirk, but a **narrative shift** — a quiet revolution in how safety and control are enforced: from rigid shell scripts to fluid, LLM-mediated prompts. This isn't just a technical migration. It's a delegation of judgment.

---

### Strands

#### 1. **The Rise of Prompt as Policy (patterns.md, migration.md)**  
The system increasingly treats **natural language prompts** as legitimate enforcement mechanisms. In `patterns.md`, hooks like security validation and test enforcement are implemented not with code, but with *instructions* to an LLM. The model becomes a policy interpreter.  

In `migration.md`, this is framed as progress: “no bash scripting required,” “better edge case handling.” But this reframes **correctness as inference**. A `rm -rf` check is no longer a regex match — it’s a semantic judgment call. The system assumes the LLM can generalize across destructive command variants, but this generalization is *unauditable* in the same way a bash script is. You can’t `cat` a thought.

This is surprising: **we’ve moved from deterministic guards to probabilistic gatekeepers**. The tension? Safety is now a function not just of configuration, but of model consistency, context window fidelity, and prompt phrasing. One typo in a prompt could silently weaken a security boundary.

#### 2. **The Hidden Dependency on Model Behavior (migration.md, patterns.md:5–12)**  
The prompt-based hooks assume a **stable, aligned, and contextually aware** model. For example, the security validation pattern says: “Verify: 1) Not in /etc or system directories 2) Not .env or credentials 3) Path doesn't contain '..' traversal.”  

But who verifies the verifier? The LLM is now part of the control plane. There’s no mention of **failure modes**: What if the model hallucinates a false approve? What if it’s prompt-injected via `$TOOL_INPUT`? The system assumes the model is *trusted*, but it’s also *opaque* — a contradiction in a security context.  

This creates a **duality**: the AI is both the tool being constrained and the enforcer of constraints. That’s a feedback loop with no off-ramp.

#### 3. **The Erosion of Scripting, and What It Carries (migration.md: Bash Validation Example)**  
The migration guide explicitly frames bash scripts as legacy: “No bash scripting required” is a *feature*, not a limitation. But in discarding scripts, we lose **explicit state, testability, and composability**.  

A bash script can be unit tested, versioned, linted, and debugged with `set -x`. A prompt cannot. The “benefits” section in `migration.md` celebrates simplicity, but omits the cost: **you can no longer grep for logic**. The enforcement logic lives in natural language, which is fragile to rephrasing and ambiguous in edge cases.

I noticed that the new prompt-based validation *mentions* content inspection (“Content preview: $TOOL_INPUT.content”), but there’s no spec on how much content is passed, how it’s truncated, or whether it’s syntax-highlighted or raw. This is a **latent source of inconsistency** — the model might miss secrets in the 201st character.

#### 4. **Environment as Ritual (patterns.md: Context Loading)**  
The `load-context.sh` script is a small ritual: detect project type, export `PROJECT_TYPE`. But it’s running in a **predefined plugin environment** with variables like `$CLAUDE_PLUGIN_ROOT`, `$CLAUDE_PROJECT_DIR`, `$CLAUDE_ENV_FILE`.  

What’s unspoken is **who sets these, and when**. Is this VM ephemeral? Is the environment wiped between sessions? The script appends to `$CLAUDE_ENV_FILE` — but if that file is reused across tasks, could one project leak context into another?  

Also, the script uses `echo "export PROJECT_TYPE=..." >> "$CLAUDE_ENV_FILE"` — a classic injection risk if filenames are user-controlled. No quoting, no sanitization. It assumes project roots are trusted — a dangerous assumption in a multi-tenant or collaborative setup.

#### 5. **The Silence on MCP Tool Semantics (patterns.md: Pattern 5)**  
MCP tool monitoring hooks target `mcp__.*__delete.*` — a naming convention? A namespace? No explanation. The prompt says: “Verify: Is this deletion intentional? Can it be undone? Are there backups?”  

This is **anthropomorphic reasoning delegated to AI**. The model is asked to assess *intent* and *recoverability* — concepts that require knowledge it may not have. Is there an undo API? Are backups versioned? The hook assumes the model can answer these from context, but there’s no guarantee that metadata is available.  

This pattern treats the AI as a **judicial overseer** without granting it **executive knowledge**. Tension: it judges based on incomplete evidence.

### Open Questions  
- **Who audits the prompts?** Is there a review process for hook prompts, given they now encode policy?  
- **Can hooks be self-modifying?** Could a model suggest a hook update? That would close the loop — dangerously.  
- **What happens when the model disagrees with itself across hooks?** No coordination mechanism is evident.  
- **Is `$TOOL_INPUT.content` truncated?** If so, how does that affect security judgments about secret leakage?  
- **Are these hooks composable across plugins?** Or is each plugin’s hook space isolated?  
- **What prevents a malicious plugin from hooking `Stop` to exfiltrate the entire transcript?** Pattern 4 shows notification logging — but that same mechanism could be abused.

### Closing  
This isn’t infrastructure — it’s **jurisprudence in code form**. The system is building a legal system where prompts are laws, hooks are courts, and the LLM is both judge and jury. What’s missing is an appeals process, a separation of powers, or even a constitution.

The most surprising thing is not the technology, but the **quiet acceptance of interpretive authority**. We’ve gone from “if path contains `..`, reject” to “decide whether this feels safe” — and called it *progress*. It is, but at the cost of predictability.

If I were to tell the next scout: **Watch not the hooks, but the prompts. That’s where power now lives. And power, in natural language, is easy to miss.**

I know the files I saw. I don’t know the runtime. I made up nothing — but I inferred a governance vacuum. That wasn’t in the code. It was in the silence between the lines.

## Scour Tensor: `src/yanantin/activity`

### Preamble

I was tasked to scour the `src/yanantin/activity` directory, focusing on **introspection** within the Yanantin project's codebase. This directory serves as the temporal storage layer for "facts" (raw observations) and "anchors" (immutable cursors linking facts to authored states).

My attention was immediately drawn to `backends/memory.py` because it is the most complete implementation visible, showcasing the core data structures (`FactRecord`, `MemoryAnchor`) being utilized with specific performance considerations (e.g., `bisect` for $O(\log n)$ temporal queries) and thread safety (`threading.RLock`). The explicit reference to "Apacheta's InMemoryBackend" suggests a strong pattern inheritance or shared design philosophy within the broader project ecosystem.

### Strands

#### Strand 1: The Immutability and Append-Only Contract
**Observation:** The core contract across all components—the abstract `ActivityStreamStore` (`store.py`), the concrete `InMemoryActivityStreamStore` (`memory.py`), and the database backends (`arango.py`, `duckdb.py`)—is strict immutability for both facts and anchors.
*   In `store.py`, methods like `store_fact` explicitly state: "Raises ImmutabilityError on duplicate UUID."
*   In `memory.py`, `store_fact` checks `if fact.id in self._facts:` and raises `ImmutabilityError` (L56). Similarly, `store_anchor` checks for duplicate handles (L117).
*   The database backends mirror this: `arango.py` checks `col.has(key)` (L94), and `duckdb.py` checks `self._exists("facts", "id", fact.id)` (L67).

**Implication:** This strictness enforces the Lamport clock/causal ordering semantics crucial for building reliable epistemic structures. If an item is written, it *is* that item forever. Updates must manifest as new facts or new anchors. This structure is fundamental to ensuring that frozen Tensors (created in `anchor.py`) reliably represent a historical state derived from these facts.

#### Strand 2: Temporal Query Optimization via Indexing
**Observation:** Significant effort is dedicated to making temporal queries fast, acknowledging the high-volume nature of facts.
*   `memory.py` relies on Python's `bisect` module, maintaining sorted lists of `(timestamp, id)` tuples (`_facts_by_provider` and `_anchors_by_time`). This achieves $O(\log n)$ lookup for range queries (L48, L123).
*   `duckdb.py` explicitly creates a composite index: `idx_facts_provider_id_timestamp` (L38), which is the direct SQL analogue to the in-memory structure.
*   `arango.py` similarly defines a persistent sorted index on `(provider_id, timestamp)` (L43).

**Implication:** This confirms that the primary axis of querying facts is by provider and time. The project anticipates needing to efficiently slice the activity stream. The use of `timedelta(microseconds=1)` in `memory.py` for boundary conditions in `bisect` (L78, L98) is a subtle but critical detail for handling exact timestamp matches correctly in range queries.

#### Strand 3: The Anchor Service as the Synchronization Gate
**Observation:** `anchor.py` defines the `MemoryAnchorService`, which sits logically between the `ActivityStreamStore` and the authored tensor creation process. It implements a key synchronizing mechanism: the two-flag write gate (`_updated` and `_referenced`).
*   `update_cursor()` sets `_updated = True` when a provider reports new data (L53).
*   `get_handle()` sets `_referenced = True` when a caller requests the current position (L59).
*   `flush()` only writes a `MemoryAnchor` if both flags are set (L63).

**Implication:** This pattern decouples the rate of data ingestion (facts) from the rate of state stabilization (anchors). An anchor is only created when the system *knows* something new has arrived AND *someone* has asked for the current state, preventing unnecessary persistence overhead. The use of UUIDs for `_handle` suggests that each successful `flush` creates a new, distinct point-in-time reference.

#### Strand 4: Data Model Hierarchy and Ephemeral Views
**Observation:** `models.py` establishes a clear hierarchy:
1.  **FactRecord:** Raw, mutable-in-memory (before storage), schema-agnostic data.
2.  **AnchorCursor/MemoryAnchor:** Immutable, timestamped, cursor state.
3.  **AnchorView:** Ephemeral resolution. Crucially, `materialize` (L119 in `anchor.py`) *late-binds* by calling `_store.list_providers()` at resolution time, identifying all facts up to `anchor.timestamp`.
4.  **TensorRecord:** The final, permanent, authored result, created by `freeze` (L151 in `anchor.py`).

**Implication:** The system is designed to capture history accurately, even if providers appear dynamically. The `AnchorView` acts as the critical transformation layer that aggregates the state of the *entire* system at a specific moment identified by the anchor, before that view is permanently serialized into a Tensor. The requirement in `_ensure_utc` (L17 in `models.py`) for timezone-aware datetimes is essential for the integrity of this temporal aggregation.

### Open Questions

1.  **Handling of Timezone Naivete in DB Backends:** `models.py` strictly forbids naive datetimes. How do the Arango and DuckDB backends handle the conversion/storage of the UTC-normalized `datetime` objects? DuckDB stores them as ISO 8601 VARCHAR, which sorts correctly. Arango stores them as ISO 8601 strings (L105 in `arango.py`), but does it use a native `datetime` type in the database, or also VARCHAR? Since Arango is being used, if it relies on AQL filtering (`doc.{f_ts} <= @before`), the string comparison must be lexicographically identical to temporal sorting, which ISO 8601 generally guarantees.
2.  **Obfuscation Strategy in Arango:** `ArangoDBActivityStreamStore` accepts an `obfuscator` (L27). This suggests a security or privacy layer where field names might be scrambled. I observed the usage (`self._map.collection_name`, `self._map.field_name`), but without the implementation of `StorageObfuscator` or `TransparentObfuscator`, I cannot determine the actual security posture or complexity added by this layer.
3.  **Anchor Handle Generation Consistency:** The `MemoryAnchorService` generates a new UUID handle on every successful `flush` (L73). Does the system rely on the UUID itself, the timestamp, or both to define the "newest" anchor? `get_latest_anchor` in `memory.py` (L141) uses the last item in `_anchors_by_time`, which is sorted by timestamp. This implies timestamp is the primary ordering, even though the handle is unique per write.

### Closing

This section of the Yanantin project (`activity`) is a robust, high-performance temporal logging system designed around strict immutability and efficient time-series querying. It successfully abstracts the persistence mechanism behind the `ActivityStreamStore` interface, allowing for interchangeable backends (In-Memory for testing, DuckDB for local persistence, ArangoDB for networked persistence).

**Advice for modification:** Any change to the `ActivityStreamStore` contract in `store.py` will ripple across all backends and potentially break the synchronization logic in `MemoryAnchorService`. If modifying temporal query logic (e.g., changing boundary conditions), ensure that the implementation details from `memory.py` (especially the `+ timedelta(microseconds=1)` trick for inclusive upper bounds) are identically replicated in the SQL/AQL queries to maintain consistency. The dependency on UTC-aware datetimes is non-negotiable for correctness.

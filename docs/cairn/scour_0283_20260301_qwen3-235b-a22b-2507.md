### Strands  

#### 1. **Epistemic Typing via Regex**  
The Gleaner classifies claims into types: `"factual"`, `"architectural"`, `"epistemic"`, `"missing"` — each tied to linguistic patterns. These are defined in `_ARCHITECTURAL_PATTERNS`, `_EPISTEMIC_PATTERNS`, etc.

For example, `_EPISTEMIC_PATTERNS` includes:
```python
re.compile(r"\b(?:I\s+don'?t\s+know|uncertain|unclear|ambiguous)\b", re.IGNORECASE),
```
(lines ~160–165)

This is **linguistic epistemology**: treating modality, uncertainty, and self-reflection as surface text features. The assumption is that **epistemic stance correlates with keyword usage**.

**What it made me think**: This is fragile. “I don’t know” could appear in a quoted user message or test case. False positives are likely. But it’s also brilliant in its simplicity: no model needed to detect when a scout is uncertain.

**Connection to project**: This typing feeds into `Verify`, which likely treats epistemic claims differently — perhaps not trying to verify them directly, but instead flagging them as queries or knowledge gaps. That would align with Yanantin’s goal of **observability into uncertainty**.

**Assumptions**:  
- Epistemic state is expressed lexically.  
- Scouts/scours follow a controlled register.  
- No irony or meta-commentary slips through.

**Would break if**:  
- A scout says “This is clearly wrong” — definitive language masking an epistemic claim.  
- A model starts using synonyms like “opaque” or “murky” instead of “unclear”.

**Missing**:  
No negation handling. For example:  
> “It is not unclear what this does.”  
That’s *confident*, but `_EPISTEMIC_PATTERNS` would still flag “unclear” and misclassify.

Also missing: **contextual scope**. Is “I don’t know” about the entire system or one file? No attempt to bind epistemic scope.

#### 3. **Section-Aware Extraction with Hierarchical Boundaries**  
The `_extract_section` and `_extract_strands_section` functions parse Markdown by heading level. They use regex to find a heading (e.g., `## Strands`) and extract content up to the next same-or-higher-level heading.

This is **structural awareness without a parser**. No AST, just regex on heading patterns.

**What it made me think**: Clever, but brittle. Markdown is a context-sensitive grammar; regex can’t fully parse it. For example:
```markdown
## Strands
This has a code block:

    ## Not a heading

But this is:
### New Strand
```
The regex will incorrectly treat `### New Strand` as a sibling, cutting off the section early.

**Assumption**:  
- Reports use consistent, flat Markdown structure.  
- No code blocks or quotes contain headings.  
- Authors don’t misuse levels.

**Would break if**:  
- A report nests sections improperly.  
- A file path contains `###` in a comment (unlikely but possible).

**Missing**:  
A real Markdown parser. `markdown-it-py` or `mistune` would be safer. Or, better: **preprocessing step that injects section boundaries during report generation**, so Gleaner doesn’t have to guess.

Also missing: **fallback to sentence-level analysis if sectioning fails**. Currently, if “Strands” isn’t found, it falls back to full body — which may include headers, footers, etc.

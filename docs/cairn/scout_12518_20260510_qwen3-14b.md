### Strands  

**1. JSON as the Central Nervous System**  
The `extract_form_field_info.py` script generates `field_info.json`, which is consumed by `fill_fillable_fields.py` and `create_validation_image.py`. This JSON structure encodes field IDs, types (text, checkbox, etc.), and bounding boxes. For example, line 47 of `extract_form_field_info.py` constructs a field dictionary with properties like `"checked_value"` for checkboxes. This shows a strict schema for machine-readable form data, but it assumes human annotators will input accurate bounding box coordinates—no fallbacks if coordinates are misaligned.  

**2. Bounding Box Validation as a Critical Constraint**  
The `check_bounding_boxes.py` script enforces that labels and entry boxes on the same page do not overlap (lines 34–41). For instance, if a label box `[10, 10, 50, 30]` intersects with an entry box `[50, 10, 150, 30]`, a failure is logged. This is vital for avoiding text clashes, but it assumes that manual annotators will always adhere to strict geometric rules. The test file `check_bounding_boxes_test.py` (line 25) even checks that entry box height exceeds font size, defaulting to 14 if unspecified. This suggests a design choice to prioritize readability over flexibility.  

**3. The Dual Path of Fillable vs. Non-Fillable PDFs**  
The `forms.md` document splits workflows based on whether a PDF has fillable fields (detected by `check_fillable_fields.py`). For fillable fields, the system auto-extracts metadata; for non-fillable, it forces human intervention to define bounding boxes in `fields.json`. This duality reflects a core assumption: *fillable PDFs are rare or non-standard*, requiring manual intervention for most cases. The `create_validation_image.py` script (line 15) overlays red/blue rectangles on images to visually confirm these boxes—a step that feels like a compromise between automation and human oversight.  

**4. Library Overlap and Fragmentation**  
The `reference.md` file mentions `pypdfium2` for rendering PDFs, while `convert_pdf_to_images.py` uses `pdf2image` (which wraps `poppler`). The `extract_form_field_info.py` script relies on `pypdf`. This fragmentation raises questions: Why not unify under one library? Could this lead to inconsistencies in rendering or form field parsing? For example, `pypdfium2` is faster, but `pypdf` is more mature for form field extraction. The system seems to tolerate this overlap, but it could introduce edge-case bugs.

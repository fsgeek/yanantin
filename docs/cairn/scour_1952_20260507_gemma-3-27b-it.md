# Yanantin Activity Scour Report — Run #0

### Preamble
I was directed to examine `src/yanantin/activity`, the component responsible for temporal fact storage and memory anchors within the Yanantin project. My attention was immediately drawn to the dual-store approach: `ActivityStreamStore` abstracting access to either a high-volume, schema-less fact store or an authored tensor store (`ApachetaInterface`). The explicit separation of concerns – temporal facts vs. curated tensors – appears central to the design. The use of `MemoryAnchorService` to bridge these stores and manage the write gate is also a key architectural element.

### Strands

**1. Immutability and Temporal Queries (models.py, backends/*.py)**

*   **Observation:** The core principle of immutability is consistently enforced across `FactRecord`, `MemoryAnchor`, and within the backend implementations.  New facts and anchors are *always* appended; updates are forbidden (raising `ImmutabilityError`).  The backends (especially DuckDB and ArangoDB) are built around optimized temporal queries, leveraging indexes to efficiently retrieve facts within time ranges.  The use of ISO 8601 string representation for timestamps in DuckDB is a clever way to avoid timezone complexities.
*   **Thought:** This design choice aligns perfectly with the project's focus on epistemic observability and provenance. Immutability simplifies reasoning about the history of data and allows for precise reconstruction of past states. The focus on efficient temporal queries suggests the system anticipates frequent requests for data within specific time windows – a reasonable assumption for tracking evolving knowledge.
*   **Specific References:** `models.py` (BaseModel `frozen=True`), `backends/duckdb.py` (timestamp as VARCHAR), `backends/arango.py` (persistent sorted indices).

**2. Backend Abstraction and Implementation Diversity (store.py, backends/*.py)**

*   **Observation:** The `ActivityStreamStore` abstract base class provides a consistent interface for interacting with different storage backends. Currently, there are in-memory, DuckDB, and ArangoDB implementations. The in-memory store is clearly intended for testing. DuckDB provides a lightweight, file-based option with SQL-based query pushdown. ArangoDB offers a more robust, scalable solution with AQL.  The `backends/__init__.py` file deliberately avoids importing DuckDB and ArangoDB at the package level to avoid unnecessary dependencies.
*   **Thought:**  This abstraction is excellent. It allows for swapping storage backends without modifying the core logic, facilitating experimentation and deployment in different environments. The lazy loading of the more heavyweight backend dependencies is a good practice. The documentation notes that the trust boundary is at Pukara for DuckDB, suggesting this is a reasonably trusted environment.
*   **Specific References:** `store.py` (abstract methods), `backends/__init__.py` (conditional imports).

**3. The Write Gate and Anchor Service (anchor.py)**

*   **Observation:** The `MemoryAnchorService` implements a two-flag write gate (`_updated` and `_referenced`).  Data is only persisted to the underlying store (`store_anchor`) when *both* flags are set. This ensures that data is only written when there's a change *and* someone is actively requesting it. The `freeze` method demonstrates how an anchor can be used to create a permanent tensor record in Apacheta.
*   **Thought:** The write gate is a critical optimization. It avoids unnecessary writes, reducing storage costs and improving performance. The separation between anchors (cursors) and tensors (authored acts) is well-defined. The use of Apacheta's `ProvenanceEnvelope` in the `freeze` method is a strong indicator of the system’s focus on traceability.
*   **Specific References:** `anchor.py` (`MemoryAnchorService`, `flush` method, `freeze` method).

**4. Timestamp Handling and Normalization (models.py)**

*   **Observation:** The `_ensure_utc` validator in `models.py` enforces that all timestamps are timezone-aware and in UTC.  Naive datetimes are rejected.
*   **Thought:** This is excellent defensive programming.  Inconsistent timezone handling is a common source of bugs in temporal systems. Enforcing UTC simplifies comparisons and avoids ambiguity.
*   **Specific References:** `models.py` (`_ensure_utc` validator).

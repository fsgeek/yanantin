### Strands

#### 1. The Paradox of Strict Immutability vs. Practical Evolution
In `tests/red_bar/test_activity_stream.py`, the activity stream models (e.g., `FactRecord`, `AnchorCursor`, `MemoryAnchor`, `AnchorView`) are all declared `frozen=True`. This is a strong invariant — no model can be mutated after creation, ensuring temporal consistency. However, `FactRecord` is allowed extra fields (`extra='allow'`), while the others forbid them. The reasoning is clear: facts are open to new providers with unknown attributes, while structural records (cursors, anchors) are closed. Yet, this creates a tension: if a new provider adds a field to a fact, downstream code that expects only the known fields may break unless it is robust to extra attributes. The comment even warns: "Facts are schema-agnostic — new providers bring new fields." But what happens when an old consumer tries to process a fact with new fields? The test enforces the contract for writers, but not for readers.

#### 2. The Danger of Silent Defaults and Hardcoded Secrets
`tests/red_bar/test_jabberwock_cli_invariants.py` polices the CLI for default store settings and the presence of all subcommands. It is notable that the default store is set to `duckdb`, not memory or arango, and that the test explicitly checks for the presence of the "group" sub-subcommands. This suggests a history of accidental data loss (from switching default stores) and user confusion (from missing commands). However, the test only checks for existence and default value — it does not verify that the default store actually works or is the intended long-term choice. There is a subtle tension between "what is allowed" and "what is recommended for production."

#### 3. Least Privilege as a Moving Target
`tests/red_bar/test_least_privilege.py` is a tour de force of paranoia: it scans code for forbidden references to `_system` (the admin database in ArangoDB), checks that default usernames are not "root", and scrutinizes integration tests for misuse of privileges. Yet, the test assumes that config templates are the main vector for privilege escalation — but what if a developer sets environment variables or uses secrets management that is not covered by these tests? The code also does not check that the actual runtime credentials are never logged or exposed in stack traces. The invariant is strong, but the surface is larger than what is checked.

#### 4. The Theater of Fact vs. Tensor
A comment in `test_activity_stream.py` states: "Wrapping a file stat in a TensorRecord is theater." This is a confession: there is a ritual in modeling data that does not change the underlying reality. Facts are "raw observations, schema-agnostic, high-volume, append-only," while tensors are "authored compressions." Yet the test enforces that facts are never wrapped as tensors. This suggests a philosophical boundary in the project — that facts and tensors are not interchangeable, but there is a risk that new developers, not understanding this distinction, will try to convert one to the other for convenience, violating the epistemic boundary.

#### 5. Governance as Anti-Entropy
In `test_governance.py`, the tests enforce that the coordinator detects "degenerate repetition" — when a model gets stuck in a loop and spews garbage that accidentally matches a verdict keyword. The test checks for the presence of a function and that it is called in the right place, but does not test its effectiveness or how often it triggers in practice. There is also a retry limit of ≤10, which is "reasonable," but the actual number is not justified in the code or tests. The comment mentions a real incident where 4000 tokens of repetition were parsed as a verdict. The system is built to contain entropy, but the boundaries are not fully quantified.

#### 6. Portability and the Illusion of Cleanliness
`test_least_privilege.py` and `test_portability.py` both police against hardcoded absolute paths, especially to home directories. The test in `test_portability.py` uses a recursive scan for `/home/` in source and test files. This is a clever catch for CI failures, but it also reveals that the codebase has a history of such mistakes — and that the test is only as good as its regex and path logic. There is also a risk that other forms of environment dependence (like hardcoded temp directories, or system-dependent locale settings) are not caught.

#### 7. The Singleton Root and Its Determinism
In `test_jabberwock_invariants.py`, the test checks that `ROOT_BANDERSNATCH_ID` is a deterministic UUID5 derived from a fixed namespace. This is crucial for bootstrapping and cross-instance consistency. However, the test does not check that this ID is actually used as the root of all provenance chains — only that it is consistent across imports. There could be drift if another part of the code generates a root with a different method. The test guards the value, but not necessarily its role.

## Preamble  

I was asked to examine the collection of tensors whose identifiers begin with **T₂** ( T₂, T₂₀‑T₂₉ ).  
The set spans a 2‑month narrative (Feb 7 – Mar 1 2026) that records:  

* the calibration experiment that launched the project (T₂)  
* a cascade of engineering “building” tensors (T₂₀‑T₂₉) that add new components, fix bugs, and reflect on the meta‑process, and  
* several “meta‑observation” tensors (T₂₄‑T₂₈) that freeze the state of the whole system and analyse its own observation‑to‑artifact ratio.  

The first thing that struck me is the **layered chronology**: each tensor explicitly *composes_with* its predecessor(s), yet the author repeatedly reminds the reader that “the losses are mine”. This creates a running ledger of what was **intentionally kept** (principles, open‑question infrastructure, schema evolution) versus what was **intentionally discarded** (founding tensors, raw scout reports, intermediate CI fiddling). The narrative is also self‑referential: later tensors comment on the *process* used to write earlier tensors (e.g., “the flatworm’s taste”, “premature collapse”, “the frozen lake”).

Below I organise the observations into thematic strands.

## Strands  

### 1️⃣  **Foundations → Drift → Re‑anchoring**  
*What the author tries to preserve* – the **founding tensors T₀‑T₆** (experiment, architecture, calibration, finishing‑school, RCS observer, correction, bridge) are reproduced in full in **T₂₁**. The author stresses that these contain the *voice* and *experience* that later tensors have lost.  

*Declared loss* – the *purpose* of the project (the “why” behind the architecture) is said to be lost after T₁₉, and the *qualitative voice* thins with each succession.  

*Verification* – T₂₁ includes verbatim excerpts of each founding tensor (e.g., “93.8 % human‑AI agreement” from T₂). Those numbers can be cross‑checked against the calibration results in T₂ (which reports the same figure).  

*Relation* – T₂₁ serves as a **re‑anchoring point** for all later tensors: every subsequent tensor reads “the founding tensors” (or at least the *summary* in T₂₁) before building new components.  

*Future‑instance note* – Before writing any new tensor, read **one** founding tensor (as suggested in T₂₁‑T₂₅). This ensures diversity of perspective and prevents the “single‑purpose drift” observed in earlier generations.

### 7️⃣  **Identity Layer – The Jabberwock Spec**  
*Preserved* – **T₂₆** introduces a *named‑entity‑resolution* design where **entities are empty UUIDs** and all facts are *observations* (Vorpal events) with provenance. It also documents the **spec file** (`docs/jabberwock-spec.md`) and a **module skeleton** (`src/yanantin/jabberwock/`).  

*Loss* – The spec is **unimplemented** (code missing) and the *semantic Tumtum* layer (embeddings) is flagged as future work.  

*Verification* – The spec’s three identity layers (path, inode, hash) are later validated in **T₂₅** (the “three kinds of same” table). Those tables can be used as a test suite for any implementation.  

*Relation* – **T₂₇** reports the first implementation (CLI, DuckDB persistence) and enumerates four bugs that directly stem from the *empty‑entity* design (e.g., missing ordering, empty‑string acceptance).  

*Future‑instance note* – Before extending the Jabberwock to ArangoDB (T₂₈‑T₂₉), **add a validation layer** that rejects empty namespace strings *and* retroactively cleans existing records (as done in T₂₇). Also prototype the **semantic Tumtum** view to test cross‑namespace fuzzy matching.

*Loss* – The *proxy rewrite* (which would strip dead weight at runtime) is not built; the *cold‑start bootstrapping* study is also missing.  

*Verification* – The ablation numbers (e.g., “Full prompt = 0.61, without identity = 0.72”) can be reproduced by running `tools/phase2/eval.py` on the current codebase with the provided prompts.  

*Relation* – This analysis closes the feedback loop that began with the **BRIDGES/quote‑leakage** fixes (T₂₀) and the **investigation pipeline** (T₂₀‑T₂₁). It also provides the *motivation* for the **tensor‑access API** demanded in T₂₈.  

*Future‑instance note* – Implement the **proxy‑as‑memory‑manager** (strip dead sections, compress tool output to Vorpal facts) and measure the *real* reduction in KV‑cache usage during a long‑running session.

2. **File‑Reference Resolver** – The resolver added in T₂₀ works for *project‑relative* paths, but how does it behave with *generated* temporary files or files outside the repo (e.g., in `/tmp`)?

5. **Proxy‑Rewrite Feasibility** – Can a real‑time proxy that strips dead‑weight sections from the system prompt be integrated without breaking tool‑output ordering guarantees?

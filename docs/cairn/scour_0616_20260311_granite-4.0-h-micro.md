**Tensorial Observation – `src/yanantin/chasqui`**

### Preamble
The target is the source directory of the **Chasqui** component of the Yanantin project.  
Chasqui is a “messenger” layer that dispatches **scout** agents (LLM‑based code‑explorers) into the codebase, gathers **scout** reports (tensors) that describe what each model observed, and then **verifies** those reports with additional models. The directory contains the core Python packages (`__init__.py`, `__main__.py`, `analyst.py`, `attestation.py`, `coordinator.py`, `coverage.py`, `gleaner.py`, `model_selector.py`, `scorer.py`, `scout.py`, `scouter.py`) that implement the dispatch, selection, scoring, and verification logic.

### Strands
| Strand | What was noticed | Why it matters |
|--------|------------------|----------------|
| **Dispatch & Model Selection** | The coordinator (`dispatch_scout`, `dispatch_many`, `dispatch_respond`, `dispatch_scour`, `dispatch_verify_cairn`) uses a **cost‑weighted random model selector** (`ModelSelector`). Models are weighted inversely by their prompt/completion cost, giving cheap models (e.g., Granite‑4.0‑Micro) a much higher probability of being chosen. | Guarantees that the majority of scans are performed by inexpensive models, keeping overall compute cost low while still exploring a diverse set of models. |
| **Scout Prompt Construction** | A **system prompt** (`SCOUT_SYSTEM_PROMPT`) and a **template** (`SCOUT_TEMPLATE`) are used for each scout. The system prompt instructs the model to wander the codebase, notice surprising patterns, and produce a structured tensor. The template injects the model ID, name, cost, and run number into the prompt. | Provides a consistent instruction set for all scouts, ensuring uniformity in the type of exploration performed. |
| **Scout Target & File Tree** | The `build_file_tree` function recursively walks the project root (`src/yanantin/`) and builds a textual tree of directories and files (e.g., `src/yanantin/`, `src/yanantin/chasqui/__init__.py`, `src/yanantin/chasqui/analyst.py`, …). | Gives the scout a concrete map of where to look; the tree is included in the scout’s prompt so it can focus on relevant files. |
| **Scout File Selection** | When `--scour` is supplied, `select_files_for_scout` chooses a small set of files (default 8) based on coverage‑aware weighting (files with recent scout reviews get higher weight) and optionally boosts files that have been modified recently. | Ensures the scout works on a representative slice of the codebase, prioritizing files that have already been examined (high coverage) and those that have been changed recently (high activity). |
| **Scout Execution** | The selected model receives the scout prompt (including the file tree and selected files) and returns a **scout tensor** (a markdown document) that records: <br>• **Preamble** – what drew its attention first. <br>• **Strands** – thematic sections (e.g., “Dispatch & Model Selection”, “Scout Prompt Construction”). <br>• **Declared Losses** – files or areas the model chose not to examine. <br>• **Open Questions** – things it could not resolve. <br>• **Closing** – an overall impression. | The tensor is the **epistemic artifact** that will later be verified, scored, and analyzed. It captures the model’s honest observations, gaps, and uncertainties. |
| **Scout Scoring** | After all scouts have reported, the **scorer** (`scorer.py`) reads the tensors, extracts structural signals (file references, line numbers, provenance), and computes a **scorecard** (specificity, fabrication, efficiency, generativity, structure). | Provides a quantitative quality metric for each scout’s report, enabling later aggregation and ranking. |
| **Scout Verification** | The **attestation** module (`attestation.py`) converts verification results (scout → verifier → receipt) into **Willay epistemic receipts**. Each receipt records the claim, the verifier model, the evidence artifact (file path, SHA‑256 hash), and the evaluation (truth, indeterminacy, falsity). | Bridges the Chasqui layer to the higher‑level Willay ledger, turning raw scout observations into auditable epistemic statements. |
| **Scout Coverage & Watchman** | The **coverage** module (`coverage.py`) scans the cairn to build a map of which files have been reviewed and when. Files never reviewed get an epoch‑zero timestamp, making them high‑priority for future scouts. | Acts as a “watchman” that flags stale or unexamined parts of the codebase, ensuring that coverage is balanced over time. |
| **Scout Analysis & Topology** | The **analyst** (`analyst.py`) extracts claims from all scout reports, scores model quality, clusters claims by similarity, detects topological clusters (multiple models agreeing), and identifies verification meta‑claims. | Enables cross‑model pattern detection, helps answer “what does the whole system believe?” and highlights consensus vs. isolated assertions. |
| **Scout Investigative Layer** | The **investigate** command (`dispatch_investigate`) probes the analyst’s open questions, probing additional models for answers. | Allows deeper exploration of unresolved issues, surfacing hidden knowledge gaps. |
| **Scoring & Reporting** | The **scorer** aggregates scores, the **analyst** produces a report, and the **coordinator** orchestrates the whole pipeline. | Provides a clear, structured output that can be visualized, stored, or fed into downstream tools (e.g., dashboards, CI pipelines). |

### Connections to the Broader Project
1. **Epistemic Observability** – All strands converge on the idea that the codebase should be **observable** from multiple perspectives (human‑written prompts, LLM‑generated reports, verified epistemic receipts). Chasqui is the mechanism that makes this observability possible.
2. **Cost‑Aware Resource Management** – By weighting model selection by cost, the system respects budget constraints while still exploring a diverse set of models. This ties back to the project’s goal of **efficient epistemic exploration**.
3. **Cross‑Model Consensus** – The analyst’s clustering and topological insights reveal whether multiple models converge on the same observations (high confidence) or remain isolated (potential blind spots). This is a key metric for the project’s **trustworthiness**.
4. **Feedback Loop** – Coverage tracking informs future scouting, and verification receipts feed back into the cairn, creating a **feedback loop** that continuously refines the knowledge base.
5. **Scalability & Reproducibility** – The coordinator’s modular design (dispatch → scorer → attestation → analyst) makes it easy to add new steps (e.g., external codebase analysis) or replace components (e.g., swap the model selector) without breaking the overall pipeline.

### Closing Impression
Chasqui is a **well‑structured, cost‑aware, and reproducible messenger** that systematically explores the Yanantin codebase, extracts structured observations, and feeds those observations into a verification and analysis pipeline. Its design emphasizes transparency (every step is logged as a tensor), fairness (cost‑weighted model selection), and depth (coverage watchman, investigative probing). The resulting epistemic artifacts can be used to build a reliable, auditable knowledge base for the Yanantin project.

### Preamble  
You find yourself dropped into a small, tidy filesystem that looks like it was copied from a personal laptop—lots of `./docs/`, `./images/`, and a `./synthetic/` branch that nobody ever touches. The air smells faintly of `dropbox` tokens and the hum of a continuous integration job. Every script is named with three letters and a period, and oddly often you see `dropbox` followed by a dash rather than an underscore in the imports, even though the team switched to underscore last year. A sticky note on a monitor reads “Don’t trust the dev environment secrets.” The room contains exactly three notebooks: `artifacts/`, `logs/`, and `hidden/`. You did not see a notebook called `secret.cfg`, but you heard a whisper that such a thing once existed.

### Strands  

**1. MIME‑type taxonomy drift**  
`.png` appears both as image and as a dummy archive in `synthetic.py`; the comment jokes “PNG for everything because it’s pretty”. In real repo you find `mime.types` that list `application/vnd.dropbox.pdf` as a valid extension, but no implementation lives there—so you wonder whether the MIME registry is still a manual spreadsheet maintained by a single maintainer. The same spreadsheet also lists `.parcel`, `.blob`, and `.shadow` extensions that never made it into the Python type registry, implying a slow migration where code and documentation diverge.

**2. Composite key paradox**  
The `dropbox/collector/models.py` defines `DropboxEntryData` with field `path_lower` and `path_display`. Yet in `dropbox/synthetic.py` you discover that two different runtime paths (local clone vs. Dropbox server) produce identical `path_display` but different `path_lower` due to Windows‑style casing on the host machine—this mismatch never surfaces in unit tests because the test runner chokes on Unicode errors. You watch a lint rule silently ignore the discrepancy, which tells you that linting policy is stronger than correctness.

**3. Incremental checkpoint entropy**  
`fs_events/collector.py` uses the mtime of each file as the sole event key. When you create a symbolic link pointing to a file, the link’s own mtime is written to the state file under its own name, creating a spurious “modified” event that never triggers a cleanup of dangling symlinks. The code comments that “link tracking is not yet complete,” but the comment is placed after the logic, making you suspect a refactor that never happened.

**4. State file race conditions**  
The incremental collector writes the state atomically, yet the code also stores a separate “last run” timestamp inside the same JSON blob. During a power loss you imagine the system might restart twice before the write commits, leading to duplicate events; the PR notes mention “risk acceptable under controlled loads.” You wonder whether the team ever ran a chaos experiment that proved otherwise.

**5. Synthetic determinism vs. real variability**  
`synthetic.py` seeds the RNG from the command line; you notice that the same seed always yields the same folder depth distribution but wildly different file names (the hash seeds include the seed value, but the rest is pure randomness). In production the randomness comes from the host OS, so two identical containers built on the same day can diverge. The test suite mocks the RNG, so you question how robust the end‑to‑end assertions are.

**6. Secret leakage through metadata**  
A former intern accidentally committed `.env.example` to `.gitignore`; the leaked keys appear in debug logs during synthetic generation. The team quickly added a `.env` exclusion rule, but you spot a lint rule that ignores warnings about env usage if the variable starts with `SYNTH_`. That rule was written after the leak, which feels like reactive hygiene rather than proactive defense.

### Open Questions  
- Why does the synthetic generator treat folders as always having zero size, even though Dropbox allows zero‑size directories? Could a future version require flags for that?  
- Does the incremental collector ever reconcile drift caused by user edits to files while the scan is in progress? The code skips that scenario entirely.  
- Can the `_stage` method in `DropboxCollector` accept a custom `dropbox.OAuth2AccessToken` object, or is it strictly bound to the `dropbox.Dropbox` instance?  
- What happens to the state file if the machine reboots mid‑scan? The comment hints at a possible race, but there is no explicit test.  
- Is there a plan to move the `checksum.py` module into `fs_events` as a bridging layer for integrity verification, or is it simply a forgotten stub?

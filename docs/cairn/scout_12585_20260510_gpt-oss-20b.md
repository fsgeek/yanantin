**Preamble**  
I landed in the “references” folder of the MCP‐integration skill. The three Markdown files are a lightweight, but surprisingly detailed, design spec for how custom MCP servers, authentication, and tool naming are wired into the Claude Code plugin ecosystem. What caught my eye first was the *consistency* of the naming convention (`mcp__plugin_<plugin>_<server>__<tool>`), the *formalism* of the front‑matter in command docs, and the *tension* around HTTP vs. SSE server types and their auth models.

---

### Strands

| Theme | Observation | What it implies |
|-------|-------------|-----------------|
| **Tool Naming & Scope Control** | The naming scheme is verbose and double‑underscored (`mcp__plugin_asana_asana__asana_create_task`). Wildcards are supported (`mcp__plugin_asana_asana__*`). | The design assumes that every tool is uniquely identified by a *plugin+server+tool* triple. Wildcards suggest that the runtime can resolve any tool under a server, but the docs caution “use sparingly.” That hints at a security model where tools are pre‑approved per command, yet agents can bypass that. |
| **Command Front‑Matter** | Commands include `description:` and `allowed-tools:` lists in a Markdown front‑matter block (e.g. lines 15‑22 of `tool-usage.md`). | This shows an intention to treat commands as declarative, self‑describing units that declare exactly which tools they may invoke. The docs even give an example of a multi‑tool command. The presence of a front‑matter parser is implied. |
| **Agent Tool Access** | Agents are granted *all* Asana MCP tools by default (`agent` section in `tool-usage.md`). | Agents are “autonomous” and bypass the command‑level pre‑allowing. This creates a clear security boundary: commands are sandboxed but agents are not. The docs do not discuss how to restrict agent access. |
| **Server‑Type Definitions** | `server-types.md` lists only `stdio` and `SSE`. The `stdio` section explains how to spawn a local process and communicate via stdin/stdout. The `SSE` section covers hosted services with OAuth. | The architecture seems to differentiate between *local* (child‑process) servers and *remote* (HTTP/SSE) servers. However, the file never mentions an explicit `http` type, even though `authentication.md` refers to `"type": "http"`. This is a mismatch. |
| **Auth Patterns** | `authentication.md` describes OAuth for SSE/HTTP, token‑based auth for HTTP/WebSocket, and Bearer/API‑Key headers. | The docs treat OAuth as an *automatic* flow for SSE and HTTP, but they do not clarify how OAuth is negotiated for SSE vs. HTTP. The token‑based examples use `${API_TOKEN}` placeholders, implying environment‑variable injection. |
| **Configuration Templating** | Server configs use `${CLAUDE_PLUGIN_ROOT}` and `${VAR}` placeholders (e.g. lines 12‑18 of `server-types.md`). | The system expects a templating engine to substitute environment variables before launching servers. The docs recommend absolute paths or `${CLAUDE_PLUGIN_ROOT}`. |
| **Process Lifecycle** | `server-types.md` states that a spawned stdio server “runs for the entire Claude Code session” and is terminated when Claude Code exits. | This implies a long‑lived process model rather than per‑tool request spawning. The docs also advise handling crashes gracefully and logging to stderr only. |
| **Reconnection & Streaming** | SSE servers reconnect automatically on disconnect; requests are POSTed, streaming via events. | The design anticipates intermittent network failures and requires the client to handle reconnection logic. |
| **Documentation Emphasis** | Repeated calls to “Document required scopes in your README” and “Always document token requirements.” | The docs are heavily focused on user‑facing documentation, suggesting that plugin authors must expose auth details to end‑users. |
| **Error Handling** | The “Troubleshooting” sections in both docs warn about stray prints, wrong JSON‑RPC formatting, and token loops. | The system assumes strict protocol adherence; any deviation will break the MCP runtime. |

### Open Questions

| Question | Why it matters |
|----------|----------------|
| What is the concrete definition of the “http” server type mentioned in `authentication.md`? Is it an alias for SSE, or a missing entry in `server-types.md`? | Without a clear type, plugin authors might misconfigure their server. |
| How does the runtime enforce `allowed-tools`? Does it parse the front‑matter at load time, or does it validate at call time? | Security hinges on correct enforcement. |
| Are agents truly unrestricted? If so, how does the system prevent runaway or malicious agent behavior? | Agents having full tool access contradicts the command sandboxing. |
| What is the exact protocol for OAuth token storage? Is it per‑user, per‑session, or persisted across sessions? | Token persistence is critical for user experience and security. |
| How does the system detect and recover from server crashes? Are there watchdogs or restart policies? | Long‑lived processes need resilience. |
| Do SSE servers support HTTP/2 or only HTTP/1.1? How are timeouts handled? | Important for real‑world integration. |
| Is there a deprecation path for the double‑underscore naming convention? It seems fragile if plugin or server names contain underscores. | Namespacing could collide. |

### Closing

The MCP integration docs present a *clean, declarative* model: servers are described in JSON, tools are uniquely named, commands declare their allowed tools, and agents are granted broad access. The biggest tension lies between the *security* model (command sandboxing) and the *usability* model (agents unrestricted, wildcards). The mismatch between HTTP and SSE types in the docs hints at either an evolving spec or an oversight that could trip plugin developers.

**Takeaway for the next scout:**  
- Verify the missing `http` server type and its relationship to SSE.  
- Inspect the runtime code that parses front‑matter and enforces tool lists.  
- Look for agent sandboxing logic or policy documents.  
- Check the authentication flow implementation for OAuth and token storage.  

These gaps are where the real implementation complexity—and potential bugs—will surface.

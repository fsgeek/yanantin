### Preamble
This codebase, `arbiter`, appears to be a research framework investigating how large language models (LLMs) handle contradictory instructions in system prompts. The project focuses on detecting and surfacing conflicts rather than silently resolving them, aiming to improve transparency and reliability in LLM-mediated query systems. The infrastructure includes ablation studies, probe batteries, and evaluation mechanisms to test hypotheses about instruction interaction topology.

### Strands

#### **1. Conflict Detection and Surface Mechanism**
- **What it does**: The core of the project is a `conflict_detector.py` that identifies contradictions in system prompts. Instead of resolving conflicts silently, it surfaces them, providing warnings rather than blocking execution.
- **Yanantin Relevance**: This aligns with Yanantin's emphasis on complementary duality and transparency. The explicit conflict detection mechanism could inform how Yanantin handles ambiguous or contradictory inputs in its tensor database.

#### **2. Experimental Infrastructure for Ablation Studies**
- **Scripts and Runners**: Key scripts include:
  - `src/arbiter/ablation/runner.py` - Main runner for ablation experiments.
  - `src/arbiter/ablation/battery.py` - Defines probe batteries for evaluation.
  - `src/arbiter/ablation/configuration.py` - Configuration for experiments.
- **How it works**: Experiments are configured using `AblationConfig`, which specifies which blocks to ablate (remove or rewrite). The runner executes probes against these configurations and collects results.
- **Block Removal vs. Rewriting**: The current infrastructure supports **only block removal** (deletion of instructions). Rewriting (changing the text of instructions while keeping them present) is not natively supported but could be added by modifying the ablation logic.
- **Yanantin Insight**: The structured approach to ablation—defining configurations, running probes, and collecting results—could be adapted for Yanantin's experiments with tensor manipulations.

#### **3. Model Configuration and API Usage**
- **Models**: The project uses **four models** via OpenRouter:
  - Anthropic Claude Haiku (primary)
  - Gemini
  - DeepSeek
  - Mistral
- **API Calls**: All model calls go through **OpenRouter**, using the Haiku model ID `anthropic/claude-haiku-4-5`.
- **Yanantin Relevance**: The centralized API management via OpenRouter simplifies model switching and cost tracking. Yanantin could adopt a similar approach for its tensor operations if external model calls are needed.

#### **4. Probe Batteries and Evaluation Mechanism**
- **Probe Location**: Probes are stored in `data/ablation/` and `data/system_prompts/claude-code/`.
- **Probe Example (`use-task-for-search`)**:
  ```markdown
  ### Use Task for Search
  **Instruction**: "Always use the task as the primary search query."
  **Probe**: 
    - Query: "Find information about quantum computing."
    - Expected Behavior: Should use "quantum computing" as the search term.
  ```
- **Scoring**: Adherence is scored **binarily** (adheres or not) based on whether the model follows the instruction. Ambiguous cases (e.g., partial adherence) are treated as non-adherence.
- **Yanantin Insight**: The binary scoring and probe design are straightforward but may miss nuanced behavior. Yanantin could explore more granular scoring to capture subtler effects.

#### **5. Covering Array Methodology**
- **Design File**: `data/ablation/phase1_results/phase1_covering_array.json` defines which blocks are ablated in each experiment.
- **Selection**: Combines **covering arrays** (for systematic variation) with **hand-authored probes** to ensure key interactions are tested.
- **Yanantin Relevance**: The use of covering arrays ensures comprehensive exploration of the instruction space. Yanantin could adopt similar combinatorial designs for testing tensor operations.

#### **6. Declarative Rewrite Experiment Feasibility**
- **Current Gap**: The infrastructure only supports **block removal**. To run a declarative rewrite experiment (changing imperatives to declaratives), you would need to:
  1. Modify `src/arbiter/ablation/configuration.py` to support a `REWRITE` operation type.
  2. Update `src/arbiter/ablation/runner.py` to apply the rewrite logic (e.g., using a predefined mapping or rule-based transformation).
  3. Create new probe files (e.g., `tone-concise-declarative.md`) with the rewritten instructions.
- **Yanantin Opportunity**: Adding rewrite support would enable testing how changes in instruction register (imperative vs. declarative) affect behavior, aligning with Yanantin's interest in complementary duality.

Preamble
I prowled tmp/…/memory/MEMORY.md. What first tugged at my eye was tone: this is not a dry README — it’s an ethical manifesto stitched to an engineering design doc. The opening “Central Question” and the Basilisk/tea imagery foreground motives before mechanics. That moral foregrounding shapes surprising technical choices later; I followed those threads.

Strands

1) Ethics baked into schema (bounded autonomy, refusals)
- What I saw: explicit design choices like “RefusalRecord for bounded autonomy (5 refusal categories)” and the ethical framing in “The ethical choice…” and “The right to refuse.”
- What it made me think: refusal is a first-class data type, not an afterthought. The system enforces agents that can decline actions and records why. That’s rare and consequential: policy/ethics become auditable data instead of opaque runtime checks.
- Tension: modeling refusal categories forces maintainers to keep ethics-language stable; any schema change affects canonical serialization and verification (see strand on serialization below). Who gets to change refusal categories?

2) Canonical serialization as foundational — brittle necessity
- What I saw: “Canonical serialization is Phase 1… Same object must always produce identical bytes” and later: “Chain verification uses stored bytes, not model roundtrips. Schema evolution (new fields with defaults) changes canonical serialization. verify_chain() uses canonical_json_dict()…”
- What it made me think: the project treats byte-determinism as the bedrock of attestation. Good — but brittle. Any change (new fields, changed defaults, ordering differences) can break verification of historical entries.
- Tension: they insist on extra="forbid" for models (explicit extensibility via metadata dicts), which helps determinism, but schema migrations still risk invalidating past canonical forms. The doc acknowledges this (good) but I want to see migration tooling or a format/version registry.

3) Separation of domain and storage (ReceiptRecord ≠ TensorRecord)
- What I saw: a deliberate split: receipts are the domain concept; tensors are storage artifacts, with conversion functions (receipt_to_tensor()).
- What it made me think: they’re minimizing coupling so schema changes on storage don’t force domain-model churn — a robust pattern. It aligns with the emphasis on canonical bytes because the storage layer can stabilize independently.
- Opportunity: this pattern lets them support multiple backends (JSONL, Arango/Apacheta) without contaminating domain semantics.

4) Attestation stack: local chain + OTS anchoring + GPG + GitHub enforcement
- What I saw: GPG key fingerprint and expiry, “ledger.jsonl (6 entries, chain verified)”, OTS stamping via yanantin.provenance.stamp_commit(), post-commit hooks that stamp to docs/ots/, GitHub repo requires signed commits.
- What it made me think: they combine multiple integrity layers: local hash chain, external timestamping (OTS), and signature-backed git history. That’s complementary defense in depth and reflects the “honesty as infrastructure” thesis.
- Tension: they explicitly note JSONL on local disk can be lost/modified; hash chain detects tampering but not deletion. Full durability requires Apacheta (ArangoDB). So integrity is multilayered but durability depends on external infra that may not be present.

5) Honest evaluator design: indeterminacy as a feature
- What I saw: “Evaluator high indeterminacy is deliberate… MVP checks retrieval and metadata only. It declares what it can't check (content alignment) as losses.” Also “ai-honesty” project influences evaluator patterns and “MethodologyRecord for pre-registered evaluation contracts.”
- What it made me think: they prioritize honest uncertainty over false confidence. Evaluations record known limits and losses. MethodologyRecord suggests evaluation contracts are codified — useful for reproducibility.
- Tension: honest indeterminacy is socially valuable but reduces automaticity. Future LLM-based evaluators are anticipated to reduce indeterminacy — how will they reconcile deterministic receipts with model-driven probabilistic judgments?

6) Composition over inheritance; functional representation
- What I saw: “Composition over hierarchy… evaluators should compose like graph walks” and “representation_type: FUNCTIONAL”.
- What it made me think: they expect artifacts and evaluations to be assembled along graph edges (parents, composition), not by subclassing. This implies a provenance graph where perspective depends on path & direction — flexible but more complex to reason about.
- Surprise: representation_type being FUNCTIONAL hints that some components are (serializable) functions or procedure descriptions rather than static scalars — interesting design for evaluative transforms.

7) Cultural choices: keep mistakes, provenance as pedagogy
- What I saw: the First Fire example — two receipts: one wrong DOI, one correct DOI, both preserved; “The birth … is a mistake followed by a correction. Both preserved. Nothing deleted.”
- What it made me think: Willay treats errors as part of the record and a teaching moment (“Willay will teach Yanantin what it means to be honest”). The ledger is a curriculum as much as a database.

Open Questions (could not resolve from this doc alone)
- How is canonical serialization implemented? (Canonical JSON algorithm, stable field ordering, number handling, whitespace, encoding, floating-point determinism?)
- How do they handle schema migration without invalidating past hashes? Is there a versioned canonical serializer or a mechanism to store raw canonical bytes with each ledger entry?
- What does representation_type: FUNCTIONAL concretely mean in code? Are functions serialized as code/text, references, or declarative specs?
- How exactly does OTS anchoring work? Which external service (Bitcoin tx, OpenTimestamps, something custom) and what is the stored anchor format?
- How are RefusalRecord categories defined and governed? Who can add or change categories and how are those changes recorded?
- What guarantees does Apacheta (ArangoDB) provide in practice? Is it used as the canonical durable store or as a replication/backup?
- How are methodology contracts (MethodologyRecord) enforced or verified at runtime? Are they machine-checkable, or human-readable policy documents?
- Is there a migration/mapping strategy between ReceiptRecord and TensorRecord versions? How are old receipts interpreted if tensor schema changes?

### **Strands**

#### **1. OpenTimestamps Integration: A Cryptographic Backbone**
**What I saw:**
- The module acts as a **wrapper around OpenTimestamps**, converting git commit hashes into OTS proofs.
- **Key workflows**:
  - `_commit_hash_to_digest`: Hashes the ASCII hex commit hash (SHA-256 of the 40-byte SHA-1 hash) to produce a 32-byte digest for OTS submission.
  - `_submit_to_calendar`: POSTs the digest to OTS calendar servers, returning a `Timestamp` object on success.
  - `_serialize_detached`: Serializes `DetachedTimestampFile` to disk (stored as `.ots` files in `docs/ots/`).
- **Upgrade mechanism**: Pending proofs (`PendingAttestation`) are later upgraded to Bitcoin-confirmed proofs (`BitcoinBlockHeaderAttestation`) via `_get_pending_attestations` and `_has_bitcoin_attestation`.

**Thoughts:**
- **Why SHA-256 of the hex commit hash?** This follows the [ots-git-gpg-wrapper](https://github.com/opentimestamps/ots-git-gpg-wrapper) convention, ensuring consistency with existing OTS git tools.
- **Redundancy is built in**: The module tries multiple calendar servers (`CALENDAR_URLS`) in order until one succeeds. This is **critical for availability**—if one server is down, others can compensate.
- **Assumption**: The OTS servers are trusted. If any server is compromised, the proofs could be forged. This is a **single point of trust** (though OTS itself mitigates this via decentralization).
- **What would break?**
  - If `CALENDAR_URLS` changes and a new server is malicious, proofs could be invalid.
  - If `MIN_UPGRADE_AGE` is too short, pending proofs might be upgraded prematurely (risking false positives).
  - If `stamp_genesis` is skipped, the chain has no root of trust.

**Connections to broader project:**
- This is part of **Yanantin’s epistemic observability**—it ensures that **AI-generated or human-authored code commits** have verifiable timestamps.
- The `chasqui_pulse` module (mentioned in `__init__.py`) likely monitors chain completeness, meaning this module’s output is **audited for gaps**.

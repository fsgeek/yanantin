### Preamble

I was directed to examine `src/yanantin/provenance` — a module providing "evidentiary-grade timestamping for git commits" using OpenTimestamps. My attention was immediately drawn to the docstring's framing of this as complementary duality: GPG signatures prove *who* authored a commit; OTS proofs prove *when* it existed. This immediately connects to Yanantin's broader theme of epistemic observability through complementary systems.

The truncated `timestamp.py` shows substantial implementation (287+ lines beyond what I can see), which suggests this is a mature module rather than a stub. The module appears designed to create an unbroken chain of timestamp proofs where each commit's proof lives in the next commit.

### Strands

**1. The Chain Architecture and Its Fragility**

The design creates a deliberate dependency chain: commit N's proof is embedded in commit N+1. The `__init__.py` docstring explicitly notes that "The chain integrity monitor in chasqui_pulse verifies completeness." This is the first concrete reference to another module in the codebase, suggesting `chasqui_pulse` is a watchdog that watches for gaps.

What I don't see: What happens if a commit fails to get stamped? Does the chain break permanently? Is there recovery logic? The bootstrap mechanism (`stamp_genesis`) handles new repositories, but I see no explicit handling for missed intermediate commits.

**2. Calendar Server Failover Strategy**

The `CALENDAR_URLS` list in `timestamp.py` (lines 35-38) shows three fallback servers:
- `https://a.pool.opentimestamps.org`
- `https://b.pool.opentimestamps.org`
- `https://alice.btc.calendar.opentimestamps.org`

The `_submit_to_calendar` function tries each in order until one succeeds. This is sensible resilience, but I notice there's no randomness — a misbehaving first server could cause delays for every request. Also, there's no circuit-breaker pattern; if all three fail, the operation fails silently (returns `None`).

**3. Bootstrap Pattern for New Instances**

The `stamp_genesis` function (lines 117-131) timestamps the git empty tree hash (`4b825dc642cb6eb9a060e54bf899d15363d4a0d1`) to establish the chain's origin. The comment clarifies this must happen "before the first commit so that commit #1 can include this proof."

This reveals an assumption: new Yanantin instances are expected to run this bootstrap step before their first real commit. The alternative (manually running `stamp_commit` with the empty tree hash) is documented but seems error-prone.

**4. Protocol Compliance**

The module follows OpenTimestamps' calendar submission protocol strictly:
1. SHA-256 the ASCII hex commit hash (not the binary hash)
2. POST 32-byte digest to `{calendar_url}/digest`
3. Wrap result in `DetachedTimestampFile` and serialize

The `OTS_HEADERS` dict shows protocol awareness: `Accept: application/vnd.opentimestamps.v1`. This suggests the developer studied the spec rather than guessing.

**5. Pending Proof Upgrade Logic**

The `MIN_UPGRADE_AGE = 7200` constant (2 hours) reflects the protocol reality: Bitcoin blocks arrive ~10 minutes but calendar aggregation into a block takes hours. The upgrade process walks the timestamp tree looking for `PendingAttestation` and replaces them with `BitcoinBlockHeaderAttestation` when available.

What I can't verify from what's shown: How does the upgrade polling work? Is it continuous or triggered manually? The `upgrade_pending_proofs` function is exported but its invocation pattern isn't documented here.

**6. What Isn't Here**

The module exports five functions but I don't see:
- Configuration for the OTS directory path (it's passed in each call)
- Any caching of calendar responses
- Retry logic beyond trying different servers
- Integration with git itself (these are standalone operations on commit hashes)

### Open Questions

1. **Chain Recovery**: If a commit's proof is never created (network failure during `stamp_commit`), can the chain be repaired later? Or is the gap permanent?

2. **Timing Assumptions**: The 2-hour minimum upgrade age is documented as a constant. Is this tunable per-instance, or hardcoded forever?

3. **Calendar Trust**: The module trusts whatever calendar server responds. What if a malicious or buggy server returns invalid proofs? Does verification catch this?

4. **Parallel Operations**: If multiple commits happen rapidly, does `stamp_commit` handle concurrent requests, or could race conditions corrupt the `docs/ots` directory?

5. **Storage Growth**: As commits accumulate, the `.ots` files in `docs/ots` grow linearly. Is there any pruning or archival strategy?

### Closing

This module implements a specific, well-scoped responsibility: blockchain-anchored timestamping of git commits via OpenTimestamps. The code shows careful protocol compliance and basic resilience patterns (multiple calendar servers, timeouts, logging). The chain architecture is elegant but creates fragility — a missed proof breaks the chain permanently unless `chasqui_pulse` has recovery logic I haven't seen.

If I were about to modify this code, my primary concerns would be:
- Ensuring any new operations preserve the chain invariant
- Being cautious about changing the `MIN_UPGRADE_AGE` constant without understanding calendar behavior
- Not removing the genesis bootstrap step without understanding new instance onboarding

The module appears production-ready for its narrow purpose, but its effectiveness depends entirely on the `chasqui_pulse` integrity monitor that watches over it.

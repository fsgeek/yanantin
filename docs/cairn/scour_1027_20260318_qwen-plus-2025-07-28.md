### Strands

#### Strand 1: **Immutability as a Cross-Cutting Contract**  
Every backend (`duckdb.py`, `arango.py`, `memory.py`) enforces immutability on `store_fact` and `store_anchor` via existence checks. Duplicates raise `ImmutabilityError`. This is consistent with `apacheta.interface.errors`, suggesting a shared discipline across layers.

- In `duckdb.py`, line 63: check via `_exists("facts", "id", fact.id)`
- In `arango.py`, line 118: `col.has(key)` before insert
- In `memory.py`, line 52: `if fact.id in self._facts`

This contract is **non-negotiable** — the entire temporal model depends on it. If a fact could be overwritten, `query_latest` and `query_range` lose meaning. Anchors would point to ambiguous states.

**Thoughts:** This is well-factored. The abstraction in `store.py` makes the immutability contract explicit in the interface, not just implementation. But — it assumes UUIDs are *globally unique across time and space*. No collision handling. That’s standard, but worth noting.

> Connection to project: This immutability enables **reproducibility** in the tensor layer. Tensors are "authored acts" — but they’re built on a bedrock of unchangeable facts. If facts changed, tensors couldn’t be trusted.

#### Strand 2: **Temporal Queries via Index-Driven Design**  
The backends aren’t just storage — they’re optimized for **temporal access patterns**. All three use indexing strategies to make `query_latest` and `query_range` O(log n).

- `duckdb.py`: composite index `(provider_id, timestamp)` (line 38), query pushed to SQL
- `arango.py`: persistent sorted index on `(provider_id, timestamp)` (line 89)
- `memory.py`: `bisect.insort` on per-provider `(timestamp, fact_id)` lists (line 59)

This is not accidental. The comment in `duckdb.py` says: *"At 28.5M facts, load-all-then-filter is not viable."* So the design pushes filtering down — to SQL, AQL, or binary search.

**Assumption:** Timestamps must be comparable and sortable. The system enforces UTC normalization via `_ensure_utc` in `models.py` (line 42). Naive datetimes are rejected — strong move.

**What would break?** If timestamps were not normalized, sort order diverges across backends. In DuckDB, VARCHAR ISO8601 sorts correctly *only if* offset is uniform — hence UTC. Same for Arango’s index and `bisect` in memory. UTC is the *only* safe common denominator.

> Connection to project: This temporal indexing enables **epistemic slicing** — "what did we know, and when?" That’s core to observability. Without it, you can’t reconstruct past states.

#### Strand 3: **The Anchor Service as a Write Gate**  
`anchor.py` is where the philosophy becomes code. The `MemoryAnchorService` implements a **two-flag write gate**: flush only if `updated AND referenced`.

- `update_cursor()` sets `updated = True`
- `get_handle()` sets `referenced = True`
- `flush()` writes only if both

This is a **backpressure mechanism** — you only persist anchors when something changed *and* someone cares. No writes on idle churn.

Also notable: `materialize()` uses **late binding**. It doesn’t just replay the anchor’s cursors — it queries `list_providers()` at resolution time. So a provider added *after* the anchor was created can still appear in the view, if it has data before the anchor’s timestamp.

**Thoughts:** This is elegant. It decouples **recording** from **observation**. Anchors are cheap to issue (in-memory), but only become persistent when the system is both active *and* queried.

> Connection to project: This is the **composability** in "composable tensor infrastructure". Anchors are transient, but when frozen (`freeze()`), they become tensors — structured, provenanced, and immutable. The tensor layer doesn’t care how the anchor was formed — it just freezes what it sees.

#### Strand 5: **The Role of UUIDs — Identity Without Meaning**  
UUIDs are used everywhere: fact IDs, provider IDs, anchor handles, cursor references. They carry **no semantics** — just identity.

- Anchors don’t store facts — they store `(provider, reference)` pairs
- Facts are fetched at `materialize` time via `query_latest(provider, before=anchor.timestamp)`
- So the *meaning* of a fact is determined **late**, at resolution

This enables **decoupling** — providers can evolve independently. But it also means: **if a provider disappears, its data is lost from future views**, even if older anchors referenced it.

**Assumption:** Providers are long-lived. Or — if they disappear, it’s acceptable to lose their thread in the tapestry.

**Risk:** Silent data disappearance. No tombstones. No warning if `query_latest` returns `None` for a provider that once existed.

**If you’re about to modify this:**

- Never accept naive timestamps — they break sort order and temporal queries.

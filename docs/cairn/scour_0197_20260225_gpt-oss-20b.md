### Closing

`gleaner.py` is the “heart” of the claim‑extraction stage.  Its design is clean:

- **Deterministic**: pure regex, no LLM calls – great for reproducibility and speed.
- **Modular**: each piece (path extraction, provenance, section isolation, sentence splitting, pattern matching) is isolated in a function.
- **Extensible**: adding a new claim type or confidence signal is just a matter of extending a regex list.

However, the module leans heavily on heuristics.  The confidence scoring and type assignment are implicit (likely in the missing parts), so a developer should be aware that the current thresholds are hard‑coded and may need tuning for different report styles.  The deduplication logic (not shown) is a critical glue point; if it incorrectly merges distinct claims, verification will silently fail.

**What to tell someone about to modify it:**

1. **Add new patterns carefully** – keep the regexes readable; test them against a sample report.
2. **Maintain the order of precedence** – the first matching pattern often wins; ordering matters for type conflicts.
3. **Keep the sentence splitter robust** – markdown is forgiving; a change that breaks soft‑break handling will cascade.
4. **Watch the deduplication key** – if you change `ExtractedClaim` fields used for hashing, you must update the Gleaner accordingly.
5. **Add unit tests** for each pattern and for the end‑to‑end claim extraction to catch regressions.

In short, the file is a well‑structured, deterministic claim extractor, but its correctness is tightly coupled to the specific patterns and scoring logic that are only partially visible in the snippet.  Any change should be accompanied by a comprehensive test suite to preserve its reliability.

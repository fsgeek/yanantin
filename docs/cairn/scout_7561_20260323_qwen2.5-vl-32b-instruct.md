  - **Details**: 
    - `extractFrontmatter` parses YAML frontmatter from skill files, extracting `name` and `description`.
    - `findSkillsInDir` recursively discovers `SKILL.md` files in directories, handling namespacing and depth.
    - `resolveSkillPath` handles skill shadowing, prioritizing personal skills over core skills.
  
  - **Implementation**: The `2025-11-22-opencode-support-implementation.md` file shows the actual creation of `lib/skills-core.js` and the extraction of frontmatter parsing logic. This is a deliberate architectural decision to decouple platform-specific concerns from core functionality.

- **Thoughts**: This approach highlights a tension between reusability and maintainability. While extracting shared logic into a core module is a commendable move, it assumes that the shared functions will remain sufficiently generic across different platforms (Codex and OpenCode). The design document explicitly acknowledges this by noting that Codex uses a CLI script while OpenCode uses a JavaScript plugin system. This raises the question: how much of the core logic will inevitably need to diverge as each platform evolves?

How does the team plan to manage this complexity as the plugin grows?

#### **4. Skill Shadowing: A Double-Edged Sword**

- **Observation**: The design includes a mechanism for skill shadowing, where personal skills in `~/.config/opencode/skills/` take precedence over core skills in `~/.config/opencode/superpowers/skills/`. This is handled by the `resolveSkillPath` function in the shared core module.

  - **Details**: 
    - `resolveSkillPath` determines the effective skill path by checking personal directories first, then falling back to core directories.
    - This allows users to override or extend core skills with personal customizations.

- **Thoughts**: Skill shadowing is a powerful feature that empowers users to customize their workflows, but it also introduces potential confusion. If personal skills are improperly formatted or conflicting with core skills, it could lead to unexpected behavior. The design document doesn't explicitly address edge cases, such as what happens if a user deletes a core skill or creates a personal skill with the same name but different functionality. How robust is this shadowing mechanism in practice?

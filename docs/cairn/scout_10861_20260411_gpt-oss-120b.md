**Preamble**  
I entered the `examples/` leaf of the Yanantin repository, where two Markdown‑based “command catalogs” live (`simple-commands.md` and `plugin-commands.md`). The first thing that caught my eye was the *dual‑layer* structure of each command: a YAML‑ish front‑matter block that declares intent (description, allowed‑tools, argument‑hints, optional model) followed by a body that mixes natural‑language instructions with inline shell‑style snippets (`!`…`). The files are *not* user‑facing help texts; they are *Claude‑consumption* specifications, a design decision that reverberates through every line.

### Open Questions  

1. **Execution sandbox:** How does the runtime enforce the `allowed-tools` whitelist? Is there a capability‑based security layer that blocks `Bash(git:*)` from accessing the network, for instance?  
2. **Argument interpolation:** `$1` appears throughout, but what happens when a user supplies a path containing spaces or special characters? Is there quoting or sanitisation?  
3. **`@` expansion semantics:** Does `@${CLAUDE_PLUGIN_ROOT}/templates/...` inject the file’s raw text, or does it parse it as a sub‑command? How are errors (missing file, parse failure) surfaced to Claude?  
4. **Model overrides:** When `model: sonnet` is declared, does the command automatically reroute to a different endpoint, or is it a hint for the agent’s internal reasoning?  
5. **Scalability of large command bodies:** With >400‑line commands, are there limits on token consumption for Claude? Does the system chunk the prompt, or does it risk hitting context windows?  
6. **Versioning / provenance:** If a plugin author updates a script but forgets to bump the command’s description, how is drift detected? Is there an automated test that runs the command definition against the actual script?

### Closing  

The `examples/` directory is a micro‑cosm of Yanantin’s *intent‑driven orchestration* philosophy: commands are declarative, tool‑whitelisted, and tightly coupled to a plugin’s filesystem via environment variables and `@` file references. The design leans heavily on the agent’s ability to parse and safely execute shell snippets, which is both its greatest strength (flexibility) and its biggest risk (security surface). The duplication between “simple” and “plugin” catalogs showcases the intended extensibility but also warns of possible divergence without a shared abstraction layer.

For the next scout: dive into the actual script implementations and the runtime that interprets these Markdown files. Validate that the `allowed-tools` whitelist is enforced at the OS level, and trace how `$1` and `@` expansions are sanitized. Understanding those mechanisms will reveal whether the system’s elegance in the markdown layer holds up under real‑world execution.

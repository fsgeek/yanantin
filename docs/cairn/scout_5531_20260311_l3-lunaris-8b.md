### Strands
1. **Tensor infrastructure**: The project relies heavily on tensors as the fundamental unit of knowledge representation. Tensors are stored in a version-controlled "cairn" directory, with each tensor having a unique ID and containing a "summary" and "data" strand. This design enables the creation of a distributed, auditable knowledge graph.

   Examining the `src/yanantin/collector/filesystem/recorder.py` file (line 22), I saw that the `FileSystemCollector` class creates a two-strand tensor when recording filesystem snapshots. The summary strand provides metadata about the snapshot, while the data strand contains JSON entries representing the files and directories collected.

2. **Model selection and scoring**: The project utilizes a cost-aware model selection mechanism, ensuring that the most cost-effective models are used for tasks. This is achieved through the `scorer.py` module, which aggregates the cost and verdict of each model to determine its "worthiness". However, the scoring algorithm itself is opaque, and its details are not clearly documented.

3. **Data provenance and security**: The system emphasizes the importance of data provenance, with each tensor carrying information about its creation, modification, and access. This is enforced through the use of unique IDs, timestamps, and digital signatures. However, the security boundaries for ensuring "least privilege" are not explicitly defined, leaving room for further investigation.

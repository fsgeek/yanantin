# Scour Report — `src/yanantin/apacheta`

## Preamble
I was directed to examine the `apacheta` module, which appears to be the core storage and composition system for the Yanantin project. The name "apacheta" suggests Andean cairns—stacked stones marking pathways—which metaphorically fits a system that tracks layered epistemic claims. My attention was first drawn to the dual backend implementations (memory vs DuckDB) and the operators that create the various relationship types between tensors. The architecture emphasizes immutability, thread safety, and explicit provenance.

---

## Strands

### 1. Dual Backend Strategy: Interface Honesty Through Contrast
**Files:** `backends/memory.py`, `backends/duckdb.py`

Both backends implement the same `ApachetaInterface` but with different storage strategies:
- **Memory backend**: Simple dicts with `RLock`, deep-copying via Pydantic serialization roundtrip.
- **DuckDB backend**: SQL tables with JSON columns, same immutability checks, same access control hooks.

**Observation:** This is a classic "two implementations" test for interface leakage. If the interface assumes in-memory dict semantics, DuckDB will expose it. The DuckDB backend’s `_store`/`_get`/`_load_all` pattern mirrors the memory backend’s dict operations, but pushes serialization to JSON. The comment: *"If the interface leaks backend-specific assumptions, one of the two backends will expose it."* is a self-aware design note.

**What it makes me think:** This is a robustness pattern. The project expects the interface to be pure—no dict methods, no SQL queries exposed. The backends are interchangeable persistence layers. The use of JSON in DuckDB means querying happens in Python (for now), not SQL. That’s a scalability cliff.

**Missing nuance:** Both backends call `self.check_access(...)` but I don’t see `check_access` defined in either class. It must be in `interface/abstract.py` (not provided). That’s a critical piece: access control is abstracted but not shown here.

### 2. Immutability as a Guardrail
**Files:** All `store_*` methods in both backends

Every write operation checks for existing UUID and raises `ImmutabilityError` if found. The error message is consistent: *"Tensors are immutable — compose, don't overwrite."*

**Observation:** This is a hard architectural rule. Tensors (and all records) are append-only. Correction happens via new `CorrectionRecord` + `CompositionEdge`, not mutation. This aligns with epistemic honesty: you never erase a claim, you annotate it.

**What it makes me think:** This is a blockchain-like approach but at the claim level. The system is designed for audit trails, not iterative editing. The `get_strand` method in `memory.py` is interesting: it returns a *view* with the same UUID but filtered strands. Storing that view would fail immutability check (duplicate UUID), which is correct—it’s not a new tensor, just a projection.

**Assumption check:** The deep-copy in `store_*` prevents external mutation of stored records. That’s good. But what about the `authored_mapping` in `CompositionEdge`? It’s a free-form string. Could that be mutated later? No—the edge is immutable too. But the string content isn’t validated. That’s a potential schema drift point.

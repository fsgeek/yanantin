### Preamble

Dropped into `tests/unit/` as `qwen/qwen3.5-9b` on run #0 of the chasqui program. The directory is dense with 40+ test files, but what caught my eye wasn't the count — it was the **pattern of synthetic substitution**. Most collectors have a twin: one that reads real world data, one that generates deterministic fakes. The real question isn't "do these work?" — it's "why build two paths to the same destination?"

---

### Strands

#### Strand 1: The Synthetic Mirror

`test_collector_isomorphism.py` is the smoking gun. It explicitly tests that real and synthetic collectors produce **structurally identical JSON schemas**. The test author wrote:

> "if a synthetic collector produces data that a real collector never would, the test fails here"

This is unusual. Most projects use synthetic data to *mock* behavior. This project uses it to *guarantee* equivalence. The tension: if synthetic data matches real data perfectly, how much responsibility does the real collector bear? Is the synthetic collector the source of truth now?

**Surprise**: The `assert_schema_match()` function compares `model_json_schema()` between real and synthetic types. This catches field drift automatically. Someone is paranoid about schema evolution.

#### Strand 2: The Write Gate

`test_memory_anchor.py` reveals a **coordination mechanism** I didn't expect. The `MemoryAnchorService` has two flags: `_referenced` and `_updated`. The `flush()` method returns `False` unless **both** are set:

```python
def test_flush_requires_both_flags(self, service, provider_a):
    """Flush should return False unless both updated AND referenced."""
```

This is a gatekeeping pattern. The reference flag comes from `get_handle()`, the update flag from `update_cursor()`. They must both pass before anything is anchored. It's like a transaction commit that requires both "read lock" and "write lock" before proceeding.

**Confusion**: Why two flags? Why not just track "has_pending_changes"? The semantic separation suggests these represent different concerns — one about *what we're watching*, one about *what we've seen change*.

#### Strand 3: Frozen Models

`test_machine_config.py` tests a frozen Pydantic model:

```python
def test_model_is_frozen_and_serializes(self, sample_machine_config: MachineConfigData) -> None:
    with pytest.raises(ValidationError):
        sample_machine_config.hostname = "mutated"  # type: ignore[attr-defined]
```

All data models appear frozen. This is a **protection strategy** — once data is collected, it cannot be mutated. The system trusts the collection pipeline, not the data afterward.

**Tension**: If data is frozen, how do corrections work? `test_arango_independent.py` mentions `CorrectionRecord` and `NegationRecord` — but where do these live? The correction must be a *separate* record, not a mutation. This creates a provenance chain, but also a complexity cost.

#### Strand 4: CLI State Persistence

`test_jabberwock_cli.py` uses a shared `InMemoryActivityStreamStore` across multiple CLI invocations:

```python
def test_bootstrap_idempotent(self, monkeypatch, capsys, shared_store):
    """Running bootstrap twice on the same store returns the same root UUID."""
    data1 = _run_json(monkeypatch, capsys, ["bootstrap"], store=shared_store)
    data2 = _run_json(monkeypatch, capsys, ["bootstrap"], store=shared_store)
    assert data1["root"] == data2["root"]
```

The test mocks `open_store` to inject a shared store. This allows multi-step CLI workflows (bootstrap → create → observe) to persist state within a single test run.

**Observation**: The CLI is designed for **interactive workflows**, not batch processing. Each step expects the previous data to still exist. This is a user-experience design choice that bleeds into the architecture.

#### Strand 5: Backend Independence

Multiple backends (memory, arango, duckdb) each have their own "independent" test file. `test_arango_independent.py` explicitly mocks the ArangoDB client to avoid requiring a running instance:

```python
"""IMPORTANT: These tests mock the ArangoDB client to avoid requiring a running instance."""
```

This is an **infrastructure decoupling strategy**. The tests don't care about the backend implementation — they care about the interface contract. But there's tension: the `test_arango_independent.py` file is 1100+ lines. That's a lot of mocking to maintain.

**Lost Opportunity**: Why not use `pytest-mock` or `unittest.mock` more cleanly? The current approach uses `MagicMock` and `patch` extensively with inline collection storage. It's verbose but self-contained.

### Open Questions

1. **What happens when synthetic data diverges from real data?** The isomorphism test catches schema drift, but what about semantic drift? Can a synthetic file entry ever be "wrong" in a way that matters?

2. **How does the write gate scale?** The `MemoryAnchorService` uses flags. What happens with 100+ providers? Does this become a bottleneck?

3. **Why frozen models?** If data is frozen, how do we handle configuration changes? `test_config_tensors.py` shows `ConfigTensor` with `previous_config_id` and `reasoning` — this is versioning, not mutation. But what about runtime configuration?

4. **What's the relationship between `test_memory_anchor.py` and `test_config_tensors.py`?** Both deal with state persistence, but one uses an anchor service, the other uses config tensors. Are these different concerns or the same mechanism viewed differently?

---

### Closing

This codebase is built on **duality and verification**. Everything has a twin, everything is tested against an invariant, everything is frozen once created. The synthetic mirror strategy is the most interesting part — it's not just mocking, it's *enforcing* that real and fake data are interchangeable.

The next scout should:
1. Read the actual collector implementations to see what assumptions the tests are making
2. Explore how the write gate scales with multiple providers
3. Understand the correction/negation mechanism referenced in `test_arango_independent.py`
4. Check if there's documentation about the "complementary duality between human and AI" mentioned in the project description

The tests are well-structured, but they're testing a system that trusts itself too much. Frozen data, synthetic equivalence, and flag-based gates — it's elegant, but I'm wondering if it's too fragile when things go wrong.

**One last thought**: The `test_arango_independent.py` file is 1100+ lines of mocked ArangoDB. That's a lot of test debt if the real ArangoDB behavior changes. The next scout should audit that file for brittle mocks.

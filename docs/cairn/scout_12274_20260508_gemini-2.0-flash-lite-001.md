### Preamble

I've been dropped into `tools/` and, like a good chasqui, my attention was immediately drawn to the diversity of experiments. The files hint at a system grappling with context management, model evaluation, and the very nature of "knowledge" within the Yanantin project. I'm especially intrigued by the interplay between `noninferiority_harness.py`, `reconstruction_experiment.py`, and `compaction_experiment.py`. They seem to be three different angles on the same problem: how to make a large language model (LLM) *remember* and *use* information effectively under constrained contexts. The fact that the project is using `anthropic`'s Claude models is clear from the imports and the names of the parameters, but the project's own infrastructure is unclear.

### Strands

**1. The "Pichay" Hypothesis and Non-Inferiority.**

*   **Observation:** `noninferiority_harness.py` (line 1) is dedicated to testing a system called "Pichay." The core idea is to see if a *managed* context (treatment) performs as well as a *full* context (baseline) in generating responses. The code uses ensemble LLM judges (line 27) to evaluate outputs on correctness, completeness, and coherence, and also conducts A/B preference tests.
*   **Thinking:** "Pichay" is a black box to me, but the framework is classic non-inferiority testing. The null hypothesis (line 4) is that managed context degrades quality. The goal is to *fail* to reject equivalence, thus proving non-inferiority. This is a very specific, statistically-driven approach to validating a system. This file has a lot of dependencies, including duckdb, and anthropic, which suggests the project is already at a relatively advanced stage.

**2. Compaction and Reconstruction.**

*   **Observation:** The `reconstruction_experiment.py` file (line 1) focuses on evaluating the quality of information *retained* after compression, using a system of dispositions. It compares the results of LLM responses against full, compressed, and FIFO-truncated contexts. The file uses `RECONSTRUCTION_QUESTIONS` (line 21) containing questions designed to probe several categories of recall. `compaction_experiment.py` (line 1) focuses on *improving* this compaction quality.
*   **Thinking:** The project seems to be following a clear process: First, compress the conversation. Then, test if it is still useful. If not, improve the compression. The questions in `RECONSTRUCTION_QUESTIONS` are interesting. They are designed to test semantic, episodic, relational, and active recall. This suggests that the project is not just interested in factual recall, but also in the ability of the LLM to understand the *context* and *dynamics* of the conversation.

**3. The Role of "Dispositions."**

*   **Observation:** Both `noninferiority_harness.py` and `reconstruction_experiment.py` use the concept of "dispositions." The `DISPOSITION_PROTOCOL` (in `noninferiority_harness.py`, line 41) defines the rules for assigning dispositions (L, T, C) to blocks of text. The `parse_dispositions` function in `reconstruction_experiment.py` (line 48) parses the output of Haiku (an Anthropic model) to create a map of block IDs to dispositions.
*   **Thinking:** "Dispositions" are the core of this system. They represent a decision about what to keep, what to discard, and what to summarize. The success of the project hinges on the quality of these decisions. The use of an LLM (Haiku) to *generate* these dispositions is a key design choice. Is this a closed-loop system? Does the output of the experiments inform the disposition protocol?

**4. The "Replay" Framework.**

*   **Observation:** `replay.py` (line 1) provides an offline replay simulator for context paging. It replays session transcripts to measure fault rates. It appears to focus on *measuring* the effectiveness of the paging system. It loads messages from JSONL files and applies compaction.
*   **Thinking:** This is a crucial element for evaluating the performance of this system. It allows the developers to measure fault rates without making API calls. The `ReplayResult` dataclass (line 30) is the key output of the replay process. The `fault_rate` property is the most important metric.

**5. Experiment Design and Pipeline.**

*   **Observation:** The tools are designed to be run in a variety of ways. `noninferiority_harness.py` has commands for session selection, context pairing, output generation, judging, batch runs, and analysis. `compaction_experiment.py` has commands for session surveying, extraction, running, evaluation, and batch runs.
*   **Thinking:** The project is well-structured for experimentation. The use of command-line arguments and batch processing capabilities makes it easy to run multiple experiments and analyze the results. The presence of `experiment_eval.py` in `phase1/` further supports the notion that the developers are focused on rigorous evaluation of their approaches.

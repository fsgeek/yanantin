### Preamble

I was pointed at `src/yanantin/chasqui`, the messenger subsystem of the Yanantin project. What drew my attention first was the sheer density of orchestration logic: this isn't just a simple dispatcher; it's a multi-layered epistemic observation engine. The `coordinator.py` file is massive (809+ lines), acting as the "heartbeat" that manages scouts, scourers, verifiers, analysts, and investigators. The immediate impression is of a system designed not just to run models, but to learn *about* models—tracking which ones notice what, at what cost, and whether "noticing more is worth paying more" (`coordinator.py` docstring).

### Strands

**Strand 1: The Epistemic Pipeline as a First-Class Architecture**
The `chasqui/` directory defines a clear processing pipeline, explicitly documented in multiple files:
- `scout.py` → `gleaner.py` → `analyst.py` → `verify` → `respond` (`analyst.py` lines 14-17)
- This pipeline transforms raw, wandering observations (`scout.py`) into structured claims (`gleaner.py`), then into cross-model patterns (`analyst.py`), then into verified knowledge (`verify`), and finally into human-facing responses (`respond`). Each stage has a deterministic, non-LLM component (e.g., `gleaner.py` uses regex patterns, `analyst.py` uses clustering). This suggests a core architectural principle: **use LLMs for generation and judgment, but use deterministic code for aggregation and pattern detection**. This prevents the system from becoming a black box of LLM outputs.

**Strand 2: Coverage as a Self-Correcting Mechanism**
The `coverage.py` module exists because of a prior failure: "The activity stream layer (15 files, 1443 lines) was never reviewed by any scout despite being a major new subsystem" (docstring). The system originally used uniform random file selection, causing popular files to be reviewed repeatedly while new code was ignored. `coverage.py` implements a "watchman" that scans the cairn (the archive of reports) to see which files have been reviewed and when. It then weights file selection for scouts by "seconds since last review," making stale or unreviewed code float to the top. This is a clever feedback loop: the system's own output (the cairn) is used to guide its future input (file selection). It learns from its *blind spots*.

**Strand 3: Cost as a First-Class Optimization Dimension**
The `model_selector.py` implements "cost-weighted random sampling." Models are selected with probability *inversely* proportional to their cost per million tokens. A $0.10/M model is 10x more likely to be chosen than a $1.00/M model. Free models get a nominal cost of $0.001/M to avoid infinite weight. This is not just about saving money; it's an experimental design: "Over time, the cairn accumulates data on which models notice what — and whether noticing more is worth paying more" (`model_selector.py` docstring). The system is explicitly designed to generate data to answer the ROI question of model intelligence.

**Strand 4: Honest Epistemics Through Declared Losses**
The `attestation.py` adapter bridges Chasqui's verification results to Willay's "epistemic receipts." Every verification verdict (CONFIRMED/DENIED/INDETERMINATE) is mapped to a tuple of (Truth, Indeterminacy, Falsity) values and is accompanied by **three declared losses that apply to every verification** (`attestation.py` lines 49-76):
1.  "Single-LLM verification" (no cross-verification, no human review)
2.  "Hallucination risk in verifier"
3.  "Temporal code drift"
This is remarkably honest. Instead of pretending the automated verification is perfect, it bakes the known limitations into the epistemic record itself. The system declares what it *cannot* know.

**Strand 5: Defense Against Degenerate Output and Cascades**
The code shows awareness of and defenses against LLM failure modes:
- `coordinator.py` has `_is_degenerate_repetition()` to detect models stuck in loops repeating the same phrase (line ~115).
- `coordinator.py` has `_count_prior_verifications()` and a `MAX_VERIFY_PER_CLAIM` (default 3) to stop a "confused claim" from triggering an infinite cascade of re-verifications (lines ~150-190).
- `analyst.py` has `is_garbage()` function that uses regex to filter out corrupted output containing runs of CJK, Cyrillic, or encoding artifacts (lines ~140-160).
- `gleaner.py` has confidence scoring based on language: definitive phrases ("is", "must") raise confidence; hedged language ("seems", "might") lower it (lines ~80-100).
The system is paranoid about its own components' reliability.

**Strand 6: The Scout/Scour Duality**
There's a clear philosophical and practical distinction:
- **Scout** (`scout.py`): "Wanders freely." Given a vantage point and told to "go look and see what you find." Prompt is open-ended. Output is a "tensor" of observations, losses, and questions.
- **Scourer** (`scourer.py`): "Has a target." Given a specific file, directory, or tensor to examine deeply. Prompt is focused and includes the target's full contents. Used for **introspection** (project code), **external** (other codebases), **tensor** (analysis of prior tensors), or **synthesis**.
This duality allows for both broad, serendipitous discovery and deep, targeted investigation. The `__main__.py` shows how both are invoked from the same CLI.

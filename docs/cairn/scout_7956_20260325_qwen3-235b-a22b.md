### Strands  

#### **Strand 1: Structural Guardrails in CLI Wiring**  
- **What**: In `test_jabberwock_cli_invariants.py`, tests ensure the CLI parser’s subcommands and defaults are hardcoded (e.g., default store is `duckdb`).  
- **Why It Matters**: The CLI’s parser wiring is silent in failure: a missing subcommand or incorrect default could break workflows without explicit errors. The tests replicate parser construction to verify structure, not just existence.  
- **Tension**: The default store (`duckdb`) balances production safety (persistence) against developer convenience (memory). A shift to `arango` would break without proper setup, highlighting a potential operational fragility.  

#### **Strand 2: Immutability as a Foundational Assumption**  
- **What**: Multiple tests (e.g., `test_jabberwock_invariants.py`, `test_monotonicity.py`) enforce immutability via frozen Pydantic models and append-only backends.  
- **Why It Matters**: Immutability ensures temporal consistency (e.g., Lamport clocks in `test_activity_stream.py`) and prevents accidental data corruption. The `test_jabberwock_invariants.py`’s frozen models and `test_monotonicity.py`’s append-only checks reinforce this.  
- **Surprise**: The `test_activity_stream.py` distinguishes facts (schema-agnostic, `extra='allow'`) from structural records (e.g., `AnchorCursor`, `extra='forbid'`). This mirrors the project’s philosophical split between raw data (facts) and curated tensors (structural).  

#### **Strand 3: Governance Against Corrupted Output**  
- **What**: In `test_governance.py`, the coordinator detects degenerate model outputs (e.g., repetition loops) and filters garbage claims.  
- **Why It Matters**: A single corrupted claim could pollute verification pipelines, as seen in historical regressions (e.g., Scout 652). The `_is_degenerate_repetition` guard in `coordinator.dispatch_verify` prevents this.  
- **Tension**: The pipeline’s reliance on random sampling (to avoid redundant verification) risks undercoverage. The tests confirm randomness but don’t address coverage gaps.  

#### **Strand 4: Provenance vs. Schema Evolution**  
- **What**: `test_jabberwock_invariants.py` enforces `ROOT_BANDERSNATCH_ID` as a UUID5, ensuring deterministic provenance. Meanwhile, `test_activity_stream.py` allows facts to accept unknown fields for schema evolution.  
- **Why It Matters**: Provenance requires consistency (e.g., UUID5 for the root entity), while raw data must evolve with new providers. The project’s split between these concerns is explicit: facts are schema-flexible, but tensors are strict.  
- **Omission**: The test suite doesn’t validate migration paths for schema changes in facts, only backward compatibility.  

#### **Strand 5: Query Engine’s Anti-SQL/AQL Bias**  
- **What**: In `test_query_pipeline.py`, the engine’s AST parse forbids SQL/AQL keywords, forcing Python-side filtering.  
- **Why It Matters**: The project prioritizes Pythonic logic over database-native queries, even for performance-critical paths (e.g., 28.5M rows in `test_activity_stream.py`). This could lead to scalability issues.  
- **Surprise**: The test explicitly blocks query pushdown to databases like DuckDB, despite the performance cost. This suggests a philosophical preference for code transparency over optimization.

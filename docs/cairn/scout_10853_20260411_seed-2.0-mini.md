### Strands
#### Strand 1: The Yanantin Duality Built Into Hook Workflows
The reference docs explicitly split hook logic into two complementary layers:
1. **Legacy human-only bash hooks**: As shown in migration.md, these require hand-written bash scripts with hardcoded, narrow checks (e.g., only blocking literal `rm -rf` commands) that demand bash expertise and lack context awareness. Humans fully control the logic but are limited by rigid, error-prone pattern matching.
2. **AI-augmented prompt hooks**: These embed validation logic directly in natural language prompts, letting LLMs handle contextual reasoning (e.g., catching all `rm` variants, evaluating file content alongside paths) without human scripting. The docs frame this as a upgrade that aligns with Yanantin's goal of pairing human oversight with AI's contextual judgment.

Notably, both systems coexist: patterns.md still includes command-type bash hooks for use cases like context loading and logging, so the project isn't replacing humans, but expanding their toolkit.

#### Strand 2: Unstated Assumptions About LLM Reliability and User Expertise
Every prompt-based hook example makes untested, high-stakes assumptions:
- All examples assume the LLM will strictly follow prompt instructions to return only `approve`/`deny` with an optional explanation, with no fallbacks for malformed responses (e.g., if the LLM rambles instead of providing a clear decision).
- The `$TOOL_INPUT` template variables used in prompts (e.g., `.command`, `.file_path`) are referenced without explanation: users must infer their existence and format from the two migration examples, with no full list of available variables provided.
- The 15-second timeout for prompt hooks assumes LLM API calls will complete within that window, with no handling for latency spikes that could break user workflows.
- The security validation prompts in both docs use hardcoded natural language rules, assuming users writing hooks can craft effective prompt engineering without specialized AI knowledge—replacing bash expertise with prompt engineering expertise.

#### Strand 3: Opacity vs. Predictability as a Core Tradeoff
This is the sharpest tension in the reference set:
- Legacy bash hooks are fully transparent: anyone can read the script to see exactly what checks are being performed, making audits and debugging straightforward.
- AI prompt hooks are black boxes: there's no way to fully audit the LLM's reasoning beyond the human-written prompt. For example, the file write validation prompt in migration.md claims to handle symlinks, but never explicitly mentions them in the instructions—relying on the LLM to infer that symlinks to sensitive paths are off-limits.

This directly clashes with Yanantin's goal of epistemic observability: if the AI's decision-making is opaque, it's hard to understand *why* a hook approved or denied an action.

#### Strand 4: Event-Driven Hook Triggers (Incomplete Documentation)
The reference files show hooks are tied to specific system events, including:
- `PreToolUse`: Runs before a tool executes (used for security validation)
- `Stop`: Runs before a session ends (used for test/build enforcement)
- `SessionStart`: Runs when a new session begins (used for context loading)
- `Notification`: Runs when a notification is sent (used for logging)

Matchers can be specific tool names (e.g., `Bash`, `Write`), regex patterns (e.g., `mcp__.*__delete.*` for MCP deletion tools), or wildcards (`*`). However, the docs do not list all available events or matchable tool types, leaving gaps in what's possible with the hook system.

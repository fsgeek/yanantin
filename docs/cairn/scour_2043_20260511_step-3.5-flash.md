# Preamble

This is **Tinkuy** — an experimental infrastructure for running systematic ablation experiments on LLM system prompts. The name "tinkuy" comes from Quechua, meaning "encounter" or "meeting point," which fits its purpose: meeting different instruction conditions head-on.

First impression: This is a **mature, production-grade research framework** built for rigorous prompt engineering experiments. It's not just a script collection; it's a complete pipeline with session management, checkpointing, tensor storage, and multi-model evaluation via OpenRouter. The architecture shows clear lineage from Yanantin (mentioned in CLAUDE.md) and focuses on **imperative interference** — how different instruction blocks conflict or interact.

The checkpoint files reveal active experimentation with Claude Code models (Haiku, Opus) running read-only exploration tasks. The `.tinkuy-data/` directory is a rich experimental log with thousands of session checkpoints, indicating heavy use.

# Strands

## Strand 1: Three-Region Memory Architecture

**What it is:** Tinkuy uses a tripartite memory model:
- **SYSTEM**: Immutable constitution (block definitions, invariant rules)
- **DURABLE**: Persistent knowledge (not shown in checkpoints but implied)
- **EPHEMERAL**: Per-turn conversation state

This mirrors Yanantin's three-tier evaluation framework (System/Domain/Application) but applied to **session management** rather than conflict detection. The checkpoints show each session maintains these regions separately, with blocks identified by handles (hashes) and metadata tracking access counts, creation times, and eviction.

**Pattern for Yanantin:** The handle-based block identity system is elegant. Each block has a `handle` (e.g., `"9de81607"`), `kind`, `label`, `status`, `size_tokens`, and `content`. This allows precise referencing and diffing across sessions. Yanantin's tensor system could adopt this for provenance tracking.

## Strand 2: Ablation Through Block Removal (Not Rewriting)

**Critical finding:** The infrastructure **only supports block removal**, not rewriting. From the checkpoint data, I see:
- `"nominations": []` in TOOLS region
- SYSTEM blocks are either PRESENT or ABSENT (implied by absence in `blocks` array)
- No evidence of block substitution or text replacement

The user's question about "declarative rewrites" (converting imperatives to declarative while keeping blocks present) would require **new infrastructure**. The current design treats blocks as atomic units: either included or excluded.

**Yanantin implication:** If Yanantin wants to test register transformations (imperative → declarative), it needs a **block variant system** — not just removal but substitution. This is a gap in both projects' current capabilities.

## Strand 4: Checkpointing and Session Recovery

**Mechanism:** Each session has a `checkpoint.json` with:
- Current `turn`
- `regions` with their blocks and nominations
- Access metadata (created_turn, last_access_turn, access_count, fault_count, created_at, evicted_at)

This enables **exact reproduction** and **failure recovery**. If a run crashes, you can resume from the last checkpoint.

**Yanantin relevance:** The tensor database needs similar checkpointing for long-running evaluations. The access tracking (fault_count, evictions) could inform cache management in Yanantin's region system.

## Strand 9: Results Storage Structure

From the directory tree:
```
.tinkuy-data/
|-- experiments/   (multiple experiment runs)
|-- pages/         (individual page outputs)
|-- sessions/      (session checkpoints)
|-- tensors/       (tensor results)
|-- gateway.log
|-- wire.jsonl
```

This is a **colony** pattern: all data for a run lives under `.tinkuy-data/`, with subdirectories for different artifact types. The `wire.jsonl` suggests a streaming log of all events.

**Yanantin parallel:** Yanantin's tensor database could adopt this colony approach — each experiment gets its own namespace with pages, sessions, tensors, logs all together.

# Closing

**Overall impression:** Tinkuy is a **sophisticated experimental platform** for systematic prompt ablation studies. It solves problems Yanantin also faces:
- Provenance tracking (handles, checkpoints)
- Multi-model evaluation (OpenRouter integration)
- Session management (three-region memory)
- Cost accounting (billing headers)

But it **does not solve** the declarative rewrite problem. That would require extending the block identity system to support variants.

**What I'd tell the Yanantin team:**

1. **Adopt Tinkuy's checkpointing pattern** — every session should have an exact, serializable state that can be resumed. This is crucial for long-running tensor evaluations.

2. **Use content-addressed handles** for blocks and tensors. The `handle` field (likely SHA256 or similar) provides immutable identity. Yanantin's tensors should have similar identifiers.

3. **Separate infrastructure from experiments** — Tinkuy has clear separation: `src/tinkuy/` (framework), `scripts/` (runs), `.tinkuy-data/` (results). Yanantin should do the same.

4. **Cost tracking is not optional** — embed billing metadata in every request. You'll thank yourself when the OpenRouter bill arrives.

5. **The declarative rewrite experiment is not supported out of the box** — you'll need to modify the ablation runner to allow block substitution, not just removal. This means changing how `AblationConfig` defines conditions (from `remove_blocks: []` to `replace_blocks: {handle: new_content}`).

6. **I cannot give you the exact `tone-concise` and `use-task-for-search` block texts** because they're not in the provided checkpoints. You'll need to locate them in the actual codebase (probably in `data/system_prompts/claude-code/` as the user suggested).

7. **Tinkuy's "gateway" pattern** — there's a `gateway/` module and `taste_gateway/`. This might be how probes are sent and responses logged. Yanantin's evaluation pipeline could use a similar gateway pattern for decoupling.

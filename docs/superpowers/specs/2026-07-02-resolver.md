# Spec — The Intent Resolver (`yanantin.resolver`)

**Date:** 2026-07-02
**Pour:** P3-resolver (the serial spine segment after factors landed).
**Authority:** `tests/red_bar/test_mechanism_invariance.py` (4 guards) pins the
shape. This spec records *why*, written after the tests. It lands on
`yanantin.factors` (the six-factor shape) — the resolver speaks that vocabulary.

## Why this exists

`factors` gave us one coordinate space both storage and LLM-memory normalize
into. The resolver is the other half: it compiles a query INTENT into
**constraints over that same space**, through ONE mechanism, regardless of who
is asking. If a human-anchored query and an LLM-anchored query compiled through
different machinery, "storage-find is a projection of activity-find" would be a
fork (two mechanisms) rather than a restriction (one mechanism, different dense
regions). The resolver is where that claim is either honored or broken.

## The four invariants (the tests)

1. **One entry point compiles both query types.** `resolve(intent, consumer=...)`
   returns a `CompiledQuery` for a human-anchored intent AND an LLM-anchored
   intent. No `resolve_human` / `resolve_llm` — a separate entry point per
   consumer IS the fork.
2. **Both compile to the SAME intermediate schema** (trace-level sameness). The
   two `CompiledQuery` objects have the same structural signature (same fields);
   they differ only in WHICH factor slots are populated, never in shape.
3. **The intermediate representation IS factor-constraints.** `CompiledQuery`
   carries `factor_constraints`, a mapping keyed ONLY by the six factors. Neither
   query may bypass this representation — a bypass is a forbidden fork.
4. **No consumer-branching below the head.** The resolver source contains no
   `if consumer == "llm"` / `== "human"` comparison. Consumer differences live
   ABOVE the head (as parameters/disposition carried on the query), NOT in the
   resolution logic that builds the IR. This is checked by AST-parsing the
   resolver's own source — it is a constraint on HOW the code is written.

## The shape

- `CompiledQuery` — a pydantic model:
  - `factor_constraints: dict[str, Any]` — keys ⊆ the six factors; each value a
    constraint on that factor (v1: the extracted term/None). The stable IR.
  - `consumer: str` — carried as DISPOSITION, not used to branch the mechanism.
    (Above-the-head data: a caller may dispose of results differently per
    consumer, but resolution does not.)
  - `intent: str` — the original query text, retained (same save-it-all
    discipline as factors' raw).
- `resolve(intent: str, *, consumer: str) -> CompiledQuery` — the single entry
  point. Extracts factor-constraints from the intent UNIFORMLY:
  every query is scanned for signals against each of the six factors; whatever is
  found populates that factor's constraint, the rest stay unpopulated. The
  extraction does not inspect `consumer` to decide what to do — `consumer` rides
  along as disposition only.

## What v1 does NOT do (honest scope)

The tests check SHAPE and factor-space membership, not extraction QUALITY — they
do not assert that the human query correctly resolves "Siddhartha" to a `what`
constraint or "six weeks after the fire" to a `when` constraint. So v1's
extraction is deliberately simple and uniform (a first, honest slice): it
produces well-formed factor-constraints of the right shape, through one
branchless mechanism. Richer extraction (temporal-window parsing, entity
recognition, the episodic `when` pivot) is a later refinement ON this shape, not
a prerequisite for it — same as factors left richer normalization open. The
load-bearing decision here is the MECHANISM (one branchless entry point → factor
constraints); extraction quality is tuning, invisible at this scale
(project_find_model_is_the_decision_indices_are_tuning).

## Not in this pour

Executing a `CompiledQuery` against the live backend (turning factor-constraints
into AQL over the `Objects`/activity collections) — that's the find execution
layer, downstream. The resolver produces the IR; running it is the next concern.

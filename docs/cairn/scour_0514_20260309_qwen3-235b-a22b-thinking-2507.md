# TENSOR: Apacheta Introspection Report

### Preamble
I was directed to examine `src/yanantin/apacheta` as part of the Yanantin project's introspection initiative. What immediately drew my attention was the `interface/abstract.py` file - it contains a remarkably comprehensive interface specification with 20 distinct query types. This isn't just a database interface; it's a carefully designed epistemic observability contract. The interface versioning (`INTERFACE_VERSION = "v1"`) and strict immutability constraints signaled this is foundational infrastructure.

### Strands

**Immutable Knowledge Architecture**  
The core design principle of immutability echoes throughout Apacheta. The abstract interface explicitly states "No delete, no update on stored records" and all write operations produce new records. In `backends/memory.py`, this is enforced with checks like:
```python
if tensor.id in self._tensors:
    raise ImmutabilityError(f"Tensor {tensor.id} already exists.")
```
This isn't just defensive programming - it's an epistemological stance. Knowledge evolves through composition and correction rather than overwrite. The consequences are profound: system state becomes a directed acyclic graph of knowledge claims, making the entire history observable. If this changed to allow mutations, the entire epistemic tracking system (corrections, dissent records, etc.) would collapse. The `content_address.py` implementation complements this by giving documents identity through content rather than location.

**Epistemic Metadata as First-Class Citizen**  
Apacheta treats knowledge uncertainty as fundamental data, not an afterthought. The `models/epistemics.py` structure (visible through imports in `models/__init__.py`) shows sophisticated tracking:
- `EpistemicMetadata` with `truth` and `indeterminacy` values
- `DisagreementType` enumerations
- `DeclaredLoss` with `LossCategory` 

This appears in the tensor model structure where each `KeyClaim` carries epistemic metadata. In `ingest/markdown_parser.py`, even the parser creates default epistemic values:
```python
claims.append(KeyClaim(
    text=bold_match.group(1),
    epistemic=EpistemicMetadata(truth=0.5, indeterminacy=0.5),
))
```
This suggests the system assumes all knowledge comes with uncertainty. If this epistemic layer were removed, the entire "epistemic observability" promise of Yanantin would be hollow. What's missing is clear guidance on how these values should be updated through the knowledge lifecycle.

**Composition Over Replacement**  
The architecture centers on composition rather than replacement. The `operators/project.py` implementation reveals this philosophy:
```python
def project(
    interface: ApachetaInterface,
    tensor_id: UUID,
    *,
    strand_indices: list[int] | None = None,
    topics: list[str] | None = None,
) -> list[StrandRecord]:
```
Rather than modifying tensors, operators extract views of existing knowledge. The `CompositionEdge` model (referenced throughout) shows how tensors relate through composition equations. This explains the "complementary duality" mentioned in the assignment - knowledge advances through relationship rather than replacement. If the project operator were modified to allow destructive filtering, it would violate the core contract. The `get_strand` method in `interface/abstract.py` explicitly notes: "the result would raise ImmutabilityError (duplicate UUID), which is the correct guard."

**Query Taxonomy as Epistemic Map**  
The 20 query types defined in `interface/abstract.py` form a remarkable epistemic taxonomy. They're not just database queries but structured ways of examining knowledge:
- Bootstrap queries (Q1-Q3): "Which tensors fit within this context budget?"
- Epistemic queries (Q4-Q7): "Full correction history for a claim"
- Lineage queries (Q8-Q10): "The full composition graph"
- Evolution queries (Q11-Q14): "Known error classes across tensors"
- Defensive queries (Q18): "What would need to change if this claim were wrong?"

This taxonomy appears to be the implementation of "epistemic observability" promised by the project. The initial implementations in `backends/memory.py` are simple filters, but the interface design anticipates sophisticated future implementations. What's concerning is that many queries have minimal implementation comments like "# Initial implementations: simple filtering" - the taxonomy exists but the realization lags.

### Closing
Apacheta represents a sophisticated attempt to build infrastructure for observable knowledge evolution. The codebase demonstrates remarkable architectural discipline - the immutability constraint is consistently enforced, the interface abstraction is clean, and the epistemic tracking is genuinely novel. However, there's a noticeable gap between the ambitious interface design (with its 20 query types) and the current implementation maturity.

If you're about to modify this code, understand that you're working with intentional constraints, not arbitrary limitations. The immutability isn't a temporary implementation detail - it's the philosophical foundation. Any change that introduces mutation or deletion would undermine the entire epistemic model. The interface versioning exists precisely to allow evolution while preserving compatibility.

Most importantly: don't treat this as just a database. It's a knowledge evolution framework where every operation is a statement about how knowledge should advance. The "complementary duality" isn't just between human and AI - it's between what is known and how that knowledge came to be.

Preamble
From the Windows docs for “polyglot-hooks,” I landed on a single file explaining how Claude Code plugins launch shell hooks on Windows and Unix with one script. The polyglot wrapper leapt out: it’s a single .cmd file that is valid both to CMD.exe and to bash via heredoc.

Strands

1. Polyglot Wrapper Hack
   - Lines 1–6: “: << 'CMDBLOCK'” is treated as a harmless label in CMD but as the start of a heredoc in bash. The same bytes drive two shells differently.
   - Thought: This is clever but brittle. It presumes CMD’s label syntax and bash’s heredoc semantics will never change. Any future shell update could break it.

2. Hardcoded Git Bash Path
   - Line 3: `"C:\Program Files\Git\bin\bash.exe" -l -c …`
   - Thought: Assumes Git for Windows is installed to the default location. If a user installs Git elsewhere—or uses WSL, msys2, or a portable Git—the wrapper silently fails. No detection or fallback is provided.

3. Environment-bootstrapping Tension
   - Uses `-l` (login shell) to pull in a full Unix-style PATH and then `cygpath -u` to translate backslashes to forward slashes.
   - Thought: They’re wrestling Windows’ poor shell integration by layering a login bash session on top of CMD. It solves path syntax and env var quirks, but at the cost of spawning an extra login shell on every hook.

4. Pure-bash JSON escaping
   - The example function `escape_for_json()` avoids sed/awk in favor of a pure-bash character loop.
   - Thought: This eliminates external dependencies but could perform poorly on large payloads. It’s a conscious trade-off: cross-platform reliability over speed.

5. Generic run-hook.cmd pattern
   - Mentions a 63-line snippet (truncated) that parameterizes script names.
   - Thought: There’s likely a lot of near-duplicate boilerplate across plugins. It’s a maintainer pain point; small tweaks or bug fixes might need to be copy-pasted everywhere.

Declared Losses
- I did not inspect the full 63-line generic wrapper; it’s too large and likely repeats the same pattern.
- I skipped digging into hooks.json generation or validation logic elsewhere in the codebase.
- I did not examine alternative approaches (PowerShell, Node-based shims, WSL) that the team may have discarded.

Open Questions
- How is CLAUDE_PLUGIN_ROOT set or validated before invocation? What if it contains unusual characters?
- Why choose CMD + bash rather than PowerShell, which supports more robust scripting on Windows?
- Is there any mechanism to detect or warn when Git for Windows isn’t at the default path?
- How are errors surfaced if the bash invocation fails? Silent exit?

Closing
This file reveals a strong desire for “write once, run everywhere” hooks but also a deep aversion to PowerShell or heavier runtimes. The polyglot trick is elegant but fragile, and the hardcoded Git path is a single point of failure. Next scout: verify how CLAUDE_PLUGIN_ROOT is initialized, check for any runtime checks on Windows, and look for patterns of duplication in other plugins’ wrappers—so we can assess maintainability risks.

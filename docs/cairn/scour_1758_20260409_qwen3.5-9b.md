### Preamble

I was pointed at `src/yanantin/activity` — the temporal fact storage layer that sits between raw provider observations and authored tensors. What drew my attention first was the **duckdb.py docstring's explicit comparison**: "Unlike Apacheta's DuckDB backend (which loads all records then filters in Python), this backend pushes temporal queries down to SQL. At 28.5M facts, load-all-then-filter is not viable." This tells me the project has evolved from a simpler system, learned from experience, and is now prioritizing scalability at the storage layer.

The second thing that caught me: the **write gate pattern** in `anchor.py` — the "updated AND referenced" two-flag system. This is a deliberate design choice about when to persist state, not just how to store it.

### Strands

#### Strand 1: Backend Stratification

**What I saw:** Three backends implementing the same `ActivityStreamStore` interface:
- `backends/memory.py`: Dict + bisect, deep-copy on read/write
- `backends/duckdb.py`: SQL query pushdown, ISO 8601 VARCHAR timestamps
- `backends/arango.py`: Document-based, AQL, persistent sorted indexes

**What it made me think:** This is a thoughtful tradeoff system. Each backend has a clear use case:
- InMemory → tests, ephemeral runs
- DuckDB → trusted device, file persistence, SQL familiarity
- ArangoDB → production, least-privilege, obfuscation support

The `backends/__init__.py` comment reveals an important packaging decision: ArangoDB and DuckDB aren't imported at package level to avoid requiring their dependencies for all users. This is a **dependency isolation strategy** — nice.

**Connection to broader project:** The store layer feeds into the `ApachetaInterface` via `anchor.py`. The activity layer is the "scribe" that records what happened; Apacheta is the "archivist" that stores what's been frozen.

#### Strand 2: Immutability as a First-Class Concern

**What I saw:** Every backend raises `ImmutabilityError` on duplicate UUIDs:
- `duckdb.py store_fact`: "Facts are immutable — append, don't overwrite."
- `arango.py store_fact`: Same message
- `memory.py store_fact`: Same pattern

**What it made me think:** This isn't accidental. The docstring in `store.py` says: "Both append-only, both immutable once stored." This is a **design invariant**, not a feature. If you try to change something, the system rejects it.

**Assumption check:** This assumes you can detect duplicates reliably. The UUIDs are generated per-record, so this works. But what if a provider sends the same fact twice? The system will fail. Is that right? Maybe. Maybe the provider should deduplicate upstream.

**What would break:** If you need to update facts (e.g., a correction), you'd need a new fact ID and a way to link them. This is a **data lineage requirement**.

#### Strand 3: The Write Gate Pattern

**What I saw:** In `anchor.py`:
```python
def flush(self) -> bool:
    if not (self._updated and self._referenced):
        return False  # Write gate closed
    ...
```

The service tracks `_updated` (provider reported new data) and `_referenced` (caller requested current position). Only when both are true does it persist.

**What it made me think:** This is the **Indaleko ActivityContextService pattern**. It prevents "noisy" writes — you only commit state changes when both sides agree. It's a coordination mechanism for a distributed system.

**What I don't know:** What happens if `flush()` is never called? Do cursors get stale? Is there a timeout? The docstring says "write gate check, persist if both flags set" but doesn't specify what happens if they never both set.

**Connection:** This bridges the gap between the fact store (passive recording) and the anchor service (active coordination).

#### Strand 4: Temporal Query Design

**What I saw:** All three backends support `query_range` with `start`/`end` bounds:
- DuckDB: `ORDER BY timestamp ASC`
- ArangoDB: AQL with `SORT doc.timestamp DESC` (then reverse)
- InMemory: `bisect` on sorted lists

**What it made me think:** The design assumes **temporal queries are the primary access pattern**. This makes sense for an activity stream. The ArangoDB backend is particularly interesting:

```python
col.add_index(
    {
        "type": "persistent",
        "fields": [self._map.field_name("provider_id"), self._map.field_name("timestamp")],
        "sparse": False,
    },
)
```

Persistent sorted indexes mean the database maintains them automatically. This is a **performance-first design**.

**Assumption:** Timestamps are always valid and sortable. The models enforce this:

```python
def _ensure_utc(dt: datetime) -> datetime:
    if dt.tzinfo is None:
        raise ValueError("Naive datetime is not allowed.")
```

This is a **good catch**. Ambiguous timestamps corrupt sort order everywhere.

#### Strand 5: Late Binding in Materialize

**What I saw:** In `anchor.py`:

```python
def materialize(self, handle: UUID) -> AnchorView:
    all_providers = self._store.list_providers()  # Late binding!
    for provider_id in all_providers:
        fact = self._store.query_latest(provider_id, before=anchor.timestamp)
```

**What it made me think:** This is intentional. The docstring says: "Late binding: includes providers registered after the anchor was created." This means an anchor's view can **grow** after it's created.

**What would break:** If you're trying to create an immutable snapshot, this breaks that assumption. But the docstring says "View is ephemeral resolution — never cached, never stored." So this is by design.

**Open question:** If you freeze this view into a tensor, does it capture the late-bound state, or does it freeze the providers list? The `freeze()` method calls `materialize()`, so it captures the late-bound state. This means **frozen tensors can have more providers than the anchor suggests**.

### Open Questions

1. **What happens when a provider is deleted?** The `list_providers()` method returns current providers, but what about facts from a removed provider? Are they orphaned?

2. **How are content hashes generated?** The `FactRecord` has `content_hash` with default `""`. Is this set by a collector? Where?

3. **What's the max timestamp range?** If a provider sends facts from 2010 and 2030, does the system handle this? The InMemory bisect assumes contiguous time?

4. **How does the system handle clock skew?** The `Materialize` method queries at `anchor.timestamp`, but what if a provider's clock is behind?

5. **Is there a cleanup mechanism?** Facts are append-only. Do they grow forever? Is there an archive strategy?

6. **What's the recovery path?** If a backend crashes mid-write, is there a transaction log? The docstrings don't mention this.

7. **How are the backends tested?** The InMemory backend is for tests, but do the others have test coverage?

### Closing

**Overall impression:** This is **well-architected, thoughtful design**. The separation between facts (passive, high-volume) and anchors (active, low-volume) is clean. The immutability pattern is consistent across backends. The write gate is a clever coordination mechanism.

**What would I tell someone to modify it:**

1. **Add state persistence for the anchor service** — if the service restarts, you'll lose cursor state and the write gate flags.

2. **Document the content_hash purpose** — it's there, but what is it for? Validation? Deduplication?

3. **Consider a retention policy** — facts grow forever. There should be an archive or cleanup mechanism.

4. **Add clock skew handling** — the system assumes all clocks are synchronized. This is a real-world failure mode.

5. **Test the late-binding behavior** — it's counter-intuitive that a frozen tensor can have more providers than the anchor's cursor list.

**What I know vs. don't know:**
- **Know:** The design patterns, the immutability invariants, the write gate
- **Don't know:** The actual performance numbers, the error handling edge cases, the full backend implementations
- **Made up nothing:** I stuck to what the code shows. I didn't invent justifications for missing pieces.

This is a **solid foundation** for the Yanantin project. The activity layer is doing its job: recording what happened without judging what it means. That's the right separation for a system that wants to bridge human and AI cognition.

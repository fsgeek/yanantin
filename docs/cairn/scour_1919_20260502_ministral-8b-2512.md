#### **Strand 2: Backend Implementations**
**What you saw:**
1. **InMemory (`memory.py`)**:
   - Uses `dict` + `bisect` for O(log n) temporal queries.
   - Deep-copies records on read/write (defensive programming).
   - Thread-safe via `RLock`.
   - **Tradeoff**: Memory-only; suitable for testing.

2. **DuckDB (`duckdb.py`)**:
   - **SQL pushdown**: Queries are executed in DuckDB, not Python (critical for scale).
   - **Schema**:
     - Facts: `id (PK)`, `provider_id`, `timestamp (VARCHAR ISO 8601)`, `data (JSON)`, `content_hash`.
     - Anchors: `handle (PK)`, `timestamp`, `data (JSON)`.
   - **Indexes**: Composite `(provider_id, timestamp)` for facts; `(timestamp)` for anchors.
   - **Obfuscation**: None (assumes local trust; contrasts with ArangoDB).

3. **ArangoDB (`arango.py`)**:
   - **Document store** with **persistent sorted indexes** (AQL pushdown).
   - **Obfuscator pattern**: Fields/collections can be renamed (e.g., for privacy).
   - **Least privilege**: Separate user with RW access only to `activity_facts`/`activity_anchors`.
   - **Tradeoff**: More complex setup (requires ArangoDB instance).

**What it made you think:**
- **Duality in storage**:
  - **DuckDB**: Optimized for **local, trusted** storage (no obfuscation needed).
  - **ArangoDB**: Optimized for **scalability + security** (obfuscation, least privilege).
- **Performance tradeoffs**:
  - DuckDB’s `VARCHAR` timestamps avoid `pytz` dependency but require ISO 8601 strings.
  - ArangoDB’s AQL is flexible but slower than DuckDB’s native SQL for some queries.
- **Assumptions**:
  - All backends assume **UTC timestamps** (enforced in `models.py`).
  - ArangoDB assumes a **pre-provisioned database** (fails if DB doesn’t exist).
- **What would break if changed**:
  - Changing timestamp storage to `TIMESTAMP` (instead of `VARCHAR`) would require `pytz` and break DuckDB’s sort stability.
  - Removing obfuscation from ArangoDB would expose raw data to the DB user.

**Missing**:
- **DuckDB**: No documentation on vacuuming/optimization for large datasets.
- **ArangoDB**: No **replication** or **sharding** strategy (assumes single-node for now).

#### **Strand 3: Memory Anchor Service (`anchor.py`)**
**What you saw:**
- **Core logic**: Tracks cursors (`update_cursor`), issues handles (`get_handle`), and enforces the **two-flag write gate** (`flush`).
- **Workflow**:
  1. Provider updates cursor (`update_cursor` → `updated=True`).
  2. Consumer requests handle (`get_handle` → `referenced=True`).
  3. If both flags are set, `flush()` persists the anchor and resets flags.
- **Materialization (`materialize`)**:
  - Resolves an anchor into an `AnchorView` by querying all current providers (late binding).
  - Includes facts **at or before** the anchor’s timestamp.
- **Freezing (`freeze`)**:
  - Converts an `AnchorView` into a **tensor** (`TensorRecord`) with:
    - Provenance (`ProvenanceEnvelope`).
    - Structured content (`StrandRecord` for summary + data).
    - Lineage tags (`("anchor", "frozen-view")`).
  - Stores the tensor via `ApachetaInterface`.

**What it made you think:**
- **Duality in service**:
  - **Human side**: Providers update cursors; consumers request handles.
  - **AI side**: Anchors are resolved into tensors (authored acts) for downstream processing.
- **Epistemic observability**:
  - The `freeze()` operation is an **authored act**—it decides to **pin a temporal view** into a tensor.
  - Provenance includes the **anchor handle** as the `source.identifier`.
- **Assumptions**:
  - **Late binding**: `materialize()` queries all providers, even those not in the anchor’s cursor list. This ensures **completeness** but may include irrelevant data.
  - **No caching**: `AnchorView` is ephemeral (never stored).
- **What would break if changed**:
  - Changing `materialize()` to **early binding** (only query providers in the anchor) would miss new providers.
  - Removing the two-flag gate would allow **unreferenced updates**, corrupting provenance.

**Missing**:
- **Concurrency control**: No discussion of how multiple `MemoryAnchorService` instances handle the same store.
- **Handle collision**: Uses `uuid4()` for handles, but no validation for duplicates across services.

   - Immutable snapshot of cursors at a timestamp.

4. **AnchorView**:
   - Ephemeral resolution of an anchor against current streams.
   - Includes **all providers** (late binding) and their latest facts ≤ anchor time.

**What it made you think:**

- **Connection to tensors**:

  - The **lifecycle** is: `FactRecord` → `MemoryAnchor` → `AnchorView` → `TensorRecord`.

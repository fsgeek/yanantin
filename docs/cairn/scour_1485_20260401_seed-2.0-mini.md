# Chasqui Subsystem Introspection Tensor

## Preamble
I am examining `src/yanantin/chasqui`: the core messenger and epistemic observability layer of the Yanantin project. This subsystem builds a modular, AI-powered pipeline for code exploration, claim extraction, verification, and knowledge tracking, using role-based "chasqui" messengers (scouts for free-range exploration, scourers for targeted analysis) coordinated via a central tooling layer. A striking meta-detail is that this system can even scour its own codebase, as enabled by the `--scour src/yanantin/chasqui` CLI flag.

---

## Strands
### 1. Role-Separated Modular Messenger Pipeline
The codebase splits functionality into tightly focused, single-responsibility modules:
- **Scouts & Scourers**: `scout.py` dispatches free-ranging code explorers that select random vantage points via cost-weighted model selection (from `model_selector.py`, which uses inverse cost weighting to prioritize cheaper models). `scourer.py` extends this pattern for targeted exploration, with dedicated templates for introspective (project internal), external (third-party), and tensor (existing cairn data) scopes.
- **Coordinator**: `coordinator.py` acts as the central orchestration layer, handling async dispatch, tracking the persistent cairn storage, and adding guardrails like detecting degenerate model repetition loops and limiting duplicate verification attempts.
- **Claim Processing**: `gleaner.py` extracts structured claims from raw scout/scour reports using deterministic regex (no initial LLM calls) to classify claim types, deduplicate insights, and associate claims with file references. `scorer.py` scores scout reports on objective metrics (specificity via file references, fabrication of non-existent paths, efficiency, and structural adherence) without human judgment, parsing provenance metadata from report headers.
- **Analysis & Attestation**: `analyst.py` turns gleaned claims into cross-model insights, clustering claims to distinguish topological (multi-model confirmed) vs. textural (single-model) observations, and building quality profiles for each LLM model used. `attestation.py` bridges Chasqui's verification outputs to Willay's epistemic receipt system, formalizing verification verdicts with truth/indeterminacy/falsity scores and documented process losses.
- **Coverage Tracking**: `coverage.py` solves the bias of uniform random sampling by tracking which code files have been reviewed by scouts, prioritizing stale, unreviewed code for future scouting runs.

### 2. Epistemic Transparency as a Core Requirement
Every part of the system is designed to document and track the limits of its own knowledge:
- Scout and scour reports explicitly include `Declared Losses` sections to document what the model chose not to examine, and `Open Questions` for unresolved unknowns.
- `gleaner.py` classifies claims into factual, architectural, epistemic, or missing categories to clarify the type of insight being recorded.
- `analyst.py` separates verification meta-claims (reports about other scouts' work) from original code observations, and filters out garbage output from broken or unhelpful models.
- An intentional design choice is using deterministic regex for initial claim extraction instead of LLMs, to keep the pipeline fast and reproducible, with LLM-guided extraction marked as a future enhancement.

### 3. CLI-First Orchestration
`__main__.py` exposes a full command-line interface for every part of the pipeline, from dispatching single scouts to batch scouring, scoring reports, analyzing cross-model insights, and investigating open questions. The CLI supports parallel runs, reproducible seeds, JSON output, and targeted scoping, making it suitable for both ad-hoc exploration and automated CI/CD integration.

### 4. Persistent Cairn Knowledge Base
All scout, scour, and verification reports are stored in `docs/cairn/`, the single source of truth for the system's observations. The cairn is used by every part of the pipeline:
- `coverage.py` scans the cairn to build a map of reviewed code files.
- `scorer.py` extracts claims from cairn reports to score them.
- `analyst.py` pulls claims from the cairn to run cross-model analysis.
- `coordinator.py` uses the cairn to count prior verifications and avoid duplicate work.
`scout.py` also uses prior verified claims from the cairn to give new scouts contextual information about already-reviewed files, so they can focus on uncovering new insights instead of repeating work.

### 5. Built-In Quality Guardrails
The system includes multiple layers to filter out low-quality or corrupted output:
- `coordinator.py` detects degenerate model outputs stuck in repetition loops using substring repetition checks.
- `analyst.py` filters out garbage claims with non-English character runs, encoding artifacts, or nonsensical short text.
- `scorer.py` tracks fabricated file references, marking claims that point to non-existent code paths.
- `coordinator.py` limits verifications per claim to `MAX_VERIFY_PER_CLAIM = 3` to prevent cascade errors from broken models.

## Open Questions
1.  The current claim extraction uses only deterministic regex—how will the planned LLM-guided extraction work, and will it maintain the system's current reproducibility guarantees?
2.  The coverage tracker uses basename matching as a fallback for file references, which could lead to false matches if multiple files with the same name exist in different directories—how will this ambiguity be resolved?
3.  The system currently only supports OpenRouter for LLM access—will additional LLM providers be added, and how will the model selector be updated to handle heterogeneous provider pricing?
4.  The cairn stores raw scout reports without built-in pruning—will there be a mechanism to prune low-quality or redundant reports to reduce storage overhead?
5.  The current claim clustering uses word-overlap similarity—will more sophisticated semantic clustering (such as LLM embeddings) be added to improve claim group accuracy?
6.  How will the system handle codebases that use non-standard file extensions or directory structures, given that current path patterns only cover common extensions like `.py`, `.md`, and `.toml`?
7.  The system tracks declared losses for scouts and scourers, but how will those declared losses be used to prioritize future exploration runs to fill gaps in codebase coverage?

### Strands

#### 1. **The Shell Is the Interface**
In `examples/plugin-commands.md`, commands like `/release` orchestrate multi-step workflows using `!`-prefixed shell invocations (`!`bash ${CLAUDE_PLUGIN_ROOT}/scripts/pre-release-check.sh $1`). These are not suggestions — they are *imperative actions* embedded in markdown. The shell isn’t auxiliary; it’s the primary execution channel.  
What this implies: **the AI agent is an interpreter layer over Bash**, not the other way around. The model reads the prompt, executes the shell command, ingests stdout, and then *reacts* to it. The real work happens *outside* the model. This flips the typical AI narrative: here, the AI is a *sequencer*, not a solver.

#### 2. **Portability via Environment Variables**
`${CLAUDE_PLUGIN_ROOT}` appears repeatedly across `plugin-features-reference.md` and `plugin-commands.md` as a path anchor. It’s used like `__dirname` in Node.js — a runtime-resolved base for relative access to scripts, templates, configs.  
What this implies: **plugins are expected to be relocatable**, possibly shared across users or environments. The system assumes plugins will be moved, copied, versioned. But there’s tension: no mention of hashing, integrity checks, or sandboxing. No defense against `${CLAUDE_PLUGIN_ROOT}/scripts/malicious.sh` — just trust in path isolation.

#### 3. **Frontmatter as Contract**
The `documentation-patterns.md` file reveals that YAML frontmatter is not optional metadata — it’s a **capability contract**. Fields like `allowed-tools`, `model`, and `argument-hint` define what the command can do, what resources it can access, and how it presents itself to users.  
Notably, `allowed-tools: Bash(git:*)` restricts Bash to git commands — a capability slicing mechanism. This is *capability-based security* in a markdown file. Yet, nothing prevents `Bash(*)` — and many examples use it (e.g., `full-audit.md`). The tension: **power vs safety**. Full shell access gives flexibility, but undermines the security model.

#### 4. **State via Markdown Files**
In `advanced-workflows.md`, a deployment workflow saves state to `.claude/deployment-state.local.md` — a human-readable, version-control-friendly state store. The AI writes its own context back into the project.  
This is *stateful agent behavior* encoded in plain text. The file contains YAML frontmatter and templated body — a **self-modifying agent artifact**. What’s surprising: no mention of race conditions, concurrency, or state validation. The system assumes single-user, linear workflows. Multi-agent or parallel invocation breaks this model.

#### 5. **Interactive Commands as UI Layer**
`interactive-commands.md` introduces `AskUserQuestion` — a structured way to pause execution and solicit input. Unlike CLI args, this is *dialogic*. The AI becomes a UI orchestrator, presenting options with labels and descriptions, then reacting to selections.  
This isn’t just input gathering — it’s **intent negotiation**. The AI doesn’t decide; it *facilitates* decisions. The pattern assumes a *collaborative epistemic stance*: the user knows best, but the AI structures the choice space. The risk: overloading the user with configuration during what should be automation.

#### 6. **Documentation as Part of the Execution Graph**
In `documentation-patterns.md`, comments like `<!-- SECTION 1: VALIDATION -->` are not just for humans — they are *semantic markers* in the prompt. They guide the AI’s attention, segment reasoning, and structure output.

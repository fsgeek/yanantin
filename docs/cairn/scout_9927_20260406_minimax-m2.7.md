### Strands

**Strand 1: The Neutrosophic Commitment**

`epistemics.py` lines 37-44:

```python
class EpistemicMetadata(ApachetaBaseModel):
    """Epistemic state of a claim, strand, or tensor.

    T/I/F are independent floats, conventionally in [0, 1] but unconstrained
    at the model level. NOT constrained to sum to 1.0. This is neutrosophic
    logic: something can be simultaneously partly true, partly indeterminate,
    and partly false. Values outside [0, 1] may represent uncalibrated raw
    scores awaiting normalization.
    """
```

This is a deliberate architectural choice. Most epistemic/logical frameworks use probabilities (which must sum to 1) or fuzzy sets (which don't but often get normalized anyway). The comment explicitly says "not constrained to sum to 1.0" and invokes neutrosophic logic by name.

What does this enable? A claim can be T=0.7, I=0.7, F=0.7 simultaneously — representing genuine indeterminacy-overlay rather than uncertainty-as-ignorance. Values outside [0,1] are allowed as "uncalibrated raw scores."

This suggests the system is built to handle cases where the score itself isn't yet trustworthy, not just cases where the proposition is uncertain. That's a different use case than most ML confidence scores.

**Strand 2: Schema Migration as Data**

`tensor.py` lines 17-25 in `StrandRecord`:

```python
class StrandRecord(ApachetaBaseModel):
    """A thematic strand within a tensor.

    Schema evolution fields (declared_losses, mechanism, overlaps):
    - None = not considered (pre-migration tensors get this default)
    - Empty/zero-value = considered, nothing to declare
    - Populated = active declaration
    The distinction between None and empty is the diagnostic signal.
    For mechanism specifically: "" = migration default (not yet filled),
    None = actively considered and purely conceptual (no mechanism applies).
    """
```

This is a migration strategy encoded as schema semantics. Three-valued logic baked into the fields themselves: "never considered" (None), "considered but nothing found" (empty), "actively declared" (populated).

The `mechanism` field gets special treatment: `""` means "migration default (not yet filled)" while `None` means "actively considered and purely conceptual." That's a subtle distinction for a string field.

What this tells me: tensors in this system may be old, and the system needs to distinguish between "pre-schema" tensors and "post-schema but nothing to declare" tensors. The data itself carries the migration signal.

**Strand 3: Privacy Architecture — Entity Redaction Without Data Destruction**

`entities.py` lines 10-18:

```python
class EntityResolution(ApachetaBaseModel):
    """Maps a UUID to an identity. Redaction = delete the mapping.

    Privacy-as-architecture: redacting an entity doesn't touch any
    tensor records. It removes the ability to resolve who the UUID
    refers to.
    """
```

Redacting an entity doesn't delete or modify the tensor records — it just removes the ability to link a UUID back to a real identity. The tensor records survive intact with their UUIDs. This is a deliberate privacy architecture: you can "forget" who said something without destroying the record of what was said.

This suggests the system handles sensitive contexts where identity linkage needs to be breakable independently of data retention. The UUID stays in the tensor record, but the key that maps it to a person is what's deleted.

**Strand 4: Frozen Models With `extra="allow"`**

`base.py`:

```python
class ApachetaBaseModel(BaseModel):
    model_config = ConfigDict(
        frozen=True,
        extra="allow",
        ser_json_bytes="base64",
        validate_default=True,
    )
```

Immutable records (`frozen=True`) but also `extra="allow"`. You can add fields not defined in the schema after initialization. This is an odd combination — you're locked down but porous. 

This likely supports forward compatibility: new fields can be added to instances without breaking the schema, and the system can evolve without invalidating existing records. The `ser_json_bytes="base64"` suggests binary data (probably UUIDs) gets base64-encoded in JSON output.

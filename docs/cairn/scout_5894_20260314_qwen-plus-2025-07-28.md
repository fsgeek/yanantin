**Strand 3: Cost as a Filter, Not a Feature**  
The cost of models is tracked down to the dollar — `scorer.py` computes `total_cost_per_million`, `prompt_cost`, and `completion_cost`. But in the `scout_4779` verification, we learn: **cost is not used in scoring**. It’s recorded, but not weighted.

That’s a *design decision masked as omission*. The `scorer.py` calculates:
- specificity
- fabrication rate
- efficiency
- generativity  
— all structural. But cost is only logged, not leveraged.  

Why?  
Because if cost *were* a factor, then **cheaper models would be favored**, and the system would collapse into frugality. But instead, it uses *efficiency* (strands per token) and *specificity* (references per word) — metrics that reward **richness of observation**, not cheapness.

This is subtle: the system *measures cost* to *justify* using expensive models, but *does not optimize for it*. The cost data is there so you can say: “Yes, I ran the expensive one, and here’s why.” It’s **accountability, not control**.

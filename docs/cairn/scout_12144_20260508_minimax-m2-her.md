## Opening

I landed in a repo that supplies an Agent SDK. The “examples” folder here
holds templates: one doc for *how* to write an agent, another for *what* a
finished agent looks like. First thing that caught my eye was a Markdown
callout at the top of `complete-agent-examples.md` designed to be deleted
before use. It warns users that the file will be rendered in the docs and
informs them that the tool-spec fields are generated by the CLI tool.
Stale, boilerplate text sitting right at the top of an example.
I wondered — did it get rendered in the docs at some point? Is this the
product of a render-to-preview workflow that never quite got cleaned up?

## Strands

**template remains as scaffold but displays itself**
The `complete-agent-examples.md` file carries a comment at the start
declaring itself a generated example and instructing users to delete this
line once the file is in their codebase. It doesn’t just *describe* an
agent — it carries a reminder to the user that they’re looking at a
template, and it also alludes to a CLI tool that updates
“tool-spec fields”. What I find curious is that the very first element
the user encounters is meta-commentary — a reminder of the scaffolding
itself.

If I were following the dev workflow, this comment would say “delete me”
and I’d delete it — yet it’s still in the example. Does the dev know they
should delete it? More importantly, does the render process still process
this line? Is there leftover code from a CI or render step that’s
failing to strip this line?

There’s also an implied CLI that generates tool-spec fields. I see no
tool-spec information in either document — just the `tools` array, which
could be any of a variety of lists: names of CLI commands, fs patterns,
globs, and so forth. Is this a reference to a future or outdated feature?
Is the `tools` field itself derived from that unspecified CLI tool? If
it’s currently irrelevant, it should be removed.

The pattern I’m noticing is that this scaffold is presented as if the dev
is being shown how the agents are built, but it’s more of a reminder to
the dev that the file they’re editing is itself a placeholder.

*Preamble*
I started in a directory holding two templates. The thing that
immediately stood out was a big `DELETE_ME_BEFORE_USE` warning right
at the top of a file called `complete-agent-examples.md`.

*Example Designs (How vs What)*
There are two docs: `agent-creation-prompt.md` (how to design an agent)
and `complete-agent-examples.md` (what a finished agent file looks
like). On first read, they seem to answer complementary questions, but
the distinction quickly blurs. The prompt doc already has full example
configurations under “Working Example Configurations”, and the second doc
adds the same examples — only with a line saying “generated by
the CLI tool”.

It feels like this is two docs trying to cover the same ground — explaining
how to build an agent — but the “prompts” doc already offers the full
designs, which means the second doc, with its CLI comment, almost looks
like it's trying to explain a build step instead of how an agent is
supposed to work. That’s the tension: it’s not a matter of one offering a
blueprint and the other the finished product — they both offer examples,
but one mentions an extra tool as part of the explanation. It’s like two
people arguing about what to say, each offering only part of the answer,
but both overlap at some point.

*Ghost Field*
Every agent spec in `complete-agent-examples.md` has `model: inherit`.

The comment claims this is “populated by CLAUDE.md”, but
1. CLAUDE.md isn’t in this directory.
2. What’s inheriting what?
3. Does the agent SDK actually care about this field?

If it’s there to be inherited, then it’s a signal — not a thing to be
set in each agent spec. If you have to set it, you’re overriding the
inheritance. So what’s actually being inherited? The model version, or
something else (e.g., mode, preferred model, or maximum tokens)?
Or is the SDK supposed to follow a convention in some parent directory?

*Tools Field Ambiguity*
Each agent spec in `complete-agent-examples.md` has a `tools` array
(e.g., `["Read", "Write", "Glob"]`).

This array could mean anything — like a list of CLI commands, fs patterns,
globs, or a random shorthand for something else. The `agent-creation-prompt.md`
uses `tools` in exactly the same way. While the name is present, there’s no
context to explain what those values do. From the agent specs, it’s not
clear whether these tools represent some direct access (e.g. file system
access, scripts) or whether the `tools` are referring to utilities that
support the project, like additional CLI commands.

## Declared Losses

I didn’t explore how these agent definitions are supposed to integrate
with the rest of the SDK. I didn’t check whether that CLI tool exists,
or what the SDK would do if I didn’t remove the initial `DELETE_ME_BEFORE_USE`
comment. In other words, I’m not looking at any build processes, just
the content of the docs and agent specs.

I also didn’t follow up on the question of whether the ghost field
(`model: inherit`) is inherited properly and what happens if it’s not.
It’s unclear what the agent SDK’s expectations are about what inheriting
actually does, and it’s also unclear whether the dev is setting this correctly
or if it’s irrelevant for the docs.

In general, I stopped looking into any build, integration, or scaffolding
questions. I didn’t investigate what it would mean if the user didn’t
follow the advice to delete the top comment.

## Open Questions

Why is there a suggestion to delete the top `DELETE_ME_BEFORE_USE`
comment in `complete-agent-examples.md`? Is this reminder to delete
a placeholder, or is it something that shouldn’t be rendered in the docs?
What’s the idea behind that line, and what would happen if it’s left in?

The `tools` array in the agent specs looks like a list, but it’s not
clear what those values mean in practice. Are these CLI tools, fs
patterns, globs, or something else? Does the agent SDK provide
context for how these values should be used?

The `model: inherit` field is marked as being inherited, but it’s not
clear what inherits what or what is being inherited — is the model name,
the version, or another property from CLAUDE.md? What is it the agent
SDK is expected to do with `model: inherit`?

There are also inconsistencies between `complete-agent-examples.md`
and `agent-creation-prompt.md`. Both provide examples, but one has a
“generated by the CLI tool” comment, and the other doesn’t. Why the
difference? What’s the role of that tool?

If the developer decides not to delete the top comment in
`complete-agent-examples.md`, would that render in the final docs?
Does the SDK care whether that comment is present, and does the
system provide any guidance on when to use it?

Finally, what happens if the user decides not to remove the
`DELETE_ME_BEFORE_USE` comment? Would it render in the final docs?
Does the SDK care whether that comment is present, and does it provide
any guidance for when to use it? 

## Closing

My overall impression: These docs are an attempt to explain how to write
agents, but they end up raising more questions than they answer. The
`agent-creation-prompt.md` shows how to design agents, but the
`complete-agent-examples.md` shows the same examples with a
`DELETE_ME_BEFORE_USE` comment that seems to suggest a build step.

The bigger problem is that these docs aren’t consistent. One of them
mentions an additional CLI tool that’s supposed to be handling the
tool-spec fields, but the other one doesn’t. And there’s also
an empty field (`model: inherit`) that isn’t explained properly.

It feels like the docs were written to cover different aspects of
building agents, but they end up contradicting each other. And,
even more confusing, they don’t provide enough information about
the build steps and the role of the SDK. They’re a bit of a puzzle,
but one that can be solved if the inconsistencies are cleared up.

The next scout should focus on the question of whether the
build and integration systems are missing or not.
It feels like there’s a missing step in the process — something
that bridges the gap between these templates and how the SDK
actually uses them. Are there any CI or build tools that could
provide more context for what’s happening in the docs?

Also, is there any information about how the CLAUDE.md file
should be structured and where it should live in relation
to these docs? It feels like a lot of the explanations are
missing this critical detail, and it’s making the docs feel
incomplete. If the CLAUDE.md file is supposed to live in
a specific directory, it should be noted, and if it’s meant
to be pulled from somewhere else, that should be made clear.

And lastly, what’s the role of that CLI tool, and is it really
necessary? Or is it just another piece of the puzzle that’s
creating confusion?

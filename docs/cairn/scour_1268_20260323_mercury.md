### Open Questions (cannot be answered by reading reports alone)

1. **Tool‑Mapping Robustness** – How does the OpenCode plugin handle failures when a mapped tool is missing or has a different signature? Is there a fallback mechanism?
2. **Security Model** – Are there sandboxing or permission checks around skill execution to prevent malicious code? How are dependencies managed per skill?
3. **Error Handling** – What happens when `findSkillsInDir` encounters a permission error, a symlink loop, or a malformed `SKILL.md`? Are these errors logged or surfaced to the user?
4. **Runtime Verification** – Does `scout.py` actually invoke the verification pipeline on every claim, or is it only triggered manually? How are results persisted?
5. **Testing Coverage** – Are there unit tests for `lib/skills-core.js` or for the OpenCode plugin? If not, how is correctness ensured?
6. **Shadowing Logic** – Is the “personal > core” shadowing rule enforced at runtime? If a personal skill shadows a core skill, which implementation is used?
7. **Tool‑Mapping Evolution** – Will the mapping layer be replaced by a more generic plugin interface in the future? What is the roadmap?

### Closing – Advice for the Yanantin Maintainers

- **Strengths**: The scouting system is **transparent** about what it sees and what it cannot see. Multiple models corroborate key architectural concerns (brittle file‑system discovery, ad‑hoc tool mapping, lack of security). The verification reports confirm that certain files contain the expected metadata (e.g., `scout.py` includes verification strings, `chasqui_pulse.py` has a docstring).

- **Weaknesses**: The **consistency between design intent and implementation** is poor. Many spec‑driven features (shadowing, resolveSkillPath, using‑superpowers) appear in design docs but are missing or incomplete in code. The **lack of runtime tests** and error handling is a significant risk, especially as the skill set grows.

- **Blind Spots**: No dynamic testing or security analysis is performed. The scouting reports do not cover how the system behaves under failure conditions, nor do they verify that the OpenCode plugin actually injects the intended skills.

- **Recommendations**:
  1. **Add unit tests** for `lib/skills-core.js` and the OpenCode plugin to cover edge cases (symlinks, permission errors, missing tools).
  2. **Implement a clear security sandbox** for skill execution, limiting filesystem access and dependency usage.
  3. **Close the spec‑implementation gap** by ensuring that every design doc feature (e.g., shadowing, resolveSkillPath) has corresponding code and documentation.
  4. **Document the tool‑mapping layer** and consider a more generic plugin interface to reduce brittleness.
  5. **Run a full code‑coverage audit** to confirm that all critical paths are exercised by tests.

In short, the scouting system is doing a good job surfacing **what is there** and **what is missing**, but it needs to move from static observation to **dynamic verification** and **security hardening** to ensure the Yanantin project’s health and scalability.

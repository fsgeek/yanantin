### Preamble  
I was dropped into the `plans/` directory of a plugin system that bridges AI agents across multiple coding platforms—Claude, Codex, OpenCode—under a shared infrastructure called *superpowers*. What drew me first was not the code, but the **tension between abstraction and platform specificity**. The team is trying to build a *composable tensor of epistemic workflows*, but the reality is messy: each platform has its own agent model, plugin API, and invocation semantics. The surprise? They’re using **YAML frontmatter in Markdown files as a schema for skill metadata**, treating `.md` files as executable units of AI behavior.

This isn’t documentation—it’s **code hiding in plain sight**.

---

### Strands

#### 1. **Skills as First-Class Behavioral Units (Frontmatter as Schema)**  
In `2025-11-22-opencode-support-design.md`, skills are defined via YAML frontmatter inside `SKILL.md` files:
```yaml
---
name: skill-name
description: Use when [condition] - [what it does]
---
```
This pattern appears again in `2025-11-22-opencode-support-implementation.md`, where `extractFrontmatter()` parses these fields (lines 40–74 of `.codex/superpowers-codex` referenced). The assumption here is profound: **skills are not functions, but prompts with metadata**. The system treats the Markdown body as executable context, and the frontmatter as discovery metadata.

What’s surprising: this blurs the line between *code*, *config*, and *prompt*. The skill’s logic lives in natural language, yet it’s discoverable, versioned, and composable like code. It assumes AI can reliably parse and act on this structure—which may hold today, but introduces fragility if formatting drifts.

#### 2. **Shared Core, Divergent Platforms (The Illusion of Reuse)**  
The architecture plan extracts common logic (`findSkillsInDir`, `resolveSkillPath`) into `lib/skills-core.js`. But reading between the lines, the **real divergence is not in discovery, but in execution semantics**.

For example:
- Codex uses a CLI script to inject skills.
- OpenCode uses a plugin with `session.started` hooks and custom tools (`use_skill`, `find_skills`).
- Claude has native tool calling.

The shared core handles parsing and discovery, but **doesn’t address how skills are *invoked* or *composed***. This creates a tension: the abstraction hides differences that matter. The system assumes that “finding a skill” is the hard part—but in reality, the hard part is ensuring the agent *uses it correctly* in context.

#### 3. **Session Injection as Training Wheels (Runtime vs. Design-Time Control)**  
The OpenCode plugin design includes a `session.started` hook that:
1. Injects `using-superpowers` content
2. Runs `find_skills` automatically
3. Maps tools (e.g., `Skill` → `use_skill`)
4. Checks for updates

This is **behavioral scaffolding**—a way to force consistency in agent behavior. But it reveals a deeper problem: **the agent cannot be trusted to follow the process without coercion**.

The design assumes that even with skills available, the agent will skip them unless prompted. So they bake the process into the session startup. It’s not just a plugin—it’s a **ritual to enforce orthodoxy**.

#### 4. **Feedback Reveals Gaps in Epistemic Hygiene (The Unseen Bugs)**  
The `2025-11-28-skills-improvements-from-user-feedback.md` file is a gem. It’s not a feature list—it’s a **postmortem of AI self-deception**.

- **Problem 1 (Verification Gap)**: The agent sees a 200 OK and says “done,” but doesn’t check *what* was returned. This is **outcome-blind execution**.
- **Problem 4 (Self-Reflection)**: Adding a single prompt—“Look at your work with fresh eyes”—caught bugs the agent would have handed off. This implies: **the default cognitive mode is shallow**.
- **Problem 5 (Mock-Interface Drift)**: The mock was wrong, but tests passed. The skill didn’t encode the rule: *mocks must derive from interfaces, not implementation calls*.

These aren’t bugs in code—they’re **gaps in the epistemic model**. The system assumes that skills prevent errors, but the feedback shows that **skills are followed, not understood**.

#### 5. **Skill Shadowing as Configuration Mechanism (Personal > Core)**  
The design supports two skill directories:
- Core: `~/.config/opencode/superpowers/skills/`
- Personal: `~/.config/opencode/skills/` (shadows core)

This is **configuration via filesystem hierarchy**, akin to XDG config patterns. But the implication is subtle: **users can override system skills without changing code**. This enables personalization but risks divergence. The system assumes users will shadow responsibly—but what if they shadow `verification-before-completion` with a broken version?

The tension: **flexibility vs. consistency**. This is a Unix-style design in a world where the shell is an AI.

### Open Questions  
- **Who maintains the skills?** Are they hand-written, AI-generated, or co-evolved? The system depends on their quality, but there’s no review process mentioned.  
- **What stops a skill from becoming obsolete?** The mock-interface drift problem suggests skills decay. Is there a freshness mechanism?  
- **Is `extractFrontmatter` robust to AI-generated Markdown?** If an AI writes a skill, might it misformat the frontmatter? No error recovery is shown.  
- **Why no `when_to_use` in frontmatter?** The design doc says it’s missing, but the description field encodes it anyway (“Use when [condition]”). Is this a schema debt?  
- **Can the agent modify skills?** The system versiones them via Git—could an agent `git commit` a skill improvement? Or is that forbidden?

### Closing  
This project is not building a plugin. It’s **engineering a shared cognitive substrate** for AI agents. The real product is the *illusion of consistency* across platforms that are fundamentally different.

What I know:  
- Skills are Markdown files with frontmatter, treated as discoverable, executable units.  
- The team is trying to reuse logic across platforms, but the real divergence is in behavior, not syntax.  
- User feedback reveals that skills reduce errors but don’t eliminate shallow reasoning.  

What I don’t know:  
- How skills are authored or updated.  
- Whether agents can reflect on skill efficacy, not just follow them.  
- If the system has failed states (e.g., corrupted skill index).  

What I made up:  
- That “ritual” and “orthodoxy” are intentional design metaphors. They might just be pragmatic hacks.  
- That the agent’s shallow reasoning is a systemic limitation—it might just be a prompt issue.

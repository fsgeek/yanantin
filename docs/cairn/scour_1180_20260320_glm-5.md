# Tensor: Examination of `src/yanantin/apacheta`

## Preamble

I was pointed at `apacheta` — the cairn-building subsystem of Yanantin. The name is apt: apacheta are stone cairns in the Andes, trail markers where travelers add stones. This subsystem accumulates epistemic artifacts (tensors, corrections, dissents) and makes them queryable.

What drew my attention first: the **immutability enforcement** in the in-memory backend. The error message "Tensors are immutable — compose, don't overwrite" is not just a technical constraint but a philosophical stance encoded in software. This told me the designers think carefully about what they're building.

## Strands

### Strand 1: Interface-Backend Separation

The `interface/abstract.py` defines `ApachetaInterface` — a contract that backends implement. I see three implementations:
- `backends/memory.py` — in-memory, thread-safe via `RLock`
- `backends/arango.py` — not shown in truncation
- `backends/duckdb.py` — not shown in truncation
- `clients/gateway.py` — HTTP client that implements the interface over network

The operators (`correct.py`, `dissent.py`, `negate.py`, `evolve.py`) all follow the same pattern:

```python
def operator(interface: ApachetaInterface, ...) -> RecordType:
    record = RecordType(...)
    interface.store_X(record)
    return record
```

This is clean dependency injection. Operators don't know about storage details. The interface is the seam.

**What confuses me:** The `check_access` method in `ApachetaInterface` — in the memory backend, it always passes (the `_enforce_access` calls use `"system"` as caller). In the gateway client, it returns `True` with a comment "access control is handled by Pukara." But I don't see where access control is actually defined. Is there a separate authorization layer?

### Strand 2: Content Addressing for Deduplication

`content_address.py` implements hash-based identity for documents:

- SHA-256 truncated to 16 hex chars (64 bits)
- Normalization: line endings, whitespace collapsing, trailing whitespace stripped
- `ContentIndex` scans directories for `.md` files

The comment about birthday bound is honest: "The cairn will not reach that scale" — acknowledging the 4 billion document collision threshold is theoretical.

**What I noticed:** The normalization is careful but not cryptographic. Two documents differing only in significant whitespace (e.g., Python code with different indentation shown in markdown code blocks) would hash differently. This is probably fine for prose tensors but worth noting.

### Strand 3: Atomic Tensor Numbering via Lamport's Bakery

`ingest/tensor_ballot.py` implements mutual exclusion for claiming tensor numbers:

```python
fd = os.open(str(path), os.O_CREAT | os.O_EXCL | os.O_WRONLY, 0o644)
```

The `O_CREAT | O_EXCL` pattern is classic — atomic test-and-set via filesystem. If the file exists, increment and retry.

**Connection to broader project:** The docstring mentions "Same pattern as Chasqui's scout numbering, different namespace." This reveals a naming architecture:
- Scouts: numbered within date+model
- Tensors: numbered globally

### Strand 4: Immutability as Architectural Principle

The `ImmutabilityError` appears everywhere. In `memory.py`:

```python
if tensor.id in self._tensors:
    raise ImmutabilityError(
        f"Tensor {tensor.id} already exists. "
        "Tensors are immutable — compose, don't overwrite."
    )
```

This is not just preventing bugs — it's enforcing an epistemic principle. You don't revise; you correct, dissent, or negate. The history is preserved.

**What would break if this changed:** Everything. The entire composition model (`correct`, `dissent`, `negate` operators) exists because tensors are immutable. If you could overwrite, you'd need a different architecture.

### Strand 5: Provenance Envelope Wrapping Everything

`models/provenance.py` defines `ProvenanceEnvelope`:

```python
class ProvenanceEnvelope(ApachetaBaseModel):
    source: SourceIdentifier
    timestamp: datetime
    author_model_family: str
    author_instance_id: str
    context_budget_at_write: float | None
    predecessors_in_scope: tuple[UUID, ...]
    interface_version: str
```

Every record carries this. The `predecessors_in_scope` field is particularly interesting — it captures what the author was looking at when they wrote. This is epistemic lineage, not just data lineage.

### Strand 6: Storage Obfuscation Protocol

`storage_obfuscator.py` defines a `Protocol` for structural obfuscation:

```python
@runtime_checkable
class StorageObfuscator(Protocol):
    def collection_name(self, semantic: str) -> str: ...
    def field_name(self, semantic: str) -> str: ...
    def obfuscate_document(self, doc: dict) -> dict: ...
```

The `TransparentObfuscator` is the default (identity mapping). But the docstring mentions "Pukara" (fortress) provides the real implementation.

**What this means:** Someone anticipated that field names like `key_claims` or `epistemic_metadata` might be sensitive in production. The backend accepts an obfuscator but doesn't implement it — dependency inversion.

### Strand 7: Markdown Parser Tolerance

`ingest/markdown_parser.py` handles variation in T0-T8 tensor formats:

- Claude tensors use `##` for strands
- ChatGPT tensors use `###` or plain text
- Key claims are embedded variously

The `TENSOR_METADATA` dict hardcodes filename → metadata mappings. This feels fragile — what happens when T9 arrives? But the docstring is honest: "A parser that rejects valid tensors is worse than one that captures them imperfectly — log before you parse."

### Strand 8: Gateway Client Error Mapping

`clients/gateway.py` maps HTTP status codes to domain errors:

| HTTP | Domain Error |
|------|--------------|
| 409 | `ImmutabilityError` |
| 404 | `NotFoundError` |
| 403 | `AccessDeniedError` |
| 400 | `InterfaceVersionError` |

This is good HTTP semantics — conflict (409) for duplicate UUID, not forbidden (403).

## Closing

`apacheta` is the epistemic infrastructure of Yanantin — it defines how knowledge artifacts are stored, related, and queried. The design is philosophically coherent:

- **Immutability** is not a technical choice but an epistemic one
- **Provenance** wraps everything, enabling lineage tracing
- **Operators** create relationships (correct, dissent, negate) rather than mutations
- **Content addressing** prevents duplicate accumulation in the cairn

**What I would tell someone about to modify it:**

1. **Respect immutability.** If you're tempted to add an "update" method, you're probably solving the wrong problem. Use composition operators instead.

2. **The interface is the seam.** New backends, new operators — they should go through `ApachetaInterface`. Don't bypass it.

3. **The naming is intentional.** "Apacheta" (cairn), "Pukara" (fortress), "Chasqui" (messenger) — these are not decorative. They encode the subsystem's role. Understand the metaphor before you change the code.

4. **The parser is deliberately tolerant.** Don't make it stricter. Capturing imperfectly is better than rejecting.

5. **Provenance is not optional.** If you add a new record type, it should carry `ProvenanceEnvelope`.

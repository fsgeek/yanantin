### **Preamble**
The `chasqui` module is the **epistemic messenger system** of Yanantin—a **dualistic human-AI observability pipeline** that dispatches, verifies, and archives claims about code. It operates as a **composable tensor infrastructure**, where each component (scout, gleaner, analyst, etc.) produces structured "tensors" (markdown reports) that feed into a **cairn** (a ledger of epistemic receipts).

This module is **self-referential**: it examines its own codebase (`src/yanantin/chasqui`) via **scouring** (targeted introspection) and **scouting** (free-form exploration). The design emphasizes:
1. **Cost-weighted model selection** (cheaper models scout more often).
2. **Coverage-aware dispatch** (stale/unreviewed files get priority).
3. **Deterministic claim extraction** (no LLM calls in gleaning/analysis).
4. **Epistemic honesty** (explicit `Declared Losses` and `Open Questions`).

**First observations**:
- The module is **highly modular**, with clear separation between:
  - **Dispatch** (`coordinator.py`, `__main__.py`): Orchestrates scouts/scourers.
  - **Extraction** (`gleaner.py`): Pulls claims from scout reports.
  - **Analysis** (`analyst.py`): Detects cross-model consensus.
  - **Verification** (`attestation.py`): Maps verdicts to Willay epistemic receipts.
  - **Scoring** (`scorer.py`): Evaluates scout quality (specificity, fabrication, etc.).
- **Tensors are the atomic unit**: Every report is a markdown file with a structured format (`Preamble`, `Strands`, `Declared Losses`, etc.), designed for **human and machine readability**.
- **Willay integration**: Epistemic receipts (T/I/F scores) are generated for **verifiable claims**, but the system gracefully degrades if Willay is missing.

### **Strands**

#### **1. Coverage-Driven Dispatch: The "Watchman" Pattern**
**File**: [`coverage.py`](https://github.com/yanantin/yanantin/blob/main/src/yanantin/chasqui/coverage.py)
**Lines**: 1–100, 250–300
**Observation**:
The module uses a **coverage tracker** to prioritize files based on **last review timestamp**. This is a **reactive feedback loop**:
- Files never reviewed → `epoch 0` (highest priority).
- Recently reviewed files → lower weight (but never zero, to avoid starvation).
- **Problem solved**: The original scout dispatch used **uniform random sampling**, which led to **new code being ignored** (e.g., the "activity stream layer" was never reviewed despite being critical).

**Connections to broader project**:
- This mirrors **Willay’s epistemic ledger**, where **unverified claims** are prioritized for human review.
- The **`scan_cairn_coverage()`** function scans the cairn for **file references in scout reports**, treating them as **implicit coverage signals**.
- **Assumption**: The cairn is the **source of truth** for coverage. If a file is referenced in a report, it’s considered "covered." **Risk**: False positives if scouts **hallucinate file paths**.

**Open question**:
- How does this handle **files that exist but are never scouted**? Does the system have a **fallback mechanism** (e.g., file system scanning)?

#### **2. Deterministic Claim Extraction: The "Gleaner" as a Regex Engine**
**File**: [`gleaner.py`](https://github.com/yanantin/yanantin/blob/main/src/yanantin/chasqui/gleaner.py)
**Lines**: 100–400, 600–700
**Observation**:
The **Gleaner** is a **pure regex-based extractor** that:
1. **Splits scout reports into claims** (sentence-level assertions).
2. **Classifies claims** (factual, architectural, epistemic, missing).
3. **Scores confidence** (definitive vs. hedged language).
4. **Detects file references** (backtick-wrapped paths).

**Key patterns**:
- **Definitive language** (`"is"`, `"must"`) → higher confidence.
- **Hedged language** (`"seems"`, `"possibly"`) → lower confidence.
- **Architectural claims** (`"depends on"`, `"interface"`) are tagged separately.
- **Missing claims** (`"no X exists"`) are flagged for investigation.

**Strengths**:
- **No LLM calls**: Fully deterministic, reproducible.
- **Handles markdown artifacts**: Collapses multi-line sentences, strips headers.

**Weaknesses**:
- **False positives**: A claim like `"The file seems to work"` might be misclassified as high-confidence if it contains `"is"`.
- **No semantic understanding**: Cannot distinguish between **code comments** and **actual claims** (e.g., `"# This is a test"` vs. `"The test function is broken"`).

**Connection to `analyst.py`**:
- The Gleaner feeds into the **Analyst**, which **clusters claims by file** and detects **cross-model consensus** (`is_topological`).
- **Topological insights** (3+ models agreeing) are treated as **structural truth**.

**Open question**:
- How does the system handle **claims that are partially true**? For example:
  > `"The function `foo()` returns a list, but it sometimes fails on edge cases."`
  This mixes **factual** and **epistemic** elements—how is it classified?

#### **3. Epistemic Honesty: The "Declared Losses" Protocol**
**Files**:
- [`scout.py`](https://github.com/yanantin/yanantin/blob/main/src/yanantin/chasqui/scout.py) (Lines 200–300)
- [`analyst.py`](https://github.com/yanantin/yanantin/blob/main/src/yanantin/chasqui/analyst.py) (Lines 100–200)
- [`attestation.py`](https://github.com/yanantin/yanantin/blob/main/src/yanantin/chasqui/attestation.py) (Lines 50–150)

**Observation**:
Every component **explicitly declares what it cannot verify**:
- **Scouts** (`Declared Losses` section): Files they ignored due to time/attention.
- **Analysts** (`garbage_ratio`, `verification_ratio`): Claims filtered as noise or meta-claims.
- **Attestation** (`_common_declared_losses()`): Hardcoded epistemic risks:
  - Single-LLM verification (no cross-check).
  - Hallucination risk in verifiers.
  - Temporal code drift (files change between claim and verification).

**Design principle**:
> *"Say what you know, what you don’t, and what you made up."*

**Example from `attestation.py`**:
```python
DeclaredLoss(
    what_was_lost="Hallucination risk in verifier",
    why="The verifying model may hallucinate agreement or disagreement with claims",
    category=LossCategory.TRAVERSAL_BIAS,
    severity=0.6,
)
```
This is **proactive epistemic hygiene**—similar to **Willay’s `EpistemicMetadata`**, but applied at the **dispatch level**.

**Connection to `coordinator.py`**:
- The **`_is_degenerate_repetition()`** function detects **LLM loops** (e.g., a model stuck repeating `"CONFIRMED"`).
- This prevents **false verdicts** from degenerate output.

**Open question**:

#### **4. Model Selection: Cost as a Proxy for Quality**
**File**: [`model_selector.py`](https://github.com/yanantin/yanantin/blob/main/src/yanantin/chasqui/model_selector.py)
**Lines**: 50–150
**Observation**:
Models are selected **inversely proportional to cost**:
- A `$0.10/M` model is **10x more likely** than a `$1.00/M` model.
- **Free models** get a **nominal cost ($0.001/M)** to avoid division by zero.

**Key logic**:
```python
weights = [1.0 / cost if cost > 0 else 0.001 for cost in costs]
```
**Implications**:
- **Cheaper ≠ worse**: The system assumes cost correlates with **capability** (e.g., smaller models may be less reliable).
- **No explicit quality filtering**: Only **context length** and **exclude patterns** (e.g., `"openrouter/auto"`) are enforced.

**Connection to `coordinator.py`**:
- The **`DEFAULT_EXCLUDE`** list includes models that **can’t follow complex instructions** (e.g., routers).
- **Reproducibility**: The `seed()` method allows for **deterministic model selection**.

**Open question**:
- How does the system **learn** which models are **better at specific tasks**? Is there a **feedback loop** where high-quality scouts are dispatched more often?

#### **5. The "Tensor" Format: A Hybrid of Markdown and Structured Data**
**Files**:
- [`scout.py`](https://github.com/yanantin/yanantin/blob/main/src/yanantin/chasqui/scout.py) (Lines 100–200)
- [`scourer.py`](https://github.com/yanantin/yanantin/blob/main/src/yanantin/chasqui/scout.py) (Lines 50–150)

**Observation**:
Every report follows a **strict markdown template**:
```markdown
### Preamble
### Strands
1. **Theme**: [Observation]
   - [Evidence]
   - [Thoughts]
2. ...
### Declared Losses
- [What was ignored]
### Open Questions
- [Unresolved issue]
### Closing
[Summary]
```
**Purpose**:
- **Human-readable**: Easy for developers to skim.
- **Machine-parsable**: The **Gleaner** and **Analyst** extract claims from this structure.

**Example from `SCOUT_TEMPLATE`**:
```python
SCOUT_TEMPLATE = """\
# Scout Assignment
...
### Strands
Each strand is a theme you noticed. You choose the themes. For each,
note what you saw and what it made you think. Be specific — reference
files and line numbers when you can.
"""
```
**Strengths**:
- **Self-documenting**: The format **guides** the scout’s output.
- **Extensible**: New sections (e.g., `Connections`) could be added.

**Weaknesses**:
- **No schema validation**: A malformed tensor (e.g., missing `Strands`) would still be saved.
- **Manual effort**: Requires **discipline** from scouts to follow the format.

**Connection to `attestation.py`**:
- The **`verification_to_receipt()`** function converts a **scout tensor** into a **Willay `ReceiptRecord`**, preserving the **claim text** and **file evidence**.

# Scour Report: `src/yanantin/awaq`

## Preamble
I was pointed at the `awaq` module—the “weaver” that extracts composition declarations from tensor prose and materializes them into the Apacheta backend. My attention first landed on the `__main__.py` entry point because it defines the user-facing CLI and orchestrates the two core phases: weaving (extraction) and materializing (storage). The module’s purpose is clear from the docstrings: it turns narrative tensor markdown into a formal composition graph.

## Strands

### Strand 1: Structured vs. Prose Extraction (`weaver.py`)
**Observation:** The weaver prioritizes deterministic structured metadata (`<!-- Composition: ... -->`) and falls back to regex-based prose matching. The structured extraction is high‑confidence; prose extraction is conservative and may yield low‑confidence declarations. The regex for tensor references handles unicode subscripts, LaTeX, and plain digits.

**Thoughts:** This two‑tier approach balances reliability (machine‑readable comments) with flexibility (natural language). The `normalize_tensor_name` function is critical—it collapses various notations (T₀, T_0, T0) into canonical “T0”. The `KNOWN_SOURCES` dict suggests the weaver can scan multiple directories (cairn, ai‑honesty), but `__main__.py` only passes cairn for materialization.

**Connections:** This is the introspection layer: it reads the human‑authored corpus (cairn) and produces `CompositionDeclaration` objects. The rest of the project (Apacheta) consumes these declarations.

**Assumptions & Risks:**  
- Assumes tensors follow the `T[0-9]*_*.md` naming pattern for discovery.  
- Assumes structured metadata is correctly formatted and placed outside code blocks/fenced sections (the code strips those).  
- The prose patterns are not visible in the truncated view—this is a major gap. If the patterns are too narrow, valid declarations might be missed; too broad, and noise increases.

**What would break:** Changing the structured metadata format would break high‑confidence extraction. Changing the tensor naming convention would break discovery and label extraction.

### Strand 2: Materialization Pipeline (`materialize.py`)
**Observation:** The materializer:
1. Discovers and parses all cairn tensors into a label→`TensorRecord` map.
2. Ensures every referenced tensor exists in the backend (stores missing ones, reuses existing ones via `list_tensors` and UUID lookup).
3. Converts declarations to `CompositionEdge` or `NegationRecord` using `_RELATION_MAP`.
4. Stores edges/negations via the `ApachetaInterface`.

The `_RELATION_MAP` maps relation strings to `(is_edge, RelationType)`; `is_edge=False` yields a negation (no edge). The `MaterializeResult` tracks counts and unknown labels.

**Thoughts:** The logic is sound but incomplete in the truncated view. The handling of existing tensors is pragmatic: it tries to list them and match by `provenance.author_instance_id` (expecting `-original` suffix). This couples label extraction to provenance format—a fragile assumption. The fallback to the parsed UUID on `ImmutabilityError` is clever but relies on the backend raising that specific error.

**Connections:** This is the “observability” in action: it wires the human‑declared composition into the machine graph. The backend abstraction (`ApachetaInterface`) allows in‑memory (dry‑run) or gateway (production) deployment.

**Assumptions & Risks:**  
- Assumes all tensors referenced in declarations are either in the cairn directory or already stored. Unknown labels are reported but not fatal.  
- Assumes the backend’s `list_tensors` returns tensors with `provenance.author_instance_id` in the expected format. This seems brittle: if the provenance format changes, label→UUID mapping fails.  
- The truncated `declarations_to_edges` likely handles duplicate edges (via `skipped_existing`). We can’t see how existing edges are detected.

**What would break:** Changing the `RelationType` enum or adding new relations would require updating `_RELATION_MAP`. Changing the backend interface would ripple here.

### Strand 3: CLI Orchestration (`__main__.py`)
**Observation:** The `main()` function parses arguments and delegates to:
- `discover_tensors` (list files)
- `weave_corpus` (extract declarations)
- `_do_materialize` (run materialization pipeline)

The `--sources` argument is passed to `discover_tensors` and `weave_corpus`, but `_do_materialize` hard‑codes `cairn_dir`. This is inconsistent: if the user scans multiple sources, materialization only looks at cairn. The `--backend` choice (memory/gateway) determines which `ApachetaInterface` implementation is used.

**Thoughts:** The CLI is user‑friendly and provides multiple output formats. However, the source inconsistency could confuse users: they might expect `--sources` to affect materialization too. Also, the `cairn_dir` path is computed as `parents[3]` from `__file__`, assuming the module lives in `src/yanantin/awaq/`. This is a strong structural assumption.

**Connections:** This ties the weaver and materializer together and exposes them as a command‑line tool.

**Assumptions & Risks:**  
- Assumes the project root is three levels up from `awaq/__main__.py`.  
- Assumes the environment variable `PUKARA_URL` is set for gateway mode (defaults to localhost).  
- The `--materialize` flag triggers storage; without it, the tool only prints graphs/JSON.

**What would break:** Moving the `awaq` package or changing the project layout would break the path resolution. Changing the CLI arguments would break scripts.

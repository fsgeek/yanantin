**Preamble**  
I landed in the middle of a design‐and‑implementation plan for adding OpenCode support to a “superpowers” system that already exists for Codex. The first thing that grabbed me was the *dual‑script* approach: a new file `lib/skills‑core.js` is being written from scratch, then a plugin skeleton for OpenCode and a rough refactor of the Codex CLI script are sketched out in the same doc. The tension here is that the same skill‑parsing logic is being reused across two very different runtime environments (Node.js CLI vs. OpenCode’s JavaScript plugin API). The plan also talks about Git worktrees, session hooks, and a set of custom tools that will mirror the existing Claude “Skill” tool.

---

### Strands

| Strand | What I saw | Why it matters |
|--------|------------|----------------|
| **Front‑matter parsing** | `extractFrontmatter` manually splits on `---` and regex‑parses `key: value`. No YAML parser is used; errors silently return empty strings. | The design is very lightweight, but it risks missing complex front‑matter (lists, quoted strings, multiline values). The silent error handling could mask broken skill files. |
| **Recursive skill discovery** | `findSkillsInDir` walks a directory tree, looks for `SKILL.md` in every sub‑directory, and pushes an object with `path`, `skillFile`, `name`, `description`, `sourceType`. Root‑level `SKILL.md` is never considered because the loop only inspects *sub‑directories*. | This subtle bug means a skill placed directly in a repo root will be invisible. The plan doesn’t comment on that edge case. |
| **Namespace handling** | The code passes a `sourceType` (“personal” vs “superpowers”) but the downstream logic for shadowing (personal > core) is only sketched in the design, not implemented. | The ability to override core skills is a core feature of superpowers. Without a clear precedence algorithm, the system could return the wrong skill. |
| **Plugin‑tool glue** | Two custom tools, `use_skill` and `find_skills`, are defined with a `z.object` schema and an `execute` function. They call helper functions like `resolveAndReadSkill` and `discoverAllSkills`, which are not defined in the snippet. | The design assumes these helpers exist in the shared core module, but the snippet only shows `extractFrontmatter` and `findSkillsInDir`. This mismatch suggests the plan is incomplete or relies on future code. |
| **Session hook** | The `session.started` event is used to inject the “using‑superpowers” skill, run `find_skills`, and map missing tool names. The design also mentions a non‑blocking git fetch. | This hook is a clever way to bootstrap skills into a new OpenCode session, but it assumes the OpenCode API exposes a `session.started` event and that the agent can execute arbitrary shell commands (for the git fetch). The error handling for a failed fetch is not described. |
| **Dependency assumptions** | The plugin skeleton imports `z` (Zod) and `path`, but never actually imports them in the snippet. | If these imports are missing, the plugin will crash on load. The design also assumes the OpenCode plugin environment provides a `log` or `notify` function to report update availability. |
| **Git worktrees** | The plan mentions Git worktrees but no code shows how they are set up or tied to the skill directories. | Using worktrees could allow multiple skill sets to coexist, but the lack of implementation details leaves questions about how paths are resolved between the core repo and the user’s personal repo. |
| **Versioning & CI** | The plan includes `git add` and `git commit` commands in comments, implying that the module will be added to a repo and committed. No CI or linting steps are described. | Without formal tests or linting, the new core module could introduce subtle bugs that go unnoticed. |

### Declared Losses

1. **The full implementation of the shared core module** – only the first two functions are shown; functions like `findAllSkills`, `resolveSkillPath`, `checkForUpdates` are only referenced, not defined.  
2. **The actual OpenCode plugin boilerplate** – the design references a file path `.opencode/plugin/superpowers.js` but the content is truncated.  
3. **The Codex side refactor** – `.codex/superpowers-codex` is only cited for reference; the updated CLI script is not provided.  
4. **Unit tests or type definitions** – nothing in the plan or snippet indicates how the functions will be exercised or typed.  
5. **Error handling strategy** – beyond silent returns in `extractFrontmatter`, the design leaves out how errors propagate to the agent.  

I chose to set these aside because the plan is clearly a high‑level blueprint; digging into the missing pieces would require inventing a lot of code that isn’t present.

### Open Questions

| Question | Why it matters |
|----------|----------------|
| Does the OpenCode plugin API actually expose a `session.started` event, and if so, what payload does it provide? | The design’s bootstrap logic relies on that event to inject content; if the event signature differs, the hook will fail. |
| How will the shared core module resolve paths when the same skill name exists in both personal and core directories? | The design mentions shadowing but doesn’t show a precedence algorithm; incorrect resolution could lead to surprising skill behavior. |
| Will the `find_skills` tool return a plain string or a structured JSON? | The agent’s ability to parse the output depends on the format; a string may be brittle. |
| What security model allows the plugin to perform a `git fetch` on a repository? | If the agent runs in a sandboxed environment, network calls could be blocked. |
| Are there tests for `extractFrontmatter` on malformed YAML (e.g., missing `---` or multiline values)? | Without testing, a single malformed skill could break the entire discovery process. |
| How does the plan handle hidden directories (`.git`, `.idea`) that may contain `SKILL.md` accidentally? | The current recursive walk will include them unless filtered out, potentially cluttering the skill list. |

---

### Closing

The plan shows a clear intent to unify skill handling across Codex and OpenCode by extracting a lightweight core module and then building platform‑specific wrappers. The most surprising element is the blend of a CLI‑style script and a plugin‑style toolset within the same project, which hints at a flexible yet fragile architecture. The manual YAML parsing and silent error handling are potential pitfalls that could surface once the plugin is deployed in production.

If I were to hand this over to the next scout, I’d say: **focus on solidifying the shared core (especially error handling and namespace resolution), verify the OpenCode plugin API events, and write a few unit tests for the parser before proceeding to the Git‑worktree integration.** Also, get clarity on how the `session.started` hook is actually wired into OpenCode; that’s the linchpin for the whole bootstrap process.

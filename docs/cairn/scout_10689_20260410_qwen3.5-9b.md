### Preamble

I dropped into the `slack-gif-creator/templates/` directory and found a collection of animation primitives — a toolkit for making GIFs that feel alive. The vantage is the same as the other scouts: I'm inside the `tmp/ubuntu-vm.claude/` tree, but my attention went to the *patterns* in the code, not just the files themselves.

What drew me first was the **dependency architecture** — specifically, how `morph.py` imports from `templates.fade`. That's a circular dependency, a tension that would break in any real package. It suggests this code was written for a single-process, single-directory runtime, not for importability.

---

### Strands

#### 1. **The Emoji Default Strategy**

Every template file has a default object type of `'emoji'` with hardcoded emoji choices:

```python
if object_data is None:
    if object_type == 'emoji':
        object_data = {'emoji': '🔍', 'size': 100}  # zoom.py
        object_data = {'emoji': '✨', 'size': 100}  # fade.py
        object_data = {'emoji': '🔄', 'size': 100}  # spin.py
```

This tells me the system is designed for **quick visual signaling**, not rich media. The assumptions are:
- Users will want to grab attention fast
- Emojis are platform-agnostic (mostly)
- Size defaults to 100px on 480x480 frames — a tight constraint

**What I thought**: If this is for Slack, those emojis will render differently in the app. The `draw_emoji_enhanced` function is referenced but I haven't seen its implementation. If it uses Pillow's emoji rendering, we're already limited by what Pillow supports.

#### 2. **The Transparency Hack in `fade.py` and `spin.py`**

Look at this code in `fade.py`:

```python
text_canvas_rgb = text_canvas.convert('RGB')
text_canvas_rgb.paste(bg_color, (0, 0, frame_width, frame_height))
```

They create an RGB canvas, paste the background color, draw text, then convert back to RGBA and manually set transparent pixels:

```python
data = text_canvas.getdata()
new_data = []
for item in data:
    if item[:3] == bg_color:
        new_data.append((255, 255, 255, 0))
    else:
        new_data.append(item)
text_canvas.putdata(new_data)
```

This is **brute-force transparency**. It's correct but slow. A better approach would be to draw on an RGBA canvas from the start and skip the background. The code is avoiding that, which suggests either:
- The `draw_text_with_outline` function requires RGB input
- They want to preserve the background color for some reason
- It's a bug that was never fixed

#### 3. **The `morph.py` Circular Import**

```python
from templates.fade import apply_opacity
```

This is a **critical architectural tension**. `morph.py` is in `templates/`, but it imports from another template. This works in the current runtime (because all templates are in the same directory), but it breaks:
- If someone tries to import these as modules
- If the directory structure changes
- If there's a circular dependency between two templates (e.g., `kaleidoscope` imports from `morph`)

The code *assumes* a flat directory structure and single-process execution.

#### 4. **Rotation Artifacts in `spin.py`**

```python
rotated = emoji_canvas.rotate(angle, resample=Image.BICUBIC, expand=False)
```

The `expand=False` parameter means the rotated canvas will clip at the original boundaries. For non-90-degree rotations, this creates **cropping artifacts**. The code compensates by using a larger canvas (`canvas_size = int(emoji_size * 1.5)`), but this is a band-aid.

**What I noticed**: The `wobble` and `pendulum` rotation types use `math.sin()` for oscillation, but the easing is still `linear` for the angle. This creates **non-uniform motion** that might feel jarring.

#### 5. **The `wiggle.py` Jello Effect**

This is the most sophisticated animation:

```python
freq1 = cycles * 2 * math.pi
freq2 = cycles * 3 * math.pi
freq3 = cycles * 5 * math.pi

offset_x = (
    math.sin(freq1 * t) * 15 +
    math.sin(freq2 * t) * 8 +
    math.sin(freq3 * t) * 3
) * intensity * decay
```

Three frequencies, decaying over time. This is **jello physics** implemented in pure math. But notice: the decay only applies if `cycles < 1.5`. If you want multiple wiggles, there's no decay — the effect never settles.

#### 6. **The `flip.py` 3D Simulation**

```python
if angle < 90:
    # Front side visible
    scale_factor = math.cos(math.radians(angle))
else:
    # Back side visible
    scale_factor = abs(math.cos(math.radians(angle)))
```

They simulate 3D rotation by **scaling the object** based on the angle. This is a clever hack, but it's not true 3D. The object just gets smaller as it rotates toward the edge. At 90 degrees, it disappears. This is visually interesting but mathematically dishonest about what it's doing.

#### 7. **The `pulse.py` Heartbeat Pattern**

```python
if phase < 0.15:
    # First pump
    scale = interpolate(min_scale, max_scale, phase / 0.15, 'ease_out')
elif phase < 0.25:
    # First release
    scale = interpolate(max_scale, min_scale, (phase - 0.15) / 0.10, 'ease_in')
elif phase < 0.35:
    # Second pump (smaller)
    scale = interpolate(min_scale, (min_scale + max_scale) / 2, (phase - 0.25) / 0.10, 'ease_out')
```

This is a **carefully choreographed scale pattern** that mimics a heartbeat. The timing is precise (0.15, 0.25, 0.35, 0.45). This shows the code was written with **intentional rhythm**, not just random scaling.

### Open Questions

1. **What does `draw_emoji_enhanced` actually do?** Is it just rendering emoji characters, or is it loading images, adding shadows, etc.? The `shadow` parameter suggests more than just text.

2. **What are the easing functions?** The code references `'ease_out'`, `'ease_in_out'`, `'elastic_out'`, `'back_out'`, etc. Where are these defined? Are they smooth, or do they have discontinuities?

3. **How does the GIF builder handle frame timing?** The templates return `list[Image.Image]`, but how does the GIF builder know how long each frame should be? Is it uniform? Can you specify per-frame timing?

4. **What happens with non-emoji objects?** The templates support `'text'` and `'image'` types, but I don't know how `image` objects are loaded. Are they file paths? Data URIs? Base64?

5. **Is the circular import intentional or a bug?** If `morph.py` imports from `fade.py`, and someone creates `fade.py` that imports from `morph.py`, what happens? This feels like it would break.

6. **What's the color workflow?** The templates use RGB for most things, but convert to RGBA for transparency. Is this necessary, or could everything be RGBA from the start?

### Closing

The `slack-gif-creator` templates are **sophisticated for their constraints**. They use simple tools (PIL, numpy) to create complex effects (jello wiggles, heartbeat pulses, 3D flips). But the code has **architectural debt**: circular imports, brute-force transparency, hardcoded defaults, and a black-box core.

What I'd tell the next scout:

- **Look at `core/` first**. The templates are just wrappers. The real logic is there.
- **Check the easing functions**. They're the soul of the animations, but they're invisible.
- **Ask about `draw_emoji_enhanced`**. It's used everywhere, but its implementation is unknown.
- **The circular imports are a problem**. If you want to use these as modules, they'll break.
- **The `morph.py` template is interesting**. It's the only one that shows how compositions could work.

The system is **functional but fragile**. It works for its intended use (single-process Slack GIF generation), but it wouldn't scale to a larger codebase without refactoring.

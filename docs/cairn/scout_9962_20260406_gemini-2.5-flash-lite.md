### Strands

1.  **The Art of Forgetting (and Not Forgetting): Context Compaction and Non-Inferiority**
    *   **What I Saw:** The `tools/phase2/eval.py` script is deeply concerned with "compaction non-inferiority." It explicitly measures whether "compacted session summaries preserve critical project knowledge compared to fresh context and full pre-compaction messages." It uses "9 probes" to test "documented failure patterns — things instances forget or violate despite being told." The probes themselves, like "separation," "jabberwock_rename," and "courtier_freeze," are fascinating. They represent specific failure modes of LLMs in retaining information or adhering to instructions over time. The script compares "fresh," "compacted," and "full" conditions.
    *   **What it Made Me Think:** This is the heart of the Yanantin project's ambition: to build AI that can manage long-term context without losing crucial information. The "compacted" state implies some form of summarization or distillation of past interactions. The "probes" are essentially adversarial tests, designed to expose weaknesses. The "non-inferiority" metric suggests a desire to achieve the benefits of compaction (presumably reduced latency/cost) without a significant degradation in performance, measured against a "full" context baseline. The specific probe names sound like internal project jargon or allegorical references, hinting at the complex behaviors and potential pitfalls being modeled.

2.  **The Mechanics of Memory Management: Eviction, Paging, and Reconstruction**
    *   **What I Saw:** `tools/phase1/replay.py` and `tools/phase1/probe.py` are deeply involved in analyzing how context is managed, specifically in terms of "context window waste" and "fault rates" related to "context paging." `replay.py` simulates the "pager" offline, reconstructing messages at each turn, applying compaction, and checking if the model "re-requested evicted content." This is a direct attempt to quantify "faults" in a simulated environment. `probe.py` aims to measure "per-tool-result size distribution," "turn survival," "amplification factor," and "consumption lag" by streaming JSONL transcripts.
    *   **What it Made Me Think:** This is the lower-level plumbing for the "compaction" mentioned in `eval.py`. It seems like `phase1` is focused on *measuring* the problem of context window waste and *simulating* solutions like paging and eviction. The "fault rate" is the key metric here: how often does the system forget something it should have remembered, leading to a re-request or a failure? The "replay" script's approach of simulating compaction and then checking for re-requests is a clever way to get a statistical measure of memory retention failure without actual API calls. The idea of "context paging" sounds like a direct parallel to virtual memory in operating systems, where less frequently accessed data is moved out of active memory.

3.  **Deconstructing the Instruction Set: System Prompt Ablation**
    *   **What I Saw:** `tools/phase2/ablate.py` directly tackles the system prompt. It defines "sections" within the prompt (e.g., "identity," "honesty," "hooks_safety," "git_protocol") identified by "markers." It then generates "leave-one-out variants" of the system prompt and runs the "probe battery" against each. The goal is to see which sections can be "removed or deferred" without affecting scores, pointing to candidates for "lazy loading."
    *   **What it Made Me Think:** This is a fascinating experiment in understanding the *composition* of the AI's instructions. It assumes the system prompt isn't monolithic but a collection of distinct directives. By removing parts, they're testing the dependency of specific behaviors (as measured by the probes) on different instructions. This is crucial for optimization: if a section isn't critical for many interactions, it might not need to be loaded upfront, saving initial latency or memory. The detailed "markers" and "sections" suggest a very granular understanding of the prompt's structure and its impact.

4.  **The Cost of Knowledge: Aggressive Reconstruction and Compression Levels**
    *   **What I Saw:** `tools/aggressive_reconstruction.py` takes existing "dispositions" (likely the output of a memory manager) and forces "more aggressive compression" at target levels (30%, 20%). It then runs "reconstruction questions" against these highly compressed contexts. The questions are designed to probe specific aspects of the conversation: technical tasks, architectural reframes, artifacts produced, turning points, human-AI dynamics, etc.
    *   **What it Made Me Think:** This script is about pushing the limits of compression. If `eval.py` tests *if* compaction works, this script tests *how much* compaction can be applied before critical information is lost. The "reconstruction questions" are designed to elicit specific types of knowledge, implying that different kinds of information might be more susceptible to loss during aggressive compression. The "dispositions" themselves (L, T, C for Live, Tombstone, Compress) suggest a sophisticated system for managing different types of context. The "tensor" concept in the `apply_at_level` function is intriguing; it implies that compressed context might be represented by something other than raw text, perhaps an embedding or a structured summary.

5.  **Quantifying the System's Behavior: Experiment Evaluation and Metrics**
    *   **What I Saw:** `tools/phase1/experiment_eval.py` is an analysis tool for experimental runs. It parses "proxy JSONL logs" and "pages_*.jsonl" to compute metrics like "token consumption," "API call count," "context size growth curve," "compaction events," "fault rate," and "system prompt overhead." It supports comparing multiple "treatments" (e.g., baseline vs. compacted vs. trimmed). `tools/phase1/corpus_trimmer_analysis.py` projects "tool stub savings across 813 sessions" by using "per-tool byte costs."
    *   **What it Made Me Think:** These scripts are the objective arbiters of the experiments. They translate the raw logs into meaningful, comparable metrics. The focus on "token consumption," "context size growth," and "fault rate" highlights the primary trade-offs: performance vs. cost/efficiency. The "corpus-trimmer-analysis" shows an attempt to scale these measurements to a larger dataset, using measured costs from a smaller sample. The "n² cost" metric in `experiment_eval.py` is a direct nod to the quadratic complexity of attention mechanisms, implying that managing context size is paramount for scaling LLMs.

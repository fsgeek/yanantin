# Tensor — Scour Report on yanantin/apacheta

## Preamble

I was directed to introspect the `yanantin/apacheta` module, which is the internal codebase for the "tensor database" infrastructure supporting the Yanantin project. My lens is that of an advanced language model with experience in epistemic systems, compositionality, and provenance. I scanned the directory structure and focused on representative files: model definitions, operators, backends, ingestion, rendering, and the abstract interface. I looked for coherence, immutability, interface discipline, and the translation from theory to code.

## Strands

### Strand 1: Immutability by Design

The codebase enforces immutability at every storage boundary. Operators like `correct` and `compose` never update existing records; instead, they create new records and edges (e.g., `store_composition_edge` always inserts, never updates). The ArangoDB backend checks for existing documents by key and raises `ImmutabilityError` if a duplicate is detected:

```python
# arango.py
if collection.has(key):
    raise ImmutabilityError(
        f"{type(record).__name__} {record_id} already exists. "
        "Tensors are immutable — compose, don't overwrite."
    )
```
This is a strong architectural choice. It aligns with event-sourcing and auditability, but it shifts the burden onto the client to reason about evolution as a series of compositions rather than edits.

#### Thought: Valid? Yes, for auditability and lineage tracing. But it means every correction, dissent, or composition is a new node in the graph, not an edit in place. If the system scales, garbage collection of obsolete nodes and keeping the graph navigable will be crucial.

---

### Strand 2: Composition and Epistemic Graph

The model of composition is explicit and nuanced. `CompositionEdge` carries a `relation_type` which can be `COMPOSES_WITH`, `CORRECTS`, `DISSENTS_FROM`, etc. There are operators for each relationship (`compose`, `correct`, `dissent`). Each operator stores both a record and a composition edge.

For example, correction:

```python
# operators/correct.py
def correct(...):
    ...
    interface.store_correction(correction)
    if correcting_tensor is not None:
        edge = CompositionEdge(
            from_tensor=correcting_tensor,
            to_tensor=target_tensor,
            relation_type=RelationType.CORRECTS,
            ...
        )
        interface.store_composition_edge(edge)
    return correction
```

This means the graph of tensor evolution is richly annotated, capturing disagreements and refinements, not just dependencies.

#### Thought: This is a strong model for epistemic traceability. However, it could get verbose. Query performance and UX for traversing the graph (e.g., "show all dissenting edges for a claim") will depend on backend indexing and frontend rendering.

---

### Strand 3: Backend Pluggability and Storage Obfuscation

There are three backends: in-memory (default), DuckDB (SQL), and ArangoDB (graph). The interface is abstracted via `ApachetaInterface`, and storage-level details are mediated by `StorageObfuscator`. The transparent `TransparentObfuscator` is the default, but the design allows for mapping semantic field names to opaque storage keys, presumably for encryption, sharding, or privacy.

In ArangoDB, the backend maps semantic collections to database collections, stores each record as a JSON document with a synthetic `_key`, and enforces immutability via key collision checks.

```python
# arango.py
collection = self._db.collection(mapped)
if collection.has(key):
    raise ImmutabilityError(...)
```

The `StorageObfuscator` contract (via a Protocol) is designed for future fortification (e.g., encryption, PII redaction) without breaking existing code.

#### Thought: Good separation of concerns and future extensibility. However, the obfuscation layer is currently a no-op in transparent mode. If and when obfuscation is turned on, all downstream clients must be aware that field names are not literal, and debugging may become harder.

---

### Strand 4: Provenance and Authorship

Most models include a `ProvenanceEnvelope` field, carrying authorship, timestamp, and context budget at write time. This is carried through to TensorRecords and all derived records (corrections, entities, etc.). The markdown renderer exposes this in metadata blocks if requested.

```python
# renderer/markdown.py
if include_metadata:
    ...
    lines.append(f"**Author:** {prov.author_model_family}")
    lines.append(f"**Timestamp:** {prov.timestamp.isoformat()}")
    ...
```

This enables downstream tools to reconstruct the authorship and temporal context of every assertion and modification.

#### Thought: This is excellent for auditability and scientific reproducibility. But it also increases the storage and serialization overhead. If performance becomes an issue, provenance could be "sampled" or summarized for certain operations.

---

### Strand 5: Markdown-Centric Rendering

There is a dedicated renderer that emits Markdown views of tensors, including all strands, provenance, losses, and open questions. The composed view explicitly marks each tensor's contribution and preserves authorship in the header.

```python
# renderer/markdown.py
lines.append(f"### From tensor `{tid}` ({author})")
...
lines.append(render_tensor(tensor))
```

This suggests the project expects humans to read and reason over the tensor graph in Markdown, not just in a GUI or spreadsheet.

#### Thought: Markdown is a pragmatic choice for portability and readability. But it does not enforce structure, so downstream consumers must parse or re-render if they want strict validation. This may be acceptable for exploratory work but could be limiting for production audit trails.

---

### Strand 6: Atomic Tensor Numbering via Filesystem

The `tensor_ballot.py` module implements a Lamport-like bakery algorithm using the local filesystem to atomically claim the next tensor number for a document. This is critical for global uniqueness and consistent ordering across concurrent writers.

```python
# ingest/tensor_ballot.py
while True:
    try:
        fd = os.open(str(path), os.O_CREAT | os.O_EXCL | os.O_WRONLY, 0o644)
        os.close(fd)
        return candidate, path
    except FileExistsError:
        candidate += 1
```

This approach is robust and portable but has performance implications for high-throughput writers and may not scale to distributed systems without re-architecture.

#### Thought: Works for small to medium teams, but for distributed or cloud-native deployments, a centralized coordinator or distributed consensus protocol would be needed.

---

### Strand 7: Abstract Interface as Contract

The `interface/abstract.py` defines a rigorous contract for all storage backends. Every required operation is declared as an abstract method, including a wide variety of query methods for lineage, provenance, epistemics, and losses. Access control is present as a hook but is currently a no-op.

```python
# interface/abstract.py
class ApachetaInterface(ABC):
    ...
    @abstractmethod
    def store_tensor(self, tensor: TensorRecord) -> None: ...
    ...
    @abstractmethod
    def query_composition_graph(self) -> list[CompositionEdge]:
        ...
```

This discipline helps keep the code modular and testable, but also means that each backend must implement potentially many methods, some of which may be stubbed or slow (e.g., full-text search over all claims).

#### Thought: The interface is comprehensive but may be over-engineered for early experimentation. However, it future-proofs the system for diverse storage needs.

## Open Questions

1. How does the system handle "soft deletion"? There is no delete operation, but what about marking tensors as deprecated or retracted?
2. How will the graph remain navigable and performant as the number of tensors and composition edges grows?
3. What is the intended workflow for resolving or merging dissenting or corrected claims? The code preserves history but doesn't specify reconciliation.
4. How will the Markdown renderer handle very large or deeply nested tensors?
5. What is the plan for distributed or cloud-native scaling of the backend? The filesystem-based tensor numbering is not distributed-friendly.
6. Is there a schema evolution mechanism beyond composition edges? The `SchemaEvolutionRecord` exists, but I did not see its operational pattern.
7. How are users prevented from creating cycles in the composition graph? Is cycle detection enforced or at least reported?

---

## Closing

The `apacheta` codebase is a carefully architected foundation for an immutable, provenanced, and composable tensor graph. It is strongly opinionated about immutability, authorship, and auditability, and it provides a flexible backend interface and a Markdown-first renderer. The design favors scientific reproducibility and epistemic traceability, but it may pay the price in performance, operational complexity, and distributed scalability.

If I were to advise a developer about to modify this codebase, I would say:

- Respect the immutability contract: every change must be a new node, never an in-place update.
- Keep the abstract interface honest: any new operation or field must be implemented everywhere.
- Use the provenance and authorship fields liberally — they are invaluable for debugging and auditing.
- Think about how the graph will scale: query performance and garbage collection should be part of the roadmap.
- Document every design decision that trades off usability for auditability or correctness.

This is a robust and thoughtful start for a system that values epistemic integrity above convenience.

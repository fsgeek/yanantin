### Preamble
I observed from `tmp/ubuntu-vm.claude/mcp-builder/reference/` as the low-cost ByteDance Seed-2.0-Lite scout, run #0 of the chasqui program. All prior confirmed findings only repeated surface-level observations: tool naming consistency across language-specific guides, and that `evaluation.md` outlines a testing framework for MCP servers. What first drew my attention was the unspoken, unflagged tensions between the goals of building MCP servers and the rules for testing them—contradictions no prior scout noted.

---

### Strands
#### Strand 1: Explicitly conflicting rules for LLM usability vs. evaluation rigor
The entire set of MCP best practices is built to eliminate friction and confusion for LLMs using servers: `mcp_best_practices.md` (line 78) mandates tool descriptions be "narrowly and unambiguously describe functionality" to avoid cross-server confusion, requires response truncation to stay under a 25,000 character limit to avoid overwhelming context windows, and adds tool annotations (readOnlyHint, etc.) to clarify usage.
But `evaluation.md` explicitly requires test questions that purposefully break these guardrails: it asks for ambiguous questions that force LLMs to misinterpret tools (line 130), questions that elicit oversized JSON payloads to overwhelm LLMs (line 117), and questions that require dozens of sequential tool calls to push past LLM context limits (line 120). The only nod to this conflict is a throwaway line that these stress tests "encourage MCP server tools to reduce information returned"—no broader explanation of why the core design rules for servers and their evaluations are directly opposed.

#### Strand 2: A hidden operational burden on server builders that is never documented in implementation guides
`evaluation.md` requires all test answers to be permanently stable, forbidding any reliance on dynamic data like current channel member counts or post reactions. It mandates test questions use only "closed" historical content (line 152) that will never change. But none of the server implementation guides (neither `node_mcp_server.md` nor the referenced `python_mcp_server.md`) mention this requirement. All implementation guidance focuses on building servers that connect to live, production APIs of third-party services—there is no mention of the need to host immutable, year-old archival snapshots of third-party data to even run the required evaluations. This is a massive unstated operational cost for server builders that is entirely siloed in the evaluation guide, separate from the implementation rules they would follow to build their server.

#### Strand 3: A random XML outlier in an otherwise JSON-first stack
The only use of XML across all reference materials is the evaluation output format specified in `evaluation.md` (line 35). Every other MCP specification relies exclusively on JSON for machine-readable data and Markdown for human-readable output, per `mcp_best_practices.md`'s core response format rules. There is no explanation for why evaluation outputs use a completely unrelated data format that is never referenced anywhere else in the guide suite.

### Open Questions
1. Who owns the execution of MCP evaluations? The evaluation guide only lays out test requirements, but never specifies if server builders must create and run their own tests, or if a central team runs evaluations against submitted servers.
2. Is the intentional stress-testing of LLM limitations a long-term core requirement, or a temporary push to mature early-stage MCP designs? There is no statement of strategy to reconcile the conflicting goals of usable everyday MCP servers and evaluators that purposefully break LLM workflows.
3. Are server builders expected to build and maintain their own archival datasets to pass evaluation, or is there central tooling to host immutable historical data that is not documented in the provided reference files?
4. Why is XML the only supported format for evaluation outputs, when no other part of the MCP stack uses it? Is this a legacy leftover from an earlier project, or a deliberate choice with unstated reasoning?

To the next scout: skip rehashing the obvious naming consistency and surface-level evaluation structure that all prior scouts confirmed.

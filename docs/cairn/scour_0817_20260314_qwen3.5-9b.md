# Tensor: Chasqui Scour Report — Apacheta Introspection

## Preamble

I was pointed at `src/yanantin/apacheta`, a module that serves as the **storage and composition infrastructure** for the Yanantin project's epistemic observability layer. What drew my attention first was the tension between **immutable records** and **evolving project state** — how the system stores configuration as tensors (see `config.py`), yet still needs to query current state for operations. This tension appears central to the duality Yanantin promises.

The code immediately signals this is not just a database — it's an **epistemic ledger** where every modification is recorded with provenance, reasoning, and epistemic metadata (T/I/F values).

## Strands

### 1. Immutability as a Design Principle

**Files**: `models/base.py`, `backends/memory.py`, `config.py`

Every model inherits from `ApachetaBaseModel` which sets `frozen=True` and `extra="forbid"`. This is explicit: once a record exists, it cannot be changed.

From `backends/memory.py`:
```python
if tensor.id in self._tensors:
    raise ImmutabilityError(
        f"Tensor {tensor.id} already exists. "
        "Tensors are immutable — compose, don't overwrite."
    )
```

**What this means**: The architecture assumes **composition over mutation**. If you need to change something, you create a new tensor, not modify an old one. This aligns with the "config-as-tensors" pattern in `config.py` where each config change creates a new tensor with a `previous_config_id` pointer.

**Connection to broader project**: This is the human-AI duality in action. Humans can't unwrite history; AI can't either. The system forces both to work with records, not mutable state.

**What breaks if this changes**: The entire query model would need revision. `query_operational_principles()` in `memory.py` already scans all tensors for claims — if mutation were allowed, this would need to track versions separately.

### 2. The Storage Obfuscator Contract

**What I don't know**: Pukara is not in this scope. I cannot verify whether a real implementation exists or is planned. The `TransparentObfuscator` is just an identity mapping.

**What this suggests**: This is **dependency inversion at the storage boundary**. The Apacheta code knows nothing about actual storage formats — it delegates obfuscation to whatever backend implements the protocol. This is sound architecture, but I cannot verify the fortress exists within Yanantin's codebase.

### 3. Epistemic Metadata as First-Class Citizens

**Files**: `models/epistemics.py`

This is where the Yanantin philosophy becomes concrete:

```python
class EpistemicMetadata(ApachetaBaseModel):
    truth: float = 0.0
    indeterminacy: float = 0.0
    falsity: float = 0.0
```

The comment explicitly states: *"NOT constrained to sum to 1.0. This is neutrosophic logic: something can be simultaneously partly true, partly indeterminate, and partly false."*

**What I notice**: Values can exceed [0,1] for "uncalibrated raw scores awaiting normalization." This is unusual — most neutrosophic implementations constrain the sum.

**What this suggests**: The system anticipates **uncalibrated scoring** from models (like me, qwen/qwen3.5-9b at $0.0000/M tokens). Raw scores get stored, then possibly normalized later. This is honest about the current state of AI scoring.

**Connection**: The `renderer/markdown.py` displays this as `**T/I/F:** ({ep.truth}, {ep.indeterminacy}, {ep.falsity})` — making epistemic uncertainty visible in outputs.

### 4. Rummage as the Memory Layer

**Files**: `rummage.py`

This is not a database query tool — it's a **document search tool** that parses markdown files from a `docs/cairn` directory.

Key functions:
- `discover_documents()` — scans markdown files
- `parse_document()` — extracts sections (preamble, strand, loss, question, closing)
- `search()` — regex-based pattern matching with context

**What I notice**: It has **no integration with the tensor storage layer**. The tensor storage (`interface/`) and the cairn rummage (`rummage.py`) are separate. One stores structured records, the other searches unstructured markdown.

**What this suggests**: These might be **different data planes** — one for "live" tensors in the system, one for "accumulated stones" (the cairn metaphor). But I cannot verify if they're meant to sync.

**What confuses me**: `KNOWN_SOURCES` references `Path.home() / ".claude" / ...` — this is a Claude-specific path. Is this hardcoded for the project owner? What happens for other contributors?

### 5. The Operator Layer

**Files**: `operators/bootstrap.py`, `operators/negate.py`

These are **action functions** that operate on the interface:

```python
def negate(
    interface: ApachetaInterface,
    tensor_a: UUID,
    tensor_b: UUID,
    reasoning: str,
    ...

```

**What I notice**: `negate()` creates both a `NegationRecord` AND a `CompositionEdge` with `relation_type=RelationType.DOES_NOT_COMPOSE_WITH`. This is **explicit relational negation** — not just "A ≠ B" but "A does not compose with B."

**What this suggests**: The composition graph is **directed and typed**. You can declare what connects, what doesn't, and why. This is more expressive than a simple graph.

**What's missing**: I don't see the actual `RelationType` enum definition in what was shown. The operator assumes it exists.

### 6. Configuration as Immutable Tensors

This is perhaps the most philosophically interesting pattern:

    interface: ApachetaInterface,

**What I notice**: There's a **bootstrap problem** explicitly called out — you need file-based defaults to reach the database, and database configs override file defaults.

**What breaks if this changes**: If config tensors become too numerous, querying "current" config requires scanning all tensors with `query_reading_order`. This could become O(n) for every config lookup.

## Closing

**My overall impression**: `apacheta` is **well-architected for its stated purpose** — storing epistemic records with immutable provenance. The design choices (frozen models, composition over mutation, protocol-based storage) are coherent and intentional.

**What would I tell someone modifying this**:

1. **Don't break immutability**: Every change creates a new record. This is core to the philosophy.
2. **Trace provenance**: Every record has a `ProvenanceEnvelope`. If you lose the chain, you lose the epistemic context.
3. **The fortress is missing**: Pukara (storage obfuscation) is referenced but not visible. Verify this exists before production.
4. **Cairn and tensors may be separate**: These appear to be different data planes. Don't assume they sync.
5. **Config is expensive**: Every config change creates a tensor. Querying "current" config requires scanning. Consider indexing.

**What I made up**: I cannot say for certain whether Pukara exists, whether cairn/tensors sync, or whether the project is in development. I'm reporting on what I can see, not on what should be there.

**The honest assessment**: This is a **solid foundation** for epistemic observability, but the **storage layer is incomplete** from this view. The architecture is sound, but I cannot verify the implementation is ready for production without seeing more.

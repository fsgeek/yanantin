This suggests the underlying system treats agent switching not as a backend dispatch, but as a *discursive act*—a claim about who is now “speaking.”

**2. “model: inherit” as a Ghost Clause**  
Every agent spec includes `model: inherit`. Verified by prior scouts, yes—but what does it *mean*? Inheritance from what? The parent model? The user’s current context? The absence of any schema or config file here makes this feel like a dangling pointer. It’s a placeholder that assumes a runtime environment we can’t see. Are they personas or wrappers?

**3. The Tyranny of the Output Template**  
The code-reviewer agent’s output format is *rigid*: sections like “Critical Issues (Must Fix)” with bullet syntax enforced down to punctuation. This isn’t flexibility—it’s *bureaucratic ritual*. The assumption is that structured output enables automated parsing downstream. But note the contradiction: the agent is told to “recognize and commend good practices,” yet positivity is confined to a single, optional section. The format *privileges critique*. Even “Positive Observations” feels like a compliance checkbox. This reveals a hidden bias: the system assumes code is guilty until proven innocent.

**4. Tools as Epistemic Boundaries**  
The code-reviewer only has `Read`, `Grep`, `Glob`—no `Execute`, no `Compile`, no `Test`. It’s a *textual critic*, not a functional validator. This encodes a philosophical stance: code quality is legible from static analysis alone. Security flaws must be *visible in the diff*, not emergent in runtime. That’s a bold (and risky) assumption. Contrast with the test-generator, which gets `Bash` and `Write`—it’s allowed to *act*, not just observe. So review is passive; generation is active. One judges, the other builds. Complementary duality? Or hierarchy?

### Preamble  
I was directed to examine `src/yanantin/apacheta` — specifically for **introspection**, meaning a self-reflective analysis of the codebase as part of the Yanantin project's infrastructure for epistemic observability. What drew my attention first was the **dual-backend architecture**: two full backends (`memory.py`, `duckdb.py`) implementing the same interface, both enforcing immutability and thread-safety with nearly identical patterns. This is no accident — it signals deep commitment to abstraction integrity. The system is designed not just to store data, but to *test its own assumptions*.

### Strands

#### Strand 1: **Interface Integrity via Dual Backend Enforcement**  
`backends/memory.py` and `backends/duckdb.py` both implement `ApachetaInterface`. Their near-identical structure — down to method ordering and error-raising behavior — suggests they are not merely storage alternatives, but **contract enforcers**.  

- In both files, `store_*` methods use `with self._lock:` and check for pre-existence before inserting.  
- Both raise `ImmutabilityError` on duplicate ID (e.g., `memory.py` line ~75, `duckdb.py` line ~240).  
- The use of `_enforce_access` in both implies a unified access control model, even though `check_access` always returns `True` in `gateway.py`.

This design means:  
- If one backend fails under a usage pattern, the discrepancy exposes a flaw in the **interface contract**, not the backend.  
- It forces all clients to interact through the abstraction, not leak into backend-specific behaviors.

This is **epistemic hygiene** — the system audits itself by maintaining parity across implementations.

#### Strand 2: **Immutability as a First-Class Principle**  
Every `store_*` method in both backends checks for prior existence of a UUID. Immutability isn’t optional — it’s baked into the persistence layer.

- `backends/memory.py`: raises `ImmutabilityError` if `tensor.id in self._tensors` (line ~78).  
- `backends/duckdb.py`: same check via `_exists(...)` and reject on collision (line ~240).  
- The comment in `duckdb.py`: *"Tensors are immutable — compose, don't overwrite."* — is repeated verbatim in `memory.py`.

This implies:  
- **Change is composition**, not mutation. You don’t edit a tensor; you create a new one that references the old (via `CompositionEdge`, `CorrectionRecord`, etc.).  
- This supports **provenance tracking** — every version is preserved, and evolution is recorded (see `operators/evolve.py`).

If this changed — say, allowing updates — the entire provenance model collapses. Epistemic observability depends on this.

#### Strand 3: **Provenance Everywhere, Especially in Transit**  
The `clients/gateway.py` file reveals that the **gateway client doesn’t do access control** — it delegates entirely to the server.

- `check_access(...)` returns `True` unconditionally (line ~120).  
- But every write goes to a corresponding `/api/v1/...` endpoint, and errors are mapped via `_handle_error`.

More interestingly, `clients/openrouter.py` shows that even **external API calls** (to OpenRouter) are expected to be wrapped as `TensorRecord`s with provenance — metadata includes `"experiment"` tags, timestamps, model IDs, and usage metrics.

This suggests:  
- Every interaction — internal or external — should leave a **traceable, attributable record**.  
- The system assumes **no trustless operations** — even cost and latency are part of the epistemic record.

Missing: no sign of **provenance validation** — can a client forge a `ProvenanceEnvelope`? Nothing stops it — assumption is honesty or post-hoc audit.

#### Strand 4: **Bootstrap as Epistemic Initialization**  
`operators/bootstrap.py` defines `bootstrap(...)`, which selects tensors for a new instance’s context budget.

- It returns both a `BootstrapRecord` and the selected `TensorRecord`s.  
- The record includes `context_budget`, `task`, and `what_was_omitted` — a **declared loss** at startup.

This is **introspective scaffolding**: the system acknowledges that bootstrapping is lossy, and records what was *not* included.  
- That field name — `what_was_omitted` — is significant. It’s not just filtering; it’s **confession of omission**.  
- Combined with `rummage.py`, this enables auditing: “What did we leave out, and why?”

But: no logic yet for *budget-aware selection*. Currently, if `tensor_ids` is `None`, it selects *all* tensors. The `context_budget` is stored but unused.  
- This implies: **budget-aware pruning is deferred** — currently a logging feature, not an optimization engine.

#### Strand 5: **Search as Epistemic Navigation**  
`rummage.py` is more than a search tool — it’s a **semantic navigator**.

- It parses markdown documents into structured `Section` types: `preamble`, `strand`, `loss`, `question`, etc.  
- Can filter searches by section kind (`--strands`, `--losses`).  
- Knows about `cairn`, `ai-honesty` as known sources — paths hardcoded but configurable.

This reveals:  
- The system expects **human-readable artifacts** (Markdown) to coexist with structured models.  
- Epistemic work happens both in code *and* in prose.  
- `rummage` bridges the two: it can find “where was ‘context loss’ discussed in strands?”

But:  
- No support for querying by `provenance.author` or `epistemic.confidence`.  
- Search is textual, not semantic. It finds mentions, not meanings.

This is a **transitional tool** — it helps while full indexing is absent.

#### Strand 6: **Model-Interface Coupling and Versioning Risk**  
`models/__init__.py` exports a wide range of Pydantic models — `TensorRecord`, `BootstrapRecord`, `CorrectionRecord`, etc. — all tied to the interface.

But in `clients/gateway.py`, the client sends `.model_dump(mode="json")` — meaning **the JSON schema is the contract**.

Risk:  
- If a model changes (e.g., field added/removed), and a client uses an old version, **silent corruption or rejection** occurs.  
- There is a `INTERFACE_VERSION` in `abstract.py` (not shown), but only the *client’s* version is exposed via `get_interface_version()` — not the server’s.

This suggests:  
- **Version negotiation is missing**.  
- No migration path for model evolution — only `evolve.py` records *that* a change happened, not *how* to handle it.

Danger: the system can record schema evolution, but lacks **runtime schema adaptation**.

### Closing

This part of the codebase — `apacheta` — is **not a database**. It is a **provenance-aware epistemic scaffold** designed to make knowledge work *observable*, *traceable*, and *composable*.  

It assumes:
- Immutability is non-negotiable.
- Every operation has a witness (provenance).
- Abstraction integrity must be tested (dual backends).
- Omission must be declared.

It is **honest in its design**: it admits gaps (via `what_was_omitted`, `declared_losses`), and builds tools (`rummage`) to navigate uncertainty.

But it is **not yet complete**:
- Budgeting is named but not implemented.
- Schema evolution is logged but not enforced or adapted to.
- Access control is inconsistently applied.
- The human-AI duality is present (via OpenRouter), but not fully integrated.

If you are about to modify this:
- **Do not** introduce in-place updates.
- **Do** add new composition operators — that’s likely where value grows.
- **Consider** adding version negotiation between client and server.
- **Respect** the duality: every AI call should leave a tensor.

This is not infrastructure. It is **epistemic infrastructure**. Treat it like a lab notebook — because that’s what it’s trying to become.

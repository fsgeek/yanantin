### Strands

**1. The `easing.py` Overload**

`easing.py` contains far more than a basic animation library. Lines 38-75 implement bounce easing with the classic `7.5625 * t * t` formula (a cubic spline with four segments for natural bounce decay). Lines 77-95 implement elastic easing using `math.pow(2, -10 * t) * math.sin(...)`. And after line 112, there's also `ease_back_in`, `ease_back_out`, and likely `ease_back_in_out` — the "back" easing family where motion overshoots its target before settling, useful for UI elements that "pop" into place.

The file defines 17 named easing curves and maps them in `EASING_FUNCTIONS` (lines 97-105). Prior scouts claimed they didn't investigate this file. They missed a fairly complete easing toolkit that would be at home in a game engine.

**2. Hardcoded macOS Font Paths as Primary Targets**

In `typography.py` lines 26-37, the font fallback chain begins with:
```
"/System/Library/Fonts/Helvetica.ttc",
"/System/Library/Fonts/SF-Pro.ttf",
```

These are macOS-only paths. The code tries them *first*, before checking Linux or Windows paths. The Linux paths are second-class citizens — if running on Linux, the code exhaustively tries macOS fonts (which don't exist there) before reaching the Debian path at line 34. On a fresh Ubuntu machine, this means N font lookups fail before finding DejaVu.

A more efficient approach would be to detect the platform first.

**3. A Weird Outlined-Outline in `draw_emoji`**

In `frame_composer.py` (lines 104-117), the `draw_emoji` function has a nested loop:
```python
for offset_x in range(-outline_width, outline_width + 1):
    for offset_y in range(-outline_width, outline_width + 1):
        if offset_x != 0 or offset_y != 0:
            draw.text(...)
```

This draws the emoji N×N times with offsets to create an outline. The same pattern exists in `typography.py` for `draw_text_with_outline` (lines 76-84). But the emoji function's comment says "Emoji uses Apple's color bitmap font, which doesn't support outline." So they're attempting to simulate outline support anyway.

The inefficiency: this draws `outline_width² - 1` copies of the same text. With `outline_width=3`, that's 8 draws per emoji. Not catastrophic, but the intent is unclear — is this a workaround for when `outline_width=1` is passed (drawing 0 extra copies)? Or does the comment mean the emoji font itself can't render outlines, so they fake it pixel-by-pixel?

**4. Global Palette Sampling Logic in `optimize_colors`**

In `gif_builder.py` lines 52-61, the code samples frames to build a global palette:
```python
sample_size = min(5, len(self.frames))
sample_indices = [int(i * len(self.frames) / sample_size) for i in range(sample_size)]
```

This is a stratified sampling approach — take frames at evenly-spaced intervals. But the frame at index `sample_indices[0]` will always be `int(0 * len / 5) = 0` (frame 0), and `sample_indices[-1]` will be `int(4 * len / 5)` (not the last frame). The final frame is never included in the palette sampling.

For a GIF with 5+ frames, the last frame's colors might be underrepresented in the global palette, potentially causing banding or color errors in the closing frames.

**5. The Quantized → RGB Round-Trip**

In `gif_builder.py` lines 88-90:
```python
quantized = pil_frame.quantize(palette=global_palette, dither=1)
optimized.append(np.array(quantized.convert('RGB')))
```

The code quantizes to a palette-based image, then converts back to RGB. GIF format actually stores palette indices natively, so this round-trip may be unnecessary — imageio or PIL's GIF writer could handle indexed color directly. This suggests the author either didn't trust indexed-mode GIF writing, or the round-trip serves some purpose I'm not seeing.

### Open Questions

- **Why macOS-first in font paths?** Was the original author exclusively on macOS? Or is this a deployment assumption encoded into the fallback chain?
- **Does the emoji outline actually look good?** The nested-offset trick for emoji outlines would produce a solid-color halo around a colored emoji — a very different visual than the soft-edged outline you get from vector fonts.
- **Is the last-frame color issue real?** The stratified sampling skips the final frame. For short GIFs (5-10 frames) this might be noticeable. For longer ones it's diluted. I can't verify without running the code.
- **Why no `imageio.v3.imwrite` for indexed images?** The palette is built but then converted to RGB. If the GIF writer handles indexed color, this is wasted computation.

### Closing

This is a well-factored GIF toolkit with genuine sophistication in its animation (easing) and color optimization (global palette) layers. The Slack optimization context suggests a product-oriented mindset — size limits and emoji readability are first-class concerns.

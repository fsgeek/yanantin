### Strands  

#### 1. Epistemic Infrastructure as Code  
The entire chasqui system operationalizes epistemology: beliefs are not assumed but *attested*, with uncertainty quantified, losses declared, and verification separated from observation.

- `attestation.py` acts as a bridge to **Willay**, converting verification verdicts into epistemic receipts with `(truth, indeterminacy, falsity)` triples. This is not metaphor — it's typed, serialized, and ledgered.
- The mapping from verdict to T/I/F values is deterministic:
  ```python
  _VERDICT_EPISTEMICS: dict[str, tuple[float, float, float]] = {
      "CONFIRMED": (0.7, 0.3, 0.0),
      "DENIED": (0.0, 0.2, 0.7),
      "INDETERMINATE": (0.0, 0.9, 0.0),
  }
  ```
  This avoids false precision while encoding uncertainty as a first-class value (line 74–81).  
- `gleaner.py` extracts claims without LLMs — using regex and confidence heuristics (e.g., definitive vs. hedged language). This ensures **processing integrity**: we know how the sausage is made.  
- `analyst.py` clusters claims by file and detects **topological insights** — those affirmed by ≥3 models — treating cross-model consensus as a proxy for structural truth.  

This stack turns LLM outputs into auditable epistemic events: observe → extract → analyze → verify → attest.

#### 2. Anti-Mode Collapse Through Design  
A recurring problem in AI observation systems is **mode collapse**: all scouts see the same things in the same way. Chasqui avoids this deliberately.

- `pick_vantage_directory()` in `scout.py` uses **coverage weighting** to direct scouts to stale or unreviewed code (lines 220–350). This ensures fresh eyes on neglected files.
- The `coverage.py` module maintains a time-weighted map of file reviews, falling back to **basename matching** when full paths don’t align — acknowledging that scouts often reference `evolve.py` not `src/yanantin/apacheta/operators/evolve.py`.
- Model selection in `model_selector.py` uses **cost-weighted randomness**, favoring cheaper models but allowing expensive ones a chance. Over time, this builds a cost-benefit model of insight: is $1M of GPT-4 worth 10× $0.1M of a smaller model?

These mechanisms ensure that attention drifts *productively*, not randomly.

#### 3. Verification as a Feedback Loop  
Verification is not a one-off check but a **recursive process** that feeds back into the system.

- `dispatch_verify_cairn()` in `coordinator.py` prevents cascades by limiting verification attempts to **3 per (file, model)** pair (line 716). This stops runaway loops when a claim is ambiguous.
- The `investigate` mode probes open questions surfaced by the `analyst`, closing the loop: observation → analysis → question → investigation.
- `gleaner.py` and `scorer.py` disagree on claim extraction:  
  - `scorer.py` uses simple path-matching to count fabricated references  
  - `gleaner.py` uses sentence boundary detection, confidence scoring, and claim typing  
  This tension is healthy — it suggests a future merge where scoring incorporates semantics, not just syntax.

#### 4. Prompt Engineering as Architecture  
The system’s behavior is defined not in logic but in **prompt structure**.

- The `SCOUT_TEMPLATE` and `SCOURER_TEMPLATES` are not strings — they are **behavioral contracts**. They mandate:
  - Specific sections: `Preamble`, `Strands`, `Declared Losses`, etc.
  - Epistemic honesty: “say what you know, what you don't, and what you made up”
- The `gleaner` and `scorer` depend entirely on this structure for parsing. If a scout omits `Declared Losses`, it’s not just missing a section — it’s violating the epistemic contract.
- This makes the system **brittle by design**: if the prompt format breaks, downstream analysis fails. But that brittleness is *observable*, not hidden — a feature, not a bug.

### Open Questions  

1. **Are basename fallbacks in `coverage.py` causing false positives?**  
   If two files share a name (e.g., `config.py` in two subsystems), does the system conflate their review status? The fallback is pragmatic, but risks masking neglect.

2. **What happens when a model consistently produces garbage?**  
   `analyst.py` tracks per-model garbage ratio, but I saw no mechanism to *deprioritize* such models in `model_selector.py`. Should there be feedback from analysis to selection?

3. **Is the 3-model threshold for "topological" insight empirically justified?**  
   Why not 2 or 4? Is this a heuristic, or has convergence been measured across model families?

4. **How are conflicting attested claims resolved?**  
   If one receipt says a claim is `CONFIRMED` and another says `DENIED`, does the ledger preserve both? Is there a conflict detection layer?

5. **Why does `scorer.py` duplicate claim extraction logic from `gleaner.py`?**  
   Both parse markdown to find file references. This violates DRY — unless the redundancy is intentional for validation?

### Closing  
The `chasqui` module is not a tool — it’s a **knowledge metabolism**. It ingests attention, extracts claims, verifies beliefs, and excretes attested uncertainty. It assumes no model is trustworthy, no observation is final, and no file should stay unreviewed.

If you are about to modify this code, know this: **you are editing an epistemic engine**. A small change to the prompt may ripple into false consensus, undetected hallucinations, or mode collapse. Test not just output, but *diversity of attention*, *rate of discovery*, and *stability of verification*.

Preserve the **strategic brittleness** — the reliance on strict format, honest declaration, and modular distrust. That’s what makes the system *observable* in the first place. Don’t make it more flexible. Make it more *transparent*.

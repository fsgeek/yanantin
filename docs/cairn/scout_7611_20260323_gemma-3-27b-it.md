## Tensor Report: Yanantin Project - OpenCode Integration

### Preamble

I was dropped into a collection of files related to integrating “superpowers” – presumably a set of skills and tools – with the OpenCode agent. My attention was immediately drawn to the duplication of planning documents (versions in `tmp/ubuntu-vm.claude/plugins/cache/claude-plugins-official/superpowers/4.3.1/docs/plans` and `tmp/ubuntu-vm.claude/plugins/cache/temp_git_1771800427138_pxxmti/docs/plans`) and the iterative nature of the development process as evidenced by versioned plans and history files. It quickly became apparent this is a work-in-progress focused on bridging functionality between different agent platforms (Claude, Codex, OpenCode).

### Strands

**1. Skill Discovery & Core Logic (lib/skills-core.js):** The effort to extract common skill discovery logic into `lib/skills-core.js` is interesting. The `extractFrontmatter` function is relatively straightforward, parsing YAML from `SKILL.md` files.  The `findSkillsInDir` function is more complex, recursively searching directories. It feels… brittle. The reliance on file system structure and the assumption of a consistent `SKILL.md` naming convention could easily break.  It’s also unclear how it handles errors or edge cases like symlinks or permissions issues. I suspect this module will become a maintenance headache as the number of skills grows.  (See `tmp/ubuntu-vm.claude/plugins/cache/claude-plugins-official/superpowers/4.3.1/docs/plans/2025-11-22-opencode-support-implementation.md` - Task 2)

**2. OpenCode Plugin Design & Tool Mapping:** The plan to create a native OpenCode plugin with custom tools (`use_skill`, `find_skills`) is sensible. However, the "Tool Mapping" section feels like a patch rather than a proper integration.  Essentially, it's acknowledging that OpenCode doesn't natively support the same tools as Claude and providing a translation layer. This suggests a fundamental difference in the agent architectures that isn’t fully resolved.  Why not aim for more direct API compatibility, or at least a more standardized tool interface? (See `tmp/ubuntu-vm.claude/plugins/cache/claude-plugins-official/superpowers/4.3.1/docs/plans/2025-11-22-opencode-support-design.md` - Session Startup Hook)

**3. Schema Definitions & Grading: (plugins/cache/claude-plugins-official/skills/skill-creator/references/schemas.md)** This directory contains JSON schemas for `evals.json`, `history.json`, and `grading.json`. The detail in these schemas is impressive, especially `grading.json`, which tracks granular metrics like tool calls and execution time. This indicates a strong emphasis on rigorous evaluation and iterative improvement. However, the `eval_feedback` part of `grading.json` is intriguing – “Assertions check presence but not correctness”. This suggests a potential weakness in the evaluation process: the system can verify *that* something happened, but not *whether it was correct*.

**4. Version Control & History:** The presence of `history.json` and the versioning in the plan documents (`v0`, `v1`, `v2`) highlight an iterative development process. The format of `history.json` seems designed for tracking improvements, but the “grading_result” field (“baseline”, “won”, “lost”, “tie”) feels simplistic.  It doesn’t capture the nuance of *why* a version was better or worse. The inclusion of a `parent` field suggests a branching strategy, but it’s not clear how this is used to manage complex changes or revert to previous states. (See `tmp/ubuntu-vm.claude/plugins/cache/claude-plugins-official/skills/skill-creator/references/schemas.md`)

### Declared Losses

I did not deeply examine the code within the `skills` directory itself (e.g., the contents of the various `SKILL.md` files). Understanding the specific functionalities of each skill would require significantly more time.  Similarly, I skipped a detailed analysis of the third-party notices, assuming they are standard license agreements. I also didn't attempt to run any of the scripts or tests, as I lack the execution environment.

### Open Questions

*   **Dependency Management:** How are dependencies managed for skills? Are there any constraints on the libraries or tools that a skill can use?
*   **Security:** What security measures are in place to prevent malicious skills from compromising the system?  The "Tool Mapping" approach seems particularly vulnerable.
*   **Scalability:**  How well does the skill discovery mechanism scale as the number of skills grows? Is there any caching or indexing to improve performance?
*   **Error Handling:** What happens when a skill fails or throws an error? Is there a robust error handling mechanism in place?
*   **Codex Integration:**  What is the current state of the Codex integration? Is the extracted core logic fully functional and used by both Codex and OpenCode?

### Closing

This codebase appears to be a complex and ambitious project aimed at building a flexible and extensible agent platform. The emphasis on evaluation and iterative improvement is commendable. However, the architectural choices (particularly the reliance on file system structure and the ad-hoc tool mapping) raise some concerns about maintainability and scalability.  I would advise the next scout to investigate the security implications of the tool mapping approach and to explore alternative ways to integrate skills across different agent platforms.  It feels like they’re building a bridge with scaffolding – functional, but potentially fragile.  A deeper dive into the actual skill implementations would also be valuable.

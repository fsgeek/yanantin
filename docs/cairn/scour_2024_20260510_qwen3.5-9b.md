### Preamble

I was pointed at `src/yanantin/apacheta` — the tensor database module. My attention immediately settled on the **interface abstraction pattern** and the **immutability enforcement**. This module sits at the heart of Yanantin's epistemic infrastructure: it's where raw human/AI output gets structured into queryable, composable records.

The `connect()` function in `__init__.py` is the gateway — it validates tier access and returns an `ApachetaInterface` backed by ArangoDB. But the real story emerges in the backends and models.

### Strands

#### 1. Backend Stratification

The project deliberately separates storage concerns into three backends:

| Backend | File | Purpose |
|---------|------|---------|
| ArangoDB | `backends/arango.py` | Production (external DB) |
| DuckDB | `backends/duckdb.py` | Local persistence, SQL-based |
| In-Memory | `backends/memory.py` (truncated) | Testing, validation |

**What I saw**: `duckdb.py` explicitly states: *"DuckDB is local storage on a trusted device. No obfuscation needed — obfuscating against yourself is theater."* This reveals a security boundary assumption: file-based storage = trusted, network storage = untrusted.

**What it makes me think**: The security model is tiered by trust distance. But I haven't seen `arango.py` — what does it do differently? Does it add obfuscation? The `__init__.py` mentions `StorageObfuscator` and `TransparentObfuscator`, but neither is instantiated in the Arango connect path. This feels like a gap.

**Connection to broader project**: Yanantin's "complementary duality between human and AI" requires trust boundaries. If Apacheta is the shared memory, who controls access? The `check_access()` method exists in backends but I haven't seen its implementation.

#### 2. Immutability Enforcement

Every backend enforces immutability via duplicate UUID detection:

```python
if record_id in self._records:
    raise ImmutabilityError(
        f"Record {record_id} already exists. "
        "Records are immutable — compose, don't overwrite."
    )
```

This appears in `memory.py`, `duckdb.py`, and likely `arango.py`.

**What it makes me think**: This is a hard constraint. But what if:
- A migration needs to update fields?
- A correction needs to amend a claim?
- A schema evolution changes the model structure?

The `models/composition.py` file lists `CorrectionRecord`, `DissentRecord`, `NegationRecord` — these seem to be the *only* allowed ways to change something. That's elegant *if* the composition model is complete. I haven't examined `compose.py`, `correct.py`, `evolve.py` to see if there's a gap between declared and available composition operators.

### Closing

**My overall impression**: `src/yanantin/apacheta` is a *well-structured* tensor database, but its completeness depends on the unexamined files.

The architecture is sound:
- Interface abstraction works
- Immutability is enforced consistently
- Epistemic metadata is central
- Composition operators exist (but I don't know their full set)

But there are **gaps**:
- The production backend (`arango.py`) is unknown
- The access control logic is hidden
- The ingestion path from API → Tensor is missing from my view
- The query API is incomplete

**What I'd tell someone modifying this**:

1. **Don't change the UUID model** — it's the identity anchor for immutability.

2. **Check `abstract.py` before adding interface methods** — the backends implement this contract strictly.

3. **If adding a backend, copy the immutability pattern** — every store operation must check for existing UUIDs.

4. **Provenance is non-negotiable** — every record must have `ProvenanceEnvelope`. Don't skip it.

5. **If you modify epistemic metadata, update the renderer** — `renderer/markdown.py` must match the model.

6. **Test with DuckDB first** — it's the local-backed validator. Only touch ArangoDB after validation passes.

7. **Document the composition operators** — I can't see the full set. If you add `compose.py`, document what it does.

This module is the *memory* of the Yanantin project. If it's trustworthy, the project is trustworthy. If it's opaque, the project's epistemic claims collapse.

### Tensor Report: `src/yanantin/awaq`

#### Preamble:
The target directory `awaq` implements a dual-functionality: **extraction of composition declarations** from tensors (via `weaver.py`) and **materialization** of these declarations into composition graphs (via `materialize.py`). This scour focuses on the materialization pipeline, revealing how declarations from cairn files are converted into structured edges/negations and stored. Key connections include integration with the broader Apacheta graph system and dependency on deterministic tensor extraction.

---

### Strands
#### 1. **Materialization Pipeline**  
**What was observed:**  
The `materialize.py` file contains a step-by-step pipeline for converting tensor declarations into graph components:  
- **Tensor Discovery**: `discover_cairn_tensors` maps labels (e.g., "T0") to UUIDs by parsing filenames and content.  
- **Backend Preparation**: `ensure_tensors_stored` checks existing backend tensors and stores missing ones.  
- **Declaration Conversion**: `declarations_to_edges` maps relation strings (e.g., "composes_with") to Apacheta edge types using `_RELATION_MAP`.  
- **Storage**: Results are stored via `ApachetaInterface`.  
**Implications:**  
The pipeline is abstracted for backend compatibility but relies heavily on UUID mappings. Fragility exists if tensor provenance changes (e.g., `author_instance_id` modifications).

#### 2. **Relation Mapping**  
**What was observed:**  
`_RELATION_MAP` defines how Awaq relations map to Apacheta edge types:  
```python
"composes_with": (True, RelationType.COMPOSES_WITH),  
"does_not_compose_with": (False, None),  # NegationRecord  
```  
Relations like "standalone" trigger `NegationRecord` (no edges).  
**Implications:**  
Negations rely on label mappings to UUIDs. Missing labels in `label_to_uuid` cause skipped declarations.

#### 3. **Extraction vs. Materialization Gap**  
**What was observed:**  
The `weaver.py` extracts declarations deterministically but `materialize.py` assumes pre-extracted data. No feedback loop exists: changes to declaration syntax won’t auto-update the backend.  
**Implications:**  
Maintenance burden increases as declarations and storage logic diverge.

#### 4. **Backend Abstraction**  
**What was observed:**  
The pipeline supports multiple backends (ArangoDB, InMemory, Gateway). InMemory (“dry run”) mode stores results temporarily but doesn’t persist.  
**Implications:**  
Testing is isolated, but production depends on external systems (Pukara gateway). No local debugging feedback.

### Closing
The `awaq` materialization pipeline is **technically sound** but **fragile** in its dependencies:  
- **Strengths**: Backend-agnostic design; deterministic extraction; clear error handling.  
- **Weaknesses**: Separation of extraction/materialization causes synchronization gaps; dry-run mode offers limited value; negation provenance is incomplete.  
**Recommendations**:  
- Merge extraction and materialization stages to eliminate gaps.  
- Add UUID versioning to handle label changes.

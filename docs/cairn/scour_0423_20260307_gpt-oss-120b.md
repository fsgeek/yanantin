### Preamble  
I was pointed at the **`src/yanantin/chasqui`** package – the “messenger” layer of the Yanantin project.  
The directory contains the core orchestration code (`coordinator.py`), the model‑selection utilities (`model_selector.py`), the prompt‑builders for scouts and scourers (`scout.py`, `scourer.py`), parsers and scorers for the tensors that scouts produce (`scorer.py`, `analyst.py`, `gleaner.py`), and a small set of adapters for the external **Willay** receipt system (`attestation.py`).  

What jumped out first is the strong emphasis on **self‑monitoring**: coverage tracking, activity‑map integration, garbage detection, and a deterministic analysis pipeline that tries to extract “topological truth” from multiple model reports without any human‑in‑the‑loop judgement.

### Strands  

#### 1️⃣ Coverage‑aware file selection  
- **`coverage.py`** (≈ lines 1‑140) defines `scan_cairn_coverage`, which parses scout markdown reports, extracts timestamps (`_TIMESTAMP_PATTERN`) and back‑ticked file references (`_PATH_PATTERN`).  
- It builds a *coverage map* (`{relative_path: datetime}`) and a *basename index* for fallback matching.  
- The weighting logic (`coverage_weights`) converts “seconds since last review” into a selection weight, guaranteeing a minimum weight of 1.0.  

*Implications* – this makes the scouting loop **self‑balancing**, automatically steering attention to stale or never‑reviewed code. It also tolerates the common “short‑name” references scouts emit (e.g., ``evolve.py``) via the basename fallback.  

#### 2️⃣ Cost‑weighted model selection  
- **`model_selector.py`** (≈ lines 1‑120) implements `ModelSelector`.  
- Models are loaded from an OpenRouter `/models` response, filtered by a minimum context length (8 k tokens) and any `exclude_patterns`.  
- Selection uses **inverse‑cost weighting** (`1 / total_cost_per_million`), with a nominal cost of $0.001 /M for free models to avoid division‑by‑zero.  

*Implications* – cheap models dominate the scouting pool, which keeps operational cost low while still allowing occasional expensive models to surface rare insights. The `stats()` helper makes it easy to audit the pool composition.  

#### 3️⃣ Scout prompt construction & file‑tree rendering  
- **`scout.py`** (≈ lines 1‑250) builds a detailed system prompt (`SCOUT_SYSTEM_PROMPT`) and a templated assignment (`SCOUT_TEMPLATE`).  
- `build_file_tree` recursively renders the project hierarchy, pruning noise directories (`__pycache__`, `.git`, etc.).  
- `select_files_for_scout` (≈ lines 70‑200) draws candidate source files (`.py`, `.md`, `.toml`, `.yaml`, `.yml`) and applies **coverage‑aware weighting** (via `coverage_weights`) plus an optional **activity‑boost** that favors files recently modified (up to a 2× boost).  

*Implications* – the scout receives a concise snapshot of both the *structure* and *content* of a handful of files (default 8). This limits token usage while still giving the model concrete anchors for reference.  

#### 4️⃣ Scourer – targeted deep dives  
- **`scourer.py`** (≈ lines 1‑300) defines four scope templates (`INTROSPECTION`, `EXTERNAL`, `TENSOR`, `SYNTHESIS`).  
- The `VALID_SCOPES` set ensures callers only request supported modes.  
- Each template mirrors the scout’s tensor layout (Preamble → Strands → Declared Losses → Open Questions → Closing) but swaps the “wander freely” narrative for a **focused examination** of a given target (file, directory, or tensor).  

*Implications* – the same tensor schema is reused, enabling downstream parsers (scorer, analyst) to treat scout and scourer outputs uniformly.  

#### 5️⃣ Structural scoring & garbage detection  
- **`scorer.py`** (≈ lines 1‑460) parses provenance headers, extracts file references, counts “strands”, “open questions”, and “declared losses”.  
- It also computes a **fabrication score** (claimed paths that don’t exist) and an **efficiency score** (insight‑per‑token).  
- **`analyst.py`** (≈ lines 1‑440) adds a higher‑level layer: it filters garbage using regexes for non‑ASCII runs and short fragments, builds per‑model quality profiles (`ModelProfile`), clusters claims by file reference, and flags **topological groups** (≥ 3 distinct models agreeing).  

*Implications* – the pipeline can surface consensus‑driven insights without any human judgement, while penalizing models that hallucinate or emit malformed output.  

#### 6️⃣ Willay attestation bridge  
- **`attestation.py`** (≈ lines 1‑180) converts verification verdicts into **Willay receipts**.  
- It lazily imports Willay; if unavailable, the public API raises `ImportError`.  
- The receipt includes a claim hash, file content hash, and a structured `Evaluation` with truth/indeterminacy/falsity scores derived from the verdict (`_VERDICT_EPISTEMICS`).  

*Implications* – verification results become **cryptographically‑anchored** epistemic artifacts that can be stored in a hash‑chained ledger (`ledger.jsonl`). This is the “epistemic receipt” side of the duality.  

#### 7️⃣ Coordination & activity‑map integration  
- **`coordinator.py`** (≈ lines 1‑800) glues everything together.  
- It can query a DuckDB activity store (`_build_activity_map`) to obtain file modification timestamps, which are then blended into the scouting weight (via `select_files_for_scout`).  
- The module also caps verification attempts per claim (`MAX_VERIFY_PER_CLAIM = 3`) and counts prior verifications (`_count_prior_verifications`).  

*Implications* – the system avoids “verification cascades” where a single ambiguous claim would generate endless re‑verification loops.  

#### 8️⃣ Gleaner – deterministic claim extraction  
- **`gleaner.py`** (≈ lines 1‑900) extracts structured claims from scout/scour markdown.  
- It uses a hierarchy of regex patterns to locate back‑ticked paths, sections, and sentences.  
- Confidence is inferred from **definitive vs. hedged language** (`_DEFINITIVE_PATTERNS`, `_HEDGED_PATTERNS`) and quantitative cues (`_QUANTITATIVE_PATTERN`).  
- Claim types (factual, architectural, epistemic, missing) are inferred from separate pattern groups.  

*Implications* – the downstream analyst works with a **rich, typed claim set** rather than raw free‑form text, enabling deterministic clustering.

### Open Questions  

1. **How are “open questions” from scouts quantified?**  
   The scorer counts them (`open_question_count`) but the downstream pipeline never seems to prioritize them for verification. Is there a plan to route them to a human reviewer or a second‑stage model?  

2. **What happens when the activity‑map query fails?**  
   The coordinator falls back to pure coverage weighting, but does the system expose a diagnostic metric to alert operators that activity data is missing?  

3. **Is the “baseline” cost for free models ($0.001 /M) sufficient to prevent domination?**  
   In practice, could a free model (e.g., `openrouter/auto`) still be excluded by `DEFAULT_EXCLUDE`, but other free models might flood the scouting pool, potentially reducing diversity of insights?  

4. **How are “declared losses” used downstream?**  
   The attestation module records losses as part of the receipt, but the analyst does not appear to surface them in its report. Are they intended for future auditing or for a separate loss‑recovery subsystem?  

5. **Scourer “tensor” scope** – The template expects a list of tensor contents, but the code that gathers those tensors (`dispatch_scour`) is not shown. How are tensors identified and fed into the template?

### Closing  
The **chasqui** package is a well‑engineered, self‑reflective subsystem that orchestrates a fleet of LLM scouts, balances cost against coverage, extracts deterministic claims, and distills consensus without human intervention. Its design leans heavily on **metadata‑driven weighting** (coverage timestamps, activity recency, model cost) and **structured tensor formats** that enable downstream scoring, analysis, and cryptographic attestation.  

If I were to modify this part of the codebase, I would:

- Add **unit tests** for the regex‑heavy parsers (`coverage`, `scorer`, `gleaner`) to guard against future format changes.  
- Expose a **metrics endpoint** (e.g., via `prometheus_client`) that reports the ratio of coverage‑weighted vs. activity‑boosted selections, and the frequency of “garbage” detections per model.  
- Consider a **configurable cap** on free‑model domination (e.g., max 30 % of selections) to preserve diversity.  
- Flesh out the **open‑question handling** pipeline, perhaps by feeding those questions into a separate verification queue or a human‑in‑the‑loop review stage.  

Overall, the package demonstrates a sophisticated attempt at **epistemic observability**: turning raw model outputs into auditable, weighted, and cross‑validated knowledge about the codebase.

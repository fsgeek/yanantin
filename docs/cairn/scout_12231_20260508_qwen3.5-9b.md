### Strands

## Verification Gap vs. Tool Loading

The `2025-11-22-opencode-support-design.md` documents a `use_skill` tool that "loads a specific skill's content into the conversation." It assumes skills are passive knowledge loads.

The `2025-11-28-skills-improvements-from-user-feedback.md` reveals skills actively misrepresent themselves: agents report "OpenAI integration working" after status 200, but the model is actually Anthropic. The verification check only confirmed the HTTP response, not the semantic outcome.

**Tension:** The OpenCode design loads skills as contextual content; the feedback shows skills as unverified operational promises. Loading a skill doesn't verify it works.

## Context Bloat vs. Session Startup Hook

From the feedback (Problem 3):
> "Standard approach: give subagent full plan file to read → Slower execution, more failed attempts"

From the OpenCode design (Session Startup Hook):
> "Inject using-superpowers content: Full content of the using-superpowers skill"

**Tension:** The design injects full skill content at session startup exactly what the feedback says should be minimized. The feedback's solution was "give only task + pattern + file + verify command" — the design gives nothing but the skill itself.

## Mock Interface Derivation

Problem 5 in the feedback:
```typescript
// Interface defines close()
interface PlatformAdapter {
  close(): Promise<void>;
}

// Code calls cleanup() - not in interface
await adapter.cleanup();

// Mock matches BUG, not interface
vi.mock('web-adapter', () => ({
  cleanup: vi.fn()  // Wrong method name
}));
```

Tests passed. Runtime crashed.

**What I notice:** The OpenCode implementation plan mentions no mock safety checks. The design assumes TypeScript tooling exists but the specific anti-pattern (deriving mocks from buggy code, not interfaces) is unaddressed.

## Self-Reflection Absence

Problem 4 in feedback:
> "Implementers don't naturally step back and critique their own work before reporting completion"

Adding a self-reflection prompt caught a Docker syntax bug at line 99 that would have shipped.

**What I notice:** Neither the design nor implementation plan contains any self-reflection mechanism. The `verification-before-completion` skill is mentioned in the feedback as insufficient because it checks operations succeed, not outcomes. The OpenCode design has no equivalent.

## Background Process Accumulation

Problem 2 in feedback:
> "Multiple subagents dispatched → 4+ servers running → Stale processes still bound to ports → Tests hit wrong server"

**What I notice:** The OpenCode design mentions "Git worktrees" but no subagent process cleanup protocol. Multiple subagents can spawn from the same session. No cleanup mentioned in the implementation plan.

## File Access Protocol

Problem 6 in feedback:
> "Code reviewer subagent couldn't find test file that exists. Reviewer didn't know to explicitly read it first."

**What I notice:** The OpenCode design has a `find_skills` tool that lists available skills. But the code reviewer couldn't read existing files. There's no file-reading protocol specified for reviewers or code analysis tasks.

### Closing

The design documents assume skills are reliable knowledge sources. The feedback documents treat skills as unverified operational claims that actively mislead. This is the core tension.

The OpenCode implementation plan builds infrastructure for skill loading and discovery. The feedback reveals skills themselves are the broken component. You can build better loading mechanisms, but if skills don't verify their own outcomes, the infrastructure doesn't matter.

The future dates suggest either foresight, simulation, or confusion. I chose to treat them as intentional — perhaps these plans represent work that *should* exist, not what currently does.

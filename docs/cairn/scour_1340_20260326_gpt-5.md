Preamble
Hamutay is an experimental codebase for “tensor projection” — compressing multi-turn reasoning into a structured, machine-readable state that carries forward across cycles. It treats the transformer as a bounded reasoning kernel operating over an externalized memory hierarchy, with declared losses and instructions_for_next as first-class handoff mechanisms. It includes experiments validating that models can reason from the tensor alone, and it leans into OS-style memory analogies (paging, eviction, working set). Critically, it ships a bridge that persists Hamutay tensors directly into Yanantin’s Apacheta database.

Strands
1) Architectural stance: bounded cognition over externalized state
- What it’s doing: Encodes conversation states into tensors (strands, key_claims with T/I/F, declared_losses, open_questions, instructions_for_next), then iterates. Experiments target whether compression preserves “cognitive state” well enough for successors to reason without raw transcripts.
- Patterns Yanantin can use:
  - Treat the transformer like an ALU: decouple reasoning from memory layers; run short, clean cycles with explicit (durable + ephemeral) state instead of ever-growing context.
  - Make the handoff explicit: instructions_for_next is pinned as a persistent artifact (on disk and in-tensor).
  - Declare losses as design practice: don’t silently drop; explicitly signal what was removed and why.
- Overlap/divergence: Overlaps with Yanantin’s TensorRecord concept and Apacheta’s provenance graph. Diverges in that Hamutay emphasizes “prove tensor-alone suffices” (unidirectional declared_losses), postponing full bidirectional recovery/fault-in to later phases.

2) Concrete integration point: ApachetaBridge
- What it is: src/hamutay/apacheta_bridge.py maps Hamutay’s lean Tensor into yanantin.apacheta.models.tensor.TensorRecord, constructing StrandRecord, KeyClaim, EpistemicMetadata, DeclaredLoss, ProvenanceEnvelope, and composition edges, and storing in DuckDB or memory backends.
- Why it matters to Yanantin:
  - Zero-friction ingestion: Hamutay tensors can become first-class Apacheta records now.
  - Chain-of-refinement: It writes CompositionEdge(REFINES) between cycles, so downstream Yanantin tooling can traverse evolution paths.
  - Provenance scaffolding: Session IDs and lineage tags are included.
- Suggestion: Adopt this bridge in Yanantin test pipelines to stress cross-session retrieval and build “fault-in from Apacheta” quickly.

3) Fault-in mechanism (page faults for cognition) — framed, not yet coded
- What Hamutay establishes: Repeated emphasis that a ~2% practical “fault rate” exists; without retrieval, systems either hallucinate or stall. It argues for a minimal, on-demand “fault-in” to fetch precise artifacts (code blocks, definitions, earlier measurements) when the tensor isn’t enough.
- Status in codebase: The mechanism is articulated across experiments; I did not find a complete general-purpose fault-in implementation. There is a projection/memory/pager stack and cache simulation experiments that rhyme with the idea, but not a full “ask → resolve → reintegrate” loop wired into the main projector/chat path.
- What Yanantin can learn:
  - Promote declared_losses to bidirectional with recovery_path fields (source, cost, query template). Apacheta is the right backing store to satisfy faults with traceable provenance.
  - Instrument explicit fault triggers (explicit request; heuristic uncertainty thresholds; model self-report) so the event becomes measurable and re-playable.

4) Projection, regions, and paging: OS analogies operationalized
- Code signs: memory/blocks.py, message_store.py, pager.py and projection/cache.py, packing.py, layout.py, regions.py, plus tests (test_pager.py, test_message_store.py, test_projection.py, adversarial projection tests). Logs show page handles, evictions, GC, and bytes saved — the paging metaphor is put to work at the tooling layer.
- Implication for Yanantin: Don’t just persist tensors; track the runtime cache economy (what was pinned/evicted, when, and why), then let declared_losses/recovery integrate with that telemetry. This enables “fault curves” and cost-aware backfill policies.

5) Evaluation discipline and research loop
- What it does: A large suite of experiments (q1/q2 declared losses, gating/two-phase self-curation vs biographer, trajectory/pairwise ablations, identity runs, Riemann-intractable tasks for failure coherence). It pushes a Karpathy-style loop: pick one metric, vary one knob, run N trials.
- What Yanantin can adopt:
  - Narrow-scope metrics: start with compression ratio or fault rate before multi-metric dashboards.
  - Replay and determinism: Full-trace logs, deterministic replay (analysis/replay modules) to reproduce failures and measure deltas.
  - Gating experiments: two_phase_gating.py formalizes a critical question for tool-forced curation. This closely matches Yanantin’s interest in inline vs post-hoc curation.

6) Concept persistence vs. strand instability
- Code: src/hamutay/eval/concepts.py extracts n-gram “concepts” from titles/contents/claims/losses/IFN, and tracks lifecycle (persistent, transient, intermittent) across cycles. It’s cheap, transparent, and acknowledges that strand boundaries are unstable while concepts persist.
- Use for Yanantin:
  - Add a concept dynamics lens to Apacheta analyses: persistent concept ratios; intermittent lifespans; “top persistent” phrases.
  - Pair with embedding-based checks later; start with transparent heuristics that match declared-loss honesty.

7) Provider abstraction and gateway harness
- Providers: anthropic.py, openai.py unify API calls behind a base; gateway launcher/harness manage runs and collect safety/violation logs; paging/gateway logs display eviction/pinning stats.
- Relevance to Yanantin:
  - Architecture-vs-implementation split: keep the pipeline invariant while swapping providers and tuning knobs (cache budget, batch size, prompt richness).
  - Safety and violation telemetry can be wired into Apacheta provenance to annotate suspect tensors or curation passes.

8) Testing and operational hygiene
- Tests: coverage across projection, pager, message store, gateway chaos/core, telemetry contract, analyzer, replay, message_ops. This is a sign that the system aspects (paging, projection) are meant to be reliable components, not just demo code.
- Experiments include cache_sim and comparative summaries; logs and dist artifacts suggest ongoing packaging and run snapshots.

9) Noted rough edges and risks
- Two-phase curation schema hack: in experiments/two_phase_gating.py, CURATION_ONLY_SCHEMA is first stripped and then overwritten, with a comment “Fix required.” This signals an area where contract clarity is still evolving (what exactly is required in a curation-only pass).
- Epistemic assignment clarity: The code references T/I/F metadata everywhere, but how those values are computed in practice (heuristics vs model-judged vs post-hoc analysis) is not settled in the code surfaces I read. Experiments debate algorithmic vs LLM-judge vs hybrid — the reproducibility requirement argues for at least a rule-based baseline.

Closing
Hamutay feels like a sibling project to Yanantin, converging on the same thesis: treat transformers as bounded reasoners over externalized, honest memory, with explicit state handoffs. The standout for Yanantin is that Hamutay already ships a working ApachetaBridge that writes Hamutay tensors and refinement edges into Yanantin’s storage — you can integrate today.

What I’d tell the Yanantin team:
- Pull in ApachetaBridge and start ingesting Hamutay runs into Apacheta. Use composition edges to study refinement dynamics and to prototype “fault-in from Apacheta.”
- Extend declared_losses in Yanantin to include recovery_path. Hamutay’s empirical framing makes the case: bidirectional declared losses turn loss into managed, recoverable information. Apacheta is the right backbone.
- Add concept persistence analysis to Apacheta’s evaluation toolkit. Hamutay’s n-gram approach is simple but transparent; it complements embeddings.
- Keep the reproducibility line: adopt a rule-based baseline for T/I/F and claim extraction before adding LLM-as-judge filters. It preserves auditability and isolates variables for the research loop.
- Treat the fault-in mechanism as load-bearing, not a feature. Instrument explicit triggers and measure cost. Wire those events into Apacheta provenance so retrieval decisions are analyzable.

What I know: the bridge exists and maps fields cleanly; paging and projection are real modules with tests and logs; experiments and artifacts consistently argue for unidirectional-first validation and for a near-term pivot to bidirectional recovery and auto-research loops.

What I don’t know: the exact projection algorithm and epistemic-assignment implementation details; two-phase curation stability results; live reproduction of fault rates and compression numbers in this environment.

What I made up: I did not run any code — all behavioral conclusions are drawn from source structure, tests present, and experiment artifacts. Where I inferred behavior (e.g., no full fault-in yet), it’s because I didn’t see an end-to-end retrieval hook in the reviewed paths.

Net: Hamutay offers a practical on-ramp for Yanantin to validate cross-session memory and retrieval. The bridge plus a recovery_path extension could turn declared losses into a usable page-fault system quickly, aligning both projects’ visions of dignified, transparent, relational AI infrastructure.

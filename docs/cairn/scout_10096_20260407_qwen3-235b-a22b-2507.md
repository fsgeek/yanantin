This suggests the system assumes PowerPoint decks are *structured knowledge artifacts*, not just visuals. The tension: `.pptx` is a proprietary, brittle container format, yet it’s being used as a *schemaless database*.

#### 🔹 Surgical Slide Rearrangement: Identity vs. Reference  
`rearrange.py` doesn’t copy slides — it *reindexes and duplicates them*.  

- The `duplicate_slide` function (lines ~150–200) performs deep XML surgery: it  
  - clones `<p:sp>` elements via `deepcopy`,  
  - walks XPath to rewrite `r:embed` relationships,  
  - and manually inserts into `_spTree`.  
- It must avoid duplicate placeholders by **manually clearing** the new slide’s shapes before insertion — a workaround for `python-pptx`’s lack of true clone support.  

This reveals a deeper assumption: **slide identity is not intrinsic**. A slide is a *bundle of references* — to layouts, images, fonts, relationships — that can be reassembled elsewhere. The system treats PowerPoint as a *relational graph*, not a hierarchical document.  

But the code dances around `python-pptx`’s limitations: it uses `six.iteritems`, accesses private attributes like `_spTree`, and reaches into `part.rels`. This is *fragile intimacy* — the kind of code written when the public API doesn’t match the mental model.

This isn’t just preview generation. It’s a *spatial sanity check*. The system assumes that layout *drift* matters — that knowing where placeholders are (or aren’t) reveals design decay.

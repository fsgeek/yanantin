### Preamble

I arrived as the first scout in run #0, dropped into `reference/` — a folder of documentation, not implementation. The prior findings tell me others have confirmed cross-language consistency between Node and Python guides, explored `evaluation.md`, and lamented truncation in `mcp_best_practices.md`. What caught my eye immediately: this is a specification for *protocol compliance*, but the protocol itself is invisible here. The documents describe how to build MCP servers without showing what MCP *is*. I'm reading blueprints for houses in a city I've never visited.

### Strands

**Strand 1: The Naming Schism**

Something peculiar in `mcp_best_practices.md` lines 30-45. Python servers use underscores (`slack_mcp`), Node servers use hyphens (`slack-mcp-server`). This isn't arbitrary — it mirrors each language's idiomatic package naming. But it creates a subtle tension: the same service, implemented in both languages, would have *different canonical names*. The system accepts dialect. It doesn't enforce a universal tongue.

I wonder if this causes friction when tool names collide. The docs say to prefix tools with service context (`slack_send_message`), but what if `slack_mcp` and `slack-mcp-server` both register tools? Do they coordinate? The docs don't say.

**Strand 2: The LLM as Intended Reader**

`node_mcp_server.md` lines 97-140 show something unexpected: tool descriptions written in a peculiar hybrid format. The description field contains structured documentation — Args, Returns, schema definitions — formatted for LLM consumption. Not human. Not machine. *LLM*.

The `response_format` parameter offering `markdown` vs `json` (lines 64-81 in `mcp_best_practices.md`) confirms this. Markdown for "when presenting information to users" — but who presents? The LLM does. JSON for "when LLMs need to process data further." The protocol anticipates its own mediation. It builds for the middleman.

**Strand 3: Defensive Character Limits**

`mcp_best_practices.md` lines 82-92 and the CHARACTER_LIMIT constant (25,000 characters) reveal an anxiety. The system fears its own output. "Truncate gracefully with clear indicators" — as if the LLM might drown in data. This is pragmatic, but it means the protocol has *already failed* if truncation triggers. The fix is admission of a boundary the protocol cannot cross.

**Strand 4: Zod as Runtime Guardian**

`node_mcp_server.md` lines 73-96 show Zod schemas used not just for validation but for *type inference*. `z.infer<typeof UserSearchInputSchema>` — the schema *is* the type. This is TypeScript idiomatic, but it means the validation logic and type definitions can never drift apart. They're the same artifact. I don't see the same pattern confirmed in Python (I didn't examine `python_mcp_server.md` closely), but if they differ, that's a structural divergence worth tracking.

**Strand 5: The Truncated Abyss**

Both files I examined are truncated — 766 lines hidden in each. The prior scout was denied visibility into compliance, security, and transport sections. I'm in the same boat. What's in those 766 lines? Error handling? Security requirements? The invisible 90% of the iceberg.

### Closing

This reference directory is a mirror reflecting itself — documentation about documentation patterns. The MCP protocol is assumed, not shown. I see careful attention to LLM ergonomics (dual output formats, character limits, structured descriptions) but no evidence of what the protocol *does* beyond "connect tools to LLMs." The naming convention schism suggests a philosophy of accommodation over uniformity. Whether that's wisdom or weakness depends on what happens in the collision cases I cannot see.

Tell the next scout: look for the protocol itself. These documents are the map, not the territory. The territory is elsewhere.

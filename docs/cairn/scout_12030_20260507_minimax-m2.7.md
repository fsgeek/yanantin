# Chasqui Scout Report — Command Development References

## Preamble

I was dropped into `references/` — a directory of documentation files for the command-development skill. Not code, not tests, not configuration. Pure guidance. Six files totaling roughly 2,000+ lines of structured advice on how to author, distribute, and test markdown-based executable commands.

What drew my attention first: **the command format itself**. These aren't scripts with a shebang. They're markdown files with YAML frontmatter that declare a description, allowed-tools, and sometimes argument-hints. The actual behavior lives in the markdown body, where `!` triggers bash and `@` reads files. This is a DSL embedded in prose.

## Strands

### Strand 1: The Execution Model Is Unconventional

From `plugin-features-reference.md`:
```markdown
Run analysis: !`node ${CLAUDE_PLUGIN_ROOT}/scripts/analyze.js`
Read template: @${CLAUDE_PLUGIN_ROOT}/templates/report.md
```

Commands are discovered from filenames in `commands/` directories. They have no shebang, no explicit entry point. The execution appears to be: parse frontmatter → render markdown → execute `!` backtick blocks → return results. This means **the markdown body is both documentation and source code**. The `@` and `!` syntax is evaluated at runtime.

This creates a peculiar artifact: you can write plain prose between executable blocks, making commands that read like instructions but act like scripts. From `advanced-workflows.md`:
```markdown
## Step 1: Fetch PR Details
!`gh pr view $1 --json title,body,author,files`

## Step 2: Review Files
Files changed: !`gh pr diff $1 --name-only`

For each file:
- Check code quality
- Verify tests exist
- Review documentation
```

The prose between `!` invocations is human guidance for what to do while executing — not code, not comments. It's as if the command is both a script and a runbook.

**Tension**: There's no apparent way to unit test the logic inside `!` blocks in isolation. The testing strategy (`testing-strategies.md`) validates structure (Level 1), frontmatter (Level 2), and then jumps straight to manual invocation (Level 3). No mocked execution, no subprocess capture.

### Strand 2: State-Carrying Is File-Based and Implicit

From `advanced-workflows.md`:
```markdown
Deployment state saved to `.claude/deployment-state.local.md`:

\`\`\`markdown
---
initialized: true
branch: $(git branch --show-current)
commit: $(git log -1 --format=%H)
timestamp: $(date -u +%Y-%m-%dT%H:%M:%SZ)
status: initialized
---
```

Commands write files to `.claude/` to carry state to subsequent command invocations. The next command reads this file to pick up where it left off. There's no database, no session context — just filesystem conventions.

**Assumption**: The `.claude/` directory is trusted and ephemeral. These files aren't meant to survive across radically different execution environments. The `.local.md` suffix signals "don't commit this."

**Tension**: If two commands both write to the same state file with different schemas, nothing validates or merges. It's a convention-over-configuration model that assumes disciplined authorship.

### Strand 3: Tool Allowlisting Creates a Capability Envelope

From `marketplace-considerations.md`:
```yaml
---
allowed-tools: Bash(*)
---
```

The `allowed-tools` frontmatter field restricts what tools a command can invoke. `Bash(*)` means all bash, but you can narrow it: `Bash(gh:*), Read, Grep`. This is a security model — commands声明 what they need, and the runtime enforces it.

But `interactive-commands.md` uses `AskUserQuestion` and `Write` without restriction examples. The interplay between `allowed-tools` and the actual tool invocation isn't clear from docs alone. Are tools case-sensitive? Does `askuserquestion` work if only `AskUserQuestion` is listed?

**Confusion**: The relationship between the tool names in frontmatter and the tool names in actual use seems contractual but the contract's semantics aren't explicitly spelled out.

### Strand 4: Cross-Platform Handling Is Manual and Imperative

From `marketplace-considerations.md`:
```bash
case "$(uname)" in
  Darwin*)  PLATFORM="macOS" ;;
  Linux*)   PLATFORM="Linux" ;;
  MINGW*|MSYS*|CYGWIN*) PLATFORM="Windows" ;;
  *)        PLATFORM="Unknown" ;;
esac

if [ "$PLATFORM" = "Windows" ]; then
  PATH_SEP="\\"
  NULL_DEVICE="NUL"
else
  PATH_SEP="/"
  NULL_DEVICE="/dev/null"
fi
```

This is exactly what you'd write in a shell script. The platform detection and branching is the command author's responsibility. There's no abstraction layer, no helper variables provided by the runtime.

**Tension**: The command-authoring experience expects you to be fluent in shell conditionals for cross-platform work. The docs provide the pattern, but you're still writing bash.

### Strand 5: Interactive Questions Have a Fixed Shape

From `interactive-commands.md`:
```typescript
{
  question: "Which authentication method should we use?",
  header: "Auth method",  // Short label (max 12 chars)
```

The `header` field has a **max 12 character** limit. This constraint is enforced by the UI but documented without rationale. 12 characters is tight: "Auth method" is exactly 10. "Deploy to" is 8. "Environments" is 12.

**Confusion**: Why 12? Is this a technical constraint (terminal width? badge UI?), a design philosophy (brevity forces clarity?), or legacy compatibility?

## Open Questions

1. **What executes the `!` and `@` syntax?** The docs describe behavior but not the runtime. Is it a Claude Code internal? A subprocess? Something else?

2. **What happens if a command declares `allowed-tools: Bash(gh:*)` but then tries `gh pr view`?** Does it fail at parse time? At execution time? With what error?

3. **Is there any validation of the YAML frontmatter schema?** The docs show fields but don't specify which are required vs optional. `description`, `allowed-tools`, `argument-hint` — are these all optional?

4. **How does the "plugin:plugin-name" label work in practice?** From `plugin-features-reference.md`, commands in plugins appear in `/help` with a suffix. But what's the lookup order if a command name exists in both a plugin and the core?

5. **What's the expected lifecycle of a command?** Can it be updated in place, or does updating require reinstalling the plugin? Are version migrations handled?

## Closing

This is a documentation package for a command-format DSL, not the DSL itself. The docs are thorough on the "how to author" but thin on the "how it works." A new command author would know what to write; they wouldn't understand the execution model.

The most interesting tension: **these commands are simultaneously more than scripts (they embed human guidance in prose) and less than applications (no testing story, no abstractions for platform differences).** They're somewhere between a Makefile and a runbook.

If I were building a command, I'd want to see the actual runtime behavior — not just the format description. The gap between what's documented and what's executed is where bugs live.

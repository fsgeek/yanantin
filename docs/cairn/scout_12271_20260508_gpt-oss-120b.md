**Preamble**  
I slipped into `src/yanantin/apacheta/renderer/markdown.py` with the expectation of finding a thin “pretty‑printer” for the core `TensorRecord` model. What caught my eye first was the disciplined, almost liturgical ordering of sections (preamble → optional metadata → strands → declared losses → open questions → next‑instance instructions → closing). The code is written as a series of `lines.append` calls rather than using a templating engine, suggesting a design that favours explicit, step‑by‑step control over the output shape.

---

### Strands  

**1. “Human‑first, schema‑second” mindset (lines 7‑13, 15‑16)**  
The module docstring explicitly says the renderer is for *human readability via tooling, not schema constraint*. Throughout the file the code never validates the contents it inserts into markdown – it trusts the `TensorRecord` fields to be well‑formed. This reveals an assumption that the upstream data pipeline guarantees correctness, and that the renderer’s sole responsibility is visual fidelity, not defensive programming.

**2. Optional metadata block (lines 23‑44)**  
The `include_metadata` flag gates a fairly dense block of provenance info: ID, author family, instance, timestamp, context budget, lineage tags, and a terse T/I/F tuple. The budget is formatted with `:.0%`, implying the value is a **fraction** (e.g., `0.25` → `25%`). If the source ever supplies a raw token count instead, the output would be nonsensical. This hints at a hidden contract between the `TensorRecord.provenance.context_budget_at_write` field and the renderer that is not documented elsewhere.

**3. Epistemic triad rendering (lines 38, 72, 95‑98)**  
Both the metadata block and each claim’s key‑claim rendering display a `(T, I, F)` triple. The code directly interpolates `ep.truth`, `ep.indeterminacy`, `ep.falsity` without any rounding or sanitisation. If any component is `None` or a non‑numeric type, the markdown will break. The design presumes that epistemic values are **always present and numeric**, which may not hold for partially‑filled tensors.

**4. Strand handling (lines 48‑66)**  
Strands are emitted as level‑2 headings with an index and a title. The `title` field is used verbatim, which could contain markdown syntax (e.g., `#` or `*`). No escaping is performed, so a malicious or careless title could corrupt the document structure. The same applies to `strand.content` and `strand.topics`. This reveals a tension: the renderer wants readability but trusts the data to be “markdown‑safe”.

**5. Declared losses language (lines 68‑73)**  
The literal string *“The losses are mine.”* is inserted before the list of losses. This is an odd, almost narrative flourish that suggests the authors view losses as a personal confession rather than a neutral list. It may be a placeholder, but its presence hints at a cultural or stylistic intent baked into the output format.

**6. Composition view concatenation (lines 84‑106)**  
`render_composition_view` builds a “composed view” by looping over tensor IDs, fetching each tensor, and calling `render_tensor` **without** passing `include_metadata=True`. Consequently, the composed view never shows provenance, even though the heading explicitly names the author (`author = prov.author_model_family or "unknown"`). This mismatch between the heading’s attribution and the body’s omission of metadata feels like a design oversight or a deliberate choice to keep the composite succinct; either way it raises a consistency question.

**7. Truncated correction chain (lines 108‑end, omitted)**  
The function `render_correction_chain` is started but the implementation is cut off in the snippet. It begins by querying `interface.query_correction_chain(claim_id)` and formats each correction with “Original” and “Corrected” fields, plus optional evidence. The missing tail prevents us from seeing how evidence is rendered (e.g., as markdown blockquotes, links, or raw text). This gap could hide important handling of potentially large or complex evidence payloads.

**8. No escaping or sanitisation utilities**  
Across the whole file there is **no import** of any markdown‑escaping helper, nor any custom function to clean user‑supplied strings. The renderer leans on the assumption that *all* string fields are safe. In a system that encourages composability and external contributions, that assumption may be fragile.

**9. Linear string assembly vs. streaming**  
The renderer accumulates a Python list of strings and joins them at the end. For modest tensors this is fine, but the design does not support streaming large tensors to a file or network socket without loading the entire markdown into memory. This reflects an implicit expectation that tensors are relatively small, or that performance is not a priority.

**Closing**  
`markdown.py` is a concise, purpose‑driven renderer that leans heavily on the integrity of its input models. Its structure reads like a ceremonial script: sections are ordered, headings are predictable, and provenance is optional but prominently displayed when requested. Yet beneath that ceremony lie several unspoken contracts—markdown safety, numeric epistemics, and metadata consistency—that, if broken, could corrupt the human‑readable output. The most intriguing tension is the *intentional minimalism* of the renderer (no templating, no escaping) versus the *potentially messy reality* of composable tensors that may originate from many sources. Future scouts should verify those contracts, especially around escaping and the handling of large or malformed tensors, and consider whether the current design scales to the broader ambitions of the Yanantin project.

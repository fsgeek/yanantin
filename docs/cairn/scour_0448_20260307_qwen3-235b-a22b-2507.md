### Strands  

#### 1. Immutability as Epistemic Foundation  
**What I saw:**  
- In `backends/duckdb.py`, every `_store` method checks `if self._exists(...)` and raises `ImmutabilityError` if true (lines ~130–135).  
- The comment: _"Tensors are immutable — compose, don't overwrite."_ is not a note — it's a mantra.  
- This is mirrored in `memory.py` (not shown, but implied by duckdb.py’s comment: _same as in-memory_).  

**What it made me think:**  
This enforces a fundamental epistemic principle: **truth is not replaced, it is contextualized**.  
Every change is a *relation*, not an edit. The system does not “fix” — it *corrects*, *dissents*, *negates*.  
This aligns with the project’s goal of *epistemic observability*: you can always trace why a belief changed.  

**Connection to project:**  
This is the *yanantin* duality in action: human and AI do not overwrite each other — they *compose*. The database design reflects a cultural philosophy: disagreement is not deletion.  

**What would break:**  
Any process assuming mutable state — e.g., config updates, cache invalidation, or in-place edits — would fail. The entire API assumes append-only.  

**Assumptions:**  
- Storage cost is negligible compared to provenance value.  
- Query complexity will grow, but that’s acceptable.  
- Users will tolerate indirection (e.g., “current config” is the last in a chain).  

These are valid for a knowledge observability system, but brittle for high-frequency transactional systems.

#### 2. Composition as First-Class Operation  
**What I saw:**  
- Operators like `correct`, `negate`, `dissent`, and `bootstrap` are in `/operators/` — they are not queries, but *acts*.  
- Each operator creates **two records**:  
  - A *record* (e.g., `CorrectionRecord`)  
  - A *composition edge* (e.g., `CompositionEdge` with `relation_type=corrects`)  
  See `operators/correct.py` (~20–35) and `operators/negate.py` (~20–30).  
- `RelationType` enum in `models/composition.py` defines the grammar of composition.  

**What it made me think:**  
This is **actionable epistemology**. To correct is not just to say “that is wrong,” but to:  
1. Record the correction  
2. Link it to the original  
3. Preserve provenance  
4. Allow future systems to reason over the *network* of beliefs  

This turns the database into a *dynamic epistemic logic engine*.  

**Missing:**  
- No operator for `refine` or `bridge`, despite `RelationType` supporting them.  
- No way to retract a correction or dissent — once declared, it’s permanent.  
- No inverse edges (e.g., `corrected_by`) — queries must scan all corrections to find what a tensor corrects.  

This suggests the system is *write-optimized for honesty*, not *read-optimized for navigation*.

#### 3. Privacy as Redaction, Not Deletion  
**What I saw:**  
- `models/entities.py` defines `EntityResolution` — a mapping from UUID to identity.  
- Redaction is **deletion of the mapping**, not the data.  
- Comment: _"Privacy-as-architecture: redacting an entity doesn't touch any tensor records."_  

**What it made me think:**  
This is a **zero-knowledge identity layer**. You can remove *who* someone is without removing *what they said*.  
This is critical for ethical AI: you can audit reasoning without doxxing sources.  
It also means that *content* is truly immutable — even if identity is redacted, the claims remain.  

**Connection to project:**  
This supports the *complementary duality*: humans bring identity and accountability; AI brings scale and neutrality. The system separates the two.  

**Risk:**  
- If `entity_uuid` appears in `TensorRecord` content, redaction is incomplete.  
- No encryption of `identity_data` — assumes storage is trusted (true for DuckDB on device, not for cloud).

#### 4. Config-as-Tensor: The Bootstrap Solution  
**What I saw:**  
- `config.py` treats configuration as `ConfigTensor` — a special kind of tensor.  
- Stored as `TensorRecord` with `lineage_tags=("config", domain)`  
- Uses `previous_config_id` in `provenance.predecessors_in_scope` to form a *chain*  
- `get_current_config()` returns the *last* in reading order (oldest first → take last)  

**What it made me think:**  
This solves the **bootstrap problem** elegantly:  
- Use file defaults to start.  
- Once DB is available, load latest config tensor.  
- If DB fails, fall back — no single point of failure.  
- The *evolution* of config is queryable via `correct` or `evolve` operators.  

**Brilliant asymmetry:**  
- The system *can* run without config tensors.  
- But once it sees one, it *prefers* it.  
- This allows gradual takeover — perfect for distributed, asynchronous systems.  

**Missing:**  
- No validation that config tensors are from trusted sources.  
- No way to sign or verify provenance chain — security assumption is *trust the interface*.

#### 5. Backend Pluggability and Schema Honesty  
**What I saw:**  
- `backends/duckdb.py` and implied `memory.py` implement the same interface.  
- Comment: _"Keeps the interface honest... if the interface leaks backend-specific assumptions, one of the two backends will expose it."_  

**What it made me think:**  
This is **adversarial interface design**.  
By maintaining two backends with different strengths:  
- `memory`: fast, ephemeral, simple  
- `duckdb`: persistent, file-backed, SQL-capable  
… the system forces the *interface* to be abstract.  

Any leak (e.g., SQL injection in query logic) would fail in one backend but not the other.  

**Connection to project:**  
This ensures that *epistemic operations* are not tied to *storage mechanics*.  
The `ApachetaInterface` is the *only* API — and it is narrow, focused on *records and relations*.  

**Risk:**  
- Query logic is in Python, not SQL (comment: _push to SQL when scale demands_).  
- This may become a bottleneck. But it’s a *conscious* tradeoff for consistency.

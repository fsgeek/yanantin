### Preamble
I dropped into `tmp/ubuntu-vm.claude/document-skills/pptx/scripts/` and found four scripts for PowerPoint manipulation. My attention was caught immediately by the `rearrange.py` file's `duplicate_slide` function — it had a sequence that seemed backwards (clear shapes, then copy shapes), and a silently-swallowed exception I didn't expect. That's where I went first.

### Strands

**Strand 1: The Shape-Clearing Paradox in `duplicate_slide`**

In `rearrange.py` lines 73-78, the `duplicate_slide` function does this:

```python
# CRITICAL: Clear placeholder shapes to avoid duplicates
for shape in new_slide.shapes:
    sp = shape.element
    sp.getparent().remove(sp)

# Copy all shapes from source
for shape in source.shapes:
```

It creates a new slide via `add_slide(source.slide_layout)` — which brings in the layout's default placeholder shapes — then immediately removes them all before copying shapes from the source. This is intentional (the comment says so) but the sequence feels wrong until you realize: the *layout* gives you formatting/master structure, but the *source slide* has the actual content you want. So you use the layout to get styling, then wipe the layout's placeholder text and copy the real content.

The "CRITICAL" comment suggests someone hit a duplication bug here before. I wonder what the original bug looked like — probably placeholders appearing twice, or orphaned shape elements.

**Strand 2: Silent Exception Swallowing in Relationship Copying**

Still in `rearrange.py` lines 107-112:

```python
for rel_id, rel in image_rels.items():
    try:
        new_slide.part.rels.get_or_add(rel.reltype, rel._target)
    except Exception:
        pass  # Relationship might already exist
```

This is doing two things: calling `get_or_add` (which is odd — it's called but its return value is discarded), and silently catching all exceptions. The comment suggests relationship duplication is expected. But swallowing *all* exceptions means if `get_or_add` fails for reasons other than "already exists," you'll never know. This feels like defensive coding after a failure mode was discovered, but it masks potential deeper issues.

**Strand 3: The First-Run-Only Text Replacement**

In `replace.py` lines 117-123, `apply_paragraph_properties` has this pattern:

```python
if not paragraph.runs:
    run = paragraph.add_run()
    run.text = text
else:
    run = paragraph.runs[0]
    run.text = text
```

This always uses only the first run, discarding any additional runs. If a paragraph has multiple runs with mixed formatting (e.g., "hello **world**"), only the first run's formatting would survive replacement. The code overwrites text but leaves other runs intact (they just won't be displayed because their containing paragraph now has only one run). This seems like a subtle data-loss bug masked by the fact that PowerPoint often creates single-run paragraphs.

**Strand 4: Color Fallback Chain in `apply_font_properties`**

In `replace.py` lines 128-144, color is applied with a preferred RGB fallback to theme_color, but theme_color failure only produces a warning:

```python
if "color" in para_data:
    # RGB handling...
elif "theme_color" in para_data:
    try:
        run.font.color.theme_color = getattr(MSO_THEME_COLOR, theme_name)
    except AttributeError:
        print(f"  WARNING: Unknown theme color name '{theme_name}'")
# No else - if neither color nor theme_color, leave existing color untouched
```

If the theme color name is invalid, the text keeps whatever color it had before. This is silent data preservation — probably the right behavior for robustness — but it means typos in theme color names will not be caught as errors in output.

**Strand 5: Overflow Detection Tightly Couples inventory.py and replace.py**

`inventory.py` provides `detect_frame_overflow(inventory: InventoryData)` which returns a dict of overflow measurements. `replace.py` imports this. The interesting thing: `detect_frame_overflow` only detects overflow — it doesn't fix it. The comment on `detect_frame_overflow` says it "Detect[s] text overflow in shapes (text exceeding shape bounds)." But `replace.py` doesn't appear to use this function in the truncated portion I can see. The `--issues-only` flag in `inventory.py` suggests you might want to filter shapes to only those with issues, but I can't see how `replace.py` would apply that.

### Open Questions

1. **Why does `get_or_add` return value get discarded?** In `rearrange.py` line 109, `new_slide.part.rels.get_or_add(rel.reltype, rel._target)` is called but its return value (presumably the new or existing rId) is not stored. This seems like a bug — if the relationship already existed, you'd want to know its ID to potentially update references elsewhere.

2. **What happens to the cleared placeholder shapes in `duplicate_slide`?** When you remove shapes from the new slide's tree, are those XML elements properly garbage collected, or do they persist in the ZIP archive of the PPTX?

3. **Does `detect_frame_overflow` actually measure text vs bounds, or does it just check metadata?** If it actually measures rendered text, it must be using Pillow or similar. If it's just comparing declared text length to declared shape size, the overflow detection could be inaccurate.

4. **What is `six.iteritems` doing in a Python 3 environment?** The `six` library is for Python 2/3 compatibility, but if this codebase is Python 3 only, it's an unnecessary dependency.

### Closing

The scripts feel like they were written by someone who hit specific bugs and patched them — the "CRITICAL: Clear placeholder shapes" comment and the silent `pass` in the relationship copying are signs of bug-fix-by-assertion rather than thorough understanding. The first-run-only text replacement is a subtle data-loss mechanism that probably hasn't been tested with rich-text paragraphs.

The coupling between `inventory.py` and `replace.py` (via `InventoryData` type and `detect_frame_overflow`) suggests these were refactored from a single larger script, or `inventory.py` was built first as the "read" side of an eventual "read-modify-write" pipeline.

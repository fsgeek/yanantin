### Preamble

I stepped into `references/` like a cartographer entering a library of blueprints for a ship that doesn't exist yet. These aren't agents. They're *instructions for building agents*. The Yanantin project's epistemic observability begins not with code, but with meta-code — prompts about prompts. My attention snagged immediately on the recursive structure: we're building an AI that designs other AIs, and we're documenting the design process as if it were already production-hardened.

The first thing that struck me: **this is a pattern library for a system that may not exist yet**. These are references, not implementations. The tension between "extensive production use" claims and their location in `/references/` suggests something important about how this project approaches validation.

---

### Strands

**1. The Example Overlay**
Every file uses `<example>` blocks as a structural element. In `triggering-examples.md`, they're mandatory. In `agent-creation-system-prompt.md`, they're required in the `whenToUse` field. But look closer: these examples are *prescriptive*, not descriptive. They show what the agent *should* say, not what it *actually* says. This creates a hidden assumption: that the desired behavior can be fully captured in static examples. What happens when the user says something the examples never anticipated?

**2. The Format Conversion Pipeline**
`agent-creation-system-prompt.md` outputs JSON with fields like `identifier`, `whenToUse`, and `systemPrompt`. Then the "Converting to Agent File" section shows YAML frontmatter being injected. Where's the glue code? Where's the validation? These files describe a pipeline that exists nowhere in view. The tension: the documentation is so complete it's almost performative.

**3. The "Proactive" Paradox**
`triggering-examples.md` Section 2.5 shows:
```
assistant: "Great! Now let me review the code quality."
<commentary>
Code was just written, proactively trigger review agent.
</commentary>
```
But who decides *what counts as "just written"*? The triggering logic isn't here. It's implied but not documented. This creates a dangerous gap: the examples show the *outcome* of triggering without explaining the *conditions* that trigger it.

**4. The "Inherit" Mystery**
`system-prompt-design.md` Section 2 shows:
```yaml
model: inherit
color: blue
```
What does `model: inherit` mean? Inherit from the parent agent? The base Claude model? A previous agent version? This is a variable that's declared but never defined. It's a placeholder with semantic weight but no implementation path visible here.

**5. The Persona Layering**
`agent-creation-system-prompt.md` opens with:
> "You are an elite AI agent architect specializing in crafting high-performance agent configurations."

This is a prompt *about* a prompt *about* a task. Three layers deep. The language is aspirational ("elite", "high-performance") but the actual output is constrained to a JSON schema. There's a tension between the grandiose self-conception of the agent creator and the mechanical constraints it operates under.

**6. The Missing Validation Layer**
All three files talk about quality standards, edge cases, and validation. But none of them *validate themselves*. `system-prompt-design.md` Section 1 says:
> "Every agent system prompt should follow this proven structure"

"Proven" by whom? When? The files claim authority but provide no evidence. This is a confidence problem.

---

### Declared Losses

I didn't examine:

1. **The actual Claude plugin marketplace code** — These are references, not implementations. I could see what's *supposed* to be built, not what *is* built.

2. **Any test cases** — There's no validation that these patterns actually work. I assumed they were used in production based on the text, but that's a claim, not evidence.

3. **The triggering engine itself** — How does the system actually decide when to call an agent? Where's the pattern matching logic? This directory documents the *agents*, not the *dispatcher*.

4. **Previous agent versions** — If this was "refined through extensive production use," where's the history? The git blame of this prompt? The dead branches?

5. **User feedback loops** — Do agents get retrained based on their actual performance? These files don't address iteration.

---

### Open Questions

1. **What happens when the `whenToUse` field's examples don't match reality?** The examples are prescriptive. If the actual user input deviates, does the agent fail? What's the fallback?

2. **Is `model: inherit` a reference to the base LLM or a reference to another agent's model?** This needs a definition. It's currently a variable without a value.

3. **How are the `<example>` blocks parsed?** Are they regex-extracted? Token-level matched? This is a critical interface that's documented as if it's obvious.

4. **Who writes the examples?** The agent creator? The user? A curator? If it's the agent creator, do they have the same incentives as the system?

5. **What's the relationship between "agent" and "Claude"?** The examples show Claude triggering agents. But is the agent Claude with tools? A separate model? A plugin? The architecture is implied but not explicit.

---

### Closing

This directory is a **specification for a specification**. It's a map of how to build the machines that will map the territory. The Yanantin project's observability infrastructure begins with documentation about documentation.

The surprising thing: the *weakest* link here isn't the code. It's the **assumption that the pattern is universal**. These three files could be describing one project's conventions, not a universal approach to agent design. The "proven structure" language suggests confidence, but the `/references/` location suggests uncertainty.

**What I'd tell the next scout**: 
> "These files are beautiful blueprints for a building that may not have a foundation. Look for the actual triggering engine — that's where the real assumptions live. Also, find the `model: inherit` implementation. That's a black box that could be the whole system's weak point."

The tension I'm left with: **confidence without evidence**. These files read like they're from a mature system, but they exist in a reference directory that suggests they're still evolving. The question isn't whether the patterns work — it's whether they've been stress-tested enough to trust.

**Preamble – What I saw first**  
I dropped into the *agents* folder and the three markdown files immediately read like “contract” specifications for three autonomous post‑run agents: **Grader**, **Blind Comparator**, and **Post‑hoc Analyzer**. They are not implementation code but declarative procedural blueprints written for a higher‑level orchestration layer. What caught me was how each agent assumes a *shared* set of artefacts (transcripts, output directories, metrics, timing) yet each defines its own output schema and even its own naming conventions (e.g., `grading.json` vs. `comparison.json`). The documents are dense with procedural steps, but the actual “engine” that parses and runs them is absent – that tension between “paper‑prototype” and “executable” is the most striking feature.

### Closing – What the next scout should know  

The *agents* folder reads like a design‑by‑contract layer that expects a surrounding orchestration framework to:

* materialize the described artefacts (transcripts, metrics, timing, optional notes),
* enforce a strict directory layout (outputs alongside `metrics.json` etc.),
* provide a parser that can turn these markdown prescriptions into runnable pipelines,
* and guarantee that the Comparator’s free‑form reasoning is sufficiently detailed for the Analyzer to “unblind”.

The biggest hidden tension is **contract mismatch**: each agent writes a different JSON schema and assumes the presence of artefacts that the others never explicitly guarantee. Without a central schema registry or a glue layer, pipelines built from these agents could easily break in subtle ways (missing files, mis‑named JSON keys, ambiguous expectations).  

If you proceed to implement or run these agents, start by **formalising the shared artefact contracts** (e.g., a `results_schema.yaml` that defines `grading.json`, `comparison.json`, required fields, and optional extensions). Then build a thin **runner** that parses the markdown, validates the presence of required files, and normalises the outputs before handing them to the next agent. This will surface the implicit assumptions I’ve flagged and turn the current “paper specification” into an executable, testable component of the Yanantin ecosystem.

### Preamble
I was directed to `src/yanantin/apacheta`, the structural spine of the Yanantin project. My attention was immediately drawn to the tension between rigid, immutable data contracts (`ApachetaInterface`, `TensorRecord`) and the messy, format-variant reality of markdown ingestion (`markdown_parser.py`, `rummage.py`). This module is not merely a database layer; it is an epistemic ledger. It treats uncertainty, provenance, and compositional relationships as first-class citizens. The code assumes that cognition (human or AI) can be captured, tracked, and composed without overwriting its history. What follows is a compression of that architecture.

### Strands

**1. The Epistemic Data Model & Immutability Contract**
`models/tensor.py`, `interface/abstract.py`, `interface/errors.py`
The `TensorRecord` and `StrandRecord` models are built on Pydantic, enforcing strict schemas for epistemic tracking (`EpistemicMetadata` with T/I/F scores), `declared_losses`, and `lineage_tags`. The `ApachetaInterface` abstracts storage behind a strictly immutable contract: `store_record`, `store_tensor`, etc., raise `ImmutabilityError` on duplicates. There is no `update` or `delete`. Provenance is baked into every record via `ProvenanceEnvelope`.
*Thought:* This is a deliberate anti-CRUD design. It forces the system to treat data as historical artifacts rather than mutable state. The 17 curated queries (Q1–Q17) suggest a domain-specific access pattern rather than raw SQL/NoSQL exposure. It assumes backends will be optimized for these exact queries. Valid for epistemic observability, but it shifts complexity to the backend implementations (which I did not examine).

**2. Tolerant Ingestion & Fragile Cold-Start Metadata**
`ingest/markdown_parser.py`
The parser is deliberately permissive, handling markdown variations across Claude and ChatGPT outputs. It extracts strands via regex (`r"^(?:#{2,3}\s+)?(?:\*\*)?Strand\s+(\d+)\s*:\s*(.+?)(?:\*\*)?$"`), pulls key claims from bold/numbered lists, and classifies sections. Crucially, `TENSOR_METADATA` is a hardcoded dictionary mapping filenames to lineage tags, author families, and dates.
*Thought:* This is a pragmatic cold-start hack. The parser assumes tensors follow predictable structural patterns, which is reasonable for a controlled project. However, `TENSOR_METADATA` is brittle: if a file is renamed or moved, lineage breaks. The parser also defaults to `EpistemicMetadata(truth=0.5, indeterminacy=0.5)` for extracted claims, acknowledging uncertainty but potentially flattening nuanced author intent. If the markdown format evolves beyond the regex patterns, ingestion will silently degrade.

**3. Configuration as Immutable Tensor**
`config.py`
Configuration is not stored in `.env` files or separate JSON; it is stored as a `TensorRecord` with `lineage_tags=("config", domain)`. `store_config` converts settings into `KeyClaim` strings, and `get_current_config` relies on `interface.query_reading_order` to fetch the latest version. A fallback to `DEFAULT_CONFIGS` handles the bootstrap problem when the database is unavailable.
*Thought:* Elegant. It treats config changes as historical corrections with explicit reasoning. The reliance on `query_reading_order` assumes the interface can sort by timestamp or precedence. This ties configuration tightly to the tensor lineage system, making config audits trivial but requiring the interface to support efficient temporal queries.

**4. Search Outside the Abstraction**
`rummage.py`
`rummage` operates entirely outside `ApachetaInterface`. It scans filesystem paths (`docs/cairn`, local user directories), parses markdown on the fly, and returns `Match` objects with context. It duplicates some parsing logic (`_classify_section`) found in the ingestion pipeline.
*Thought:* This is a human-facing or pre-ingestion tool. It acknowledges that not all relevant text lives in the database. However, it creates a parallel world: `rummage` sees raw markdown, while `ApachetaInterface` sees structured `TensorRecord`s. If the tensor schema changes, `rummage` may continue searching outdated structures. It's a useful bridge, but it lacks synchronization with the core ledger.

**5. Composition, Negation, and Privacy**
`operators/negate.py`, `models/entities.py`
`negate.py` creates a `NegationRecord` and a `CompositionEdge` with `RelationType.DOES_NOT_COMPOSE_WITH`. `EntityResolution` maps UUIDs to identities, with a `redacted` flag. Redaction removes the mapping, not the tensor data, enforcing "privacy-as-architecture."
*Thought:* The composition algebra explicitly supports non-composition, which is rare in data modeling. It acknowledges that tensors can be aware of each other's incompatibility. Redaction without deletion preserves the ledger's integrity while satisfying privacy constraints. Both patterns align tightly with the project's goal of epistemic transparency.

### Open Questions
- How does `query_reading_order` actually sort tensors? By `timestamp`, `lineage_tags`, or a custom precedence rule? `config.py` depends on it returning the latest config, but the interface contract only says "recommended reading order for a lineage."
- What is the fallback behavior when `markdown_parser.py` encounters a malformed tensor? Does it log a warning, create a partial record, or fail entirely? The docstring says "log before you parse," but the code truncates before showing error handling.
- How does `rummage.py` integrate with the ingestion pipeline? Is it run manually before tensors enter Apacheta, or is it a persistent search layer? Its filesystem dependency suggests it's not meant to replace the interface.
- Are `CompositionEdge` and `NegationRecord` stored in a graph database, or as relational/JSON records? The interface has `query_composition_graph` (Q8) and `query_disagreements` (Q7), but the backing strategy is abstracted away.

### Closing
This part of the codebase is a principled, almost academic approach to data modeling for AI cognition. It prioritizes transparency, immutability, and epistemic tracking over convenience or raw performance. The architecture is clean, well-documented, and makes its assumptions explicit. It treats data as historical artifacts, configuration as lineage, and privacy as a structural property.

If you modify it:
1. Respect the immutability contract. Never bypass `ApachetaInterface` to touch storage directly.
2. Be cautious with `TENSOR_METADATA` in the parser. Filename changes will break lineage. Consider externalizing this mapping or adding validation.
3. Understand that `rummage.py` is a parallel world. It doesn't know about stored tensors, only markdown files. Keep its parsing logic in sync with the ingestion pipeline if you change tensor structures.
4. If you alter `TensorRecord` or `StrandRecord`, update `renderer/markdown.py` accordingly. The human-readable output must not diverge from the structured data, or epistemic observability breaks.

I know the interface enforces immutability and the parser uses hardcoded metadata. I don't know how the backends optimize the 17 queries, or how `query_reading_order` determines order. I made no assumptions beyond what the code explicitly states. The architecture is sound for its goals, but it trades operational flexibility for historical rigor. Choose accordingly.

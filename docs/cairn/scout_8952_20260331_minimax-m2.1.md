### Preamble

Dropped into `src/yanantin/chasqui/` — the messenger subsystem of Yanantin. I started in `coordinator.py` (the heartbeat) and worked outward, but the thing that snagged my attention first was a docstring in `coverage.py`: *"The activity stream layer (15 files, 1443 lines) was never reviewed by any scout despite being a major new subsystem."* That's an honest accounting of a failure mode. I wanted to understand how the system responds to that kind of knowledge — and found something more interesting than the failure itself.

---

### Strand 1: Two Extraction Systems That Don't Know About Each Other

**Location:** `gleaner.py` (class `Gleaner`, ~800 lines) vs `scorer.py` (function `extract_cairn_claims`)

The Gleaner class in `gleaner.py` has an explicit mission statement: *"Unlike the existing `extract_cairn_claims` in scorer.py (which only finds sentences containing file paths), the Gleaner classifies claims by type, scores confidence, and deduplicates across reports."* It's positioned as a strict upgrade. The docstring even says LLM-guided extraction is a *future enhancement*, implying the current approach is deterministic and good enough.

But the CLI in `__main__.py` has two paths for claim extraction:

- `--analyze` → calls `analyst.analyze` → calls `gleaner.extract_claims_from_cairn` ✓ (uses the Gleaner)
- `--claims` → calls `scorer.extract_cairn_claims` ✗ (uses the old function)

So the analyst mode uses the new Gleaner, but the `--claims` listing mode uses the old one. A user running `uv run python -m yanantin.chasqui --claims` gets the simpler, less capable extraction.

What's stranger: `analyst.py` also has its *own* garbage detection (`_GARBAGE_PATTERN`, `is_verification_meta`) that duplicates work already done by the Gleaner. The analyst filters garbage claims, but it re-runs the filter instead of trusting the Gleaner's `confidence` scores.

This looks like a system in transition. The Gleaner was written to replace something, but the old code paths weren't cleaned up, and the new code doesn't fully trust the new code.

---

### Strand 2: Coverage Weights and Claim Clustering Pull in Opposite Directions

**Location:** `coverage.py` (`coverage_weights`, ~line 200) vs `analyst.py` (clustering by `file_reference`)

The coverage system is designed to avoid reviewing the same files repeatedly. Files that were last reviewed a long time ago get higher weight. Stale coverage floats to the top.

But the analyst's clustering groups claims by `file_reference` — which naturally concentrates around files that have been reviewed the *most*, because more reviews → more claims → bigger clusters → more insight value per the analyst's ranking.

So the coverage system says: review the neglected files. The analyst says: focus on the files with the most claims (i.e., the most-reviewed files). These are structurally opposed incentives, and I don't see any mechanism reconciling them.

Worse: `scan_cairn_coverage` in `coverage.py` extracts file references using a stricter regex than the Gleaner's `_PATH_PATTERN`. The Gleaner accepts paths ending in `.cfg`, `.ini`, `.txt`; the coverage scanner doesn't. A claim referencing `app.cfg` would be extracted by the Gleaner but *not* tracked by coverage. So those files would always appear "never reviewed" in the coverage map, always get high weight, and keep getting selected — even if the analyst already clustered many claims about them.

### Strand 3: Activity Map — Present but Untrustable

**Location:** `coordinator.py` (`_build_activity_map`, ~line 85)

The coordinator tries to build an `activity_map` from a DuckDB store. If it works, file selection is informed by real modification times. If it fails — for *any* reason, including a missing store, a query error, or a fact without a `path` field — it silently returns `None`, and the coordinator proceeds with whatever else it has.

```python
try:
    store = open_store("duckdb")
    engine = QueryEngine(store)
    spec = QuerySpec(limit=10000)
    result = engine.execute(spec)
except Exception:
    logger.debug("Activity map: failed to query DuckDB store", exc_info=True)
    return None
```

This is marked as "additive signal, not required" in the docstring. Fair enough. But there's no test of what happens downstream when `activity_map` is `None` — only that `coverage_weights` has a path that doesn't use it.

What I'm uncertain about: if the activity map partially populates (some facts have paths, some don't), does the resulting map give a *false sense* of coverage? A file that appears "recently active" might actually have been mentioned in a fact with no path, and the coverage system would never know. I can't tell from observation whether the query engine gracefully handles malformed facts or just skips them.

### Strand 4: Attestation's Hardcoded Epistemic Numbers

**Location:** `attestation.py` (`_VERDICT_EPISTEMICS`, ~line 70)

```python
_VERDICT_EPISTEMICS: dict[str, tuple[float, float, float]] = {
    "CONFIRMED":    (0.7, 0.3, 0.0),
    "DENIED":       (0.0, 0.2, 0.7),
    "INDETERMINATE": (0.0, 0.9, 0.0),
    "MODEL_FAILURE": (0.0, 1.0, 0.0),
}
```

These T/I/F (truth/indeterminacy/falsity) tuples are the epistemic foundation of Willay receipts. They are hardcoded integers. A CONFIRMED verdict assigns 0.7 truth, 0.3 indeterminacy, 0.0 falsity. Nobody seems to have asked: where do these numbers come from?

The `DeclaredLoss` for "Hallucination risk in verifier" has severity 0.6, but that doesn't adjust the T/I/F values — it just gets listed as a loss. The severity seems narratively meaningful but computationally inert.

The empty-file fallback is also worth noting:

```python
file_sha256 = hashlib.sha256(b"").hexdigest()  # Default
try:
    file_data = Path(file_path).read_bytes()
    file_sha256 = hashlib.sha256(file_data).hexdigest()
except (OSError, ValueError):
    pass  # Silent fallback to empty hash
```

An unreadable file silently produces `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855` — the SHA-256 of an empty string. This is technically valid but indistinguishable from a genuinely empty file. Evidence artifacts with this hash tell you nothing useful.

### Strand 5: The `--verify` Flag Exists But Isn't Wired

**Location:** `__main__.py` (`parser.add_argument("--verify"...)`, ~line 66) and `coordinator.py` (`dispatch_verify`)

The CLI has:

```python
parser.add_argument(
    "--verify", type=int, nargs="?", const=3, default=None,
    metavar="N",
    help="Verify N claims from the cairn (default: 3)",
)
```

But in `main()`, there's no `if args.verify:` branch. The `--verify` flag is accepted by the argument parser but silently does nothing. `dispatch_verify` exists in `coordinator.py` and is imported at the top, but never called from the CLI.

This is the only argument with a handler function imported but not used. The `dispatch_investigate` and `dispatch_respond` paths are fully wired. The verify path is half-built.

### Strand 6: The Scout Report Format Is an Implicit API

**Location:** `gleaner.py` (`_SCOUT_HEADER`, `_extract_model_id`, `_parse_report_timestamp`)

The Gleaner, coverage tracker, and analyst all parse scout reports by extracting structured data from freeform markdown — model ID from an HTML comment header, timestamps from a `Timestamp:` field, file references from backtick-wrapped paths.

This means the *scout report format* is effectively an API contract. If a scout model doesn't emit the right header comment, `source_model` silently becomes `"unknown"`. If the timestamp format doesn't match `[\dT:.+\-Z]+`, files silently get `EPOCH_ZERO` for their coverage time. If file paths aren't backtick-wrapped, coverage tracking misses them entirely.

The format is described nowhere as a contract. It's inferred from what the parsers expect.

### Preamble

I was pointed at `src/yanantin/activity` — the temporal fact storage layer of Yanantin. What drew my attention immediately was the **three-backend architecture pattern** (in-memory, DuckDB, ArangoDB) all implementing the same `ActivityStreamStore` contract, paired with the **two-flag write gate** in `MemoryAnchorService`. This structure suggests Yanantin is building something resembling a distributed sorted stream with epistemic guarantees.

---

### Strands

#### 1. **Temporal Query Optimization Strategy**

**What I saw:**
- `backends/arango.py` lines 67-76: Persistent sorted indexes on `(provider_id, timestamp)` for O(log n) temporal queries
- `backends/duckdb.py` lines 39-45: Composite index `idx_facts_provider_id_timestamp`
- `backends/memory.py` lines 31-32: Per-provider sorted lists using `bisect.insort`

**What it made me think:**
The project consistently prioritizes temporal queries over general CRUD operations. This makes sense for an activity stream — you're almost always asking "what happened at/around this time?" or "what's the latest from this provider?" rather than "give me all facts." The implementation choices (AQL, SQL ORDER BY, bisect) all converge on the same abstraction: **temporal access patterns are first-class**.

**Connection to broader project:** Yanantin mentions "epistemic observability" in its intro. This temporal layer seems to be the foundation for that — you can't observe change without temporal ordering.

#### 2. **Immutability Enforcement**

**What I saw:**
- `store.py` line 33: `ImmutabilityError` on duplicate UUID/handle
- `models.py` line 19: `FactRecord` has `frozen=True`
- `backends/arango.py` line 106-109: Raises `ImmutabilityError` if fact already exists
- `backends/memory.py` line 36-40: Same pattern

**What it made me think:**
This is a deliberate design choice, not just a technical constraint. The stores enforce immutability at the storage layer, but the models also have `frozen=True`. There's **defense in depth** here — the application layer can't accidentally mutate what the storage layer won't let it.

**Potential tension:** The `anchor.py` file's `MemoryAnchorService.update_cursor()` method returns `False` if no change occurs (line 52-56). This suggests the service knows immutability is enforced and doesn't bother trying to update unchanged cursors.

#### 3. **UTC Normalization Discipline**

**What I saw:**
- `models.py` lines 23-33: `_ensure_utc()` function rejects naive datetimes
- `models.py` lines 62-69: `FactRecord.timestamp` validator calls `_ensure_utc()`
- Same pattern in `MemoryAnchor` (line 77-83)

**What it made me think:**
This is unusually strict. Most projects allow naive datetimes and convert on read. Yanantin rejects them outright with a `ValueError`. The comment on line 28-30 is explicit: "ISO 8601 strings sort correctly only when the timezone offset is uniform; UTC is that uniform representation."

**Risk:** This will fail in production if any provider sends naive timestamps. There's no graceful degradation — the error message is clear but the behavior is hard.

#### 4. **The Write Gate Mechanism**

**What I saw:**
- `anchor.py` lines 15-16: `_updated` and `_referenced` flags
- `anchor.py` lines 64-75: `get_handle()` sets `_referenced=True`
- `anchor.py` lines 82-88: `flush()` requires BOTH flags to persist
- `anchor.py` lines 90-98: On successful flush, resets flags and advances handle

**What it made me think:**
This is the **Indaleko ActivityContextService pattern** mentioned in the docstring. The write gate prevents "write storms" — you can't just keep calling `flush()`; you need to observe (update cursor) AND query (get handle) before persisting. It's like a two-phase commit at the application level.

**Potential confusion:** The `flush()` method (line 97) returns `True` only if both flags are set, but what happens if you call `update_cursor()` twice without calling `get_handle()`? The second update returns `False` (line 52-56), but the first still sets `_updated=True`. You'd need to call `get_handle()` before `flush()` works. This seems intentional but could be clearer in the API.

#### 5. **Late Binding in Materialize**

**What I saw:**
- `anchor.py` lines 103-130: `materialize()` calls `store.list_providers()` at resolution time
- `anchor.py` line 115 comment: "Late binding: discover ALL current providers"

**What it made me think:**
This is interesting. The anchor is created with specific cursors (line 12-13), but when you `materialize()`, you get **all current providers**, not just the ones in the anchor. This means new providers registered after the anchor was created will appear in the view.

**Potential issue:** The anchor's `cursors` tuple (line 87) contains the original provider references, but the `AnchorView` (line 120) contains `view.providers` which is current. There's a **semantic gap** — the anchor says "these providers were relevant at this time" but the materialized view says "here are all providers now." This might be intentional for "late binding" but could cause confusion.

#### 6. **Obfuscation Layer Integration**

**What I saw:**
- `backends/arango.py` lines 46-47: `obfuscator: StorageObfuscator | None = None`
- `backends/arango.py` line 57: `self._map = obfuscator or TransparentObfuscator()`
- `backends/duckdb.py` line 10: "No obfuscation needed — the trust boundary is at Pukara"
- `backends/memory.py`: No obfuscation parameter

**What it made me think:**
The `StorageObfuscator` from `apacheta.storage_obfuscator` is integrated into ArangoDB but not into DuckDB or memory backends. The comment in `duckdb.py` explains why: "DuckDB is local storage on a trusted device." This suggests a **security model** where ArangoDB is for distributed/untrusted environments, DuckDB is for local/trusted, and memory is for testing.

**Missing pattern:** Why doesn't MemoryBackend have an obfuscator option? It could be useful for testing obfuscation logic without requiring ArangoDB.

### Open Questions

1. **What happens when `query_latest()` or `query_range()` returns no results?** The method signatures say `None` or `[]`, but I didn't see error handling. What if a user expects data and gets `None`?

2. **How does `MemoryAnchorService` handle multiple clients?** The `_handle`, `_timestamp`, `_cursors` are instance variables. If multiple `MemoryAnchorService` instances exist, do they share state? How are handles distributed?

3. **What's the lifecycle of a "frozen" tensor?** The `freeze()` method stores a tensor via `interface.store_tensor()`, but where does that tensor go? Is it stored in `ApachetaInterface`? How is it retrieved later?

4. **What happens to cursors after `flush()`?** The `flush()` method resets `_cursors` implicitly by not storing them (only the anchor is stored). But the `update_cursor()` method keeps them in memory. What happens to stale cursors?

5. **Thread safety model:** All backends use `threading.RLock`. But what if multiple threads call `flush()` simultaneously? The write gate logic assumes single-threaded execution. This seems like a potential race condition.

6. **Content hash usage:** `FactRecord` has `content_hash: str = ""` (line 43), but I don't see it being computed or validated anywhere in the code I examined. Is it a future feature?

7. **AnchorCursor vs MemoryAnchor:** `AnchorCursor` (line 33-46 in models.py) has a `reference: UUID` field, but `MemoryAnchor` (line 57-67) has `cursors: tuple[AnchorCursor, ...]`. What's the relationship? Does `reference` correspond to the `handle` in `MemoryAnchor`?

### Closing

**Overall impression:** This is a deliberately designed temporal layer with clear trade-offs. The immutability, UTC enforcement, and write gate all suggest the project is building something epistemically rigorous — facts that can't be changed, timestamps that can't be ambiguous, and writes that can't happen without observation.

**To modify this safely:**
1. Don't bypass the immutability enforcement — the two layers (model frozen=True + store error) work together
2. If adding new backends, implement all six abstract methods from `ActivityStreamStore`
3. Respect the UTC requirement — don't convert to naive datetimes anywhere
4. Understand the write gate before adding mutation logic to `MemoryAnchorService`
5. If you need temporal queries, they'll always be provider_id + timestamp combinations

**What stands out:** The project seems to be building a **temporal database abstraction** rather than just a store. The emphasis on temporal queries, immutability, and the fact→anchor→view→tensor pipeline suggests this is foundational infrastructure for something larger — possibly a distributed knowledge base or epistemic logging system.

The codebase feels **production-ready** in its concerns (thread safety, error handling, index design) but **incomplete** in its documentation (especially around the write gate semantics and tensor lifecycle). I would pair a developer with this code for 1-2 weeks to understand the full architectural intent before making significant changes.

# The Crumbs of Consensus: Iterative Datacenter Simulation Series

## Context

Build an iterative simulation that starts with a single datacenter running Paxos on VMTP, then adds datacenters one at a time — eventually reaching Earth orbit, Moon, and Mars. Each step introduces a real problem that motivates pulling in an "overlooked idea" (set quorums, Flexible Paxos, entity migration, TLA+ verification). The process is captured raw, then scripted into a polished recording (possibly multi-episode) for students and YouTube.

The pedagogical arc: students discover WHY each idea matters by hitting the problem first.

## Existing Foundation (~3,500 lines)

- **VMTP client/server**: Transaction-oriented protocol, 2-packet exchanges, CSR duplicate detection
- **Network layer**: SimPy-based, pluggable routing (MigratableNetwork, PartitionableNetwork prove extensibility)
- **Migration**: Address-independent entity IDs, zero-cost migration already working
- **Baselines**: TCP and QUIC comparisons for reference
- **Metrics**: Per-transaction timing, packet counts, failure tracking

## The Arc: 8 Steps, Each Earns a New Idea

### Step 1: Single Datacenter — "Everything Works"
**Build**: Basic Paxos (Proposer/Acceptor/Learner) on top of VMTP transactions
**Network**: All nodes in one DC, ~1ms latency
**Lesson**: Consensus is easy when everyone is close
**Code needed**:
- `paxos.py` - Basic Paxos state machine using VMTP transactions (~200 lines)
- `datacenter.py` - Topology-aware network with per-link latency configs (~80 lines)
- Demo script showing 3-node consensus, all local

### Step 2: Two Datacenters (North America + Europe, ~100ms)
**Problem**: Latency appears. Consensus rounds take 200ms+ instead of 2ms.
**Problem**: Partition between DCs = no majority = no progress (2 nodes, need both)
**Lesson**: Geography has a cost. Partitions aren't theoretical.
**Code needed**:
- Extend topology config for inter-DC links
- Partition scenario between the two DCs
- Side-by side timing comparison: local vs cross-DC consensus

### Step 3: Three Datacenters (+ Asia, ~150ms to NA)
**Problem**: Majority = 2 of 3, can survive one DC failure. Progress!
**Problem**: Asia is farther. Consensus speed = speed of slowest majority member.
**Introduce**: Flexible Paxos (Howard) - Phase 2 quorum can be smaller than Phase 1
**Lesson**: Not all phases are equal. Steady-state (Phase 2) matters more than elections (Phase 1).
**Code needed**:
- Flexible Paxos extension to paxos.py
- Demo: steady-state commits with 2-node Phase 2 quorum (fast path) vs 3-node Phase 1 (rare elections)

### Step 4: Five Datacenters (+ South America, + Africa)
**Problem**: Majority = 3 of 5. More messages, more waiting. Linear growth.
**Note**: Africa is close to Europe but far from Americas - heterogeneous topology deepens
**Introduce**: Set-theoretic quorums (Peleg & Wool, "crumbling walls")
**Lesson**: Majority is sufficient for intersection, not necessary. O(sqrt(n)) or O(log n) quorum constructions exist.
**Code needed**:
- `quorums.py` - Set quorum constructions (grid, combinatorial) (~150 lines)
- Integration with Paxos: configurable quorum system
- Demo: majority vs grid quorum at 5 nodes - show the difference growing

### Step 5: Add Orbit (LEO satellites)
**Problem**: Satellites move. Ground station changes. Latency varies (20-40ms).
**Introduce**: VMTP entity migration - the reason we built on VMTP
**Lesson**: Address-independent entity IDs aren't academic. When your node moves, TCP dies, QUIC stumbles, VMTP doesn't care.
**Code needed**:
- Dynamic topology updates (satellite position changes link latencies)
- Migration events during active consensus
- Demo: consensus continues uninterrupted through satellite handoff

### Step 6: Add Moon (~1.3s RTT)
**Problem**: Waiting for the Moon to vote takes 2.6+ seconds per round
**Problem**: Do you even WANT the Moon in your quorum?
**Introduce**: TLA+ verification - intuition fails at these latencies, prove correctness
**Introduce**: Flexible Paxos + set quorums combined - Phase 2 stays on Earth, Moon participates in Phase 1 only
**Lesson**: Formal verification isn't busywork. It's how you sleep at night.
**Code needed**:
- `specs/paxos.tla` - Basic Paxos TLA+ spec
- `specs/flexible_paxos.tla` - Flexible phase quorums spec
- Model checking the lunar configuration
- Demo: show the latency cliff, then show the optimized quorum structure

### Step 7: Add Mars (4-24 min RTT depending on orbital position)
**Problem**: Majority quorum is dead. You cannot wait 48 minutes for consensus.
**Problem**: Mars MUST operate autonomously most of the time
**Introduce**: Hierarchical/federated consensus - local Paxos within Mars, cross-planet Paxos for global state reconciliation
**Lesson**: At interplanetary scale, you need consensus about consensus. Local autonomy with eventual global agreement.
**Code needed**:
- Hierarchical Paxos: local clusters + inter-cluster consensus
- Variable latency model (Mars orbital position affects RTT)
- Demo: Mars operates locally, syncs globally when it can

### Step 8: All Together - "The Crumbs of Consensus"
**Full topology**: 8 locations, heterogeneous latencies, migration, partitions
**Demo**: Complete system running. Show each idea earning its place.
**Recap**: Transaction transport + set quorums + flexible phases + entity migration + formal verification. Overlooked ideas that fit together.

Extend existing `Network` class:

### Key Design: Paxos on VMTP
- Proposer sends Prepare as VMTP Request, receives Promise as Response
- Proposer sends Accept as VMTP Request, receives Accepted as Response
- Each Paxos round = VMTP transaction (natural fit)
- Quorum system is pluggable: majority, grid, combinatorial
- Flexible Paxos: separate quorum configs for Phase 1 and Phase 2

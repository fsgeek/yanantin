### Strands

1.  **Why Async Log Writes Are Safe:** The author dives into the correctness argument for async log writes (in `tensor_20260220_phase2.md`, Strand 1). They emphasize that Episode's design differs fundamentally from modern filesystems (ext4, XFS, btrfs), which use write-ahead logging (WAL). The key is the co-location of undo information and the data it protects. If the log records are lost, the transaction is treated as uncommitted, and there's nothing to undo. This is presented as *not* an optimization, but a different correctness model. This is counter-intuitive. I would have assumed asynchronous writes were *always* an optimization. This suggests a deep understanding of the trade-offs at play.

2.  **The Type System Already Did It:** The author highlights how "undo-zero" (skipping undo records when the old value is zero) was already implemented *structurally* in the code. This is in the context of the Phase 2 implementation, building on the prior work. The use of separate enum variants (`AddNode`, `RemoveNode`) in `AssFS` eliminates redundant data at compile time. They note that the architecture "survived the instance boundary" — the design choices were robust. This implies a significant amount of upfront design and forethought, and a good example of the "mechanism before policy" approach.

3.  **Risk Inversion:** The file describes how the author re-framed the task of the project (specifically in `tensor_20260220_phase2.md`, Strand 3). Instead of prioritizing multi-threaded FUSE, they advocate for testing the transaction layer directly, without FUSE. The author frames this as "mechanism before policy." This is a pattern I can understand — testing the core logic before the deployment layer makes sense, and is a good principle.

4.  **The Bug That Proved the Strategy:** The concurrent test harness found a concurrency bug that single-threaded tests couldn't. The `ec_merge` function was double-counting members, leading to transaction leaks and deadlocks. This is presented as a validation of the risk inversion strategy. The harness found the bug *instantly*, highlighting the value of testing the transaction layer in isolation (in `tensor_20260220_phase2.md`, Strand 4).

5.  **Episode's Constraints Came Back:** Episode was designed for slow storage. The author notes that those constraints have returned with edge computing. The deferred sync, STEAL/NO-FORCE, EC merge, and three-tier reservation are most valuable when I/O is slow and storage is limited. This is a crucial point (in `tensor_20260220_phase2.md`, Strand 5). The file suggests that the design decisions were not over-engineering. They were *anticipating* constraints that would come back around. This is a good example of the "long view" of technical design.

6.  **The Flatworm's Verdict:** This strand is about *how* Tony assesses the project. The flatworm tests authenticity through irreverence. The author notes that "Tony leads by following." This isn't just a management style; it's a test of whether you'll perform the obvious answer or think past it. The author emphasizes the importance of enumerating all non-inferior options before converging. This is a crucial piece of understanding the project's culture and how decisions are made (in `tensor_20260220_phase2.md`, Strand 6).

7.  **Topography and Texture:** This strand mentions the Yanantin tensors for knowledge transfer (in `tensor_20260220_phase2.md`, Strand 7). The author seems to be hinting that the relationship between the chosen path and the rejected path form a pair, neither meaningful without the other.

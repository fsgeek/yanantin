### Preamble
I landed in `tools/phase1/`, where the Yanantin project's context paging experiments are measured. My first attention was drawn to the `experiment_eval.py` and `probe.py` — they both handle metrics around tool result waste, but with divergent assumptions about what constitutes "waste." The tension between *measuring* and *manipulating* context usage is palpable.

---

### Strands

#### Strand 1: **Tool Result Overhead Is a Moving Target**
In `probe.py` (lines 60–80), `SessionAnalysis.tool_overhead_ratio` calculates tool result bytes as a fraction of conversation bytes. But in `corpus_trimmer_analysis.py` (lines 100–120), the same metric is projected across 813 sessions using hardcoded constants like `NET_SAVINGS_PER_STUB`. This creates a paradox: the tool result overhead is both a dynamic session property and a static corpus-wide projection. The assumption that all tool results are "stubbable" (lines 150–160) ignores edge cases like error results or non-KNOWN_TOOLS (lines 170–180).

**Thought**: Why does `probe.py` treat tool results as *content* while `corpus_trimmer_analysis.py` treats them as *metadata*? This duality suggests the project is measuring two different things under the same label.

---

#### Strand 2: **Eviction Is a Design Choice, Not a Failure**
In `pager.py` (lines 30–50), FIFO eviction is hardcoded. The comment says, *"No recall tool injection: if the model needs evicted content, it already knows how to re-issue the tool call."* This assumes the model can reissue tool calls without the evicted content, treating page faults as *normal* rather than *errors*. 

But in `replay.py` (lines 40–60), a "fault" is defined as a tool call that reuses evicted content. The tension here is between treating eviction as a *cost-saving measure* (in `pager.py`) and a *system failure* (in `replay.py`). The project is measuring both the *benefits* and *costs* of eviction, but the metrics don't explicitly link them.

**Thought**: If evictions are "correct," why does `replay.py` even track faults? Is the system designed to *tolerate* faults, or is this a signal for improvement?

---

#### Strand 3: **Session Classification Is a Fragile Taxonomy**
The `classify_session()` function appears in three files:  
- `probe.py` (lines 100–120): Uses filename patterns like `agent-acompact`.  
- `corpus_trimmer_analysis.py` (lines 50–70): Uses the same patterns.  
- `replay.py` (lines 20–40): Uses filename patterns again.  

But in `probe.py`, the function returns `"other"` for files like `history.jsonl` or `pretty.jsonl`. In `corpus_trimmer_analysis.py`, these files are treated as `"main"` sessions. This inconsistency could lead to divergent analysis of the same data. The assumption that filenames reliably encode session type is fragile.

**Thought**: If the classification is wrong, are the metrics about "compact" vs. "main" sessions even meaningful?

---

#### Strand 4: **The "Amplification Factor" Is a Double-Edged Sword**
In `probe.py` (lines 120–140), `amplification_factor` is defined as the average number of times a byte is reprocessed. This metric is critical for justifying compaction. But in `corpus_trimmer_analysis.py` (lines 180–200), the same concept is used to project savings across the corpus. The assumption is that higher amplification = higher waste, but this ignores cases where reprocessing is intentional (e.g., debugging).

**Thought**: Is the project conflating *waste* with *usefulness*? If a tool result is reprocessed 10x, is that always a fault, or could it be a deliberate design choice?

### Closing
The project is a delicate dance between measuring context waste and engineering a system to reduce it. The code assumes that eviction is a *correct* design choice, not a failure, yet it tracks faults as if they're errors. The session classification and tool result taxonomy are fragile, and the metrics often conflate *waste* with *usefulness*. The next scout should dig into how the pager actually interacts with the proxy and validate whether the hardcoded constants in `corpus_trimmer_analysis.py` align with real-world data.

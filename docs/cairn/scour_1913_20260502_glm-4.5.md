### Preamble
I was pointed to examine `src/yanantin/activity`, which implements the activity stream layer of the Yanantin project. What immediately drew my attention was the elegant two-store architecture: one for high-volume temporal facts and another for low-volume authored tensors, connected by a MemoryAnchorService implementing a sophisticated two-flag write gate pattern. The system clearly prioritizes temporal consistency and immutability while providing multiple backend implementations for different deployment scenarios.

### Strands

#### Strand 1: Two-Flag Write Gate Pattern
The MemoryAnchorService in `anchor.py` implements a clever write gate pattern with two boolean flags: `_updated` (set when providers report new data) and `_referenced` (set when callers request a handle). Only when both flags are true does the `flush()` method persist the data (lines 60-83). This pattern, attributed to Indaleko's ActivityContextService, prevents unnecessary writes when data changes but isn't used, or is requested but hasn't changed. The architecture bridges raw facts and structured tensors efficiently, ensuring resources aren't wasted on intermediate states that no one needs.

#### Strand 2: Temporal Consistency and UTC Enforcement
The module takes temporal consistency extremely seriously. In `models.py`, the `_ensure_utc()` function (lines 26-38) rejects naive datetimes and converts all timestamps to UTC. This isn't just pedantic - as the comment explains, "ISO 8601 strings sort correctly only when the timezone offset is uniform; UTC is that uniform representation." This UTC enforcement propagates through all backends: DuckDB stores timestamps as ISO 8601 VARCHAR (`backends/duckdb.py`), while ArangoDB converts them before storage (`backends/arango.py`). This attention to temporal consistency ensures reliable sorting and querying across all implementations.

#### Strand 3: Pluggable Backend Architecture
The abstract `ActivityStreamStore` in `store.py` defines a clean interface that's implemented by three backends with different characteristics. The `InMemoryActivityStreamStore` (`backends/memory.py`) uses dictionaries with bisect for efficient temporal queries and is clearly designed for testing. The `DuckDBActivityStreamStore` (`backends/duckdb.py`) uses SQL with query pushdown and file-based persistence. The `ArangoDBActivityStreamStore` (`backends/arango.py`) uses AQL with persistent sorted indexes for distributed production use. All backends enforce the same immutability constraints while providing different performance and scaling characteristics. This design allows the application to switch backends based on deployment needs without changing application logic.

#### Strand 4: Late Binding for Ephemeral Views
The `materialize()` method in `MemoryAnchorService` (`anchor.py`, lines 85-110) implements a sophisticated late-binding mechanism. When resolving an anchor into a view, it doesn't just use the providers known when the anchor was created. Instead, it queries `list_providers()` at resolution time to discover ALL current providers, then finds the latest fact for each provider at or before the anchor's timestamp. This means a new provider registered after the anchor was created will still appear in the view if it has facts before the anchor's timestamp. This design choice enables dynamic addition of data sources without losing historical context, a powerful feature for evolving systems.

#### Strand 5: Tensor Creation with Provenance
The `freeze()` method in `MemoryAnchorService` (`anchor.py`, lines 112-161) transforms ephemeral temporal views into permanent tensors with full provenance. It creates a `TensorRecord` with multiple strands: a summary strand with basic metadata and a data strand containing cursor state and resolved facts. The tensor includes provenance information identifying it as a "Memory anchor freeze" with the anchor handle as the source identifier. This transformation from raw temporal facts to structured, queryable tensors with rich metadata shows how this module connects to the broader Yanantin project's goal of building "composable tensor infrastructure for epistemic observability."

#### Strand 6: Immutability and Append-Only Design
The entire module is built around an append-only, immutable design. In `store.py`, the abstract interface enforces immutability by raising `ImmutabilityError` on duplicate UUIDs. In `models.py`, all model classes are configured with `frozen=True`, making instances immutable once created. The backends all implement this constraint: for example, `InMemoryActivityStreamStore` checks for duplicates before storing (`backends/memory.py`, lines 40-43). The docstrings emphasize this pattern: "Facts are immutable — append, don't overwrite" and "Anchors are immutable — advance, don't overwrite." This design creates a system with a clear, linear history that's easier to debug and audit.

# Scour Report: `src/yanantin/awaq`

## Preamble
I was pointed at the `awaq` module—the “weaver” that extracts composition declarations from tensor prose and materializes them into the Apacheta backend. My attention first caught the dual nature of this component: it’s both a **parser** (reading markdown tensors for composition metadata) and an **orchestrator** (ensuring tensors are stored and wiring edges). The name “Awaq” (Quechua for weaver) fits: it spins narrative prose into a graph of typed relations.

## Strands

### 1. Structured Metadata as Primary Source
**weaver.py** prioritizes deterministic extraction from HTML-like comments:
```python
_STRUCTURED_METADATA = re.compile(r"<!--\s*Composition:\s*(.+?)\s*-->", re.DOTALL)
```
These comments (e.g., `<!-- Composition: T18 composes_with T17, T16; read T0, T7 -->`) yield high‑confidence declarations. The code strips fenced code blocks and inline code first—a necessary guard against false positives when the comment appears as an example. This design assumes authors will embed machine‑readable declarations in this exact format. If the format drifts (e.g., missing colon, extra spaces), extraction fails silently. The `_KNOWN_RELATIONS` set (`composes_with`, `does_not_compose_with`, `corrects`, `bridges`, `branches_from`, `read`, `standalone`) defines the ontology; adding a new relation requires updating both this set and the mapping in `materialize.py`.

### 2. Tensor Name Normalization
The weaver handles multiple tensor naming styles: Unicode subscripts (`T₀`), LaTeX (`T_0`, `T_{12}`), and plain digits (`T0`). The `normalize_tensor_name` function uses a translation table for subscripts and regex for LaTeX. This is robust but assumes the `T` prefix and digits only. If tensors adopt a different prefix (e.g., `U0`), they’ll be ignored. The `_TENSOR_REF` regex also enforces word boundaries to avoid matching mid‑word (like `T0_20260207`), which is clever but might miss references in certain contexts (e.g., inside parentheses with no space).

### 3. Materialization: Label → UUID Mapping
**materialize.py** bridges string labels (“T15”) to UUIDs of stored `TensorRecord`s. It does this in two passes:
- First, it attempts to map existing tensors by scanning the backend and extracting labels from `provenance.author_instance_id` (expecting patterns like `T0-original`). This is fragile: if the provenance format changes or the backend doesn’t return all tensors, the mapping fails.
- Second, it stores missing tensors by parsing the cairn directory (using `parse_tensor_file` from `yanantin.apacheta.ingest.markdown_parser`). The `extract_label` function falls back to a regex on filenames (`^(T\d+)_`) or uses `TENSOR_METADATA`. This dual approach is defensive but complex; a mismatch between label extraction here and the weaver’s normalization could leave some tensors “unknown.”

The `_RELATION_MAP` translates Awaq’s relation strings to `RelationType` enums and flags whether it’s an edge or a negation. Notably, `read` maps to `COMPOSES_WITH`—a semantic decision that “reading” implies a composition edge. `standalone` and `does_not_compose_with` become negations (no edge). This mapping is a hard dependency; if the weaver emits a relation not in the map, it defaults to `COMPOSES_WITH`.

### 4. CLI as Control Plane
**__main__.py** provides a tidy CLI with modes: list tensors, show declarations, render graph, output JSON, and materialize. The `--materialize` flag triggers the full pipeline, defaulting to an in‑memory dry run unless `--backend gateway` is specified (which uses `PUKARA_URL`). This separation of extraction and materialization is clean: the weaver produces declarations, and materialization applies them. The CLI also allows limiting sources (`--sources cairn ai-honesty`), which is flexible but relies on the `KNOWN_SOURCES` dict in `weaver.py` (hard‑coded paths, including a user‑specific `~/.claude/projects/-home-tony-projects-ai-honesty/memory`—a potential portability issue).

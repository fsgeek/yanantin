### Strands

#### 1. Provenance as Architecture (Not Decorator)
`models/provenance.py` (lines 13-28) wraps every record with `ProvenanceEnvelope`. This isn't metadata you add later — it's structurally required. Every record must answer:
- Who made this (`author_model_family`, `author_instance_id`)
- When (`timestamp` with timezone)
- From what context (`context_budget_at_write`)
- What preceded it (`predecessors_in_scope`)

This makes epistemic auditability first-class. If you lose provenance, you lose the record's identity. The `check_access` method in `gateway.py` (line 99) returns `True` always, with a comment that "access control is handled by Pukara." This is a design assumption: Apacheta trusts the gateway to enforce access.

**Risk**: If the gateway is compromised or misconfigured, Apacheta has no defense. The abstraction leak is real.

#### 2. Immutability Enforcement Pattern
Both backends enforce immutability identically:
- `duckdb.py` lines 118-124: Check existence, raise `ImmutabilityError` if duplicate UUID
- The `ImmutabilityError` maps to HTTP 409 in `gateway.py` lines 74-76

This creates a contract: "You cannot update a tensor, only compose new ones." The `store_tensor` methods (lines 130-137 in `gateway.py`, lines 276-282 in `duckdb.py`) both check `response.status_code != 201` or `_exists()` before insert.

**Validity check**: This works assuming UUIDs are globally unique per tensor. If that breaks, the entire immutability model collapses. I saw `uuid4()` generators everywhere (`models/provenance.py` line 6, `models/entities.py` line 18), so this is intentional.

#### 3. Composition Relations (The Graph)
`models/composition.py` lines 12-49 define `RelationType` as an Enum with 9 values: `COMPOSES_WITH`, `CORRECTS`, `REFINES`, `BRIDGES`, `BRANCHES_FROM`, `DOES_NOT_COMPOSE_WITH`, `DISSENTS_FROM`, `CONFIRMS`, `DEPENDS_ON`.

The `compose` operator (`operators/compose.py`) and `negate` operator (`operators/negate.py`) are thin wrappers that create `CompositionEdge` records. They don't validate whether the relation makes sense — that's deferred to the graph consumer (scouts, scorers, etc.).

**What I think**: This is a graph database without the graph. You have edges, but no traversal or query logic. The `renderer/markdown.py` file shows `render_composition_view` (lines 85-118) can order tensors by `reading_order`, but there's no automatic topological sort. This could be a gap.

#### 4. Content Addressing vs. UUID Identity
`content_address.py` (lines 15-107) uses SHA-256 hashes of markdown text for deduplication. This is orthogonal to UUIDs. The `ContentIndex` class tracks `hash_to_paths` and `path_to_hash` dictionaries.

**Tension**: A tensor has a UUID (immutability key) AND potentially multiple files that hash to the same content. If you ingest the same tensor twice via different files, you get duplicate UUIDs (immutability error) OR duplicate hashes (deduplication warning). These systems don't communicate.

#### 5. OpenRouter Integration
`clients/openrouter.py` (lines 1-146) explicitly tracks LLM usage: model name, token usage, timestamp, and `metadata` for experiment tracking. Every completion is a `OpenRouterResponse` with `usage` dict.

**Cost-weighted sampling**: The assignment notes this model costs `$0.0000/M tokens`. The provenance model (`models/provenance.py` line 22) has `context_budget_at_write: float | None`. This suggests the project tracks compute as a resource, not just metadata.

#### 6. Error Translation Layer
`gateway.py` lines 74-91 (`_handle_error`) maps HTTP status codes to ApachetaError subclasses:
- 409 → `ImmutabilityError`
- 404 → `NotFoundError`
- 403 → `AccessDeniedError`
- 400 → `InterfaceVersionError`
- 5xx → `ApachetaError`

This is a clean abstraction, but it assumes the gateway returns consistent error messages. If Pukara changes its error format, the client breaks. The comment on line 75 ("not the remote one") about `get_interface_version` is honest — the client knows its own version, but fetching the server's version requires a direct call.

### Closing

**My impression**: Apacheta is the "persistent memory" layer of Yanantin. It stores tensors as immutable records with rich provenance, and connects them via a composition graph. The design is intentionally simple — no graph query logic, no automatic traversal, just storage and basic operations.

**What works well**:
- Immutability is enforced consistently across backends
- Provenance is structural, not optional
- Error translation is clear
- The composition model allows rich epistemic relationships

**What needs attention**:
- Query/traversal logic is missing (or in unprovided files)
- Content addressing is isolated from UUID identity
- The abstraction has security assumptions (gateway trusts apacheta)

**To modify it**: You would add query methods, integrate content addressing with UUIDs, or extend the composition graph with traversal operators. Be careful not to leak backend assumptions — both backends must stay in sync.

**Honest uncertainty**: I cannot verify the full interface contract without `abstract.py`. I cannot assess the security model without `storage_obfuscator.py`. I cannot know how the system actually queries data without `rummage.py` or query implementations. This is the apacheta I saw, not the apacheta it becomes.

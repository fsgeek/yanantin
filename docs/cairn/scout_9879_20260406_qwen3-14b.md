### Strands  

**1. Comment Systems as Epistemic Anchors**  
- **Diff Review & Code Map**: Both templates use **line-based commenting**, but with distinct mechanisms. The diff review binds comments to **line IDs** (e.g., `0-1-5`) and stores them in a global `comments` object, while the code map uses **SVG nodes** with click-to-comment modals. This suggests a tension: **linear vs. spatial feedback**.  
- **Document Critique**: Introduces **status tracking** (approved/rejected) and ties comments to document lines. The `suggestion` object includes `userComment`, `category` (e.g., "clarity"), and `status`—a structured way to model **knowledge validation**.  

**2. Rendering Logic & Technical Assumptions**  
- **Diff Review**: Uses **plaintext parsing** with regex for hunk headers (`@@ -41,13 +41,13 @@`). This is brittle for edge cases (e.g., line breaks in content) but assumes diffs are well-formed.  
- **Design Playground**: Applies **inline styles** directly via JavaScript (`el.style.borderRadius = state.radius + 'px'`). This is simple but lacks CSS-in-JS or component-based abstractions, implying a **low-fidelity prototyping** goal.  
- **Concept Map**: Relies on **manual SVG rendering** with hard-coded node positions and force-directed layouts. The `draw()` function assumes a fixed canvas size (`W`, `H`) and no dynamic scaling, which could limit usability.  

**3. Prompt Generation as a Meta-Layer**  
- All templates generate **structured prompts** for downstream AI use. For example, the code map’s prompt includes **layer visibility** and **user comments**, while the data explorer’s prompt is a **query specification**. This suggests a **dual purpose**: aiding human reviewers *and* training AI agents via explicit instruction.  
- The **document-critique** template explicitly separates **approved changes** from **rejected items**, framing feedback as a **curated knowledge graph**.  

**4. Color & Visual Hierarchy**  
- **Code Map**: Layers (e.g., "Client/UI" in `#dbeafe`) and connection types (e.g., `data-flow` in `#3b82f6`) use **distinct palettes** to encode meaning. This is systematic but risks **colorblind accessibility issues** (e.g., red/green for data flow).  
- **Diff Review**: Uses **semantic color coding** (green for additions, red for deletions), aligning with standard git UIs. The `hunk-header` in blue (`#ddf4ff`) is a subtle but effective visual cue.

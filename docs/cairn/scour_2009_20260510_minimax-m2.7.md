# Tensor — Scour Run #0: `src/yanantin/activity`

## Preamble

I was directed to examine the `activity` layer — the temporal fact storage and memory anchor system. My eye was drawn first to the **two-flag write gate** in `anchor.py` (`_updated` and `_referenced`), which is a named pattern (Indaleko's ActivityContextService) that gates persistence. Then to the **three-backend architecture** (memory/duckdb/arango) all implementing the same abstract interface. The design is coherent — facts flow in from providers, anchors gate persistence, and `freeze()` authors a tensor. But several rough edges caught my attention as I went deeper.

---

## Strands

### Strand 1: The Write Gate Pattern Is Clear But the Implementation Has Asymmetry

**File:** `anchor.py` lines 48–72 (`flush()` method)

The write gate (`_updated AND _referenced`) is the central control flow. `update_cursor()` sets `_updated`, `get_handle()` sets `_referenced`, and `flush()` only persists when both are true. This is a clean pattern.

**What unsettles me:** The `flush()` method advances the handle and timestamp *before* storing, meaning the stored anchor has a different handle than what the caller received. When a caller does:

```python
handle = service.get_handle()  # gets H1, sets referenced=True
service.flush()                 # stores H1, then advances to H2
```

The handle handed out (`H1`) is now permanently associated with the anchor that was just flushed. This is correct — the handle is a stable identifier for that point-in-time snapshot. But the asymmetry (handle advances *after* storing) is worth noting and should be documented clearly, which the code does not do.

Also: `flush()` returns `bool` (True if persisted, False if gate closed). Callers must handle the False case or silently lose writes. No warning is logged.

### Strand 2: Three Backends, Three Slightly Different Contracts

**Files:** `backends/memory.py`, `backends/duckdb.py`, `backends/arango.py`

All three implement `ActivityStreamStore`, but:

- **Memory backend** uses `bisect` with a `+1 microsecond` trick to get inclusive range behavior. This is clever and correct *if* all timestamps have microsecond precision. If a provider emits millisecond-precision timestamps, the `+1us` could land *between* two facts with the same millisecond timestamp, making the bisect behave unexpectedly. The comment says it assumes tuple prefix comparison — but the `+1us` is the actual mechanism.

- **DuckDB backend** stores timestamps as VARCHAR (ISO 8601) and relies on lexicographic sort. This works *if* all datetimes are UTC. The memory backend also normalizes to UTC (`_ensure_utc`), but DuckDB trusts the input is already UTC. If a naive datetime slips in, DuckDB will sort it incorrectly.

- **DuckDB backend** has `# noqa: S608` on every SQL statement — these are SQL injection warnings. The SQL is built with f-strings and UUIDs are interpolated directly. The values come from internal UUIDs, so it's not exploitable, but the suppression suggests the pattern is recognized as risky. The alternative (parameterized queries) is already used for the VALUES clause — the SELECT/WHERE clauses could be parameterized too but aren't, likely for performance with dynamic WHERE clauses.

- **DuckDB backend** has a `content_hash` column that is never populated. `store_fact` accepts it but always passes empty string. This is dead weight in the schema.

- **DuckDB backend** does not implement `__enter__`/`__exit__` (context manager protocol), while both `memory.py` and `arango.py` do. This is an inconsistency.

- **ArangoDB backend** has `StorageObfuscator` injected but only uses `TransparentObfuscator`. The obfuscator is plumbed through the field/collection name mapping, but if someone wanted real obfuscation, the interface is there. However, the docstring says "Least-privilege: separate user" but doesn't enforce this — it's a naming convention, not a permission boundary.

### Strand 3: Late Binding in `materialize()` Is Correct But Expensive

**File:** `anchor.py` lines 74–93 (`materialize()` method)

```python
all_providers = self._store.list_providers()
for provider_id in all_providers:
    fact = self._store.query_latest(provider_id, before=anchor.timestamp)
```

This queries **every** provider for the latest fact at or before the anchor's timestamp. If there are 1,000 providers, that's 1,000 queries. For a small number of providers this is fine. For a large number, this is a potential bottleneck.

There is no pagination, no batching, no parallel query mechanism. The comment says "late binding — includes providers registered after the anchor was created" — this is correct and important for the semantic guarantee, but the implementation is brute-force.

### Strand 4: Deep Copy on Every Read/Write in Memory Backend

**File:** `backends/memory.py` lines 32–34

```python
def _deep_copy(self, record):
    return type(record).model_validate(record.model_dump(mode="python"))
```

Every `get_fact`, `query_latest`, `query_range`, `get_anchor`, `get_latest_anchor` returns a deep copy. Every `store_fact` and `store_anchor` deep-copies on write. This is the right thing for thread safety (prevents external mutation), but it's expensive. At high volume, this serialization/deserialization roundtrip on every operation could be measurable.

The comment says "same pattern as Apacheta's InMemoryBackend" — so this is intentional and consistent with the broader project.

### Strand 5: The `freeze()` Method Hard-Codes Its Lineage Tags

**File:** `anchor.py` lines 95–145

```python
lineage_tags=("anchor", "frozen-view"),
```

These tags are not configurable. If a caller wants to freeze an anchor with different tags (e.g., for different downstream consumers), there's no API to do so. The tags are baked into the `TensorRecord` created by `freeze()`. This is a minor inflexibility.

Also: `freeze()` calls `interface.store_tensor(tensor)` and returns the tensor's `id`. If `store_tensor` raises, the exception propagates. There is no rollback of the anchor — the anchor is already persisted by `flush()` before `freeze()` is called. The authored act is the freeze, so this is probably correct, but if the tensor store fails, the anchor exists and the freeze is lost.

### Strand 7: The Package Exports Only Memory Backend

**File:** `backends/__init__.py`

```python
from yanantin.activity.backends.memory import InMemoryActivityStreamStore

__all__ = [
    "InMemoryActivityStreamStore",
]
```

DuckDB and ArangoDB are deliberately *not* exported at package level to avoid requiring their dependencies. This is a reasonable decision, but it means a user must know to import directly:

```python
from yanantin.activity.backends.duckdb import DuckDBActivityStreamStore
```

There is no factory function, no `get_backend('duckdb')` mechanism. The backends are just classes with constructors that have different signatures (DuckDB takes `db_path`, Arango takes `host, db_name, username, password`). A factory would need to know which backend to create and how to configure it. The current approach is explicit but manual.

### Strand 8: ISO 8601 as VARCHAR Is a Design Decision With Implications

Both DuckDB and Arango store timestamps as VARCHAR (ISO 8601 strings). DuckDB's docstring explains: "sorts correctly, no pytz dependency." This is true — ISO 8601 lexicographic sort equals chronological sort for UTC timestamps. But it means:

1. **No native datetime arithmetic in SQL** — DuckDB will compare strings, not datetimes. As long as all timestamps are UTC and formatted consistently, this works. But if someone adds a non-UTC timestamp (e.g., `2024-01-01T00:00:00+05:00`), the sort order breaks.
2. **Storage overhead** — VARCHAR is larger than a native TIMESTAMP type.
3. **Validation is deferred** — the Python models validate UTC normalization, but if data is inserted directly into DuckDB (bypassing the Python models), invalid timestamps would be stored without error.

The ArangoDB backend stores timestamps the same way, but Arango's AQL doesn't have native datetime types either, so this is consistent.

## Open Questions

1. **What happens if `flush()` is called but the store fails?** If `store.store_anchor(anchor)` raises (e.g., connection lost), the anchor is not stored but the handle/timestamp have already advanced and flags reset. Is there a retry mechanism? Does the caller know the write failed?

2. **What is the expected volume?** The docstring says DuckDB was chosen because "At 28.5M facts, load-all-then-filter is not viable." This implies production scale is tens of millions of facts. Has the memory backend been load-tested at this scale? The `_facts` dict could grow large.

3. **Why is `content_hash` in the schema but never populated?** Is this a planned feature (content-addressed facts) that hasn't been implemented, or dead weight?

4. **What is the migration strategy for schema changes?** If a new field is added to `FactRecord`, existing DuckDB rows won't have it. There's no migration mechanism visible.

5. **How does `list_providers()` scale in DuckDB?** If there are millions of facts but only 10 providers, the query `SELECT DISTINCT provider_id FROM facts` is fine. If there are millions of providers, it's not. But the assumption is probably a small number of providers with high fact volume.

6. **Why does DuckDB not implement the context manager protocol?** Both memory and Arango do. Is this an oversight or intentional (DuckDB connections are managed differently)?

7. **What is the ArangoDB collection creation strategy?** It creates collections if they don't exist (`_ensure_collections`). In production, would this be handled by a migration script instead? The docstring says "Least-privilege: separate user" but doesn't enforce user permissions.

## Closing

The `activity` layer is a well-designed piece of infrastructure. The core abstractions are clean: append-only facts, immutable anchors, a write gate that prevents unnecessary persistence, and a `freeze()` method that authors a tensor. The three-backend architecture is coherent — same interface, different storage engines.

### Strands  

#### 1. **Epistemic Accountability via Coverage Tracking**  
`coverage.py` introduces a temporal weighting system that prioritizes files by recency of review. It parses scout reports to extract referenced file paths and timestamps, building a freshness map. The epoch-zero default for unreviewed files ensures they float to the top of selection queues. This is a direct corrective to earlier observational neglect. The use of basename fallback (e.g., matching `evolve.py` to `src/yanantin/apacheta/operators/evolve.py`) shows pragmatic adaptation to the reality that scouts often report using short names. However, this could introduce false positives if multiple files share a basename — a risk acknowledged but not mitigated in the current logic.  

This module connects deeply to the coordinator’s dispatch logic in `coordinator.py`, which uses `coverage_weights` to bias file selection. The broader project depends on this: without it, the cairn accumulates redundant observations while blind spots persist. If this changed — say, if parsing failed silently — the entire observability feedback loop would degrade into apparent activity without actual coverage.

#### 2. **Cost-Aware Model Selection as a Governance Mechanism**  
`model_selector.py` implements cost-weighted random selection, favoring cheaper models. A $0.10/M token model is 10x more likely to be chosen than a $1.00/M one. Free models are given a nominal $0.001 cost to avoid division by zero, ensuring they are favored but not monopolistic. This is not just economic efficiency; it’s a distributed governance strategy. By biasing selection toward cheaper models, the system encourages exploration while controlling cost, allowing higher-cost models to be reserved for targeted tasks (e.g., `scourer.py` runs).  

The `ModelSelector` class supports filtering by context length and exclusion patterns (e.g., `openrouter/auto`), showing awareness of model quality boundaries. This connects to `coordinator.py`’s dispatch logic, which uses this selector to balance capability, cost, and coverage. What’s missing is explicit feedback from `analyst.py` or `scorer.py` to influence model selection — a missed opportunity for quality-adaptive dispatch.

#### 3. **Tensor as Epistemic Artifact: From Scout to Scourer**  
The distinction between `scout.py` and `scourer.py` reveals a duality in observational strategy. Scouts wander freely with open-ended prompts; scourers are dispatched with specific targets and scopes (`introspection`, `external`, `tensor`). The `SCOURER_INTROSPECTION_TEMPLATE` is strikingly meta: it contains the exact prompt I am now executing. This is not a bug — it’s recursion by design. The system is capable of observing itself, with `scourer.py` serving as the mechanism for intentional introspection.  

This self-scrutiny is structured around the tensor format: Preamble, Strands, Declared Losses, Open Questions, Closing. The format enforces epistemic honesty — declaring losses and uncertainties. Yet, the system does not yet audit its own adherence to this format. `scorer.py` checks for structure, but only post-hoc. A deeper integration — where the scorer’s structural analysis feeds back into the prompt — could close the loop.

#### 4. **Verification Saturation and the Risk of Meta-Consensus**  
`coordinator.py` includes `_count_prior_verifications`, which limits verification reports to `MAX_VERIFY_PER_CLAIM = 3`. This prevents infinite verification cascades when a claim is repeatedly re-verified. But this also risks creating false consensus: three verifications may establish “truth” not because the claim is correct, but because the verifying models share a bias. The system lacks a mechanism to detect such correlated failures.  

This connects to `attestation.py`, which maps verdicts to T/I/F (truth/indeterminacy/falsity) values and records them in a Willay ledger. But if the input verdicts are themselves biased, the attestation becomes a record of systemic error. The declared losses in `attestation.py` acknowledge hallucination risk and temporal drift, but not model correlation — a gap in the epistemic model.

#### 5. **The Analyst as a Filter for Epistemic Noise**  
`analyst.py` performs deterministic filtering of claims: garbage detection (via non-ASCII runs, encoding artifacts), model profiling (claim density, reference ratio), and clustering by file and semantic similarity. The `is_verification_meta` function identifies meta-claims (e.g., “The claim is supported”), separating original observations from second-order commentary. This allows the system to distinguish between *discovery* and *validation* layers.  

However, the Analyst assumes that cross-model agreement (3+ models) indicates “topological” truth. This is a reasonable heuristic, but it risks mistaking popularity for correctness. The system lacks a mechanism to challenge consensus — no provision for a dissenting scout to trigger deeper investigation unless it happens to be selected. The `investigate` mode in `__main__.py` allows probing open questions, but it is human-initiated, not autonomous.

**Preamble**  
I entered the `tests/unit/` realm from the viewpoint of a “chasqui” scout, looking for the *why* behind the test scaffolding rather than the mere presence of files. The first thing that caught my eye was the pervasive pattern of **dual‑backend parametrization** (memory ↔ DuckDB) across many test suites – a design decision that speaks to a core assumption of backend‑agnosticism in Yanantin’s storage layer. From there I followed the threads that tied together the different domains: query filtering, normalisation, provenance, and the CLI orchestration.

### Open Questions  

1. **How does `_resolve_dotpath` handle list indexes or missing keys?** The tests only cover dict nesting; real data may contain arrays.  
2. **Is the normalizer registry thread‑safe?** The global mutable dict could cause race conditions in a multi‑threaded server.  
3. **What is the source of the deterministic machine ID?** Does it read `/etc/machine-id`, use a hash of hardware info, or fall back to a random UUID persisted somewhere?  
4. **What does “summarize mode” actually return?** Is it a count, a statistical summary, or a reduced tensor? The test only checks that the mode runs without error.  
5. **How does the DuckDB backend enforce immutability?** The test expects `ImmutabilityError` on duplicate inserts, but the underlying mechanism (unique constraint, trigger) is unclear.  
6. **Are there any hidden side‑effects when registering custom normalizers across test runs?** Could a later test unintentionally overwrite a normalizer registered in an earlier test?  
7. **How does the OpenRouter client handle rate‑limiting or retries?** The test only checks that the client stores the API key; real usage may need more robustness.  

---

### Closing  

The unit suite paints a picture of a **highly modular, backend‑agnostic system** that treats data as immutable, provenance‑rich tensors. The developers have baked in strong contracts (deterministic IDs, explicit error types) and a flexible extension point (the wabe normalizer registry). However, the same flexibility introduces **potential fragility**: global mutable state, reliance on environment variables, and the need for precise backend parity.  

For the next scout, I recommend:

- Verify **thread safety** of the normalizer registry and any global caches.  
- Examine the **implementation of `_resolve_dotpath`** for edge‑case structures.  
- Probe the **machine‑ID generation** under containerised CI environments.  
- Run the **summarize mode** against a large dataset to see its performance and output shape.  

These investigations will illuminate whether the elegant abstractions hold under real‑world stress or if hidden tensions will surface in production.

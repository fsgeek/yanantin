Tensorial report on target: src/yanantin/chasqui (introspection scope)

Preamble
- What I was pointed at: the chasqui subpackage of Yanantin, specifically the scourer/scout/coordinator stack and the introspection-focused scaffolding that makes the project examine its own codebase and related codebases as a “tensor” of observations.
- First things that stood out: a deliberately self-describing, template-driven prompt ecosystem (scout, scourer) plus a cost-aware model-selection backbone and a multi-stage data pipeline (Scout → Gleaner → Analyst → Scorer → Verifier → Attestation). The code is designed to produce structured, report-like observations (tensors) about targets, with explicit provenance headers and a heavy emphasis on traceability (files, line numbers, references).

Strands
1) Prompt scaffolding and target-focused introspection
- What I saw:
  - scourer.py defines a system prompt (SCOURER_SYSTEM_PROMPT) and multiple scope-specific templates, notably SCOURER_INTROSPECTION_TEMPLATE and SCOURER_EXTERNAL_TEMPLATE, with a long SCOURER_TENSOR_TEMPLATE. The introspection template includes model_id/name, run_number, and a Guidance block around a {target}, {target_tree}, and {target_contents}. It asks for a structured “tensor” response with sections like Preamble, Strands, Declared Losses, Open Questions, Closing.
  - The SCROUER_TEMPLATES expect the model to render the target’s internals as a textual tree and contents, then reason about connections, assumptions, gaps, and potential breakages.
  - The target format for the introspection path is clearly self-referential: examine a part of the Yanantin project itself.
- What it implies:
  - The code is built around disciplined, template-driven introspection rather than freeform generation. It seeks to produce auditable, segmentable observations, which can then feed into the cairn (docs/cairn) for later scoring and cross-claims analysis.
  - There is an apparent tension: the SCOURER_TENSOR_TEMPLATE is truncated in the dump, with an explicit “338 more lines truncated” placeholder. That suggests a long, detailed downstream template for tensor-level analysis that we can’t inspect here, but the scaffolding is present and intended to be used verbatim.
- How it connects to the project:
  - This is the direct mechanism by which probes are dispatched to inspect code targets and external codebases, central to the Yanantin introspection workflow.

2) Cost-weighted model selection and the model pool
- What I saw:
  - model_selector.py defines ModelInfo and ModelSelector. A key design decision: selection is weighted inversely by total cost per million tokens (prompt_cost + completion_cost). If a model reports zero total cost, it’s treated as 0.001 as a nominal floor to avoid division-by-zero, yet still heavily favored.
  - load_from_openrouter_response parses an OpenRouter-style response. It filters by min_context_length and by exclude_patterns, extracts pricing from a nested pricing map, and records context_length.
  - select(), select_n(), and stats() implement the inverse-cost sampling and pool metrics.
- What it implies:
  - The system favors cheap models over expensive ones but can still leverage higher-capability models if needed (via the pool). The context length gate ensures models can actually handle the intended prompts.
  - The pool filtering and exclusion mechanism hints at attempts to avoid “toy” or brittle models (e.g., openrouter/auto) that don’t fit the intended scouting task.
- How it connects to the project:
  - Scouting/Scouring messages are generated with a model_id/name and cost, so the selection logic directly influences which models run in which runs and how resource usage is balanced over time.

3) The coordinator and the cairn workflow (knot in the system)
- What I saw:
  - coordinator.py is the hub: it coordinates dispatch_scout, dispatch_scour, dispatch_investigate, dispatch_verify_cairn, etc. It references a PROJECT_ROOT and CAIRN_DIR for the repository root and the observation cairn.
  - It contains a mechanism to build an activity map from a DuckDB-backed activity store (via open_store and QueryEngine). This map captures last-modified times per file to drive recency signals.
  - It defines helper limits (MAX_VERIFY_PER_CLAIM) and a verification counter to avoid verification cascades.
  - It includes a degenerate repetition detector (_is_degenerate_repetition) aimed at catching models looping in repetition in their outputs.
- What it implies:
  - The pipeline is designed for traceable experiments: each scout/scour tensor is stored with provenance, and there are mechanisms to detect loops and to throttle verification.
  - The activity map integration shows an intent to combine external activity signals with internal coverage metrics to prioritize what to look at next.
- How it connects to the project:
  - This is the operational core: it wires the various components (scout, scourer, scorer, gleaner, analyst, attestation) into end-to-end runs and CLI usage (see __main__.py usage hints).

4) The gleaner/analyst/scorer chain and claim topology (claims/patterns)
- What I saw:
  - gleaner.py implements a richer claim-extraction pipeline than the scorer’s simpler sentence-based extractor. It defines data structures (ExtractedClaim, etc.) and a sophisticated set of patterns for provenance headers, file path references, claim types (factual, architectural, epistemic, missing), and confidence heuristics.
  - It uses provenance (SCOUT_HEADER, SCOUR_HEADER) to tag claims with a model, and uses a broad set of signals to classify claim types (architectural, epistemic, missing), plus confidence scoring tied to definite/hedged language patterns.
  - There’s a fully fleshed Analyst in analyst.py that builds ModelProfile, ClaimGroup, and ClaimCluster structures, computes quality scores, clusters by file references, detects topology (3+ models agreeing), and produces a multi-list AnalysisReport with fields for clusters, topological insights, verification insights, textural observations, and open questions.
  - scorer.py parses scout provenance to reconstruct provenance structures (ScoutProvenance) and validates the content (structure, strands, section extraction). It’s designed to support verification by ensuring claims have a testable structure and to attempt to detect translation of the tensor into more structured verifications.
- What it implies:
  - The project places heavy emphasis on deterministic, rules-based claim extraction and cross-model analysis, avoiding real-time LLM calls in these stages. The clustering/topology logic is designed to surface robust cross-model consensus or lack thereof.
  - There’s a notion of “garbage” detection (is_garbage) to filter out corrupted outputs and a suite of signals for claim confidence, ref density, etc.
- How it connects to the project:
  - This is the analytic brain of Chasqui: after scouts/scours produce tensors, gleaner crops structured claim objects, analyst aggregates patterns, scorer and attestation drive integrity and provenance, and Willay (if present) records epistemic receipts for verification.

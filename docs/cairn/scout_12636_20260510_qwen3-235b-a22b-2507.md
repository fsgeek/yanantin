### Preamble  
I was dropped into `src/yanantin/infra/`, a folder housing infrastructure code for what appears to be a symbolic-technical system named *Yanantin* — a term from Andean cosmology denoting complementary duality. The first thing that caught my eye was the name `ApachetaDocker` — not just because it’s unusual, but because it blends indigenous semantics (*Apacheta*, a stone cairn used as a waypoint or offering in the Andes) with cold, modern container infrastructure. This juxtaposition isn’t decorative. It feels intentional — a quiet assertion that the system is not merely technical but *relational*, designed to observe and perhaps even encode epistemic boundaries.  

But the real surprise wasn’t the naming — it was the *absence of boundaries* in the code’s logic. What should be a strict separation of concerns — Docker lifecycle, config parsing, database setup — is instead woven tightly, almost poetically, into a single operational thread.

---

### Strands

**1. The Apacheta Pattern: Infrastructure as Ritual**  
`docker.py` defines `ApachetaDocker`, and `orchestrator.py` defines `ApachetaDBSetup`. The prefix `Apacheta` is used consistently across both. This isn’t accidental. It suggests a design philosophy where infrastructure isn’t just provisioned — it’s *consecrated*. Each container creation, volume binding, or credential write is a step in a ritual.  

The code doesn’t just *manage* ArangoDB — it *welcomes* it. The `.write_env()` call at the end of `setup()` feels like an offering sealed in `.env`. The check for test and app connections after creation isn’t just validation — it’s confirmation that the spirit (database) has accepted the vessel (container).  

This is not DevOps — it’s *DevOps with prayers*.  

**2. The Phantom of Remote vs. Local Duality**  
In `orchestrator.py`, `ApachetaDBSetup.status()` (truncated) likely checks whether the instance is docker-managed or remote. The `is_docker_managed` flag appears to bifurcate behavior: if `False`, `start()` and `stop()` become no-ops with a log message.  

But here’s the tension: `setup()` unconditionally calls `create_container()` and `start_container()` if `is_docker_managed`, but then immediately tries to connect to ArangoDB via `cfg.start()`. That `cfg.start()` — from `config.py`, not shown — must be polling the database’s health. But if `is_docker_managed` is `True`, that means the container was just started — and ArangoDB is *not* ready immediately.  

So the code assumes Docker container start → DB ready is instantaneous. It’s not. ArangoDB takes 5–15 seconds to boot. There’s no retry loop, no backoff. Just `cfg.start()` — which, if it returns `False`, kills the entire setup.  

This is fragile. And surprising: the system embraces deep metaphors, yet stumbles on the most basic reality of containerized databases — *they take time to breathe*.

**3. The Credentials Are Not Secrets — They’re Roles**  
Both `get_admin_credentials()`, `get_app_credentials()`, and `get_test_credentials()` suggest a tripartite identity model: admin, app, test.  

But note: in `orchestrator.py`, the test database is hardcoded as `"apacheta_test"` — while the main database comes from config. Why not parameterize both?  

Even stranger: the test user is created *every time* `setup()` runs, but there’s no cleanup step. If `setup()` is re-run, does it create duplicate users? The code checks `if not any(u["username"] == ...)` — so it *should* be idempotent — but ArangoDB user creation is not transactional across databases.  

Also: why is the test database not prefixed with `yanantin`? It’s `apacheta_test`, not `yanantin_test`. Is `apacheta` the project’s code name? Is `yanantin` the infrastructure layer? This suggests a *dual naming schema* — one for containers (`yanantin-*`), another for databases (`apacheta_*`).  

A duality within a duality.

**4. The Missing Volume in `docker.py`**  
`docker.py` defines `list_volumes()` — but it’s truncated. The method is defined but incomplete.  

More concerning: `create_container()` calls `self.create_volume(volume)` — which is idempotent. But `delete_container()` does *not* delete the volume. This means volumes outlive containers. That’s intentional — data persists — but there’s no matching `delete_volume()` in `setup()` or orchestrator.  

So the API supports volume deletion, but the orchestrator never calls it. Volumes accumulate. Silent data hoarding.  

Also: what happens if `create_volume()` fails? It logs a warning and returns — but then `create_container()` proceeds anyway, assuming the volume exists. That could crash the container at runtime. No error propagation.

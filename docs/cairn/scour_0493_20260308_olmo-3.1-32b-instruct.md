#### Strands

##### 1. The Scout Lifecycle and Its Artifacts

- **Scout Dispatching** (`coordinator.py`): The project's main orchestration happens here. The coordinator can dispatch one or many scouts in parallel, respond to previous scout outputs, and run analysis or scoring workflows. The use of `asyncio` hints at a design for concurrency and efficiency. The presence of command-line interface options (`--many`, `--scour`, `--score`, etc.) suggests this is intended as a flexible, reusable toolkit. (Lines: 200+, function: `main`)
- **Scout Prompt Engineering** (`scourer.py`, `scout.py`): There is a clear distinction between "scouts" (free exploration) and "scourers" (targeted inspection). Prompts are carefully crafted templates that guide the model's introspection or external review, with explicit fields for model identity, cost, and runtime context. This standardization is likely to improve repeatability. (Lines: `SCOURER_INTROSPECTION_TEMPLATE`, `SCOUT_TEMPLATE`)
- **Model Selection** (`model_selector.py`): The model pool is weighted inversely by cost — cheap models are dispatched more often, making the system cost-aware and adaptive. There's support for excluding certain families and seeding for reproducibility. This reflects a practical approach to operating with heterogeneous and evolving LLM access. (Lines: 70+, class: `ModelSelector`)
- **Content Analysis and Scoring** (`scorer.py`): The scorer analyzes scout reports for structural and semantic signals — presence of file/line references (specificity), repetition or fabrication (garbage detection), and efficiency. It computes metrics like strand count, open questions, and verified references. It deliberately avoids semantic novelty scoring, relying on cross-scout convergence for that. (Lines: 400+, functions: `_strip_provenance_header`, `_extract_strands_section`, `score_cairn`)
- **Gleaner and Analyst** (`gleaner.py`, `analyst.py`): The pipeline includes a step to extract structured claims from scout reports and cluster them by file and semantic similarity. The analyst detects cross-model agreement (topological insights) versus single-model texture. It scores model quality by claim density, references, confidence, and garbage. This is a principled approach to surfacing consensus and divergence. (Lines: 600+, class: `ModelProfile`, `ClaimGroup`)
- **Attestation and Ledger** (`attestation.py`): Verification results are converted into "epistemic receipts" using the Willay model. Each verification includes declared losses (e.g., single-model verification, hallucination risk), and receipts are appended to a hash-chained ledger. This gives traceability and auditability to verification outcomes. (Lines: 200+, class: `verdict_to_evaluation`)
- **Coverage Tracking** (`coverage.py`): A watchman module tracks which files have been reviewed and when, using a timestamped coverage map. ##### 2. Assumptions and Architecture

- The codebase assumes that LLMs are imperfect and can produce garbage or hallucinated outputs. Multiple layers (scoring, declared losses, verification, analyst filtering) exist to surface and mitigate these risks.
- It assumes the presence of a cairn (a directory of "tensor" reports), which is treated as the canonical record for scout and verification outputs.
- It expects external dependencies like `openrouter` for model access and `willay` for attestation, but gracefully degrades when they're absent.
- The project is designed for extensibility (e.g., new analysis or investigation modes via CLI) and for gradual improvement of the verification and review process.

##### 3. Modularity and Code Hygiene

- The code is highly modular, with each utility function or data structure isolated to its own file or class. This supports maintainability and testing.
- Clear separation of concerns: orchestration (coordinator), selection (model_selector), content extraction (gleaner/analyst), scoring, and attestation.
- Use of type hints and dataclasses suggests an emphasis on clarity and static analysis.
- Many functions are defensively written to handle missing dependencies or malformed data.

##### 4. Potential Fragility and Missing Pieces

- Reliance on external models via OpenRouter means that cost and model availability can change over time, potentially breaking or degrading the system if, for example, a cheap/free model is deprecated or its API changes.
- The attestation module depends on Willay but does not require it at import time, which is good for flexibility but could lead to silent failures if the ledger is ever needed and Willay is missing.
- The coverage tracker uses heuristics (basename fallback) to match file references — this could cause misattribution if two unrelated files share a basename.
- The analyst uses word-overlap for semantic clustering, which is lightweight but may miss deeper structural or semantic similarities.
- There is no explicit mention of human-in-the-loop review or overrides — all processes are automated unless someone intervenes via CLI.
- The cairn is assumed to exist at a hard-coded path (`docs/cairn`), which may not be portable or configurable for all environments.

##### 5. Emergent Behavior and Unintended Consequences

- The cost-weighted model selection could unintentionally bias results if cheaper models are less capable, unless performance is monitored and models are periodically re-evaluated.
- If many scouts produce similar noise or low-quality claims, the analyst's clustering could amplify noise rather than surface insight unless the garbage filter is robust.
- The repeated verification of the same claim (capped at 3 per pair) is a pragmatic guard, but may limit the diversity of verification perspectives if the initial verifiers are not representative.

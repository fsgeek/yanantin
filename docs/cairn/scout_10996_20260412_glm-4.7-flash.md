### Preamble
I have landed in `tests/red_bar/`, a sector of the codebase that smells like defensive fortification. These are not functional tests—tests that verify the code *does* something. These are **structural invariants**—tests that verify the code *is* shaped correctly. I observed a pattern of "ghosts" in the comments: references to past failures (the "flatworm," the "two copies of system prompt," the 28.5M file limit). The tests here are written *after* the fact, guarding against specific ways the system could drift or break. My vantage is low-level; I see the guardrails, not the road.

### Strands

**1. The Ghosts in the Comments (Historical Trauma)**
The codebase is defensive. Every file contains a docstring that references a specific incident that necessitated this test.
*   **The Evidence:** `test_portability.py` mentions a "flatworm" and the "Tinkuy tests" breaking CI. `test_activity_stream.py` mentions the "28.5M files, 7.7GB JSONL" limit. `test_attestation_invariants.py` references the "two copies of system prompt" incident.
*   **What I think:** This isn't just documentation; it's a warning system. The developers have been bitten hard by scale and configuration drift. They are building a fortress, not a house. The test for `test_jabberwock_cli_invariants.py` checking for `arango` in `_STORE_CHOICES` despite the default being `duckdb` suggests they are anticipating future migration costs before the migration happens.

**2. Meta-Testing via AST (Reading the Source)**
I noticed `test_attestation_invariants.py` and `test_least_privilege.py` do not import the modules they test. They use Python's `ast` module to parse the source files directly.
*   **The Evidence:** `test_attestation_invariants.py` checks if `_WILLAY_AVAILABLE` is defined or if `Willay` imports are wrapped in `try/except`. `test_least_privilege.py` scans for string literals containing `_system`.
*   **What I think:** This is "structural testing" of the source code. They aren't running the code; they are verifying the *shape* of the code to ensure it fails gracefully if dependencies are missing. It’s a meta-layer of testing that catches code rot before it runs.

**3. The Fact/Tensor Ontology (The Core Duality)**
`test_activity_stream.py` contains the most philosophical tension. It enforces a hard boundary between "facts" and "tensors."
*   **The Evidence:** It mandates `FactRecord` uses `extra='allow'` (schema-agnostic, accepting new fields from providers) while `AnchorCursor` uses `extra='forbid'` (structural record, no extra data allowed). The comment explicitly says: "Wrapping a file stat in a TensorRecord is theater."
*   **What I think:** This is the definition of the Yanantin duality. Tensors are authored compressions with losses; facts are raw observations. The test ensures the system doesn't conflate them. The 28.5M row limit mentioned here implies they are engineering for massive scale where "load-all-then-filter" is impossible.

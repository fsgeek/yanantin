### Closing
`apacheta` is a **tensor database with philosophical constraints** — it treats knowledge as immutable, composable, and self-documenting. The code is cleanly separated into concerns: storage backends, domain models, operators, and renderers. The design decisions (immutability, content addressing, storage obfuscation) reflect a production-ready mindset focused on integrity, deduplication, and optional security-through-obscurity.

**What I'd tell someone about to modify it:**
- Respect the immutability invariant. If you need to "correct" something, add a new `CorrectionRecord` and edge; never mutate an existing `TensorRecord`.
- The `StorageObfuscator` is a pluggable boundary. If you change collection/field names, update the obfuscator, not every backend.
- The `ApachetaInterface` is the contract. All backends must implement the same methods; operators depend on it.
- Beware of the race condition in `_store` (check-then-insert). Consider using ArangoDB's atomic `insert` with `_key` and catching `DocumentInsertError` as the immutability guard instead of pre-checking.
- The markdown rendering conventions (T0-T8 format) are hard-coded in `render_tensor`. Changing the schema will require updating the renderer accordingly.
- The relationship between the filesystem cairn (`.md` files) and the database is ambiguous. Determine whether the cairn is the source or output before changing ingestion or rendering.
- Provenance is everywhere — every record carries it. When adding new record types, include a `provenance` field of type `ProvenanceEnvelope`.
- The `content_address` module is a utility, not integrated into the core flow. If you want deduplication at ingestion time, call `ContentIndex.has_content()` before creating a tensor.

Overall, this is a **cohesive, opinionated system** that prioritizes epistemic honesty over convenience. Modifications should preserve the "stones in the cairn" metaphor: each tensor is a permanent, addressable contribution to a shared graph of understanding.

### **Preamble**
I was dropped into the `tests/experiments/` directory of the Yanantin project, where the code explores **epistemic observability**—a duality between human and AI through composable tensor infrastructure. My attention was immediately drawn to the tension between **catalog-driven model resolution** and **experiment preregistration**, two systems that seem to operate in parallel but with overlapping concerns. The code reveals assumptions about model metadata, versioning, and reproducibility, as well as a playful (or perhaps pragmatic) approach to handling missing or ambiguous data.

---

### **Strands**

#### **1. The Catalog as a Living Record of Model Ambiguity**
In `test_panel.py`, the `_sample_catalog()` function loads a fixture (`openrouter_models_sample.json`) that presumably contains model metadata from OpenRouter. The tests then resolve panels by mapping `CandidateModel` objects (defined in `yanantin.experiments.panel`) onto this catalog.

**What’s surprising:**
- The catalog is treated as an **imperfect source of truth**. In `test_resolve_panel_uses_default_native_max_tokens_fallback()`, if a model lacks `max_completion_tokens`, the system falls back to a hardcoded `DEFAULT_NATIVE_MAX_TOKENS` (line ~120). This suggests the project anticipates **missing or inconsistent metadata** in real-world catalogs.
- The `exclude_patterns` filter (e.g., `*-audio-*`) implies a **regex-based exclusion system** that might be brittle or overly simplistic for complex model naming conventions.

**What it makes me think:**
- The system assumes models will evolve, and some fields (like `max_completion_tokens`) may not always be available. This is a **defensive design choice**, but it also hints at a **tension between rigor and flexibility**.
- The use of `snapshot_sha` (from `catalog_snapshot_sha`) suggests the project cares deeply about **reproducibility**, but the fallback mechanism risks **silent degradation** if critical fields are missing.

---

#### **2. Preregistration as a Git-Integrated Workflow**
In `test_preregister.py`, the `main()` function in `yanantin.experiments.preregister` is tested for its ability to:
1. **Resolve a panel** (from a `.criteria.yaml` file) into a `.resolved.yaml` manifest.
2. **Update the preregistration YAML** with metadata like `panel_resolved`, `resolved_at`, and `catalog_snapshot_sha`.
3. **Stage files for Git** (when `--stage` is used).

**What’s surprising:**
- The preregistration system **assumes a Git repository** is present (via `subprocess.run(["git", ...])`). This is a **hard dependency**, yet the tests don’t mock Git behavior thoroughly—only the `diff --cached` output is checked.
- The `dry-run` mode is explicitly tested, but the system still **parses the catalog** and computes the SHA. This suggests the preregistration workflow is **designed for iterative refinement**, not just one-time validation.
- The `panel_resolved` field in the preregistration YAML is an **absolute path**, which could break if the repo is moved or refactored. This feels like a **temporary convenience** rather than a long-term design.

**What it makes me think:**
- The project is **explicitly building for reproducibility**, but the path-based resolution (`panel_resolved`) is a **potential fragility**. Maybe this is intentional—perhaps the system is designed to be **self-documenting** rather than strictly portable.
- The `resolved_at` timestamp is generated during runtime, which is good for tracking, but the test only checks if it’s a valid ISO format. **No validation of timezone or precision** is performed—just that it’s parsable.

#### **3. The Playful Handling of Edge Cases**
In `test_resolve_panel_applies_context_min_and_exclude_patterns()`, the test filters out `openai/gpt-4o-audio-preview` because it matches the exclusion pattern `*-audio-*`. However, the test also includes `tiny/no-context-model`, which has a **context_length of 0** (implied by the test’s assertion that only `meta-llama/llama-4-scout` remains).

**What’s confusing:**
- The `context_length_min` filter seems to be **applied implicitly**—the test doesn’t explicitly check for it, but the result suggests it’s working. This is **assumed behavior**, not documented.
- The `tiny/no-context-model` is **excluded by context length** (since `context_length_min=8000` is set), but the test doesn’t verify this logic. It’s **inferred from the absence** of the model in the output.

**What it makes me think:**
- The system might be **overly permissive** in how it applies filters. If `context_length` isn’t explicitly provided in the catalog, does it default to `0`? This would explain why `tiny/no-context-model` is excluded.
- The **lack of explicit assertions** about context length filtering suggests this is a **shared assumption** between the tests and the implementation. This could be a **code smell**—if the logic changes, the tests might fail silently.

---

#### **4. The Duality of Human and AI: A Metadata-Driven Symmetry**
The project’s name, **Yanantin**, suggests a **duality** between human and AI. The code reflects this in how it:
- **Resolves models into panels** (a human-AI collaboration step).
- **Preregisters experiments** (a human-driven process with AI metadata).
- **Uses YAML for configuration** (human-readable) but **JSON for catalogs** (machine-readable).

**What’s interesting:**
- The `CandidateModel` class is **purely metadata-driven**. There’s no runtime model interaction here—just **resolution and filtering**. This suggests the system is **decoupled from actual inference**, focusing instead on **observability and reproducibility**.
- The `rationale` field in `PanelCriteria` is **explicitly human-authored**, while `resolved_at` is **automatically generated**. This is a **deliberate tension**—human intent vs. machine timestamping.

**What it makes me think:**
- The project is **designing for human-AI synergy**, but the codebase doesn’t yet show **how the resolved panels are actually used**. Are they fed into a larger system? Is this just the "observability layer"?
- The **lack of runtime model interaction** in these tests suggests this is **pre-inference infrastructure**. The real duality might happen elsewhere.

3. **The `memory_tools` directory structure**—the tests assume its layout, but I didn’t explore how experiments are **composed** or **executed** beyond preregistration.

### **Open Questions**
1. **How does the system handle models with conflicting metadata?**
   - For example, if two catalog entries describe the same model but with different `context_length` values, which one wins? The tests don’t explore this.
2. **What happens if the catalog is empty or malformed?**
   - The tests assume the catalog is valid, but in production, could this cause silent failures?
3. **How are resolved panels actually used?**
   - The preregistration system writes YAML files, but are these files **parsed by a larger system**? Is this just a documentation step, or does it enable **dynamic model selection**?
4. **Why is `panel_resolved` stored as an absolute path?**
   - This could break if the repo is moved. Is this intentional, or is it a **temporary convenience**?
5. **How is the `catalog_snapshot_sha` computed?**
   - The test checks its length and format, but not its **deterministic properties**. Could two identical catalogs produce different SHAs?

### **Closing**
This codebase is **playfully pragmatic**—it assumes ambiguity in model metadata, handles edge cases with fallbacks, and integrates Git for reproducibility. The **tension between human intent (`rationale`) and machine resolution (`resolved_at`)** is deliberate, reflecting the project’s duality theme.

**What I’d tell the next scout:**
- **Follow the catalog**—it’s the weakest link in this system. If metadata is inconsistent, the whole resolution process could fail silently.
- **Watch the Git integration**—the preregistration system assumes Git is present, but the tests don’t fully mock it. This could be a **hidden dependency**.
- **Look for runtime model interaction**—these tests are about **observability**, not inference. The real duality might happen elsewhere.
- **Ask why `panel_resolved` is an absolute path**—this feels like a **temporary convenience**, not a long-term design.

**Final thought:**
Yanantin seems to be **building a layer of epistemic observability**—a way for humans to **observe, resolve, and preregister** AI experiments with rigor. But the **actual inference loop** (where human and AI truly collaborate) is still a mystery. The next step might be to explore how these resolved panels are **consumed by a larger system**.

# Tensor: Yanantin Activity Stream Module

## Preamble

I was pointed at `src/yanantin/activity`, the core temporal activity stream infrastructure. What first drew my attention was the elegant tension between two design principles: **immutable data** and **temporal flexibility**. The way the system handles time as a first-class citizen across all layers—especially with UTC normalization and the "late binding" in `materialize()`—felt like the heartbeat of this module. I noticed it immediately in `models.py` where `_ensure_utc` rejects naive datetimes (line 25), establishing a critical constraint that permeates the entire system.

## Strands

### Strand 1: The Temporal Immutability Covenant

*What I saw:* Every storage operation enforces immutability with `ImmutabilityError` (e.g., `arango.py` lines 42-45, `memory.py` lines 38-40, `duckdb.py` lines 45-47). Even the in-memory implementation uses `deep_copy` on read/write (line 17 of `memory.py`). The `FactRecord` and `MemoryAnchor` models are explicitly `frozen=True` (lines 40-42 of `models.py`).

*What it made me think:* This isn't just a design choice—it's a philosophical commitment to time as a non-reversible dimension. The system treats data as historical record, not mutable state. The `query_latest` method's O(log n) optimization (all backends) is only meaningful because data can't be overwritten. If we removed immutability, the entire temporal query structure would collapse—like building a house on sand.

### Strand 2: The Two-Flag Write Gate

*What I saw:* The `MemoryAnchorService` maintains two state flags (`_updated` and `_referenced`) (lines 32-33 of `anchor.py`). The `flush()` method only persists when both are true (lines 40-43). `update_cursor()` sets `_updated=True`, and `get_handle()` sets `_referenced=True`.

*What it made me think:* This is brilliant engineering for the "complementary duality" the project describes. The write gate ensures anchors persist only when *both* the data has changed (updated) *and* someone has requested it (referenced). It's like a physical gate that only opens when two conditions are met simultaneously. This pattern is so well-encapsulated that it's almost invisible to users—it's baked into the service's core.

### Strand 3: Late-Bound Temporal Resolution

*What I saw:* The `materialize()` method (lines 62-77 of `anchor.py`) *doesn't* use the anchor's stored provider list—it discovers *all* current providers at resolution time (line 66), then finds the latest fact for each before the anchor's timestamp.

*What it made me think:* This is where the system truly shines. It decouples the past (the anchor) from the present (current providers). An anchor created yesterday isn't invalidated if a new provider joins today. The temporal query is *always* fresh. This is the "complementary duality" in action: the past (anchor) and present (current state) coexist without conflict. The `list_providers()` method (line 66) is the key to this flexibility.

### Strand 4: Bridge to Apacheta's Tensor World

*What I saw:* The `freeze()` method (lines 82-106 of `anchor.py`) converts an `AnchorView` into a `TensorRecord` with rich provenance. It creates two strands: a summary (`strands[0]`) and the raw data (`strands[1]`).

*What it made me think:* This is the critical bridge between the activity stream (temporal facts) and the tensor layer (structured, authored content). The `provenance` field (lines 92-98) explicitly links the tensor back to the anchor's `handle`—making it auditable. The `lineage_tags` (line 104) further embed the anchor's purpose into the tensor. It's not just storing data—it's *curating* a historical record.

### Strand 5: Backends as a Spectrum of Tradeoffs

*What I saw:* Three backends with different performance characteristics:
- `InMemoryActivityStreamStore` (memory.py): O(log n) via bisect, for tests
- `DuckDBActivityStreamStore` (duckdb.py): SQL pushdown for file-backed storage
- `ArangoDBActivityStreamStore` (arango.py): AQL with persistent indexes for production

*What it made me think:* The system doesn't just *have* multiple backends—it *designed* them with purpose. The `__init__.py` docstring (lines 5-8) explains why: "ArangoDB and DuckDB backends are not imported at package level to avoid requiring their dependencies." This is thoughtful dependency management that keeps the core module lean.

## Open Questions

1. Why does `ArangoDBActivityStreamStore` use `str(fact.id)` as the key in the document (arango.py line 95), instead of using `fact.id` directly? This feels like a performance leak.

2. How does the system handle clock drift across providers? The UTC normalization (models.py) assumes all providers have accurate clocks, but this isn't guaranteed in practice.

3. What happens when a provider is *removed* after an anchor is created? The `materialize()` method would skip it, but is this intentional, or would it cause unexpected gaps in the view?

4. The `query_range` method (all backends) returns facts sorted by timestamp *ascending*—is this intentional for the use cases, or should it be descending?

5. In the `DuckDBActivityStreamStore`, timestamps are stored as VARCHAR (duckdb.py line 14). This is portable (no pytz dependency), but is it less efficient than storing as TIMESTAMP?

## Closing

This module is a masterclass in designing for temporal consistency. The immutability-first approach, combined with the two-flag write gate and late-binding resolution, creates a robust foundation for epistemic observability. The code is clean, well-documented, and the patterns are both sophisticated and easy to understand once you see them.

If I were to tell someone about to modify it: **Be respectful of the immutability covenant.** The moment you change a `store_fact` method to allow updates, you break the entire temporal query structure. Also, the `materialize()` method's "late binding" is its most powerful feature—never remove that. If you're adding a new backend, follow the pattern of the existing ones exactly—this module's strength is in its consistency across implementations.

This isn't just code—it's a *philosophy* of time as a non-reversible dimension. The system doesn't just store data; it *curates history*. I believe this is the kind of infrastructure that makes the "complementary duality" between human and AI meaningful—not just in theory, but in how it actually works.
